# Recommendations for Improving Test Coverage in Biscuit Terminal

After reviewing the current test suite for `biscuit-terminal` (library) and `biscuit-terminal-cli` (CLI), here are several actionable recommendations to improve testing architecture, coverage, and long-term maintainability.

## 1. Refactor the CLI for Unit Testing
Currently, the `biscuit-terminal-cli` has 0 unit tests and relies entirely on 80 integration tests via `assert_cmd`. The entire CLI logic—including argument parsing, command routing, and output formatting—is concentrated in `cli/src/main.rs`.

**Recommendation:**
- **Extract Modules:** Move the core logic out of `main.rs` into separate, testable modules (e.g., `args.rs` for clap definitions, `commands/` for individual subcommands, `output.rs` for formatting). `main.rs` should ideally only contain a thin wrapper that calls an `execute()` function in your library or an extracted module.
- **Add Unit Tests:** Once the logic is decoupled, write unit tests for the CLI's internal functions. Test that argument validations work correctly for edge cases, and verify that the serializers (like the JSON formatter) produce the expected structures without needing to spawn a full binary process for every test.

## 2. Enhance Terminal Environment Testing
The `biscuit-terminal` library has excellent overall coverage (over 1000 combined tests), but some tests (e.g., `test_actual_terminal_query_integration` in `osc_queries.rs`) are currently `#[ignore]`d because they require a real terminal.

**Recommendation:**
- **Use Pseudo-Terminals (PTY):** Integrate a crate like `ptyprocess` or `expectrl` to spawn a pseudo-terminal during tests. This allows you to simulate a real terminal environment in CI and run tests that depend on TTY capabilities (like OSC queries and cursor positioning) without manual intervention.
- **Abstract and Mock Interactions:** Use traits to abstract the underlying terminal reads/writes and OS interactions. By leveraging a mocking library like `mockall`, you can inject mock terminals to test how the library handles various terminal responses (e.g., unexpected escape codes or query timeouts) reliably.

## 3. Introduce Snapshot Testing for Visual Output
Both the library and CLI generate complex visual outputs involving ANSI escape codes, such as tables, Mermaid diagrams, and formatted text blocks. Validating these outputs using simple string containment (e.g., `predicate::str::contains`) in integration tests can be brittle and miss subtle formatting or color regressions.

**Recommendation:**
- **Adopt `insta`:** Use the `insta` crate for snapshot testing. This is especially useful for the CLI integration tests and complex library components. You can capture the exact ANSI output generated by the CLI or UI components and ensure it remains structurally and visually identical across changes.

## 4. Add Property-Based Testing
Functions that parse user input or complex strings—such as `parse_width_spec`, `parse_filepath_and_width`, layout constraint calculations, and the escape code evaluator (`eval.rs`)—are prime candidates for property-based testing.

**Recommendation:**
- **Use `proptest`:** Integrate `proptest` to generate pseudo-random, adversarial strings and edge-case values for your parsing logic. This guarantees the parser never panics and handles invalid inputs gracefully, greatly increasing the robustness of the terminal capabilities detection.

## 5. Leverage `cargo-nextest` Features
The project is already taking advantage of `cargo nextest` via the `just test` runner, which provides excellent speed and output.

**Recommendation:**
- **Flaky Test Management:** If you introduce PTYs or timeout-based tests for terminal queries, configure retries in `.config/nextest.toml` to gracefully handle occasional failures caused by system load or timing constraints in CI environments.
