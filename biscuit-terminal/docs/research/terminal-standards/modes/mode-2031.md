# DEC private mode 2031: color-palette update notifications

DEC private mode 2031 is a community terminal extension, not a specification published by DEC or an ECMA/ISO standard. Contour proposed and documents it as “Dark and Light Mode detection.” It gives terminal applications a semantic signal about the terminal’s current light/dark preference and a way to learn when the terminal palette changes. This matters because a process in a PTY cannot directly observe the graphical terminal’s theme or the desktop’s appearance setting.

## Protocol

The extension has a current-state query and an opt-in change notification:

| Direction      | Sequence           | Meaning                                                                  |
|----------------|--------------------|--------------------------------------------------------------------------|
| App → terminal | `CSI ? 996 n`      | Query the current dark/light preference.                                 |
| Terminal → app | `CSI ? 997 ; 1 n`  | Dark preference.                                                         |
| Terminal → app | `CSI ? 997 ; 2 n`  | Light preference.                                                        |
| App → terminal | `CSI ? 2031 h`     | Enable unsolicited palette-change reports.                               |
| App → terminal | `CSI ? 2031 l`     | Disable unsolicited palette-change reports.                              |
| Terminal → app | `CSI ? 997 ; Ps n` | Report the new preference after a palette change (`Ps` 1 dark, 2 light). |

`CSI` is usually written as `ESC [`; `n` is the Device Status Report final byte. The notification carries the new value, so an application can update immediately without issuing another query. Applications should still query once at startup: enabling mode 2031 does not itself promise an initial report. The request is scoped to the terminal session and should be reset when the application no longer needs notifications (and on orderly exit).

The intended trigger is a change to the terminal’s active palette, not only a system light/dark toggle. For example, an OS appearance change may cause the terminal to choose a corresponding palette, and a user may directly switch a terminal profile or theme. A terminal should notify when that palette update occurs. If the OS appearance changes but the terminal keeps the same palette, there is no palette update to report.

## Detection and DECRQM

This extension can be tested interactively or in an automated PTY test. Send `CSI ? 996 n` and read a bounded-time reply; a `997;1` or `997;2` report is positive evidence that the query is implemented. To test notifications, enable 2031, cause a known palette change, and check for the unsolicited 997 report; then reset the mode and verify the event stream stops. A test must avoid mistaking its own query reply for a change event and should account for multiplexers between the application and emulator.

DECRQM (`CSI ? 2031 $ p`) is a query about the *mode state*, not about the current theme. Where implemented, DECRPM uses status 0 for unrecognized, 1 for set, 2 for reset, 3 for permanently set, and 4 for permanently reset. Since applications normally begin with notifications disabled, a recognized, currently-disabled mode commonly replies `CSI ? 2031 ; 2 $ y`. A `;1` means notifications are presently enabled; it does not mean “light mode.” Ghostty maintainers explicitly clarify that `2031$p` is not the color-scheme query; use `996n` for that.

DECRQM is useful diagnostic evidence but is not a portable capability test. Some emulators do not implement DECRQM for this private mode, some report unknown or silence, and a multiplexer may answer for itself rather than forward the request to the outer terminal. A recognized mode only proves mode-state handling, not that the terminal emits notifications on every relevant palette change. For an application feature probe, the bounded `996n` query plus an optional observed change is stronger; still treat timeout as “unknown or unsupported,” not as a protocol error.

## Comparison with OSC 11

`OSC 11 ; ? ST` queries the terminal’s background color. A common reply is `OSC 11 ; rgb:RRRR/GGGG/BBBB ST` (the number of hex digits per component can vary). OSC 11 reports an actual color, while mode 2031 reports the terminal’s semantic dark/light choice and can push an update asynchronously. With OSC 11, the application must parse the RGB components and choose a brightness threshold; unusual backgrounds, transparency, and custom palettes make that classification ambiguous. OSC 11 also has no standard change notification, so applications typically query on startup or focus regain and may miss a change while continuously running. It remains a useful fallback when 996/997 is absent, but it answers a different question.

## Terminal support and behavior

The list below distinguishes documented or otherwise positive support from similar-sounding features. Versions and front ends matter: support may come from a shared parser, a toolkit such as VTE, or a multiplexer rather than an individual product implementation. The support list in frontmatter is a discovery aid, not a promise of identical trigger behavior.

| Terminal                          | Status and trigger notes                                                                                                                                                                                                                                                                     |
|-----------------------------------|----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| **Contour**                       | Supports the query and notifications since 0.4.0. Its specification explicitly includes both OS-driven theme changes and direct terminal palette/profile changes.                                                                                                                            |
| **Ghostty**                       | Supports since 1.0.0. Do not use `2031$p` to ask for the theme; use `996n`. Public documentation confirms the protocol, but exact behavior for every configuration/profile transition is not separately specified.                                                                           |
| **cmux**                          | Uses libghostty, so its VT engine supports mode 2031. This is engine-derived evidence; cmux-specific behavior when its frontend changes palette should be verified in the target release. Its chrome theme selection and a pane’s terminal palette are distinct settings.                    |
| **kitty**                         | Supports since 0.38.1. Check the installed version; headless/batch bridges may not expose replies even when the interactive terminal supports them.                                                                                                                                          |
| **foot**                          | Its changelog adds private mode 2031; foot also supports explicit alternative color themes and theme switching. Reports should be tied to actual palette changes; do not assume that every desktop appearance event changes foot’s configured palette.                                       |
| **GNOME Terminal**                | Inherits support from VTE 0.82.0 or later. Older GNOME Terminal builds linked to older VTE do not qualify. The behavior follows palette changes delivered through VTE; do not assume the application directly follows every OS appearance change independently of its palette configuration. |
| **iTerm2**                        | Supported in current releases (reported from 3.6.6). Older versions should not be assumed to support it. Its documented OSC color queries are separate; exact notification behavior for every automatic-profile-switching setup is not specified in the protocol docs.                       |
| **tmux**                          | Support is reported for 3.6 and later. A multiplexer must proxy both query/reply traffic and unsolicited events; when nested, each layer can affect what the application observes. Test inside the actual tmux configuration rather than inferring from the outer terminal.                  |
| **Zellij**                        | Support is reported since 0.44.2. As with tmux, verify the complete terminal-to-multiplexer-to-application path.                                                                                                                                                                             |
| **WezTerm**                       | Not listed as supporting mode 2031 in the current Contour adoption notes; its issue tracker has tracked the request. Do not infer support from its color-scheme configuration or OSC color querying.                                                                                         |
| **Apple Terminal (Terminal.app)** | No confirmed mode-2031 implementation. OSC background-color querying is a separate capability and does not provide push notifications.                                                                                                                                                       |
| **Alacritty**                     | No confirmed implementation in the reviewed support references. Its ability to query or configure colors does not establish mode-2031 support.                                                                                                                                               |
| **Konsole**                       | No confirmed implementation in the reviewed support references.                                                                                                                                                                                                                              |
| **Windows Terminal**              | No confirmed implementation in the reviewed support references.                                                                                                                                                                                                                              |
| **xterm**                         | No confirmed implementation in the reviewed support references.                                                                                                                                                                                                                              |

The protocol began as Contour’s VT extension and is documented there as available in Contour 0.4.0 and Ghostty 1.0.0, with kitty 0.38.1, VTE 0.82, and other implementations added later. Adoption is real but not universal: several active emulators still lack it, while toolkit and multiplexer support has expanded the set of applications that can receive it. Neovim and Helix have adopted it on the application side; this demonstrates ongoing use, but does not make every terminal compatible.

For portable applications, query `996n` at startup, listen for `2031` events where available, and use OSC 11 or a user setting as fallback. Keep response parsing asynchronous and time-bounded so an unsupported terminal or an intermediary that filters the sequences cannot hang startup. Do not use the DECRQM status value as the light/dark answer.
