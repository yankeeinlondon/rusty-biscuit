DEC private mode 2027 coordinates terminal cell layout with programs that write or move across Unicode text. In legacy terminal models, width is often computed for each code point with a `wcwidth`-style function. A displayed grapheme can instead consist of several code points: a base plus combining marks, an emoji plus skin-tone modifier, a regional-indicator flag, or an emoji ZWJ sequence. If the application and terminal count those pieces differently, cursor movement, redraws, selection, and wrapping can drift.

## How the mode works

The convention is carried in DEC private mode controls:

| Operation            | Sequence                          |
|----------------------|-----------------------------------|
| Enable (DECSET)      | `CSI ? 2027 h` (`ESC [ ? 2027 h`) |
| Disable (DECRST)     | `CSI ? 2027 l` (`ESC [ ? 2027 l`) |
| Query (DECRQM)       | `CSI ? 2027 $ p`                  |
| Query reply (DECRPM) | `CSI ? 2027 ; Ps $ y`             |

The draft asks terminals to process grapheme clusters as units when the mode is set. It does not dictate the behavior when reset, and implementations have made different choices about defaults. It is also not a command that makes an application grapheme-aware: the application must use compatible segmentation and width calculations in its own layout. A legacy application can become misaligned if the terminal changes width semantics under it.

DECRPM follows the familiar status values: `Ps=0` means not recognized, `1` means set, `2` means reset, `3` means permanently set, and `4` means permanently reset. A positive reply establishes that the terminal recognizes the mode, not that its Unicode width rules match the application's. Some implementations always use grapheme layout, and may report it permanently set; others default to it but honor reset. Replies have also varied by terminal/version, so a missing or negative reply is not proof that the terminal cannot render graphemes. Treat the query as a negotiation hint, then test the actual sequences and width behavior your application needs.

## Visible behavior and width rules

With grapheme-aware layout, multi-code-point clusters are assigned a cell span as a whole. Typical visible improvements include a flag occupying two columns rather than the sum of two regional indicators, a ZWJ family or profession emoji occupying the expected emoji span, and variation selectors affecting presentation without leaving the cursor at the wrong column. The precise glyph depends on fonts and shaping; mode 2027 concerns terminal grid accounting, not a guarantee that a font contains or joins a glyph.

“Grapheme width” is not a single universal width algorithm. UAX #29 defines grapheme boundaries, while Unicode East Asian Width and emoji data, terminal policy, and implementation-specific rules influence how many cells a cluster occupies. The draft is commonly associated with Unicode grapheme processing, but does not freeze a Unicode version or a single width function. Implementers may update their Unicode tables independently. For example, Foot exposes `wcswidth`, `double-width`, and `max` cluster-width policies: `wcswidth` sums code-point widths and can preserve legacy application agreement, while the other policies better match a cluster's rendered span but can cause cursor desynchronization in applications that still sum per-code-point `wcwidth`. Ghostty offers `legacy` and `unicode` methods; setting mode 2027 forces its Unicode method for the duration of the mode. Contour documents whole-cluster measurement with VS15/VS16 presentation handling. Rio documents shared Unicode 17 segmentation and width data in its current implementation.

This is related to, but distinct from, libc `wcwidth`/`wcswidth`. Those interfaces generally measure code points (or sum code-point widths), and their data and locale behavior vary. UAX #29 segmentation plus a cluster-level width policy can yield a different answer. Programs should use the same grapheme segmentation and width model as the terminal when mode 2027 is active; otherwise they should retain a compatible legacy model. No mode query can identify the exact Unicode data version or width policy.

## Origins and adoption

Mode 2027 emerged from the Terminal Unicode Core draft maintained by the Contour project; its initial draft is dated September 6, 2021. It is an informal terminal convention rather than a Unicode Standard annex or a ratified ECMA/ISO terminal standard. Contour's release notes identify its implementation as support for the draft. Adoption has continued in modern emulators, but it remains uneven: some terminals support the toggle, some implement grapheme layout unconditionally, and others have no equivalent. There is no universal capability registry or reliable TERM value for it.

The current `apps_supporting` list names apps with positive evidence for the grapheme-mode behavior: WezTerm, Ghostty, cmux, Contour, Foot, and Rio. Applications should not classify terminals from their names alone; versions and configuration matter.

## Practical testing

For a protocol probe, send `CSI ? 2027 $ p` and read a bounded response from the PTY. Accept only a correctly framed DECRPM response for mode 2027. Then, where the terminal claims it can be toggled, compare its response before and after `CSI ? 2027 h` and `CSI ? 2027 l`; restore the original mode afterward. Do not leave the mode changed in the user's shell. A mode that is permanently set or reset cannot be toggled, and a query timeout is ambiguous because terminals, multiplexers, SSH hops, and terminal wrappers may suppress replies.

A behavioral probe is more informative: position the cursor, print a small set of clusters (for example `e` plus combining acute, a two-indicator flag, an emoji with VS16, a skin-tone sequence, and a ZWJ emoji), and inspect the resulting cursor position or cell grid using DSR/cursor reports or a controlled PTY harness. Include the application's own width calculation in the check. This detects actual cases of interest but cannot exhaust the Unicode space; new Unicode versions and terminal-specific policy can still differ. When a terminal uses a fixed always-on model, adapting the application is safer than trying to reset the mode.
