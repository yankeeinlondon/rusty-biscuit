## Overview

DEC private mode 2048 is an informal terminal-emulator extension proposed by Rockorager and documented in a public specification gist. TUI ecosystem notes already identify support in Foot, Ghostty, iTerm2, and Kitty by July 2024; the proposal was being discussed publicly by June 2025. It is not part of a published DEC or ECMA standard. The proposal addresses the difficulty of coordinating asynchronous `SIGWINCH` signals with an application's input loop, and of obtaining a fresh terminal size after a resize. [The proposal](https://gist.github.com/rockorager/e695fb2924d36b2bcf1fff4a3704bd83) defines one private mode for automatic reports of text-area size in cells and pixels.

An application may ask whether mode 2048 is recognized with DECRQM:

```text
Application: CSI ? 2048 $ p
Terminal:    CSI ? 2048 ; Ps $ y
```

The DECRPM status values are `0` not recognized, `1` set, `2` reset (recognized but off), `3` permanently set, and `4` permanently reset. For this mode, `1` or `2` indicates recognition; `3` and `4` are general DECRPM states and are not expected for a normal user-toggleable resize mode. The proposal's example returns `2`, because the mode is supported but initially disabled. A terminal that does not implement DECRQM may remain silent, so query with a short timeout and treat silence as unknown/unsupported. A positive reply is a useful recognition test, but not proof that reports will reach the application: terminal multiplexers, SSH wrappers, and nested terminal layers may consume, rewrite, or fail to forward private modes or reports. Querying also does not prove that reported pixel dimensions are useful.

Enable and disable with private mode set/reset:

```text
CSI ? 2048 h    enable reports
CSI ? 2048 l    disable reports
```

Enabling must immediately produce the current dimensions, including if the mode was already enabled. Each later completed resize produces another report. The proposal does not prescribe rate limiting, and says the report must wait until the terminal and application-visible TTY have settled at the new size. Applications should parse control sequences in their normal input parser, including partial sequences split across reads, and should retain a fallback resize path.

The report is a CSI window-operation response:

```text
CSI 48 ; height_chars ; width_chars ; height_pixels ; width_pixels t
```

The first two values are rows and columns; the last two are pixel height and width. If pixel geometry is unavailable, both pixel fields are reported as zero. Values may contain colon subparameters in future implementations; a parser should accept and ignore unknown subparameters. Dimensions refer to the text area and exclude terminal padding. The ordering is easy to confuse with other window-size reports: mode 2048 uses `48` and includes both cell and pixel dimensions, whereas the familiar `CSI 8;rows;columns t` reports cells only.

## Relationship to operating-system resize events

On Unix-like systems, a process attached to a PTY commonly receives `SIGWINCH`, then calls `ioctl(TIOCGWINSZ)` to read the current rows and columns. This is widely available and should remain the compatibility path. A signal can coalesce rapid resizes and is delivered outside the byte stream, so an application may observe input on either side of a resize before reconciling its size. `TIOCGWINSZ` normally supplies cells (and optional pixel fields), but applications cannot assume pixel fields are populated.

Mode 2048 puts the event and its dimensions in-band with keyboard input. This lets a single event loop order the resize relative to input without a separate size query. Through SSH, the report can travel in the same encrypted byte stream as other terminal input; it does not depend on every SSH hop correctly forwarding a window-change signal. SSH still normally propagates PTY dimensions and SIGWINCH, so this is a complement rather than a replacement, and it only helps when the remote application's terminal parser and every intervening layer preserve the sequence. Multiplexers such as tmux and screen need explicit support or passthrough handling; otherwise use their normal pane resize and signal behavior.

On Windows, `ReadConsoleInput` already yields console window-size events in the input event stream, making mode 2048 less necessary for programs using that native API. Programs using Unix-like PTY/ConPTY abstractions may still benefit from a cross-platform byte-stream event, but support depends on the terminal and console host. In particular, do not assume that Windows Terminal or a generic ConPTY path implements mode 2048 merely because native console APIs can report a resize.

## Adoption and support

The idea has moved from a small public proposal into several emulators and TUI libraries. Support is growing but remains a minority feature: a volunteer `ucs-detect` survey observed only four supporting terminals among 33 tested in November 2025, and its test records automatic responses in default builds and configurations rather than every possible option. Its result is a dated snapshot, not a conformance guarantee. Since then, Contour's release notes have explicitly added mode 2048, and iTerm2's 3.6 release notes document handling and safeguards for the mode. This is evidence of continued adoption, but the mode is still informal and no universal deployment baseline exists.

## Implementation guidance and quirks

- Do not enable the mode merely because a terminal identifies itself by `TERM` or `TERM_PROGRAM`; use DECRQM with a bounded timeout. Some emulators recognize the mode only in newer releases, and the query can be intercepted by a multiplexer.
- Keep `SIGWINCH` handling (or the appropriate native Windows event) active. Reconcile with the current PTY dimensions when receiving that fallback, and guard against duplicate notifications from both channels.
- Treat the report as an input-parser event, not as printable text. CSI sequences can be fragmented across reads, and a process may receive multiple reports quickly. Apply the latest valid dimensions while preserving input ordering.
- Always accept zero pixel dimensions. Cell dimensions are the portable minimum; pixel geometry varies with terminal scaling and may be unavailable.
- In iTerm2, the release notes warn that programs can accidentally leave DEC 2048 reporting enabled. iTerm2 detects this from echoed input and turns the mode off when it detects a hostname change, so applications should disable the mode during orderly shutdown and not assume the state survives a reconnect.
- When running in a multiplexer, prefer its documented resize API/events or configure an explicit passthrough. Do not enable mode 2048 in an inner application unless the outer layer forwards the enable request and the resulting `CSI 48 ... t` reports.
