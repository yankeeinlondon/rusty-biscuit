# Mouse coordinate and button encodings: DEC private modes 1005, 1006, 1015, and 1016

These are xterm-originated, informal DEC private mode extensions. They select the *encoding* of mouse reports; they do not turn mouse reporting on by themselves. An application normally combines one tracking mode (`?1000` for press/release, `?1002` for button motion, or `?1003` for all motion) with one encoding mode. The original X10 report stores each field in one byte after adding 32, so its coordinate range ends at column/row 223. These extensions provide larger coordinates or a more parseable representation.

Enable a tracking mode and one encoding with DECSET (`CSI ? … h`), and reset them on exit with DECRST (`CSI ? … l`). Avoid leaving a mode enabled after the application exits. The encoding modes are alternatives: do not enable 1005, 1006, 1015, and 1016 together and assume the result is portable. In particular, 1016 extends the SGR report shape and should be paired with 1006 and a tracking mode.

## Wire formats

All coordinates are one-based. `Cb` is the button/event value: low bits identify the button or release/wheel event, and higher bits carry modifiers and (for motion) the motion flag. The precise event-bit mapping is inherited from xterm mouse tracking; use a tested parser rather than treating `Cb` as a simple button number.

| Mode            | Report form                                                                 | Coordinate representation and cautions                                                                                                                                                                                                     |
|-----------------|-----------------------------------------------------------------------------|--------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| X10 baseline    | `CSI M Cb Cx Cy`                                                            | Each field is one byte encoded as value + 32. Coordinates stop at 223.                                                                                                                                                                     |
| 1005 UTF-8      | `CSI M <UTF-8(Cb)> <UTF-8(Cx)> <UTF-8(Cy)>`                                 | Extends the byte fields to UTF-8 encoded values (xterm documents positions up to 2015). The byte stream is not ordinary text: middleware, UTF-8 decoders, and parsers can split, transform, or mistake report bytes for text/control data. |
| 1006 SGR        | `CSI < Cb ; Cx ; Cy M` for press/motion; `CSI < Cb ; Cx ; Cy m` for release | Decimal, semicolon-separated parameters; release has its own final `m`, removing X10's release-button ambiguity. No 223-column byte ceiling.                                                                                               |
| 1015 urxvt      | `CSI Cb ; Cx ; Cy M`                                                        | Decimal parameters and the same button encoding as X10. It retains final `M` for reports, making the sequence prefix ambiguous with CSI `M` (delete lines); it is not recommended by xterm.                                                |
| 1016 SGR-Pixels | `CSI < Cb ; Px ; Py M` for press/motion; `CSI < Cb ; Px ; Py m` for release | Same syntax and button data as 1006, but `Px`/`Py` are physical pixel coordinates, not cells.                                                                                                                                              |

1005's UTF-8 coordinate encoding is a transitional solution. It can confuse software that does not consume the input as a byte stream and does not safely compose with non-UTF-8 terminal filters. 1015 removes the coordinate byte limit but keeps an ambiguous CSI final. Prefer **1006 SGR** for ordinary text-cell interfaces. It is explicit, decimal, unambiguous about release, and the most widely interoperable extended format. Use 1016 only when the application truly needs pixel precision and has confirmed support in the actual terminal path. Keep X10 as a fallback only for older terminals, accepting its coordinate limit.

## SGR-Pixels and cell conversion

Mode 1016 changes units; it does not change the shape of the 1006 report. Pixel positions are measured from the terminal area's upper-left edge, in device/physical pixels according to the terminal implementation. They are one-based in the xterm description. Do not assume CSS logical pixels, a fixed DPI, or that a cell has a universal pixel size.

To map an event to a cell, obtain the terminal's current pixel dimensions and character grid dimensions (where supported, xterm window reports `CSI 14 t` and `CSI 18 t` provide these), then compute cell width and height from the usable text area. For one-based pixel coordinates and cell dimensions `W` × `H`, a basic mapping is `column = floor((Px - 1) / W) + 1`, `row = floor((Py - 1) / H) + 1`. Clamp to the current grid and account for borders, padding, title bars, status regions, DPI scaling, and resize changes as applicable. If exact cell metrics are unavailable, 1016 cannot be converted reliably from grid dimensions alone; use cell-based 1006 instead. The pixel report can also support image/canvas hit-testing without converting to cells.

## Detecting support and querying mode state

There is no universal capability-negotiation handshake for these informal modes. A program can send `CSI ? 1006 h` and observe whether it later receives SGR-shaped mouse events, but that requires a real mouse action, an enabled tracking mode, and a functioning input path. Merely seeing the sequence consumed or seeing a valid mode-state reply does not prove that reports are generated correctly. Automated testing can use a real terminal or an emulator with an injectable mouse-event API; headless parser tests establish only parser behavior, not host-window hit-testing, pixel scaling, or event delivery.

DECRQM asks for current DEC private mode state with `CSI ? Pm $ p`; a DECRPM response has the form `CSI ? Pm ; Ps $ y`. The status values are `0` not recognized, `1` set, `2` reset, `3` permanently set, and `4` permanently reset. The xterm documentation defines this query and xterm reports mode state. Implementations differ: some report 1005/1006 as reset even when they accept the set sequence, some omit a response, and some answer only a subset. This is not a reliable capability test. `2` means “currently reset” where the mode is known; it does not mean unsupported. `0` is useful evidence that this terminal does not recognize that mode, but a missing/malformed response can also mean the query is unsupported, intercepted, or lost in a multiplexer. `1` confirms current state, not that the behavior is correct in every event case. A positive query is therefore supporting evidence, not a substitute for observed reports.

For a safe probe, serialize the query and parse only its matching response with a bounded timeout while preserving unrelated input for the application. Do not issue probes asynchronously into an unstructured key-input stream. If choosing a protocol at runtime, prefer a documented terminal capability database or known terminal/version mapping, then validate behavior during integration testing; a silent “try every mode” sequence is unsafe because terminals may accept modes without implementing their intended encoding.

## Origin, adoption, and present support

The modes are xterm extensions rather than an ECMA/DEC standard. Xterm's control-sequence history and current manual are the primary specification; exact first-release dates for every encoding are not consistently documented. The 1005/1006/1015 family arose to extend the old X10 coordinate representation as terminal emulators added mouse tracking. Mode 1016 is newer: it preserves SGR's parseable form while expressing positions in pixels. Support is still growing for pixel reporting as terminal graphics and sub-cell interfaces become more common, but it is less universal than cell-based SGR. No terminal-name list is stable across releases, forks, multiplexers, remote shells, or embedded terminal widgets. Recheck a current support matrix and test the actual chain (app → multiplexer/SSH/filter → terminal) before depending on a mode.

Treat `apps_supporting` as a discovery list, not a portability guarantee.

## Practical quirks and workarounds

- **Mode state is not capability state.** A DECRQM response of reset is normal before enabling the mode. Test report bytes when possible; if querying, send the query after setting the mode and still do not infer a complete mouse implementation from the answer alone.
- **Multiplexers and remote paths can change input.** Mouse support must be enabled and passed through at each layer. Start with 1006; if a multiplexer cannot preserve reports or 1016 coordinates, disable pixel mode and use cell reports.
- **1005 depends on byte transparency.** UTF-8 conversion or text-oriented input handling can corrupt its multi-byte fields. Prefer 1006.
- **1015 has CSI ambiguity.** Do not choose it for new programs; it offers no advantage over 1006 and is harder to parse safely.
- **1016 is physical-pixel and implementation-sensitive.** Keep 1006 available as fallback; refresh geometry after resize or DPI changes, and test with a real terminal window. A terminal's web/headless bridge may not expose the same capability as its desktop app.
- **Users may reserve Shift for terminal selection.** Some terminals let Shift-click bypass application mouse reporting to select/copy text. Document the terminal's override or test with an unmodified click before diagnosing missing reports.
