# DEC mouse tracking modes 9, 1000, 1002, and 1003

These DEC private modes are a family of xterm-originated, de facto terminal controls for forwarding mouse input from a terminal emulator to the program running in its pseudo-terminal. A program enables a mode with `CSI ? <n> h` and disables it with `CSI ? <n> l` (7-bit spelling: `ESC [ ? <n> h/l`). They select *which events* are reported; separate modes such as 1006 select the *encoding* of their coordinates. The names “DEC private mode” describe the escape-sequence mechanism and do not mean the modes were standardized by DEC.

## Event behavior

| Mode | Common name             | Events reported                                                                                                                   |
|------|-------------------------|-----------------------------------------------------------------------------------------------------------------------------------|
| 9    | X10 compatibility       | Button press only. It is the older, restricted form; it does not report releases.                                                 |
| 1000 | Normal / VT200 tracking | Button press and release, plus wheel actions where the emulator maps the wheel to mouse buttons. No pointer motion.               |
| 1002 | Button-event tracking   | Mode 1000 events plus motion while a button is held. Motion is generally reported when the pointer enters another character cell. |
| 1003 | Any-event tracking      | Mode 1002 events plus pointer motion with no button held, generally cell-by-cell. This can generate a high volume of input.       |

Wheel reporting is not a distinct tracking mode: common xterm-compatible encodings represent wheel up/down as button-like events (often button codes 64 and 65). The exact wheel behavior and horizontal-wheel support vary. Xterm documents the event semantics and the button-motion encoding in its [Mouse Tracking reference](https://invisible-island.net/xterm/ctlseqs/ctlseqs.html#h2-Mouse-Tracking).

These modes should be treated as alternative tracking levels, not additive subscriptions. Applications conventionally enable one level and reset it on exit. Emulators differ in how they resolve multiple simultaneously-set bits; do not assume that setting 1000, 1002, and 1003 produces a union or that resetting one leaves another effective. Set the intended level explicitly, then reset the modes your program changed during cleanup. Multiparameter DECSET and DECRST are supported by common terminals, but robust apps should not rely on undefined combinations.

## Reporting formats and capability detection

The original X10 coordinate format is compact but limited: coordinates are encoded as bytes and therefore fail at large row/column values. UTF-8 mode 1005 was an attempted extension with compatibility problems. SGR mode 1006 is the widely supported modern choice: a report resembles `CSI < Cb ; Cx ; Cy M` for a press and uses lowercase `m` for release, allowing an unambiguous release and avoiding the old coordinate ceiling. Tracking and encoding are independent; for example, a typical modern application enables `?1000;1006h` or `?1002;1006h`. See the xterm reference above and the [iTerm2 feature reporting specification](https://iterm2.com/feature-reporting/) for a current description of safe SGR support.

There is no passive, universally reliable “does this emulator implement mouse tracking?” probe. An application can send DECRQM, `CSI ? <n> $ p`, to ask for the current state of private mode `<n>`. A supporting terminal answers `CSI ? <n> ; <state> $ p`: state 0 means not recognized, 1 set, 2 reset, 3 permanently set, and 4 permanently reset. This is a *state query*, not a capability query: 2 means recognized but currently reset, while silence may mean unsupported, filtered, delayed, or lost response. Some emulators do not implement DECRQM consistently for private modes, and multiplexers or remote PTY layers may affect the answer. Even state 1 only says the mode is active, not that all desired event classes, encodings, or modifiers work. Prefer documented terminal feature reporting where available (iTerm2 has a feature reporting protocol), or use a controlled active probe that enables the desired mode, observes actual input, and always restores terminal state. Never infer support from `$TERM` alone.

## Text selection and modifier overrides

While a tracking mode is active, the emulator normally forwards the captured mouse events, so ordinary click-and-drag selection in terminal scrollback may stop working. Emulators commonly reserve a modifier to bypass reporting and perform terminal-side selection. This override is emulator policy, not part of the DEC protocol, and differs across apps and configuration:

| Terminal       | Selection while the application has grabbed the mouse                                                                                                                                                                                               |
|----------------|-----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| WezTerm        | Hold **Shift** by default; `bypass_mouse_reporting_modifiers` can change it. ([docs](https://wezterm.org/config/mouse.html))                                                                                                                        |
| Ghostty        | **Shift** normally bypasses reporting. Its `CSI > Pn s` XTSHIFTESCAPE extension lets applications request whether Shift itself is reported; terminal policy can still override it. ([docs](https://ghostty.org/docs/vt/csi/xtshiftescape))          |
| iTerm2         | Hold **Option**; mouse reporting can also be disabled in the profile, and click/drag and wheel reporting have separate preferences. ([docs](https://iterm2.com/documentation-preferences-profiles-terminal.html))                                   |
| kitty          | Hold **Shift**; its `mouse_map` can customize selection while grabbed. ([docs](https://sw.kovidgoyal.net/kitty/overview/))                                                                                                                          |
| Alacritty      | Hold **Shift** to bypass capture and select text. ([docs](https://github.com/alacritty/alacritty/blob/master/docs/features.md))                                                                                                                     |
| GNOME Terminal | Hold **Shift** to make Terminal catch the mouse for selection. ([docs](https://teams.pages.gitlab.gnome.org/Websites/help.gnome.org/gnome-terminal/txt-select-text.html))                                                                           |
| Apple Terminal | The “View > Allow Mouse Reporting” switch controls whether reporting is permitted; Apple’s user guide does not document a universal modifier override. ([guide](https://support.apple.com/guide/terminal/turn-on-mouse-reporting-trmlc69728a5/mac)) |
| Konsole        | Has a user preference (“Allow mouse tracking”) that can disable forwarding; selection behavior depends on that setting and active application. ([source note](https://sources.debian.org/src/konsole/4%3A16.12.0-4/src/Vt102Emulation.cpp))         |

Modifier behavior can change by platform, version, and user configuration. When documenting an app, describe its default and point to the setting rather than treating a modifier as a protocol guarantee.

## Origin, adoption, and practical support

The family originated in xterm’s emulation of X10/VT-style mouse input and evolved through xterm’s VT200 and motion-tracking extensions. The public xterm control-sequence reference and source history trace the mode names to xterm; the mode family was already represented in xterm source by the late 1990s. It became an informal standard because terminal applications and emulators independently implemented the same byte protocol. It remains in active use: modern editors, pagers, multiplexers, and TUIs still request these modes, and current terminal documentation continues to describe mouse reporting. Newer SGR encoding and richer terminal-specific protocols extend the reporting format without replacing the tracking modes.

The table below reflects public documentation or implementation evidence available when researched (September 2026). “Yes” means support is documented for the general mouse-reporting family; it does not imply that all four modes or all coordinate formats behave identically. In particular, DECSET 9 is a legacy compatibility mode and is less consistently documented than 1000, 1002, and 1003. Where evidence only establishes the commonly used 1000/1002/ 1003 modes, the entry says so.

For portable applications, request the least event-intensive mode that meets the need: 1000 for clicks, 1002 for drag interaction, and 1003 only when hover/motion is essential. Pair it with SGR 1006 when supported, handle legacy X10 coordinates only when required, restore modes on normal shutdown, and provide keyboard alternatives. The terminal may suppress or transform input, and remote multiplexers add another compatibility layer, so test real event delivery rather than treating mode setting or DECRQM as proof.
