## Overview

DEC private mode 1004 is an Xterm extension commonly called *focus reporting* or *focus tracking*. It is not part of the original DEC VT100/VT220 standards. A program enables it with `CSI ? 1004 h` (7-bit form `ESC [ ? 1004 h`) and disables it with `CSI ? 1004 l`. While enabled, the terminal sends `CSI I` when the terminal surface containing the program becomes focused and `CSI O` when it loses focus. These are input bytes delivered to the foreground process, not replies to a query. Applications should restore terminal state and disable reporting on exit.

The feature originated in Xterm: patch #224 added private mode 1004 on February 11, 2007. Xterm's control-sequence reference documents the mode and its FocusIn/FocusOut reports. It has no standalone standards-track specification. [Xterm patch history](https://invisible-island.net/xterm/xterm.log.html) It has nevertheless spread broadly across contemporary emulators and multiplexers, with continuing adoption. [Xterm Control Sequences](https://invisible-island.net/xterm/ctlseqs/ctlseqs.html)

### Testing and capability queries

Test behavior directly: enable mode 1004 in a PTY-backed program, switch focus away and back, and verify received `ESC [ O` and `ESC [ I`. Parse these as input events, not terminal replies. `CSI O` also overlaps the SS3 key-sequence family; recognize it as focus-out only in the appropriate input context and when reporting is enabled.

DECRQM (`CSI ? 1004 $ p`) asks for current mode state. A DECRPM reply can indicate `0` (not recognized/not reportable), `1` (set), `2` (reset), `3` (permanently set), or `4` (permanently reset). Implementations vary: some track mode 1004 but report reset even after it was enabled, and others provide no useful reply. A positive set reply is evidence of state, but reset, unrecognized, absent, and even successful DECSET parsing do not reliably prove whether UI focus events will be emitted. Reporting may be gated or intercepted by a multiplexer. Treat DECRQM as a diagnostic hint, not capability negotiation. [Xterm DECRQM/DECRPM](https://invisible-island.net/xterm/ctlseqs/ctlseqs.html#h3-Requesting-mode) · [Mode probe observations](https://www.terminfo.dev/modes/decset-1004-focus-tracking)

### Focus scope

The protocol reports terminal input focus and carries no window, tab, or pane identity. The common baseline is the terminal window becoming or ceasing to be the active OS window. Tab and split behavior differs: some emulators report selected-tab or embedded-pane changes, while others only report containing-window activation. Focus-follows-mouse and transient dialogs can also affect transitions. Applications should treat reports as advisory and avoid assuming a one-to-one mapping to a window switch.

There is no portable requirement for an immediate report of current focus when mode 1004 is enabled. VTE-based terminals have been observed to send current focus state on activation of the mode, unlike the common transition-only behavior. Do not depend on the first report for initialization. [VTE behavior notes](https://terminalguide.namepad.de/mode/p1004/)

### Multiplexers

A multiplexer mediates mode requests and input events between the host terminal and the inner program.

- **tmux:** `focus-events` is off by default. Configure `set -g focus-events on` to request host focus reports and synthesize reports when the active pane changes. The inner program must also enable mode 1004. [tmux manual](https://man.openbsd.org/tmux.1)
- **Zellij:** tracks host focus per connected client and forwards `CSI I`/`CSI O` to panes that enabled mode 1004; the documented behavior works across nested sessions. [Zellij compatibility guide](https://zellij.dev/documentation/compatibility.html)
- **GNU Screen:** do not assume support. Its manual documents region focus controls, but not a clear mode-1004 forwarding contract. Test the exact build or use a multiplexer with documented forwarding when this matters.

A layer cannot invent host focus data that the outer terminal does not provide. In nested multiplexers, verify every layer: one may consume mode requests, synthesize pane changes, or forward only when separately enabled.

### Application guidance

Enable reporting only while the application owns terminal input and disable it during cleanup. Parse focus events with key input, keep refresh operations safe to repeat, and use the signal for optional UI behavior such as pausing animation or refreshing on regain—not correctness or persistence. Document `set -g focus-events on` for tmux users. For GNU Screen, assume no forwarding until the exact setup is verified. To characterize an app, log received bytes while separately switching OS windows, tabs, and splits.
