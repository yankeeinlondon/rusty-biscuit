# OSC 10, OSC 11, and OSC 12: dynamic terminal colors

OSC 10, 11, and 12 are related xterm conventions for a terminal's dynamic default colors:

| Sequence | Color                   |
|----------|-------------------------|
| OSC 10   | Default text foreground |
| OSC 11   | Default text background |
| OSC 12   | Text cursor             |

They are often called “informal standards”: they are widely implemented and documented by xterm, but are not part of ECMA-48 and have no single standards body governing their exact behavior. The xterm control-sequence reference is the historical interoperability reference. These commands come from xterm's dynamic-color feature set; the available xterm documentation describes their behavior but does not give a reliable first-release date. They predate today's rapid terminal-protocol adoption and have subsequently spread across desktop, GPU-accelerated, and web terminal emulators. Their continued inclusion in current emulator references and use by theme-aware software show ongoing adoption, although query coverage—especially OSC 12—is less uniform than setting colors.

## Wire format and behavior

An OSC begins with `ESC ]` (or the C1 OSC byte), carries a command number and semicolon-separated parameters, then ends with String Terminator (`ESC \\` or C1 ST). BEL is also accepted by many xterm-derived emulators for compatibility. For example, a program can query the three colors with:

```text
ESC ] 10 ; ? ST
ESC ] 11 ; ? ST
ESC ] 12 ; ? ST
```

The terminal replies with the matching command number and its color, commonly in X11-style `rgb:rrrr/gggg/bbbb` notation, terminated by BEL or ST. Channel width varies: replies can use one to four hexadecimal digits per component, so parsers should scale each component according to its digit width rather than assuming exactly 8-bit or 16-bit output. `#RRGGBB` and other accepted color forms are commonly usable when setting; the accepted forms and alpha handling vary by emulator. A color can typically be reset with OSC 110, 111, or 112, respectively, though reset support is also implementation-dependent.

Queries are useful for adapting application colors to the user's active terminal theme, including determining whether the background is light or dark. They are not a guaranteed capability-negotiation mechanism: an unsupported terminal may silently ignore a query. Query each value independently, use a short bounded timeout, parse either BEL or ST, accept variable-width RGB components, and fall back to a configured/default theme. A query is directly testable by sending it through a real terminal PTY and capturing the response; setting can be tested by querying before and after a controlled set/reset. Avoid emitting a probe when the application cannot safely read terminal input, since an unrecognized query may leave bytes in the user's input stream. A multiplexer or remote shell can also intercept, suppress, or fail to route the reply, so test the complete path actually used by the application.

The [OSC utility's tested list](https://github.com/c-blake/osc) provides practical test evidence for Alacritty and several other emulators. [Current cross-terminal surveys](https://terminfo.dev/osc) help identify candidates but are secondary sources and should not override conflicting direct tests.

## Practical guidance

OSC queries can reveal a terminal's actual active colors, but they do not provide an atomic snapshot: colors can change between separate replies, and some emulators report configured rather than composited/display-adjusted colors. Query only when the result materially improves behavior, impose a timeout, handle unrelated input safely, and gracefully continue if any reply is missing or malformed. For broad compatibility, OSC 10 and 11 are the useful baseline; make OSC 12 optional.
