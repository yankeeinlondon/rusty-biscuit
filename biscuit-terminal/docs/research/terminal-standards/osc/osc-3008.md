# OSC 3008: Hierarchical Context Signaling

## Overview

OSC 3008 is UAPI.15, an informal terminal protocol for recording which shell, command, session, or nested execution environment currently owns terminal interaction. It gives a terminal an in-band account of context transitions and of the output written while each context is active. It is not a request/response capability negotiation protocol and is not part of ECMA-48; it uses ECMA-48's OSC framing and assigns meaning to command number 3008.

There are two operations, conventionally terminated by the String Terminator (`ESC \`):

```text
ESC ] 3008;start=<context-id>[;key=value...] ESC \
ESC ] 3008;end=<context-id>[;key=value...] ESC \
```

`start` opens a context, updates an existing context, or returns to one already on the stack. Opening a child makes it active and makes the former active context its parent. `end` closes the identified context. A repeated `start` for the same ID replaces that context's metadata and implicitly ends its child contexts. Context IDs are at most 64 printable characters and should be unique; senders should escape literal semicolons as `\x3b` and backslashes as `\x5c` in UTF-8 field values. Unknown or invalid fields should be ignored without discarding valid fields. The specification recommends bounded context depth and metadata storage and says ordinary terminal reset sequences must not clear the context stack.

The defined `type` values describe boot, service, session, shell, command, app, remote, VM, container, privilege elevation (`elevate`), user switching (`chpriv`), and same-privilege nesting (`subcontext`). Other fields identify the user, host, machine and boot IDs, process and command, working directory, container/VM, target host/user, and session. An `end` may include `exit=success|failure|crash|interrupt`, a numeric `status`, and a signal. Metadata is advisory; senders must not put secrets in it.

## What it enables and how to test it

The protocol does not prescribe a particular UI. A terminal can associate scrollback with its active context and use that association for output bookmarks, context breadcrumbs, labels/tooltips, status indicators, failure attention markers, context-aware shell launches, or process-group actions. These are use cases, not required behaviors. Some terminals only parse and retain events; that may have no immediate visible effect. Contour documents using the shell/command contexts to recover command and output boundaries, working directories, and exit status. This can complement OSC 133 semantic prompt reporting, though OSC 3008 does not identify the exact boundary between a prompt and the user's typed command.

There is no standard query to ask whether OSC 3008 is supported. A sender cannot reliably distinguish “understood” from “ignored” by sending an event. Test parser acceptance with a harmless, unique `start` followed by its matching `end`, then inspect the terminal's debug/protocol trace or an API/UI that exposes contexts. Test actual user-visible behavior separately by using a shell integration that emits command and nested-context events and checking output association, context metadata, and exit status. A terminal that merely swallows the sequence is not necessarily implementing context tracking. Test through the intended path (including SSH, tmux, or other multiplexers if used), since intermediaries may pass, consume, or display the sequence. Avoid treating an unchanged cursor or absence of raw escape text as proof of semantic support.

## Origin, maturity, and emitters

The design grew out of systemd's need to describe the changing source of terminal output across service sessions, privilege changes, containers, VMs, and commands. It was discussed as the systemd OSC context proposal and published by the UAPI Group as UAPI.15, version 1.0. systemd 258 introduced the broad implementation: the `80-systemd-osc-context.sh` Bash profile integration emits shell and per-command events, and systemd components emit contexts for boot, interactive services/sessions, `run0`, `systemd-nspawn`, `machinectl login`/`shell`, and `systemd-vmspawn`. The integration is Bash-specific and is skipped when `TERM` is unset or `dumb`, or when Bash prompt expansion is disabled. The systemd design also describes remote contexts for tools such as SSH, but that does not mean every SSH client emits OSC 3008; verify the particular client or remote shell setup.

Adoption is active but early and uneven. Contour has dedicated documentation and connects contexts to command/output features. Ghostty's VT parser has an OSC 3008 implementation, and cmux is based on libghostty, so parser behavior can be inherited from its embedded version. Other positive entries in the matrix below come from a 2026 empirical terminal probe and should be read as evidence that the tested build consumed the sequence, not as a promise of the same UI behavior or of support in every release. The format has no universal capability advertisement, and applications should continue to work when events are ignored.

When testing a terminal integration, include both start/end nesting and metadata escaping, not only an unknown-field sequence. OSC 3008 does not have a reply; capability detection must therefore use known-terminal/version data, an out-of-band integration contract, or a user-visible functional test rather than an OSC query.
