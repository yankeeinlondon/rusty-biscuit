## Overview

OSC 133 is an informal terminal interoperability convention, not an ECMA-48 or IETF standard. It originated in FinalTerm and is commonly called FinalTerm shell integration or semantic prompts. FinalTerm is defunct, but iTerm2 documented and continued the convention, and independent terminal projects adopted it. WezTerm records adding support in February 2021, and kitty documents support since 0.24.0. [iTerm2's specification](https://iterm2.com/3.6/documentation-escape-codes.html) [WezTerm's changelog](https://wezterm.org/changelog.html) [kitty's shell integration docs](https://sw.kovidgoyal.net/kitty/shell-integration/)

OSC begins with `ESC ]` (`\x1b]`) and ends with String Terminator (`ESC \`, `\x1b\\`) or, in many implementations, BEL (`\x07`). OSC 133 then carries a semicolon-delimited event:

| Event          | Meaning                                    | Typical placement                                   |
|----------------|--------------------------------------------|-----------------------------------------------------|
| `133;A`        | Prompt begins                              | Before the primary prompt                           |
| `133;B`        | Prompt ends; editable input begins         | After the prompt                                    |
| `133;C`        | Input ends; command output begins          | When the line is submitted, before execution/output |
| `133;D;status` | Command finishes, optionally with a status | After command output, before the next prompt        |

For example, `ESC ]133;A ESC \\` precedes prompt text and `ESC ]133;B ESC \\` follows it. After Enter the shell emits C, runs the command, and emits D with the exit status. D without a status is useful for a cancelled input line, such as Ctrl-C before execution. A terminal can mark the whole prompt/command/output block and later associate the completion status with it. The basic sequence is documented by [Contour](https://contour-terminal.org/vt-extensions/osc-133-shell-integration/) and [Windows Terminal](https://learn.microsoft.com/en-us/windows/terminal/tutorials/shell-integration).

Implementations do not all use only these four events. Some support `P` for an explicit prompt segment, `N` for a new command/prompt, `I` for input ending at the line boundary, and `L` for a fresh line. These richer forms help with multi-line prompts and line editors; they are extensions and are not uniformly understood. `A`, `B`, `C`, and `D` remain the portable baseline. iTerm2 documents only part of the broader convention and explicitly says some sequences in the original FinalTerm specification are not supported there.

## What it enables

OSC 133 describes regions; it does not prescribe a particular UI. Depending on the terminal and its shell integration, the regions can enable:

- Navigation to previous/next prompts or commands in scrollback.
- Selecting, copying, or piping a command's output without manually dragging over it; some terminals can open the last output in a pager.
- Command marks in scrollback and the scrollbar, often colored by success or failure when D carries an exit code.
- Command completion notifications, command history, and shell-aware pane or tab behavior.
- Accurate prompt and input boundaries for mouse cursor placement or accessibility features.

These capabilities are app-specific. WezTerm supports semantic zones, prompt jumps, and selecting complete input/output regions. kitty offers prompt navigation, last-output paging and mouse-assisted command editing. Ghostty supports prompt navigation and output copying and, in version 1.3, click-to-move for supported shells. iTerm2 presents command marks and status-aware history, including scrollbar annotations as part of its broader integration. Windows Terminal uses marks and scrollbar indicators. Contour exposes prompt/output copy actions, output folding and accessibility prompt regions. Foot can pipe the last command's output. Some apps record boundaries or provide navigation without a scrollbar marker or dedicated selection command. [WezTerm](https://wezterm.org/shell-integration.html) [kitty](https://sw.kovidgoyal.net/kitty/shell-integration/) [Ghostty](https://ghostty.org/docs/install/release-notes/1-3-0) [Contour](https://contour-terminal.org/configuration/key-mapping/) [Foot](https://codeberg.org/dnkl/foot/wiki#jumping-between-prompts)

## Detecting and testing support

There is no standard capability query or negotiation handshake for OSC 133. An application cannot safely infer complete semantic-prompt support from `TERM` alone. OSC 133 is one-way metadata, and a terminal that silently accepts an unknown OSC sequence can look much like one that implements it. The practical check is to emit a controlled A/B/C/D sequence and inspect the terminal's observable behavior or a terminal-specific debug/semantic-region view. Test the feature being relied on (marks, status coloring, prompt jumps, output selection) rather than treating parser acceptance as proof of every UI feature. Do this in an interactive test terminal, not a production shell: a test sequence changes that terminal's semantic history.

For implementation tests, assert that generated shell output contains the expected markers at prompt, submit, and completion boundaries, and test the terminal integration separately. Test success, nonzero status, cancelled input, wrapped/multiline prompts, missing final newline, resize, and nested shell/multiplexer cases where relevant. Shell hooks can be disrupted by prompt frameworks, line editors, remote sessions, or multiplexers, so a basic echo probe alone is insufficient.

## Shell emission

The terminal usually parses the markers, but the interactive shell must emit them. Bash and Zsh do not generally emit OSC 133 by default; terminals such as WezTerm, Ghostty, kitty, and iTerm2 provide injected or sourceable integration scripts. Those scripts install prompt/pre-execution hooks and preserve shell status and prompt rendering behavior. Fish emits prompt markers natively starting with fish 4.0 (`mark-prompt` is enabled by default); earlier versions and terminal scripts may supply them. Fish 4.1 adds behavior used by newer click-to-move extensions. Nushell has native configurable shell integration, though details and compatibility have varied by terminal/version. Xonsh integrations are available, including a WezTerm plugin. Consult the shell and terminal versions in use rather than assuming the terminal bundled integration is active. [Fish language documentation](https://fishshell.com/docs/4.1/language.html) [WezTerm shell integration](https://wezterm.org/shell-integration.html) [Zellij shell integration](https://zellij.dev/documentation/shell-integration.html)

Terminal-provided scripts do not necessarily reach subshells, containers, SSH hosts, or shells launched through a multiplexer. For those environments, load the integration on the remote/inner shell or use the terminal's documented forwarding/bootstrap mechanism. Avoid enabling two integrations at once: they can duplicate prompt events or conflict over PS1, hooks, and redraw behavior.

## Parameters and extensions

The payload after the event letter may contain semicolon-separated optional fields. Unknown fields should be ignored, but their meaning is not portable unless a terminal documents it.

- `k=` labels prompt kind. Values used by implementations include `i` for the primary prompt and `s` for a continuation prompt; newer variants use `c` or `r` for continuation/right prompts. Kitty and WezTerm use this to classify prompt segments.
- `aid=` identifies the emitting application or shell instance. Newer extensions use it to correlate nested command lifecycles. It appears in WezTerm and Ghostty integration output, but is not required by the original four-event flow and has limited cross-terminal semantics.
- `cl=` requests click-to-move behavior in the input region. `cl=line` is used by Ghostty; WezTerm uses `cl=m` in its shell integration. This is an extension, not a baseline guarantee.
- `click_events=1` or `2` advertises shell support for mouse click reporting; Kitty documents coordinate modes and Fish/Nushell can emit related forms. Ghostty 1.3 supports the `click-events` extension.
- `cmdline=` or `cmdline_url=` can attach command text to C. Kitty documents both encodings; Contour documents `cmdline_url`. These fields support richer command history/run-recent-command features, but are not universally consumed.
- Other implementation-specific fields include Kitty's `redraw=0` and `special_key=1`, and Ghostty's `redraw=last`. Do not assume another terminal interprets them.

In short, A/B/C/D and an optional decimal status on D have the broadest interoperability. Parameters and events beyond that baseline should be treated as best-effort extensions, not required protocol features. References: [kitty's shell-developer notes](https://sw.kovidgoyal.net/kitty/shell-integration/#notes-for-shell-developers), [Ghostty 1.3 release notes](https://ghostty.org/docs/install/release-notes/1-3-0), [Contour sequence reference](https://contour-terminal.org/vt-extensions/osc-133-shell-integration/).

## Adoption

Adoption is continuing: modern terminal emulators expose command-aware scrollback and shell integrations, Fish emits the core markers by default, Ghostty is adding click-to-move extensions, and Contour uses marks for accessibility and structured command blocks. The protocol remains informal, and compatibility is strongest at the basic lifecycle boundary. New terminal features should degrade cleanly when markers or extensions are absent, and shell authors should emit the smallest compatible set their line editor can place correctly.
