# OSC 633: VS Code shell integration

OSC 633 is an informal, application-specific protocol created by Visual Studio Code for its integrated terminal. It is a parallel extension to FinalTerm's OSC 133 shell-integration markers: `A` through `D` describe prompt and command lifecycle, while OSC 633 adds an exact command-line report and named terminal properties. The shell emits these control sequences on the terminal's output stream; the emulator parses them without displaying them and updates its model of the active prompt, command, result, and working directory.

## Message forms

The introducer is `ESC ] 633 ;`, and the sequence ends with a BEL (`\x07`) or String Terminator (`ESC \\`). A shell integration script emits events at lifecycle boundaries:

| Message                      | Meaning                                                                                                         |
|------------------------------|-----------------------------------------------------------------------------------------------------------------|
| `A`                          | Prompt begins.                                                                                                  |
| `B`                          | Prompt ends and the editable command input begins.                                                              |
| `C`                          | Command is about to execute.                                                                                    |
| `D[;<exit-code>]`            | Command finished; the optional status is its exit code.                                                         |
| `E;<command-line>[;<nonce>]` | Supplies the exact command line, optionally with a nonce used to establish that the integration script sent it. |
| `P;<name>=<value>`           | Sets a recognized terminal property. Unknown property names are ignored.                                        |

The ordering expected for rich command detection is `A, B, E, C, D`. `E` is commonly emitted by a line-editor hook immediately before `C`; `D` is emitted on the next prompt after the shell has the exit status. If `E` is absent, a terminal can infer a command from the text between `B` and `C`, but this is less reliable for multiline input, edits, or shell-specific syntax. `P;Cwd=...` reports the current directory. VS Code also defines `IsWindows` for backend heuristics, `HasRichCommandDetection` to indicate an ideal event stream, and properties such as `ContinuationPrompt` and `Prompt` in its shell integration implementation. Implementations handle only the properties they recognize.

The `E` command-line field is not URI encoding or shell quoting. Escape a literal backslash as `\\`; encode ASCII control characters (0x00–0x20) and semicolon (0x3b) as `\xAB`, with case-insensitive hexadecimal digits. For example, a newline becomes `\x0a`, a semicolon `\x3b`, and a backslash `\\`. Property values use VS Code's message serialization: backslashes, semicolons, and control characters are escaped so they cannot terminate or split the OSC fields. The optional nonce follows the command line as another semicolon-delimited field. Treat command and property strings as untrusted unless the nonce is validated; terminal output can otherwise spoof shell metadata.

## What it enables

The event stream lets a terminal distinguish prompt text, user input, command output, and command completion. In VS Code this powers command decorations and navigation, command/output selection, current-directory tracking, rerunning or opening detected commands, exit-status cues, and improved terminal input synchronization. Exact features depend on the consumer; OSC 633 itself specifies metadata, not a mandatory UI. A terminal that recognizes only `A`–`D` can still provide prompt navigation and command boundaries but cannot rely on the richer command line or properties. VS Code scripts also emit OSC 133 where appropriate, allowing terminals that implement FinalTerm's common subset to benefit from the lifecycle markers.

This is tested in two ways. Protocol-level tests can feed representative `A`–`D`, `E`, and `P` sequences into a parser and assert its event/state updates, including escaped delimiters and malformed messages. End-to-end tests run an instrumented shell through a PTY, issue commands containing spaces, semicolons, backslashes, and newlines, and verify the terminal's command, cwd, and exit status. Merely checking that an unknown OSC is consumed without visible garbage tests parser tolerance, not OSC 633 support. Detection should be capability-based or opt-in: VS Code recommends checking `TERM_PROGRAM=vscode` before emitting VS Code-specific sequences to another terminal.

## Origin and adoption

OSC 633 originated in VS Code's integrated terminal shell-integration work, documented publicly as a VS Code custom sequence. It was designed to add exact command capture and properties without changing OSC 133's lifecycle model. The public documentation does not identify a separate standards body, formal ratification date, or versioned interoperability profile; treat it as a de facto vendor protocol. Adoption continues in shells, editors, and terminal-adjacent tools that want command-aware features, but broad terminal implementation of the extra subcommands remains limited. OSC 133 has wider cross-terminal support and remains the better baseline for portable prompt/command boundaries.

## Terminal support

The table separates explicit support for the OSC 633 extension from support for the overlapping OSC 133 lifecycle. “No confirmed support” means no reliable primary documentation was found that the named terminal consumes the `E` command-line and `P` property extensions; it does not imply that its parser displays unknown OSC sequences. A shell integration script and an emulator implementation are separate requirements: installing a shell script does not make an emulator understand its reports.

Version and feature coverage can change independently. For portable integrations, emit OSC 133 for lifecycle boundaries, gate OSC 633-specific metadata on a known consumer, and retain ordinary process/cwd detection as fallback. Through SSH or multiplexers, verify that the intermediary passes OSC sequences through and that the integration script runs in the remote shell; shell hooks do not automatically cross either boundary.
