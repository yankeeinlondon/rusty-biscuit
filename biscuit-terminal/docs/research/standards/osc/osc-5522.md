# OSC 5522: Kitty extended clipboard

**Research checked: September 28, 2026.** OSC 5522 is an informal protocol created by Kitty as an extension to OSC 52. It carries clipboard data in named MIME formats, including binary formats such as `image/png` and rich-text formats such as `text/html`. It is not an ECMA-48 or xterm standard. The protocol's living specification is the [Kitty clipboard documentation](https://sw.kovidgoyal.net/kitty/clipboard/); its history starts in December 2022. Current implementation evidence is still narrow: Kitty and Contour support it, while several other terminals parse it or offer related clipboard features without implementing the protocol.

## How the protocol works

Each message is an operating system command framed as `ESC ] 5522;metadata;payload ESC \`. Metadata is a colon-separated set of key/value fields. Payloads, and specified metadata values such as MIME names and passwords, use padded standard Base64. The protocol supports clipboard and (where available) primary-selection locations.

A client reads by sending `type=read` with a Base64-encoded, space-separated list of requested MIME types. It can send the encoded single period `.` to list available formats. Successful reads return an `OK` status, one or more `DATA` packets naming the MIME type, then `DONE`. Data is sent in ordered chunks of at most 4096 decoded bytes per type. A write starts with `type=write`, sends sequential `type=wdata` chunks for each MIME type, and ends with an empty `type=wdata`. The terminal acknowledges with `DONE`; errors include permission denial (`EPERM`), unsupported data/location (`ENOSYS`), invalid input (`EINVAL`), I/O failure (`EIO`), contention (`EBUSY`), and excessive size (`EFBIG`). Implementations may limit clipboard size, but the specification requires accepting at least 64 MiB. MIME aliases can advertise the same bytes under multiple formats without sending the content repeatedly.

Clipboard reads can disclose private information, so terminals should request user permission. A client can provide a password and display name so a user may grant future reads on that terminal session; the client should use a fresh unpredictable password for a grant scoped to its process/session. Listing MIME types is permission-free so a user is not prompted once for enumeration and again for retrieval.

An optional DEC private mode, `CSI ? 5522 h`, asks the terminal to report MIME formats when the user invokes Paste. The unsolicited event includes a one-time password, allowing the application to request the chosen representation without a second prompt. This event advertises a paste action; the application still performs a normal OSC 5522 read. It was added to Kitty in 0.44.1. For multiplexers, requests can carry an `id` echoed in replies so responses can be routed to the requesting pane. Multiplexers should serialize in-flight transactions because the clipboard is shared; paste events have no request ID and go to the active pane.

## Testing and capability detection

The specification defines a DECRQM query for private mode 5522: send `CSI ? 5522 $ p` and look for `CSI ? 5522 ; Ps $ y`. Values `0` and `4` indicate unsupported mode; supported mode states indicate paste-event support. This query does not prove that all MIME read/write operations work. Use a timeout and consume the reply safely, then handle absent replies and protocol errors for the operation the application actually needs. Do not infer support from `$TERM`, OSC 52, or graphics support.

Test actual behavior in a PTY with the target terminal and system clipboard: probe the mode, enumerate formats, exercise read and write for text and binary data, test multichunk payloads and permission denial/grant, and test user-triggered paste events if used. Repeat through the supported multiplexer and SSH paths. Parser tests can cover framing and Base64 validation, but only end-to-end tests establish OS clipboard integration, MIME preservation, permission UI, and paste-key routing.

## Visual behavior

OSC 5522 defines no on-screen rendering for clipboard contents. It transfers data. A terminal may show a permission prompt, but its appearance and policy are implementation-specific. The receiving application chooses how to display the returned format: it might show an image preview or attachment for `image/png`, render rich text, or use plain text. If it asks only for `text/plain`, the other clipboard representations are irrelevant. Differences between terminals therefore concern permission prompts, supported native MIME types, and paste-event integration, not a standard OSC 5522 visual. A terminal's rendering of selected text is separate from this protocol.

## Terminal support and developer notes

“No public implementation evidence found” means the project's public documentation or source checked for this research does not establish OSC 5522 support. It does not rule out later or unpublished work. OSC 52 text clipboard, local image paste, rich-text copy, and parsing an escape sequence are not sufficient evidence of OSC 5522 read/write support.

## Adoption and outlook

Kitty introduced the protocol and documents its original arbitrary-MIME clipboard transfer in the 0.27.0 kitten release notes; the public specification history begins in December 2022. The protocol continues to gain details, including user-triggered paste events, but terminal adoption remains limited. Contour's 0.7.0 support is a concrete additional implementation; Ghostty's parser-only support and feature requests elsewhere show interest, not interoperability. It is useful for remote workflows because the clipboard bytes can travel through the terminal stream without requiring a clipboard executable on the remote host, but applications should provide OSC 52 text and file/path fallbacks. Runtime capability and actual operation checks are preferable to terminal-name assumptions.
