# OSC 5113: Kitty file transfer

OSC 5113 is Kitty's informal file-transfer protocol for moving files between the host running a terminal emulator and the remote system attached to its TTY. It is useful when the terminal connection is the only available channel, including nested SSH sessions and serial links. It is not intended to replace SFTP or another direct transfer mechanism: protocol payloads are base64 encoded and therefore add overhead. The protocol specification is maintained by Kitty and is not an IETF or ECMA standard. [Kitty protocol specification](https://sw.kovidgoyal.net/kitty/file-transfer-protocol/)

## How it works

The wire format is an OSC control string terminated by ST:

```text
ESC ] 5113 ; key=value ; key=value ... ESC \
```

Commands use compact keys (`ac` for action, `n` for path, `d` for data), with UTF-8 paths and binary data encoded in base64. Keys describe a session and its files: action, session and file identifiers, paths, file type, size, permissions, modification time, and optional compression or transfer mode. Unknown keys are ignored so implementations can extend the format. Paths are POSIX-style UTF-8 paths using `/`; Windows drive paths are represented as `/C:/...`. Non-UTF-8 Linux filenames are outside the common format.

A session first identifies its direction and lists or requests file metadata. For a send (remote to terminal host), the terminal must authorize the session before the client sends file data. The client then sends file entries and data in chunks of at most 4096 bytes, receives status/progress acknowledgements, and finishes the session so metadata and links can be committed. For a receive (terminal host to remote), the remote client requests paths; after approval, the terminal returns metadata and streams requested file contents. Directories are expanded into entries, and symlinks are not followed when traversing. Sessions can be canceled. Implementations can support regular files, directory trees, symbolic and hard links, metadata preservation, zlib compression, and an rsync-style delta transfer; optional features should be negotiated through the commands and responses rather than assumed.

## Detection and testing

OSC 5113 has no standardized support-query command. A terminal identification string, TERM value, or support for Kitty's graphics/keyboard protocols does not prove file-transfer support. Test the actual operation in a disposable environment: use a small file in each direction, verify content and expected metadata, exercise a directory and cancellation, and confirm the terminal's refusal path. The Kitty `kitten transfer` command is the reference client and works most conveniently with `kitten ssh`, which makes the client available remotely. Implementers can also test against a small client that exchanges the documented OSC commands through a PTY and validates returned status packets. Exercise real terminal apps as well, since some test captures consume OSC output or do not model interactive authorization.

## Feedback, consent, and security

In Kitty, starting a transfer presents a confirmation prompt before filesystem data is read or written. The request is denied or approved in the terminal UI; the program receives a corresponding status response. The standard specifies this consent boundary but does not prescribe prompt layout, wording, path preview, or a progress visualization, so presentation is implementation specific. Kitty's transfer kitten displays progress in its client-side CLI; the terminal's required role is authorization and protocol status handling.

Kitty's optional `file_transfer_confirmation_bypass` setting allows a pre-shared password to bypass interactive confirmation. Kitty's SSH workflow uses its public-key-based bypass scheme; the generic specification also describes a session-bound SHA-256 password hash, while warning that this does not effectively conceal a weak secret from an observer. Kitty warns that software on the remote machine may obtain a bypass password and gain local filesystem access, so only use bypass with trusted remote systems and secure transports. The protocol itself does not define a universal allowed-path root or sandbox. The terminal implementation and the user's OS permissions govern which paths can be accessed. Kitty documents path selection and an optional `--confirm-paths` preview for the transfer client; that preview is distinct from terminal authorization.

## History and adoption

Kitty added the user-facing transfer kitten in version 0.30.0, released September 18, 2023. Kitty's SSH kitten had made automatic file transfer available from version 0.25.0, but the separately documented file-transfer kitten/protocol arrived in 0.30.0. The feature remains present in current Kitty documentation and releases. Outside Kitty, the protocol remains specialized: as of September 2026, the public protocol documentation and terminal feature references reviewed for this page establish Kitty as the only supported app among the apps below. There is continuing ecosystem interest in Kitty protocol implementations, but implementation of the format in a client library is not evidence that a terminal emulator accepts OSC 5113.

## Terminal app support

“Supported” here means the terminal emulator itself implements the OSC 5113 filesystem endpoint. A remote `kitten` client alone does not make another terminal compatible. Kitty's documentation is the positive implementation evidence; absence from the table's supported set means no public implementation evidence was found, not a claim that an unreleased fork could not implement it.

For non-Kitty terminals, the practical workaround is to use ordinary SSH file transfer (SCP/SFTP), or another transfer protocol the terminal explicitly implements. A silent or ignored OSC request should not be presented to users as a successful transfer. In Kitty, use an up-to-date local and remote kitten; if automatic remote bootstrapping is unavailable, install the standalone kitten binary. For scripts, do not request quiet mode unless authorization is already bypassed: suppressing responses also removes the consent acknowledgement and makes failure detection unreliable.
