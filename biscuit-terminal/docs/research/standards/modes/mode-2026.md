# DEC Private Mode 2026: Synchronized Output

DEC private mode 2026 is a de facto terminal extension for making a screen update appear as one visual commit. It was proposed in the terminal-emulator ecosystem as a DECSET/DECRST form of synchronized rendering inspired by iTerm2’s earlier synchronized-output mechanism; it is not a DEC-published standard. The [Contour synchronized-output specification](https://contour-terminal.org/vt-extensions/synchronized-output/) is the clearest living description of its semantics and detection behavior.

## How it works

An application brackets a redraw with:

```text
CSI ? 2026 h    begin synchronized update (BSU)
... screen updates ...
CSI ? 2026 l    end synchronized update (ESU)
```

In 7-bit form these are `ESC [ ? 2026 h` and `ESC [ ? 2026 l`. While the mode is set, a supporting emulator continues parsing input and updating its terminal grid, but keeps displaying the previously rendered state. On reset it renders the latest state. This reduces visible partial frames when a full-screen interface updates many cells, especially on fast renderers, slow connections, or multiplexed/remote sessions. The guarantee is visual atomicity at the emulator, not atomic delivery of bytes through a PTY, SSH, or multiplexer. Terminals that ignore the private mode generally continue rendering normally, so applications commonly emit the pair without probing first.

Applications should end every update on every control-flow path, including errors and cancellation. A lost ESU can leave a supported terminal showing a stale frame until its safety timeout or a reset. Use short brackets around a complete frame; do not wait for user input or a capability-query response inside one.

## Detection with DECRQM

The request is `CSI ? 2026 $ p` (`ESC [ ? 2026 $ p`). A DECRPM response is `CSI ? 2026 ; Ps $ y`. The Contour specification assigns the standard status meanings:

| `Ps` | Meaning             | Interpretation for mode 2026                                         |
|------|---------------------|----------------------------------------------------------------------|
| `0`  | Mode not recognized | No support indicated                                                 |
| `1`  | Set                 | Recognized and currently enabled                                     |
| `2`  | Reset               | Recognized and currently disabled; support indicated                 |
| `3`  | Permanently set     | Not defined for this mode; do not treat as ordinary support evidence |
| `4`  | Permanently reset   | Recognized but unavailable                                           |

No reply is inconclusive: the terminal may lack DECRQM, a multiplexer may consume or fail to forward the query, or the response may be delayed/lost. A `0` reply is useful negative evidence only when the query has reached the actual emulator and the emulator implements DECRQM correctly. A `1` or `2` is a good recognition signal, but not a guarantee that the full output path behaves correctly: a multiplexer can report its own state, legacy implementations can acknowledge without useful synchronization, and implementations have shipped bugs. If detection is needed, use a bounded asynchronous query and continue with ordinary rendering on timeout; never block startup indefinitely. There is no universally reliable capability database or terminfo flag for this mode.

## Visual effect and implementation differences

The benefit is most visible during full-screen redraws: without synchronization the emulator may paint a partly updated frame, seen as a horizontal tear, flash, or brief mixture of old and new content. The effect depends on redraw strategy, frame size, emulator speed, refresh timing, transport latency, and the application. Efficient differential updates often make it imperceptible. Ghostty’s developer guidance specifically notes that its fast rendering can expose tearing in applications that clear and redraw broad regions; it recommends synchronized output and also recommends updating only changed cells where possible ([Ghostty guidance](https://ghostty.org/docs/help/synchronized-output)).

The mode does not itself prevent flicker caused by an application repeatedly clearing the display, nor does it repair incorrect cursor addressing or lost output. On unsupported terminals it degrades to the unsynchronized behavior. Avoid clearing the whole screen when a smaller update will do, and make redraws idempotent so a later frame can repair any transport or multiplexer damage.

## Timeouts and multiplexers

The protocol does not prescribe a timeout. Implementations choose their own safety policy, and some have no timeout. The following values are specifically reported in implementation material available for this research; unlisted values should not be inferred:

| Implementation             | Abandoned-update behavior                                                                                                                                                                                                                                                                                                                                |
|----------------------------|----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| Ghostty                    | Resets an abandoned update after about 1 second, according to its implementation report; queries continue to be processed while rendering is paused.                                                                                                                                                                                                     |
| kitty                      | Expires stale synchronized updates after about 2 seconds, according to its implementation report; parsing and query handling continue during the pause.                                                                                                                                                                                                  |
| Alacritty                  | The VTE parser’s synchronized-update byte buffering is bounded by a 150 ms timeout and a 2 MiB limit. This can delay replies to queries placed inside the bracket.                                                                                                                                                                                       |
| WezTerm                    | No deadline was found in the current mux implementation report: mode 2026 holds parsed actions until reset, soft reset, or pane EOF. In particular, capability replies can be held too. Keep queries outside the bracket.                                                                                                                                |
| tmux                       | Current implementations have a one-second safety limit reported in upstream discussion/code references. tmux parses/handles synchronized updates and relays the screen; it is not merely a transparent byte tunnel. Releases have had redraw/flush and split-input bugs, so use a current release and test the actual outer-terminal + tmux combination. |
| Other emulators and Zellij | No dependable timeout value was found in the cited public documentation. Do not rely on an undocumented timeout.                                                                                                                                                                                                                                         |

Multiplexers create another state boundary. tmux has native synchronized-output handling in current versions; historical and recent releases have had regressions involving updates split across reads and full-screen clear/redraw flushes. A workaround for a broken version is to update tmux, avoid a clear-screen sequence inside the synchronized bracket where possible, or disable synchronization for that multiplexer/version. Zellij added synchronized rendering in 0.40.0 and supports the CSI begin/end sequences; its compatibility layer may translate or mediate terminal behavior, so capability detection inside a pane should be validated against the installed Zellij and outer emulator. Do not wrap mode 2026 in tmux’s generic DCS passthrough when using native support; passthrough can leave tmux unaware of terminal state and permit it to undo that state ([tmux passthrough documentation](https://github.com/tmux/tmux/wiki/FAQ)).

## Adoption and application support

The feature grew from an iTerm2/Contour proposal into a shared convention. Contour’s history records fixes to synchronized updates by July 2022, while a later project inventory already listed iTerm2, Contour, Kitty, WezTerm, and foot as supporting it. Adoption continues: Ghostty documents it for application developers, and current inventories/source histories include Alacritty, Konsole, Windows Terminal, mintty, Zellij, and other implementations. Its status remains informal, with differences in timeout, query handling, and multiplexer behavior.

The list below means there is affirmative implementation or project documentation for mode 2026, not that every released version or nested terminal stack has been tested. `cmux` is Ghostty-based; its support is inherited from that engine rather than independently specified here.

| Terminal or multiplexer       | Status and developer notes                                                                                                                                                                                                                                |
|-------------------------------|-----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| WezTerm                       | Supported. Queries issued while an update is open may be delayed until the update closes; perform capability probes before beginning a frame. An unclosed update has no documented deadline in the current mux report.                                    |
| Ghostty                       | Supported and documented. Fast redraw can expose tearing in applications that repaint incrementally without synchronization; wrap complete frames and reduce unnecessary full-screen clears.                                                              |
| iTerm2                        | Supported in current project material; it helped inspire the earlier synchronized-output design and adopted the DEC mode form. Verify old versions and DECRQM behavior rather than assuming the original DCS mechanism and mode 2026 are interchangeable. |
| cmux                          | Supported through its Ghostty-based terminal engine. Treat exact Ghostty engine/version behavior as the relevant compatibility boundary.                                                                                                                  |
| kitty                         | Supported. Stale updates reportedly expire after about 2 seconds. Rendering is paused while parsing continues.                                                                                                                                            |
| Contour                       | Supported and documents the protocol, DECRQM statuses, and explicitly says the timeout is not standardized. Its release history records synchronized-update fixes, so use a current version.                                                              |
| foot                          | Supported; it is included in the Contour adoption list and current compatibility inventories. A timeout value was not verified.                                                                                                                           |
| Alacritty                     | Supported in current source inventories; its older implementation used a DCS form and current history records the move to CSI 2026. Parser buffering is bounded at 150 ms / 2 MiB; query outside the bracket.                                             |
