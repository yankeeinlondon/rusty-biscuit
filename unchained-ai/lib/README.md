# unchained-ai (lib)

This crate provides the core building blocks for assembling LLM workflows in the Dockhand monorepo. It combines pipeline primitives (typed state, step execution, error handling) with a rig-core integration layer that knows about multiple providers, model catalogs, and web tools.

The codebase is intentionally split into a few focused modules:

- `primitives`: pipeline execution model and atomic steps
- `rigging`: provider registry, model enums/metadata, and rig-core tools/adaptors
- `api`: OpenAI-compatible model discovery utilities
- `models`: capability abstractions and runtime metadata types
- `utils`: small shared helpers

## Architecture at a glance

- A pipeline is a sequence of `Runnable` steps that share a typed `PipelineState`.
- Steps can declare state dependencies (reads/writes) for validation before execution.
- Errors are accumulated; only fatal errors halt the pipeline.
- The rigging layer exposes provider model catalogs and agent tools for rig-core.
- Provider and model metadata are largely auto-generated from live provider APIs.

## Module map and behavior

### `primitives/`

Core pipeline machinery and the atomic steps used by the CLI and higher-level flows.

**Pipeline state and errors**

- `PipelineState` is a heterogeneous container keyed by `StateKey<T>` (name + `TypeId`). The same string key can coexist for different types.
- `StepError` carries a step name, message, optional source error, and a `fatal` flag.
- Errors are accumulated. `Pipeline::execute` stops when a fatal error is present.

**Runnable trait**

- `Runnable` is the step interface: `execute(&mut PipelineState) -> Result<Output, StepError>`.
- `execute_readonly` supports safe parallelism for steps that do not mutate state.
- `declares_reads` and `declares_writes` provide static key metadata for validation.
- `RunnableExt::with_output_key` wraps a step to persist output into state.

**Grouping**

- `grouping::Pipeline` composes heterogenous steps serially. It can validate that reads are satisfied by prior writes.
- `grouping::InParallel` executes homogeneous tasks with read-only state. The implementation is currently sequential but uses the read-only contract to enable future true parallelism.

**Atomic primitives**

- `Prompt<V>`: multi-modal prompt container. It supports:
    - `file://` text loading
    - `image://` external image URLs
    - `audio://` external audio URLs
    - binary detection (PNG/JPEG/GIF/WebP/SVG, MP3/WAV/OGG/FLAC)
    - a builder-style API for capability selection and structured responses
    - async validation of external resources via HEAD requests
    - `execute` / `execute_readonly` resolve the requested capability to a concrete provider/model and run a single-turn completion through the `execution/` surface
- `OpenCodeDelegation`: delegates a step to the `opencode` CLI. It builds prompts embedding state and JSON schema, supports interactive/headless modes, manages sessions, and parses the JSON event stream to return assistant output.
- `UserContent` and `Transcribe` are placeholders for future atomic steps.

**Foreign agents (in progress)**

- `foreign_agent` contains a trait skeleton for integrating external agentic systems (e.g., Claude Code, Firecrawl). It is currently incomplete, not publicly exported, and not yet wired into the pipeline.

**Services**

- `services::AgentStatus` detects installed agentic CLI platforms (Claude Code, Codex) via `sniff::programs::InstalledAiClients` and queries their usage limits.
- `services::pty_runner` executes CLI commands in a pseudo-terminal via `portable-pty`, strips ANSI escape codes, and returns clean text output.
- `services::parsers` extracts short-term/long-term cap usage percentages from platform-specific status command output.
- `services::error::AgentStatusError` provides error types for PTY spawn, read, parse, timeout, and platform-not-installed failures.

### `rigging/`

Rig-core integration and provider/model plumbing.

**Provider registry**

- `rigging::providers::Provider` enumerates supported providers.
- `ProviderConfig` defines env vars, auth method, base URL, model endpoint overrides, and whether the provider is local.
- `provider_errors::ProviderError` centralizes error cases for API and client operations.

**Model catalogs**

- `rigging::providers::models` provides provider-specific enums (OpenAI, Anthropic, Gemini, etc.) and an aggregated `ProviderModel` enum.
- Each provider enum uses `model_id::ModelId` derive to expose `model_id()` and `metadata()`.
- `metadata_generated.rs` is auto-generated by `gen-models` and maps model IDs to `ModelMetadata` (context windows, modalities, capabilities).
- `build/enum_name.rs` defines the naming algorithm that converts model IDs into Rust enum variant names.

**Rig tools**

- `BraveSearchTool`: rig-core `Tool` implementation for Brave Search API. Includes plan-based rate limiting, structured results, and tracing.
- `ScreenScrapeTool`: rig-core `Tool` for HTTP scraping with HTML parsing, main content extraction, multiple output formats, link extraction, configurable user agents, and metadata reporting.

**Provider client adaptors**

- `client_adaptors::zai`: OpenAI-compatible client wrapper for Z.ai (GLM models). Provides `from_env` and builder APIs.
- `client_adaptors::zenmux`: OpenAI-compatible client wrapper for ZenMux. Uses provider-prefixed model IDs.

### `api/`

- `auth::ApiAuthMethod` defines how providers accept authentication (bearer token, header API key, query param, or none).
- `openai_api` fetches model lists from OpenAI-compatible `/models` endpoints with:
    - provider-specific auth handling
    - exponential backoff retries
    - response size limits
    - parallel fan-out across configured providers
- `hugging_face_api` is currently empty (placeholder).

### `models/`

- `ModelCapability` is an abstract capability stack with tiers (FastCheap/Fast, Normal/NormalCheap, Smart/SmartCheap), thinking variants (NormalThinking/NormalUltrathink, SmartThink/SmartUltrathink, and their cheap counterparts), and specialist stacks (Creative and Literal at fast/normal/smart tiers).
- `model_metadata` defines `ModelMetadata`, `ModelModalities`, and `Modality` to query runtime capabilities.
- `metadata.rs` defines richer provider model shapes (e.g., OpenRouter and Mistral fields) but is currently data-only and not wired into fetch logic.

### `utils/`

- `datetime::Epoch` provides a simple seconds-since-epoch timestamp wrapper.

## Tool configuration

- `BraveSearchTool`: requires `BRAVE_API_KEY`. Optional `BRAVE_PLAN` (`free`, `base`, `pro`) controls rate limits.
- `ScreenScrapeTool`: no required env vars; behavior is controlled via `ScrapeArgs` (formats, main-content extraction, timeouts, etc.).

## Generated code and build-time artifacts

- Provider model enums in `rigging/providers/models/` are generated by querying live `/models` endpoints.
- `metadata_generated.rs` is generated from provider APIs plus models.dev enrichment and provides runtime metadata lookup.
- The naming transform for enum variants lives in `rigging/providers/models/build/enum_name.rs`.

## Known gaps and placeholders

- `api/hugging_face_api.rs`, `functional_grouping::SmartConcat`, `Transcribe`, `UserContent`, and `foreign_agent` are scaffolds for future work.
