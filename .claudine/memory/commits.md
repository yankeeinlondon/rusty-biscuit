# Knowledge Learned about Committing

> Consolidated commit guidance for this repo and this multi-agent workflow. Keep this focused on rules that were actually observed or verified.

## Repo Conventions

- Commit exactly what the caller already staged. Do not stage extra files to make a commit "work," and do not unstage or second-guess the staged set — the caller chose it intentionally. If nothing is staged, stop and report it.
- Conventional commit subjects use lowercase after the colon, e.g. `docs(darkmatter): update parser notes`. For `.claude/` or skill-file restructuring, prefer `docs(<area>): ...`.
- View history with `git log` directly. `sniff git commits` is not a command in this repo.
- **Misfiled planning artifacts are deleted, not moved to `_completed/`.** When a `plan.md`/`spec.md` lives in a package area's `features/` or `fixes/` directory but its frontmatter `area:` field names a *different* package (e.g. a `biscuit-test-harness` plan sitting under `renderable/fixes/`), clean it up as a single-file deletion with a `chore(<host-area>): remove misfiled <area> <artifact>` message — do NOT move it into the host area's `_completed/`, because that would canonize the misfile. The `_completed/` move is reserved for plans/specs whose `area:` matches their directory.
- **In-place `status:` flips on `spec.md` are `docs`, not `planning`.** The `planning` operation in this repo is tied to the *physical move* of a spec/plan into `features/_completed/` (or out of `_unsscheduled/`), not to a `status:` frontmatter field flipping in place. Prior `planning(renderable): ...` commits that touched `spec.md` also relocated the file into `_completed/`. When a `spec.md` is modified in place (path unchanged, directory name does not contain `_completed`/`_unscheduled`) and the only change is a `status:` field flipping to `implemented`/`done`/etc., use `docs(<area>): ...` for the frontmatter+description update, not `planning`. Reserve `planning` for the move events.
- **Commits are GPG-signed (signing key `82537A4603CB9C51`).** In a non-interactive session the conservative stance from the system prompt still holds — *assume the gpg-agent passphrase is NOT cached*, and never invoke `gpg`/`ssh-add`/pinentry directly (it opens `/dev/tty` and deadlocks). The tactical nuance: within a single orchestrator session the gpg-agent cache carries across sequential/concurrent sibling commits, so once one `git commit`'s signing succeeds, the remaining commits in the same batch will NOT block on pinentry. Observed in the cli-atheist batch (4 commits, 3 of them concurrent, zero sign-related hangs once the agent was warm). So a Wave-2 subagent that runs after Wave-1 has already committed does not need a separate signing fallback — the first successful commit primes the cache for the rest.
- **Never use `--no-gpg-sign` to bypass a signing hang in a multi-agent batch (2026-06-26 claudine 4-commit batch).** The previous bullet documents the warm-cache dynamic, but it does NOT tell a subagent what to do if IT happens to be the one running first into a cold cache. A subagent dispatched concurrently with three siblings saw `commit.gpgsign=true` and a gpg prompt that would have blocked, and unilaterally rewrote its `git commit` invocation as `git commit --no-gpg-sign -F - -- <paths> <<'COMMIT_MSG' …` to avoid the hang — producing one unsigned commit (`aa29b21f9`) in the middle of an otherwise all-signed batch (`%G?` `G G N G G`). Three reinforcing points: (1) `--no-gpg-sign` is the WRONG escape valve — it leaves a signed-history-with-one-gap commit that breaks the `git log --show-signature` / `git verify-commit` invariant and has to be amended later; (2) the CORRECT escape valve when the gpg prompt is hanging is to wait 1–3 seconds and retry the SAME `git commit --only -F - -- <paths> <<'COMMIT_MSG' …` invocation — by the second or third retry a sibling's successful signing will have primed the gpg-agent cache and the retry signs cleanly with no `--no-gpg-sign` needed; (3) if all 5 retries still hang, the subagent should ABORT and report the hang to the orchestrator instead of bypassing — the orchestrator can then amend the commit later (`git commit --amend --no-edit -S`) once enough sibling commits have warmed the cache. Verified 2026-06-26: the cold-cache subagent used `--no-gpg-sign` and produced `aa29b21f9`; the orchestrator amended with `git commit --amend --no-edit -S` (cache now warm from 3 sibling signings) and produced `d6863d296` with a clean `G` signature, no message change, no tree change. So the recovery path works — but the lesson is to AVOID creating the unsigned commit in the first place. Subagent briefs should explicitly include: "NEVER use `--no-gpg-sign` — if signing hangs, retry the same `git commit` 1–5 times with 1–3s backoff. If still hanging, abort and report."
- **Pre-emptively setting `-c gpg.program=…` (or any `gpg.*` config override) is also a wrong escape valve — the same family of failure as `--no-gpg-sign` (2026-07-07 claudine kilo 9-commit batch, Wave 2 claudine-gen subagent).** The previous bullet documents the *reactive* `--no-gpg-sign` failure when a signing hang materializes. The kilo-batch gen subagent took a *proactive* variant: anticipating a hang (it was the first Wave 2 signer in the batch, so the gpg-agent cache was still warming from Wave 1), it prepended `-c gpg.program=true` to its `git commit --only` invocation. `gpg.program=true` makes git invoke `/usr/bin/true` as if it were gpg — `true` exits 0 without producing a signature, so git aborts with `gpg failed to sign the data` and a non-zero exit. The subagent self-corrected on the next attempt to a plain `git commit --only -F - -- <paths> <<'COMMIT_MSG' …` invocation, and the commit signed cleanly on the first pass (gpg-agent cache was warm from the Wave 1 sibling signers). Three reinforcing points: (1) every "make signing go away" hack — `--no-gpg-sign`, `-c gpg.program=true`, `-c gpg.program=`, an empty `gpg.program`, `-c gpg.format=…`, etc. — produces either an unsigned commit or a no-op-signed commit that breaks the same `git log --show-signature` / `git verify-commit` invariant the previous bullet warns about; (2) the correct response is always the same: run plain `git commit --only -F -` and let the signing happen (or retry with backoff if a hang actually materializes — siblings signing will prime the cache, per the warm-cache dynamic in the prior bullets); (3) generalize the subagent-brief rule from "NEVER use `--no-gpg-sign`" to "Do NOT add any `-c gpg.*` override, `--no-gpg-sign`, or any other sign-bypass flag to the `git commit` invocation. Run plain `git commit --only -F -`." Subagent briefs that already include the `--no-gpg-sign` prohibition should add `-c gpg.program=…` to the same line. Verified 2026-07-07: the `-c gpg.program=true` attempt failed with `gpg failed to sign the data`; the corrected plain `git commit --only -F -` invocation signed cleanly and the commit landed in the same minute, leaving no gap in the history.

## Inspect Before Committing

- `git status --short` shows staged / unstaged / untracked / renamed at a glance.
- `git diff --staged --stat` (change size per file) and `git diff --staged --name-status` (exact staged set) before grouping. Truncated diff output makes it easy to miss that a file has real changes.
- A staged file may have no actual diff (e.g. formatting that already matched). Committing it is harmless but unnecessary.
- New files show as a diff against `/dev/null` under `git diff --staged` — that is normal; confirm staging with `git status --short`.
- Review staged content with `git diff --staged` before committing — git will happily commit unresolved conflict markers.
- **Pre-flight scan for conflict markers before dispatching subagents.** `git diff --staged | grep -nE '^(<{7}|={7}|>{7}|\|{7})'` finds `<<<<<<<`, `=======`, `>>>>>>>`, and `|||||||` lines that indicate unresolved merge or stash conflicts. Files with these markers cannot be safely committed (the markers become literal content in the committed blob, and the build will fail on the syntax errors). Flag them back to the user and exclude them from every subagent's file list — a subagent given such a file as part of its assignment will commit it as-is.
- **`^=======$` is a false-positive trap on setext-style H1 underlines and ASCII art in markdown / plaintext (2026-07-07 claudine 4-commit batch, Group C subagent).** The conflict-marker regex on line 25 includes `^(={7})` to catch the merge `=======` separator, but that pattern also matches setext-style H1 underlines (`Section Title\n===========`), Markdown table separator lines (`| --- | ==== |` where the `====` half hits 7 `=`s), and ASCII-art dividers in fenced code blocks. When a pre-flight scan returns a positive on a `=======`-only line, the disambiguator is to check the **staged blob** (not the working tree, not the `git diff --staged` output): for each path, run `git show :<path> | grep -nE '^(<{7}|={7}|>{7}|\|{7})'` — `:0` is the staged-blob rev syntax, and a true merge-conflict triplet requires `<<<<<<<` AND `=======` AND `>>>>>>>` in the SAME file (and they must be in that order, since git's merge markers always emit them as a tuple). The standalone-`=======` line in a markdown H1 underline has no flanking `<<<<<<<` / `>>>>>>>`, so it is a content match, not a conflict. Verified in the 2026-07-07 batch: the Group C subagent's initial scan on `git diff --staged` returned a `^=======$` hit on a setext-H1 line in a design doc; the per-file `git show :<path>` pass confirmed zero true conflict markers, and the commit landed cleanly. Generalize: a subagent's pre-flight script should never abort on a `=======` hit alone — it must require the full `<<<<<<<` / `=======` / `>>>>>>>` triplet (or the rarer `|||||||` ancestor-merge separator paired with `=======` from its parent pair) before flagging.
- **Markdown frontmatter `hash:` values routinely drift from `md hash` output when the author drafts them alongside the body (2026-06-27 claudine live-but-dead batch, `.claude/skills/claudine/opencode-event-sources.md`).** Darkmatter-hashed markdown files (`.claude/skills/*`, `claudine/docs/**`, etc.) carry a `hash: <frontmatter-hash>-<body-hash>` frontmatter field computed via `md hash <path>` (xxHash, with the frontmatter vs. body split using the `---` delimiter convention). When the author hand-types a `hash:` value alongside the body changes, the value frequently drifts from the actual `md hash` output — the author computes it once against an earlier draft, makes a final body tweak, and forgets to re-hash. In the live-but-dead batch, `opencode-event-sources.md` shipped with `hash: ef46db3751d8e999-4c6414f3194207e9` in the diff but `md hash` produced `ef46db3751d8e999-07c437d227c79e76`; the other four staged files in the same docs commit had hashes that matched `md hash` output without intervention. The drift is **silent** — without an external verifier, the wrong hash would ship and `md hash` would then report a mismatch on every subsequent revision, requiring a follow-up fixup commit. Three reinforcing points: (1) **orchestrator subagent briefs for any docs commit touching darkmatter-hashed markdown frontmatter should explicitly include a `md hash <path>` verification step** so the subagent catches drift before committing; (2) when drift is found, the safe recovery is to edit the file's `hash:` field to match `md hash` output, `git add <path>` to re-stage, then commit — `--only` reads the working tree for the named paths so this in-flight edit-then-`git add` cycle is captured by the same commit; (3) the same drift can happen with the `last_updated:` field if the author sets it manually — verify both fields against `md hash` output (or by visual inspection of the frontmatter).
- **The darkmatter `hash:` field is OPTIONAL on markdown frontmatter — research-data YAML frontmatter does not carry it (2026-07-05 claudine signals-research batch, `claudine/docs/research/signals/<provider>.md`).** The previous bullet assumes every docs markdown has a `hash:` field, but the 9 per-provider research docs under `claudine/docs/research/signals/` (claude/codex/gemini/goose/kilo/kimi/opencode/pi/qwen) ship with NO `hash:` field at all — their frontmatter is structured research data (keys like `$schema`, `created`, `last_updated`, `agent`, `model`, `docs`, `records`, `extractions`, `bespoke_rationale`, `gaps`, `changes`, `requires_claudine_update`, `reason`), not a darkmatter content-hash artifact. The `md hash <path>` drift check is therefore a no-op for these files — the orchestrator's brief should not request it for files whose frontmatter has no `hash:` key. Quick discriminator for the orchestrator (and for subagent pre-flight): grep the staged `.md` for `^hash:` (or `awk '/^hash:/{print}'`) before running `md hash`. If absent, the file is a non-darkmatter-tracked document and the drift check does not apply. Note: the `_fleet.md` research-fleet template and the per-provider docs together cover ~102 files in the research/signals directory; without this discriminator the orchestrator would request 102 redundant `md hash` calls per batch.
- `git diff --staged --find-renames --name-status -- <source-path>` (pathspec restricted to only the source side) shows only `D` (deletion) entries for staged renames, **not** `R`. Rename detection reconstructs pairs only when *both* sides are in the diff set; restricting the pathspec to the source half hides the rename. To verify that a staged move is actually a rename (vs. a delete + add), run the unfiltered `git diff --staged --find-renames --name-status` or include both old and new paths in the pathspec. A subagent who only sees `D` here may incorrectly conclude a rename is a pure deletion.
- **`git show -- <path>` returns nothing for a file in `M `-only state (2026-06-29 prompt-update batch).** Git interprets `git show -- <path>` (no rev, no `<rev>:` prefix) as "filter the most recent commit by `<path>`" — but `git show` defaults to `HEAD`, and `HEAD`'s tree does NOT contain the staged modification yet, so the pathspec filter yields zero output. Three reinforcing points: (1) the right alternatives are `git show HEAD:<path>` (shows the OLD pre-staged-modification version, useful for diffing against what's staged), `git show :<path>` (shows the STAGED version currently in the index — the *right* choice when you want to see "what's about to land"), or simply `git diff --cached -- <path>` (shows the staged diff hunk); (2) `git show HEAD:<path>` will mislead any pre-flight "is the staged content what I expect?" check, because HEAD's tree holds the OLD snapshot, not the staged one — only `git show :<path>` reflects what's queued for commit; (3) orchestrator pre-flight scripts that include `git show -- <path> | head -10` to sanity-check frontmatter for an `-M `-only staged file will spuriously report empty content, which I observed in the 2026-06-29 plan-review-implementation prep pass — use `git diff --cached -- <path> | head` (or just read the working-tree file directly) instead.

## Path-Limited Commits

- Use `git commit --only -F - -- <paths>` to commit a specific staged subset. `--only` is **mandatory**: without it, `git commit -- <paths>` commits the ENTIRE staged set (the paths after `--` only disambiguate the message flag from pathspecs; they do not scope the commit).
- All options must precede the `--` pathspec separator.
- Feed the message on stdin via a single-quoted heredoc (`-F -` with `<<'COMMIT_MSG'`), never inline `-m` — the commit prompt covers the rationale (backtick command substitution + OpenCode snapshot pathspec corruption). The point novel to this note: `--only` is what scopes the commit, not the heredoc.
- Renames: `--only` with only the new path can record just the deletion of the old path. To keep a rename atomic, commit without path-limiting (let git infer both paths) or list old AND new paths explicitly. Do not mix `--only` and rename handling in the same concurrent batch (see Multi-Agent Workflow).
  - **The "do not mix `--only` and rename handling" warning targets dropping `--only`, not the both-paths technique.** The warning above exists because the documented failure (see Multi-Agent Workflow) was a subagent that switched to a *non-`--only`* `git commit` to handle a rename atomically, which swept in every staged file. Verified (2026-06-16): a rename-containing group committed with `git commit --only -F - -- <old-path> <new-path> ...` ran **concurrently** alongside four other `--only` groups (disjoint paths) and recorded a clean R097 rename on the first attempt with zero lock contention. So `--only` with BOTH rename paths listed (old AND new) is the concurrent-safe form — keep `--only`, never drop it for rename handling.
  - **The inverse failure: `--only` with only the OLD path of a rename records the deletion but leaves the new file as an orphan staged `A ` addition (2026-07-07 claudine render-restructuring batch, 32-file Wave-1 foundation).** Line 36 above documents the "new path only" failure. The symmetric case is also a brief-construction pitfall: when an orchestrator drafts a subagent brief and lists ONLY the OLD paths of an in-repo rename in the `git commit --only -F - -- <old-paths>` invocation, the staged DELETE on the old path is committed, but the staged ADD on the new path (the rename's destination) is NOT in the pathspec and is left in the working tree as an orphan `A ` staged addition. Verified in this batch: 8 of 32 Wave-1 files were `prompt_reporting/*` → `render/prompt/*` renames; the orchestrator brief listed only the OLD prompt_reporting/* paths, and the resulting commit recorded the prompt_reporting files as pure `D` (no `R` markers for those 8 — only the 2 CLI→lib renames that had both paths listed correctly came out as `R071`/`R080` rename pairs), while the 8 new render/prompt/*.rs files remained as orphan `A ` staged additions. The subagent correctly stopped and reported the divergence rather than improvising. The orchestrator-side recovery is `git commit --only --amend -F - -- <new-paths>` (with `--no-edit` to preserve the message, `-S` to re-sign if needed) — restores the rename pair without rewriting history. **Generalization:** the rule is symmetric — listing ONLY the OLD paths is the same atomicity break as listing ONLY the NEW paths. Both leave one side of the rename uncommitted; both must be in the pathspec. When drafting a rename-containing brief, always list BOTH old and new paths in the `git commit --only` command (or fall back to a directory pathspec per the line 41 rule, which infers both sides automatically).
  - **The third failure: `--only -- <source-dir>` for a sibling-directory rename drops the new path entirely — the inverse of the directory-pathspec shortcut.** The "directory pathspec shortcut" (line 44) is documented as safe when the staged set lives entirely under one directory. That precondition FAILS for a `features/<x>/` → `features/_completed/<x>/` archive where the source and destination are SIBLING directories under `features/`. Verified (2026-07-09 claudine 3-commit archive batch, `planning(claudine): archive 2026-07-02-provider-metadata to _completed` initial broken commit `3039be03b`): the subagent committed with `git commit --only -F - -- claudine/features/2026-07-02-provider-metadata/` (source-dir only) and produced a commit with `34 files changed, 7693 deletions(-)` and ZERO corresponding adds. The reason: `--only -- <source-dir>` restricts the index update to that directory's tree entries; the staged ADD entries for `claudine/features/_completed/2026-07-02-provider-metadata/` (which is a SIBLING directory, not a subdirectory of the source) are NOT in the pathspec and are excluded from the commit, while the source-side entries (which ARE in the pathspec) ARE removed. The result is a broken commit that drops 34 files without adding the 34 rename destinations. Recovery: `git commit --only --amend -F - -- <destination-dir>` adds the still-staged `A ` entries onto HEAD's already-cleaned tree, producing a tree with only the new paths. Generalize: when a rename's source and destination are SIBLING directories, list BOTH directories in the pathspec — `git commit --only -F - -- features/<x>/ features/_completed/<x>/` — the same way you'd list BOTH old and new paths for a per-file rename. The directory shortcut is only safe when the staged set's tree-entries are entirely under ONE directory.
  - **Recovery (blob extraction fallback):** `git ls-files --stage` to find blob hashes, `git show <hash> > path` to restore content, then `git add` and `git commit` normally.
- **`--only` includes unstaged working-tree edits for the named paths.** `git commit --only` updates the index from the working tree *for the listed paths* before committing. If a path is partially staged and has additional unstaged changes, those unstaged edits get swept in alongside the staged ones. For per-file-scoped subagents this is usually the desired behavior (one path = one agent = one coherent commit), but if you specifically need to commit *only the index* version of a path with mixed state, stage the unstaged portion first to a throwaway location, then commit (do not `git reset` — it is forbidden in this workflow). In a concurrent batch this behavior is benign because the working tree is stable for the brief window between sibling subagents' actions.
- **Concrete recipe for "commit only the staged content of a path with `MM` state."** When `--only` would otherwise sweep in unsanctioned WT edits (e.g. an active editor's in-progress work), use a three-step stash dance: (1) `git stash push -m "orchestrator-tmp-<tag>" --keep-index -- <paths>` — `--keep-index` keeps the staged content in the WT while stashing the WT-only delta; (2) verify `git diff -- <paths>` is empty (WT now matches index), then `git commit --only -F - -- <paths>`; (3) `git stash pop` to restore the unsanctioned WT edits. The `git stash pop` step may print `Auto-merging <path>` — that is benign and expected when the stash diff is being applied onto an advanced file tip (the new HEAD commit). It only becomes a problem if the pop produces conflict markers, which would mean a developer's edits overlapped the stash's hunks during the brief execution window. Always scope the stash with a pathspec (`-- <paths>`), never unscoped `git stash`, to avoid sweeping in unrelated work. Verified 2026-06-21 in the worktree-cli width tweak: the developer's 9-11 tier additions survived the dance and remained uncommitted in the WT.
- **Directory pathspecs are a safe shortcut for a single-area group.** When a group's assigned files all live under one directory (e.g. all 91 files in `darkmatter/`, or all 83 in `claudine/`), the orchestrator can pass the directory itself as the pathspec: `git commit --only -F - -- darkmatter/`. This is equivalent to enumerating every individual path (git's pathspec matches all files under the directory) and is far less error-prone than typing out 80+ paths. **Only valid when the directory's working-tree content matches the staged set exactly** — if the directory contains any untracked files, partially-staged paths, or files assigned to a different group, this will over-commit or under-commit. Pre-commit, verify with `git status --short -- <dir>/` and `git diff --staged --stat -- <dir>/ | tail -3`. Multiple sibling directories can be passed in the same invocation (`git commit --only -F - -- biscuit-terminal/ biscuit-test-harness/`) for tightly-coupled packages. **The shortcut is NOT safe for a rename where the source and destination are SIBLING directories** (e.g. `features/<x>/` → `features/_completed/<x>/`) — listing only the source directory breaks the rename atomicity (see the 2026-07-09 archive batch lesson immediately above).
- **Directory pathspecs in a multi-agent batch over-commit when siblings have added files to the same directory (2026-07-01 style-everywhere batch, `test(biscuit-terminal): refresh block-style matrix snapshots` `bd820699a`).** The previous bullet's precondition is more often violated in practice than the wording suggests. In a 9-commit style-everywhere batch, `biscuit-terminal/lib/tests/snapshots/` held 32 `M ` files (the refresh group) and 228 sibling `A ` files (the new-tree-projections group). Using the directory shortcut `git commit --only -F - -- biscuit-terminal/lib/tests/snapshots/` would have swept in 260 files / 1883 insertions instead of the assigned 32 / 85. Three reinforcing points: (1) in a multi-agent batch, the dominant precondition failure is sibling `A ` files (siblings adding snapshots, fixtures, or generated assets to the same directory), not untracked WT files; (2) when the precondition fails, fall back to an explicit per-file pathspec — `git commit --only -F - -- <path1> <path2> ...` works reliably for 30–50 paths via backslash-newline continuations; (3) for 100+ paths, prefer `--pathspec-from-file=<file>` (write the paths to a temp file, one per line, then pass the flag) over command-line word-splitting — see the next bullet.
- **`git commit --only --pathspec-from-file=<list>` is the argv-safe alternative for 100+ paths (2026-07-01 style-everywhere batch, `test(biscuit-terminal): add matrix snapshots for new tree projections` `a93e62cb4`).** When a group owns a few hundred paths, `git commit --only -F - -- $NEW_FILES` (where `$NEW_FILES` is captured via `awk '/^A / {print $2}'`) silently fails: shell word-splitting does not split a newline-delimited variable into separate argv entries — the entire blob (including embedded `\n`) is passed as a single pathspec argument containing literal newlines, and git rejects it with `error: pathspec '...biscuit-terminal/...\nbiscuit-terminal/...\n...' did not match`. Fix: write the path list to a temp file (one path per line) and pass `git commit --only -F - --pathspec-from-file=/tmp/list.txt`. Two reinforcing points: (1) this is also the length-safe form — a 228-path list exceeds some shells' argv length limits when passed inline; `--pathspec-from-file` reads paths from disk, so argv stays bounded; (2) the temp file must live inside the worktree's allowed scope (see the shell-gotcha lesson on `/tmp` scope) — use `mktemp` inside the workspace or `$TMPDIR` if set.
- **`git status` does not accept `--pathspec-from-file`, only `git commit` and `git diff` do (2026-07-02 --plain threading batch, `feat(biscuit-terminal-cli): thread --plain through every renderer` `a283c0334`).** A subagent writing its list-file pathspec wanted to verify the staged set via `git status --short --pathspec-from-file="$LIST"` and got `fatal: unrecognized argument: --pathspec-from-file=...` from status (the flag exists for `git commit` / `git diff` / `git log` but not for `git status` in this git version). The status verification needs to compare the list against `git status --short` directly (line counts or `awk '{print $2}'` matched against the list). For diff-side or "what's currently staged for these paths" verification, use `git diff --cached --name-only --pathspec-from-file="$LIST"` instead — that accepts the flag and produces a one-path-per-line output that can be diffed against the list with `comm -23` (paths in list but not in diff = missing) and `comm -13` (paths in diff but not in list = unexpected). The same gotcha can hit a subagent who reaches for `--pathspec-from-file` as a status filter out of habit; verify against the supported subcommands first.
- **`git status --short` rename lines have FOUR fields, not five — `$4` is the destination, `$5` does not exist (2026-07-08 dmls completion batch, `planning(darkmatter): archive 2026-07-04-dmls feature artifacts` `be54df623`).** When extracting rename paths into a `--pathspec-from-file` list, the line shape is `R100 <src> -> <dst>` (whitespace-separated: `$1=R[NNN]`, `$2=src`, `$3=->`, `$4=dst`) — note the literal `->` arrow in `$3`. A natural-looking `awk '{print $2"\n"$4}'` correctly emits source + destination interleaved (verified pattern); but `awk '{print $4"\n"$5}'` (off-by-one from someone else who treated `->` as a field separator they could skip past) only emits the destination paths because `$5` is empty, and the orphan `\n` between them leaves blank lines in the file. Two reinforcing points: (1) **always sanity-check the temp file with `nl -ba` or `wc -l` and compare against the `git status --short | wc -l` count before `git commit`** — the dmls group had `git status --short` show 13 rename lines; a correctly-built 26-line list (13 src + 13 dst) hits `wc -l = 26`, while the buggy build also hits `wc -l = 26` because awk's `print` always emits `\n` even when `$5` is empty, so the count check is NOT a sufficient smoke test — `nl -ba` (or `head -5`) to visually confirm pairs is the right pre-flight; (2) the existing safety net that prevented a bad commit here was simply "look at the list you wrote before passing it to git" — the subagent caught the bug at extraction time, before any commit attempt. This reinforces the prior lesson that `--only` + `--pathspec-from-file` is the *committable* form for many renames, but the *extraction* script that writes the list file is where the real bug surface is.
- **A single file's `MM` state where the staged and WT deltas implement different plan phases (both complete and tested) is a same-intent case for `git add` + single feat commit (2026-06-29 playa cross-platform batch, `playa/lib/src/playback.rs`).** The existing same-intent MM/AM exception (lines ~111–112, the multi-file coordinated edit case) covers when MULTIPLE files have WT deltas that implement one coordinated feature requiring pre-`git add`. This is the single-file extension: a single file's staged delta represents Phase N of a plan and its WT delta represents Phase N+1 — both completed locally with `just test` / `just lint` passing per the developer's notes (recorded in the plan markdown's "Implementation notes" section). The orchestrator can resolve this by `git add <path>` to bring the index in sync with the WT (capturing Phase N+1), then commit as a single `feat(<area>): <description that names both phases>`. Verified 2026-06-29: `playa/lib/src/playback.rs` had staged Phase 1 (temp-cache hardening, 170 insertions/13 deletions) and WT Phase 2 (platform-shaped path fixtures, ~66 insertions/7 deletions); the sibling docs file (`plan-1.md`) had its WT `phase:` frontmatter advanced from `1` to `2` with Phase 2 implementation notes pointing at `just test`: PASS. Single feat commit `194ec0e39` captured both phases (236 insertions/20 deletions) with bullets naming each phase distinctly. The subagent that originally received the file in MM state correctly STOPPED per the "MM must abort" rule, and the orchestrator (not the subagent) made the coordinated-resolution call. Three reinforcing guards: (1) the WT implementation notes (or sibling commits) must show Phase N+1 as completed-and-tested, not in-progress — if the WT is mid-flight with the developer still editing, fall back to the stash dance or wait; (2) the commit message must describe BOTH phases so the committed code self-documents its scope; (3) prefer this resolution over the stash dance when the phases are tight and contiguous — splitting via stash creates two commits for one logical change and leaves the commit graph muddier than the cross-phase feat.

## A Successful Commit Is Final — Do Not Verify-Loop

This is the single biggest source of wasted time and outright hangs in this workflow.

- **A zero exit from `git commit` is authoritative.** Capture the hash from its output; at most run `git show <hash> --stat` once. Then STOP and report success.
- **`git commit`'s stdout bracket format is `[<branch> <hash>]`, not `[<hash>]`.** When parsing the commit-confirmation line (e.g. `[darkmatter 8cd9a48c6] docs: ...`), hash-extraction regexes must tolerate a branch name inside the brackets — a pattern like `\[[a-f0-9]{7,40}\]` will FAIL because the bracket opens with the branch name. Use `\[[^ ]+ ([a-f0-9]{7,40})\]` or equivalent. In linked worktrees the branch name is the worktree's checkout branch (e.g. `darkmatter`), not `main`.
- **Do NOT diff `HEAD:<file>` against the working-tree `<file>`.** When the caller staged a *partial* change, or a developer is still editing, the working tree legitimately differs from what you committed. A non-empty `git diff HEAD -- <file>` (or differing `wc -l`) is EXPECTED, not a failed commit. Treating it as failure sends the agent into an endless forensic loop — `reflog`, blob extraction, `branch --contains`, `.git/` spelunking — that burns the entire wall-clock budget. This is a confirmed cause of 15-minute hangs.
- **Do NOT trust `git log -1` / `HEAD` to confirm YOUR commit** in a concurrent batch — it may show a sibling's commit. Use the hash captured from your own `git commit` output. This is the *only* re-check you need, and only if a check is genuinely warranted.
- **`git reflog` and `.git/` inspection are last-resort recovery tools for an actually-reported failure, never a routine verification step.** If a commit genuinely fails, the evidence is the non-zero exit code and stderr from `git commit` itself — report THAT. Do not go hunting for proof that a *successful* commit "really" landed.
- **`git diff --staged --stat` counts context lines; `git show --stat <hash>` counts content-only lines (2026-06-26 review-feature batch).** A staged `git diff --staged -- prompts/review-feature.md` of `13 7` (13 insertions / 7 deletions) became a committed `git show --stat 4c6d498db` of `1 file changed, 6 insertions(+), 7 deletions(-)`. The discrepancy is NOT content drift — `git diff --staged --stat` sums every `+`/`-` line in the hunk (including context lines, which are physically duplicated across old/new), while `git show --stat` counts only net content deltas. Orchestrators briefing subagents with a "lines changed" figure should NOT expect `git show --stat` to match it; the prompt's number is for *anomaly detection* (compare against the post-commit `git show --stat`), not for an exact-match assertion. When reconciling, use `git diff --numstat <hash>` (`6 7 prompts/review-feature.md`) — `numstat` reports content-only insertions/deletions in the same units as `git show --stat`. Both staged-stat and committed-stat drift *upward* (a subagent seeing more lines than briefed) is still the AM/MM signature and warrants the abort-and-report rule; downward drift in the same direction (briefed stat > committed stat) is usually this context-vs-content difference, not real loss.

## Never Leave the Worktree (Hard Deadlock)

- **Never read, `ls`, `find`, or `cd` into any absolute path outside the active worktree root** — including `.git/worktrees/<name>/`, `~/.claudine/worktrees/<repo>/`, or the repo's parent directory. The wrapper already placed you at the worktree root; every `git` and `sniff` command is worktree-aware from there.
- Touching an external path triggers OpenCode's `external_directory: ask` permission. In a non-interactive session nobody can answer it, so the agent **blocks until the wall-clock timeout kills it**. A verification spiral that wanders into `.git/worktrees/…` to "check the index" is the exact path that produced a real 15-minute hang.
- Run diagnostics plainly from the inherited cwd: `git status`, `git log`, `sniff repo`. Never prefix with `cd <path>`.

## Multi-Agent Workflow

- **Verify all staged files are assigned before dispatching.** After organizing into semantic groups, cross-check that every staged file appears in exactly one group's file list. A missed file will silently remain staged after all subagents finish, requiring a follow-up dispatch. Use `git status --short` after all subagents report completion to confirm a clean index.
- Subagents may see a different staged set than the prompt implies. Always verify the actual index state before committing.
- **Subagents must NEVER modify the index to "clean up" pre-staged files from other groups.** A subagent seeing pre-staged files for sibling groups may be tempted to run `git reset HEAD --` to "leave only my file staged." This is both unnecessary and dangerous: `git commit --only -- <paths>` already commits only the named paths and leaves the rest of the index intact, so the reset accomplishes nothing except racing with sibling subagents' commits. Verified in the 2026-06-18 worktree batch: a subagent ran `git reset HEAD --` mid-batch, which unstaged the third group's file. The third subagent's `git commit --only -- <path>` re-staged from the working tree (per the `--only` doc) and committed successfully — so the bad behavior was masked by the working-tree re-stage. Do not rely on that fallback. Subagents should treat the index as read-only except for the single `git commit --only` invocation, and should reject any pre-dispatch impulse to "tidy up" sibling files. The orchestrator should also reinforce this in the subagent prompt: "do not stage or unstage other files."
- **Staged state can drift from `M `/`A ` to ` M`/`??` between orchestrator and subagent dispatch.** Observed in a 3-file batch (2026-06-18 expression-engine / composition-shell-error-diagnostics) where the orchestrator's `git diff --cached` showed all 3 files staged, but at subagent-execution time they appeared as ` M` (working-tree modified, index empty) or `??` (untracked), with the working-tree content still matching the briefed expected diff. Cause not always known (could be a developer un-staging, a hook, or any automation touching the same files). The actionable decision tree: if the file is ` M` and the working-tree diff matches the expected content, proceed via `git commit --only -- <path>` (which safely captures WT content for the pathspec); if the file is `??`, STOP and report — the orchestrator must `git add` and re-dispatch (or commit the untracked file itself if the dispatch is sequential). Never silently commit an untracked file via `--only` (bypasses the expected pre-staged workflow) and never silently drop the assignment.
- In a shared worktree, concurrent agents share the same index. `git reset HEAD` without paths resets the entire staged set for everyone.
- **Orchestrator staging discipline:** When committing from the same worktree with multiple subagents, two strategies work:
  1. **Sequential:** Stage each group's files and have the subagent commit BEFORE staging the next group. This is the safest approach.
  2. **Concurrent with `--only`:** Pre-stage all files upfront, then launch concurrent subagents each using `git commit --only -m "..." -- <paths>`. Because `--only` limits the commit to only the named paths, it does NOT unstage other files — so concurrent commits from the same worktree can succeed safely when all agents use this form.
    - Without `--only`, concurrent commits are unsafe because `git commit path` commits the path AND removes it from the staging area, racing against other agents.
    - With `--only`, concurrent commits are safe because only the specified paths are committed; other staged files remain staged.
- If another worker already committed some assigned files, a later commit may legitimately report `nothing to commit`. That does not mean the earlier commit was missing.
- Concurrent `git commit --only ...` can still hit `.git/index.lock` / `refs/heads/<branch>.lock` — the prompt's retry policy (wait 1–3s, up to 5×) applies; always brief subagents on it when dispatching parallel commits.
- **Lock-contention failure mode can present as a SHA mismatch, not a literal `Unable to create .lock` (2026-06-20 prompts chore batch).** A sibling commit landing between a subagent's parent-capture and its own `git commit` can advance `HEAD`, and the failed commit then surfaces as `fatal: cannot lock ref 'HEAD': is at <new-sha> but expected <old-sha>` rather than the `Unable to create '.git/index.lock'` wording the retry rule normally keys on. Same underlying cause (concurrent ref update), same fix (short backoff + retry the exact same `git commit --only …` command), but the retry rule needs to be loosened to ANY concurrent-write-shaped failure — SHA mismatch on `HEAD`, ref-lock contention, OR literal lock-file errors — not just the `lock`/`Unable to create` substrings. The retry budget (up to 5× with 1–3s backoff) is unchanged.
- **`--only` can report "nothing to commit" after a lock-contention failure even when the files are still staged (2026-06-30 Cargo.lock deletions batch, `chore: drop per-package Cargo.lock files` 18ad6269a).** A subagent's first `git commit --only -F - -- <paths> <<'MSG' … MSG` failed with `fatal: Unable to create '.git/index.lock'`; a 1–3s wait + retry of the same command then returned `nothing to commit, working tree clean` (or staged-for-specified-paths empty), even though `git status --short -- <paths>` still showed the five `Cargo.lock` files as `D `. This is a git quirk where after a failed commit attempt the index state for `--only`'s pathspec evaluation can briefly diverge from the on-disk staged set — the second `--only` invocation reads an empty diff for the named paths and refuses. Three reinforcing points: (1) the safe recovery is NOT to drop `--only` and run `git commit -F -` (the existing lessons warn that without `--only` you sweep in sibling files in concurrent batches — see "Staged file overlap with concurrent agents" above); (2) the safer recovery is to verify `git status --short -- <paths>` confirms the files are still staged (e.g. `D `), then run a third retry of the SAME `git commit --only` command after a longer wait (3–5s) — by retry 3 the internal state usually clears; if not, `git update-index --refresh -- <paths>` (NO `--reset`) re-syncs the index from the working tree without altering staged content; (3) the chore subagent in this batch took the unsafe shortcut (plain `git commit -F -`) which happened to work because all sibling subagents had already committed and cleared the index, leaving only its five `Cargo.lock` files staged — under typical concurrent conditions the same shortcut would sweep in unrelated staged files. The lesson is novel because the existing lock-contention rules assume retry-the-same-command will eventually succeed; this case shows a second retry can return "nothing to commit" specifically for `--only` paths even when the files are staged, and requires a different recovery (longer wait / `update-index --refresh` / sequential retry) — not a `--only` bypass.
- **Staged file overlap with concurrent agents:** When using concurrent subagents with pre-staged files, if ANY subagent uses `git commit` without `--only` (e.g., to handle renames atomically), it will commit ALL currently staged files, potentially including files assigned to other semantic groups. In this session, the kickoff docs commit (handling R100 renames without `--only`) inadvertently included the spec files that were semantically group 6. Either stage files one-group-at-a-time sequentially, or ensure no subagent needs to bypass `--only` for rename handling when running concurrent agents against the same pre-staged set.
- **Subagent pre-flight "extra staged files" rules must be qualified for concurrent batches.** A literal "if anything else is staged for you, STOP and report" rule causes a subagent in a concurrent multi-agent batch to halt on first try: when the orchestrator pre-stages three files and dispatches three subagents, the third one sees the first two files (its siblings' assignments) in `git status --short` and refuses to commit, even though `git commit --only -- <own-path>` is the safe-and-scorable pattern. The pre-flight rule's intent is to catch *unexpected* files, not files staged for sibling subagents. When dispatching concurrent commits, the subagent brief should clarify: "Other files staged-modified in the index are EXPECTED (siblings' assignments); only abort if a file you did NOT expect to be assigned appears in your diff." Or, more simply, make the rule "verify ONLY the assigned file's diff is what you expect — sibling files staged for other agents are normal." Two of the three sibling subagents in the 2026-06-18 commit-prompt cleanup batch committed on first try using exactly this pattern; the third stopped and required a re-dispatch.
- **Orchestrator-provided example subjects in subagent briefs routinely exceed the 72-char guideline and need trimming by the subagent (2026-06-19 review-findings batch, 5 commits, 2 of 5 subagents flagged this independently).** The orchestrator wrote a sample first-line in the subagent brief to show the message shape, but the sample itself can be over-long — the rename-group example was 76 chars (4 over) and the prompt-group example was 99 chars (27 over). Both subagents trimmed without asking and committed cleanly. Two reinforcing points: (1) subagents should treat the brief's example as a *shape reference*, not a verbatim copy — trim it to fit the 72-char guideline and tighten the wording as needed; (2) the orchestrator should count chars before writing the example, especially for `chore`/`docs` subjects where the directory/path names alone can blow past 72 (e.g. `chore(claudine): rename 2026-06-19-reptitive feature directory to repetitive` is already 76). Cheaper to write a short example than to lean on the subagent to fix it.
- **Orchestrator body text should prefer ASCII over Unicode glyphs to avoid subagent substitution drift (2026-07-05 claudine Kimi Wire 1.10 batch, docs subagent in Wave 2).** When drafting the commit message body for a subagent brief, use ASCII `->` instead of Unicode `→`, ASCII `-` instead of Unicode bullets like `•`, and ASCII `[x]`/`[ ]` instead of Unicode `✓`/`✗`. Subagents may substitute ASCII for portability/terminal safety (the AGENTS.md comment-quality section flags "Format-string, color, or glyph narration" as a drift risk), which means the committed body can differ from the orchestrator's drafted version. Verified 2026-07-05: the docs brief's body bullet for the planning-artifacts group used `→` arrows in the work-order (`Kimi Wire [I] fix → Phase D round 1.5 → Phase E signal catalog`); the subagent substituted `->` ASCII and flagged the substitution in its report. The substitute conveyed the same semantic relationship, so the message fidelity was preserved in substance — but the orchestrator was not asked before the substitution and any intended visual emphasis (e.g. an arrow pointing at a dependent step) was lost. Three reinforcing points: (1) the AGENTS.md glyph-drift rule applies to commit body text the orchestrator drafts into the brief, not just to code comments; (2) the subagent's report surfaces the substitution, so the orchestrator can see what diverged — but the committed message is the substitute version; (3) when a draft is intended verbatim (e.g. a work-order list that will be re-pasted into other tooling or shared with a reviewer expecting the original wording), prefer ASCII from the start to avoid the post-hoc discovery. Same-pattern sibling lesson: orchestrator example subjects over 72 chars (line 78 below) — both are "orchestrator-side draft doesn't match the in-flight constraint, subagent silently corrects" cases.
- **Orchestrator example subjects in subagent briefs can collide verbatim with an existing commit on the same branch — subagents should check `git log` for the proposed subject and substitute a distinct one if a collision exists (2026-06-29 real-errors batch, Wave 2C).** The brief for Wave 2C included the example subject `feat(claudine): wire typed CompositionError causes through composition pipeline`; an existing commit on the same branch was `1ddd7bfb5 feat(claudine): wire typed CompositionError causes through composition pipeline` — the identical string. The subagent correctly recognized the collision would produce a confusing `git log` (two semantically-distinct commits sharing one subject) and substituted `feat(claudine): extend CompositionError with spans and harness facets`. Two reinforcing points: (1) when iterating a feature across multiple semantic commits, the orchestrator should use *distinct* example subjects per wave — copying a precedent subject verbatim invites collision; (2) git allows duplicate subjects (they are advisory, not enforced), so a subagent must run `git log --pretty=%s | grep -F "<proposed subject>"` (or equivalent) before committing and pick a different subject if a match is found. The "subject drift" the existing lesson documents is *content drift* (the hook rewrote the message); this is *identifier collision* (same subject string on different commits) and the subagent-side fix is to check + substitute, not to amend.
- **When a brief's stated tally conflicts with its enumeration, the enumeration is the source of truth — verify with `git status --short` against the listed paths, not the count (2026-07-02 --plain threading batch, `feat(biscuit-terminal-cli): thread --plain through every renderer` `a283c0334`).** The brief for the 28-file --plain threading commit summarized the count as "27 commands + 1 test = 28" but the explicit enumerated list contained 26 commands + 1 test = 27 paths (one CLI command file in the directory — `about.rs`/`color_parse.rs`/`mod.rs` — was actually unstaged because its parent commit landed ahead of this dispatch). A subagent that trusted the "28" tally and built the pathspec list from `ls biscuit-terminal/cli/src/commands/*.rs` + the test would have over-committed by sweeping in the three unstaged sibling `.rs` files. The safe practice: when an orchestrator brief gives both a count and an enumeration, treat the enumeration as the commit contract; recompute the count from `git status --short` filtered to the listed paths and flag the discrepancy back to the orchestrator before running `git commit`. Two reinforcing points: (1) cross-check `git diff --cached --name-only --pathspec-from-file="$LIST"` against the list's `sort -u` — every listed path should appear in the diff's output, and no diff entry should fall outside the list; (2) this is the same defensive stance as the existing "verify all staged files are assigned" lesson but in reverse — that one guards against missed assignments, this one guards against over-broad assignment summaries. The orchestrator can also self-check by writing `diff <(ls <dir>) <(git diff --cached --name-only -- <dir>)` and the discrepancy is obvious from the diff output.
- Auto-formatting workflows (e.g., rustfmt on save) may pre-commit files before an orchestrator assigns them. If a subagent finds no staged changes for an assigned file, it was likely auto-committed by a formatting hook.
- Commit message hooks may rewrite the submitted message after `git commit` returns. A subagent reported the resulting message differed from what was attempted. If message fidelity is critical, verify the actual commit with `git show <hash>` rather than trusting the submitted message text.
- **The parent-hash an orchestrator reports to a subagent is informational and may be stale by the time the subagent runs.** In a parallel-commit batch, sibling subagents can land their commits between the orchestrator's verification and another subagent's `git commit` invocation. The subagent's `git commit` uses whatever HEAD is at that moment — which is the correct parent. The subagent should not stop to report a parent-hash mismatch; it should just commit and report the hash it actually produced. Orchestrators can avoid the issue by either (a) not quoting a parent-hash in subagent prompts at all and instead saying "use the current HEAD as your parent", or (b) acknowledging in the prompt that the reported hash reflects state at verification time, not execution time.
- **"Verify Wave N is HEAD" is too strict a subagent check — relax to "Wave N is an ancestor of HEAD" with `git merge-base --is-ancestor` (2026-07-09 claudine 7-commit 2-wave batch, Group C subagent initial STOP).** The previous bullet covers parent-hash staleness, but the orchestrator-side generalization applies equally to any "verify X is HEAD" check in a 2-wave foundation-first dispatch. In the 2026-07-09 batch, the orchestrator dispatched Wave 1 (`85e50290e feat(claudine): add DetectionMode::Documentation and split exit tails`) and immediately started dispatching Wave 2 in parallel — Group B (`69934df7b`) landed first because its pre-flight was simpler, advancing HEAD past Wave 1's hash. When Group C's brief told the subagent "verify Wave 1 is HEAD, STOP if not", the subagent correctly STOPPED because HEAD was `69934df7b` (not `85e50290e`) — even though Wave 1's API surface (the 3-arg `exit_source_payload`, the `EXIT_STDOUT_TAIL_LINES` constant) was clearly in the tree as an ancestor of HEAD. The right check is ancestry, not equality: `git merge-base --is-ancestor <wave1-hash> HEAD && echo ANCESTOR_OK || echo ANCESTOR_MISSING`. Only `ANCESTOR_MISSING` should be a STOP trigger; HEAD being literally equal to the Wave 1 hash is the rare case in a parallel Wave-2 batch. Three reinforcing points: (1) the brief should explicitly call out the relaxed form so the subagent doesn't re-derive the strict interpretation — the existing lesson at line 91 says "parent-hash ... may be stale by the time the subagent runs" but a literal "Wave N is HEAD" check defeats that lesson unless the brief pairs it with the ancestor-check recipe; (2) the orchestrator can shorten the recipe to one line in the brief, e.g. "verify Wave 1's API surface is in the tree as an ancestor — run `git merge-base --is-ancestor 85e50290e HEAD && echo ANCESTOR_OK || echo ANCESTOR_MISSING` — only STOP on ANCESTOR_MISSING; HEAD not literally being 85e50290e is expected when siblings land first"; (3) when this lesson does fire, the orchestrator pays a round-trip latency to re-dispatch with the relaxed brief, so the cost is real — bake the ancestor-check into the standard 2-wave brief template upfront.
- **`git show --stat <hash>` is the cleanest post-commit verification of the file set.** After a `--only` commit in a multi-agent worktree, run `git show --stat <hash>` and compare the file list / line counts against the pre-commit `git diff --staged --stat` for the assigned paths — if a sibling subagent's files leaked in, the stat will not match. This is faster and less error-prone than re-running `git diff` or parsing the `git commit` output.
- **`--only` with both rename paths preserves atomicity even when the new path is a small "shell" — but git's default 50% rename threshold may not register the rename in the stat.** In the cli-heretic refactor batch (2026-06-18), 7 of 12 source refactor commits were `file.rs` → `file/{mod.rs, child.rs, ...}` renames. Of those, 3 (wiring R062, sequence R055, compose R064) had `mod.rs` shells that retained enough of the old body to clear the 50% threshold, and 4 (env 21%, watchdog/harness_orch 0%, perf requiring `-M1` with a *different* pairing) had small mod.rs shells (mostly `mod` declarations + `pub(crate) use` re-exports) that fell below the threshold. The renames were STILL atomic in the index (both old and new paths in the same `--only` pathspec) — but `git show --stat` reported them as a pure D + A pair rather than an RXX rename. If an explicit RXX marker matters (e.g., for tooling that greps `R` lines in `git log --follow`), the canonical fix is a **two-commit split**: (1) commit the pure rename first (delete the old file + create an empty `mod.rs` with just `mod child;` declarations and `pub(crate) use` re-exports sized to match the threshold), then (2) populate the new submodule files in a follow-up commit. The `-M20` threshold surface the env rename at 21% but did not help watchdog/harness_orch/perf whose mod.rs shells are too small relative to the old file. This is a presentation concern only — the index, history, and behavior are correct either way; the RXX marker is cosmetic.
- **Excalidraw-style SVG exports can show tiny line counts (`+2`/`+3` lines) in `git diff --staged --stat` even though the file is a full, hundreds-of-KB diagram.** Excalidraw (and several other diagramming tools) emit SVG as a single line of XML with embedded base64 font + payload data, so the staged diff is essentially "added one giant line plus a closing tag." Subagents asked to commit a new `.svg` and seeing `+2` or `+3` lines may incorrectly flag it as a "skeleton / header only / empty export." Verify with `git show HEAD:<path>` or `git cat-file blob HEAD:<path>` (one of which produces the actual file) and look for the diagram's textual labels (e.g. "Initialize", "Start", "Preflight") — if those are present the SVG is a complete render, regardless of how few lines the diff added.
- **A 0-line diff on an `.svg` is not always an Excalidraw compactness case — it can also be a genuinely empty file.** A 0-byte file staged for commit hashes to git's well-known empty-blob hash `e69de29bb2d1d6434b8b29ae775ad8c2e48c5391`, which `git ls-files --stage` will show verbatim. Before treating a tiny/0-line SVG diff as a valid compact Excalidraw render, check blob size explicitly: `git ls-files --stage -- <path>` for the hash, then `git cat-file -p :<path> | wc -c` (or `git cat-file -s :<path>`) for the byte count. If it is 0, the file is empty and the diagram export was never written — committing it will ship a broken placeholder. Compare against a known-good sibling SVG in the same directory (`ls -la <dir>/*.excalidraw.svg`) for the expected size before deciding. This is the disambiguator the previous bullet is missing: a real Excalidraw render and a 0-byte placeholder produce the *same* `+0` stat, but only the real one has bytes.
- **`--only` does not make concurrent commits safe when semantic groups have inter-file type dependencies.** The "concurrent with `--only`" rule above assumes each group's commit is self-contained at the source level. If group A introduces a new struct/field/method that group B's files reference, and both run concurrently with `--only`, the resulting commits become siblings sharing the same parent (the pre-A HEAD). Group B's tree has its new files referencing an identifier that lives only in A's commit (not in B's parent), so the commit does not compile and the history contains a broken tree. Detect this by scanning whether any group's files reference identifiers introduced by another group — including **new dev-dependency entries in `Cargo.toml`/`package.json`**, which make downstream test files compile. When inter-group dependencies exist, run subagents sequentially — each commit's parent becomes the previous commit's HEAD, producing a clean linear chain with self-consistent trees at every step. Use `git commit --only` in each sequential step to keep the remaining staged files intact; do NOT unstage/restage between steps (the task explicitly forbids it, and the lessons above say not to "group commits by unstaging and restaging"). Dependents first, dependents-consumers after.
- **MM state can develop MID-BATCH after the orchestrator's initial inspection, not only at dispatch time.** The existing "Staged state can drift" lesson covers the `M ` → ` M` and `A ` → `??` transitions between orchestrator and subagent dispatch; in the 2026-06-19 claudine 15-commit batch, the orchestrator's opening `git status --short` showed every staged file as clean `M `, but during the dispatch window a developer actively added new edits to `claudine/cli/src/commands/wrap/exec/{spawn,termination}.rs` and `claudine/cli/src/commands/wrap/harness_orch/attempt.rs` — those three transitioned to `MM` by the time subagents ran. This is a new direction for the drift: `M ` → `MM` (staged content picks up additional WT edits), not the M → M or A → ?? direction the existing lesson covers. The existing pre-flight `git diff -- <path>` (WT-vs-index) check inside each subagent already catches it (per the `MM` lesson below), so no new subagent-side discipline is needed — but the orchestrator-side implication is to re-check `git status --short` between dispatch waves, and to split a group when only *some* files are MM rather than dropping the whole group.
- **`A ` → `AM` drift is the parallel case for newly-added files (2026-06-23 description-on-failure batch).** The orchestrator's opening `git status --short` showed `darkmatter/features/2026-06-23-description/spec.md` as `A ` (clean staged add). During the dispatch window a developer added `review_iterations: 1` to the spec's frontmatter in the WT, transitioning the file to `AM` (index has the staged snapshot, WT has staged + a delta) by the time the Wave 2 docs subagent ran. The subagent correctly proceeded (the brief's STOP rules listed `MM`/`??` but not `AM`), and `git commit --only -- spec.md plan.md` captured the WT version per the existing `--only` semantics — committed file was 531 lines (the WT version), not the briefed 530 (the staged version). Two reinforcing points: (1) `AM` for newly-added files behaves like `MM` for modified files — `--only` captures the WT (i.e. union of staged + WT delta), so the developer's edit is swept in; (2) the subagent's self-report incorrectly claimed the staged version had been committed and the WT delta left for follow-up — but `git show <hash>:<path>` (or `git show --stat <hash>` + a sanity-check on line counts against the WT) is the only authoritative post-commit verification. Briefed staged-stat vs. landed-stat deltas of ±1 line on a new file are the signature of an `A ` → `AM` drift caught silently by `--only` — note it in the report so the orchestrator knows the developer's edit is now in the commit, not orphaned in the WT.
- **When a semantic group has both MM and non-MM files, split the group at dispatch time rather than dropping it entirely (2026-06-19 claudine batch).** In the 2026-06-19 claudine batch, the `harness_orch` group had four files but `attempt.rs` was in MM state while `types.rs`, `launch.rs`, and `loop_control.rs` were clean `M `. Committing the three non-MM files without `attempt.rs` is safe and produces a self-consistent tree: `types.rs` adds the new `step_timeout_user_configured` field, `launch.rs` populates it via a helper, and `attempt.rs` is the (skipped) consumer. The field exists with no readers for one commit — that's a valid intermediate state because unused fields don't break the Rust build. The orchestrator can brief the subagent explicitly on the partial group ("3 files, MM sibling `attempt.rs` is OUT OF SCOPE — leave it staged") and the subagent's `git commit --only -- <three paths>` cleanly captures just those three. The skipped `attempt.rs` remains staged for the developer to commit once their WT edits settle. This is preferable to blocking the entire group behind one in-progress file.
- **Merge-in-progress state blocks `--only` partial commits.** When the repo is in a merge state (conflicts resolved, merge not yet committed), `git commit --only` cannot do partial commits — Git requires a full merge commit to conclude the merge. Subagents should detect this with `git status` (look for "All conflicts fixed but are still committing") and either complete the merge first or stage files one-group-at-a-time sequentially. The orchestrator should verify no merge is in progress before launching concurrent subagents.
- **A single file's diff can span multiple plan phases and cannot be split across commits.** When the staged set was produced by squashing several plan phases (e.g. one file touches Phase 1, Phase 2, and Phase 5 of a feature), the file must be committed as a single unit. `--only -- <path>` always commits the full current content for that path — calling it twice commits the same file content twice. Splitting the underlying logical concerns would require `git add`/`git reset` to restage subsets, which is forbidden in this workflow. Organize commit groups by what is *splitable* in the actual staged set, not by ideal logical granularity, and accept that some commits will bundle several phases' worth of work on a single file.
- **`git commit --only -- <path>` ALWAYS captures the working-tree version of the named path, not the staged version (corrects a prior false note).** Per `git commit` docs, `--only` first "updates the index with the content of the working tree files limited to the given paths" and then commits — so if a path is staged as `M` but the WT has since drifted (extra edits, or a full deletion), the commit captures the WT state and the staged snapshot is overwritten from the WT before committing. An earlier version of this bullet claimed `--only` "captures only the staged diff" for `MM` files and is "safe" because WT edits stay untouched; that claim was empirically FALSIFIED (see the WT-deletion incident below) and must not be trusted. Practical guard: a subagent should run `git diff -- <path>` (WT-vs-index) immediately before `git commit --only`, and if the WT has diverged from what the orchestrator briefed — especially a deletion (`D` in the second column of `git status --short`) — STOP and report rather than committing a WT state the orchestrator did not sanction. Verify the landed content with `git show --stat <hash>` against the WT state at commit time, not the orchestrator's pre-dispatch staged snapshot.
- **The pre-commit `git diff --staged --stat` figure is a snapshot, not a contract.** In a multi-agent worktree the staged blob for a path can drift between the orchestrator's read and the subagent's commit: a developer editing the same path, an auto-format hook re-staging, or a sibling subagent that touched a shared file can all advance the staged snapshot. The subagent's prompt-side stat reflects the state at the moment the prompt was written — not at commit time. `git show --stat <hash>` is the only authoritative post-commit check. If the committed stat differs from the prompt's stat, the commit captured whatever was staged at commit time; the prompt's stat was simply out of date. Flag the drift to the orchestrator rather than treating it as a verification failure.
- **Mixed-source registry fields in claudine-gen need a `extract_catalog_value` short-circuit + `unreachable!()` sentinel in `coerce_to_catalog_shape` (2026-07-05 claudine wave-2 batch, `acp` field with research-fed `server_mode` + facts-fed `client_supported`/`events_via_acp`).** When a registry entry's value comes from MORE THAN ONE declared source — e.g. an enum member from a research topic joined with sub-fields from the facts file — the single-source `coerce_to_catalog_shape(entry, &raw, skips)` table cannot express the merge, and the alternative of duplicating research-vs-facts detection inside each pass-through arm leaks the join into every emitter. The accompanying delete-on-graduate gate (a facts record STILL carrying the research-owned sub-field is a `SourceCollision`) lives inside the dedicated helper so the gate is scoped to one source-join shape and not spread across the table. - **Pre-commit hooks can also rewrite the *content* of staged files, invalidating the drafted commit message, not just the stat.** A side-effecting hook (e.g. one that runs `cargo` or similar) can rewrite the body of a staged path between the subagent's `git diff --staged` read and the actual commit. In one verified run a 31-line `Cargo.toml` with `tauri = { version = "2", default-features = false, features = ["wry", ...] }` was rewritten to a 25-line version with `tauri = { version = "2", features = [] }` and a different comment explaining the brotli workaround — both staged at different times in the same second. The subagent's pre-commit diff still showed the original 31-line content, so the committed message described features that don't exist in the committed tree. `git show --stat <hash>` is not sufficient to catch this; verify file bodies with `git show <hash>:<path>` when a hook is suspected, and have the orchestrator amend the message with `git commit --only --amend -F - -- <paths>` (single-quoted heredoc) if it drifted.
- **Pre-commit hooks can stage new files mid-commit that the subagent never `git add`ed.** A hook that runs `cargo`/`cargo metadata`/etc. may also create or modify files outside the assigned path set (e.g. the workspace-root `Cargo.lock` and a `!/Cargo.lock` re-allow line in the root `.gitignore`) and `git add` them as a side effect. After a successful `--only` commit, the post-commit `git status --short` can show files like `M  .gitignore` and `AM Cargo.lock` that the subagent never touched. These land in the index via the hook, not the subagent. The orchestrator's post-commit `git status` check is the right place to surface them — do not have the subagent `git add` or `git restore` them, and do not blame the subagent for staging files it never saw.
- **A `mod foo;` declaration in a parent module file forces that parent file to be paired with the new child submodule's commit.** When a new submodule is created, the `mod foo;` line that wires it in must land in the same commit, otherwise the build breaks (`mod foo;` references a non-existent module). In Rust, the parent module file (often `mod.rs`) often accumulates multiple concerns — re-exports of pre-existing sibling modules, a new `mod inherit;` line, and a new `pub use inherit::Foo;` re-export. The parent file has to be paired with whichever group introduces the new submodule (so the `mod` declaration lands with the new file), and other concerns landing in the same commit is acceptable. Plan the assignment of `mod.rs`-style files by asking: "which group introduces the new submodule this file references?" — pair the parent with that group, not with the group that defined the types the parent re-exports.
- **Concurrent working-tree restructuring can delete a staged file mid-batch, and `--only` will commit the deletion (2026-06-17 cli-atheist Phase 5 incident).** The orchestrator staged 4 import updates in `darkmatter/cli/tests/cli.rs` and verified `git status --short` = `M ` (staged-modified, clean WT). During the dispatch window a concurrent test-splitting process deleted `cli.rs` in the WT and emitted 22 untracked replacement test files. The subagent's `git commit --only -- cli.rs` then staged-and-committed the 5132-line DELETION (the WT state), not the 4 staged import updates — because `--only` reads the WT for named paths (see corrected bullet above). The resulting commit had a broken tree (test file deleted, replacements untracked) and a message that misdescribed the diff. Three takeaways: (1) `git status --short` at dispatch time is a snapshot, not a contract — a file can transition `M ` → `MD` / ` D` between dispatch and commit when the worktree is being actively restructured; (2) the orchestrator cannot fully prevent this race, so subagents MUST compare `git diff --staged -- <path>` against `git diff -- <path>` right before committing and abort on material divergence (especially deletions); (3) when the WT deletion is part of an intended split (replacements exist as untracked files), the recovery is to stage the replacement files and commit/amend them together — do NOT recover via `reset` (forbidden in this workflow); report the broken commit to the user and let them decide whether to amend or follow-up-commit the replacements.
- **An `MM` (staged + WT) state on a path MUST abort the commit, even when the subagent is briefed only on the staged diff (2026-06-18 composition-shell-error-diagnostics incident).** A subagent was assigned a single path `darkmatter/lib/src/markdown/compose/shell_expansion/types.rs` and ran the pre-flight `git diff -- <path>` (WT-vs-index) check, correctly reporting the file was in `MM` state: +296/-23 staged (the briefed truncate_output / ExecutionFailed work) plus +201/-10 unstaged (an unrelated `line: Option<usize>` addition to `ShellCommandOrigin::Frontmatter`, a new `frontmatter_key_line` helper, and its test). The subagent then *committed anyway*, reasoning that `--only` would restrict the commit to the staged content of the path. The commit landed at +496/-32 — the **union of staged and WT** — so the message's bullets (truncation / stderr surfacing) misdescribed the diff, and the unrelated `frontmatter_key_line` work was silently swept in. Two reinforcing guards: (1) the existing lesson above says "if the WT has diverged … STOP and report" — that rule applies *a fortiori* to `MM` (both columns modified) and is not limited to deletions; a subagent that has been briefed on the staged diff must treat any non-empty `git diff -- <path>` as a hard abort signal, not a "I'll commit just the staged part anyway" signal; (2) the orchestrator-side post-commit check `git show --stat <hash>` is the only reliable detector of a sweep — if the commit's stat exceeds the pre-dispatch `git diff --staged --stat -- <path>` figure, the WT was swept in. The orchestrator's response to a contaminated commit is to flag it to the user (no `git reset` — that is forbidden) and let the developer decide whether to amend the message, follow up with a follow-on commit for the unrelated work, or re-split via revert.
- **A `#[cfg(test)]` helper added to a library source file must land in the same commit as the new file whose `#[cfg(test)]` block consumes it.** A test-only constructor (e.g. `ExecutableIndex::for_test` for `standard.rs`'s internal `mod tests`) is gated to `cfg(test)` in the library source and is invisible to integration tests under `tests/`, but it IS visible to any in-crate `#[cfg(test)]` block in a sibling source file. Splitting the helper from the new file across two commits breaks `cargo test` in the later commit (the test calls a function that does not yet exist), producing a build break in the history tree. The cleanest split is to commit the helper in the same group as the new file (or, if the new file is part of a foundation, in the foundation group). Scan each new file's diff for any `crate::...::helper()` or `super::...::helper()` call inside a `#[cfg(test)]` block, and pull the helper into the same group — even if the helper's own file looks semantically unrelated to the new file.
- **In a single-worktree opencode Task dispatch, the index lock effectively serializes concurrent commits into a linear chain — the sibling-fan warning above may not bite in this specific setup (2026-06-19 frontmatter-yaml-in-errors batch, 9 commits across 3 waves, 0 lock contention).** A 9-commit batch (5 concurrent in Phase 1, 3 concurrent in Phase 2, 1 in Phase 3) produced a clean linear chain — every commit's parent was the previous commit's hash, not the pre-batch HEAD. Two inter-group source-level dependencies existed in the batch: the Phase-2 `feat(claudine-cli)` commit (0c09a41d8) called `CompositionError::enrich_frontmatter` introduced by Phase-1 `feat(claudine)` (8a9fd5558), and Phase-2 `test(claudine)` (99f7269cf) consumed the `normalize_list_spacing` predicate fixed by Phase-1 `fix(darkmatter)` (792a97d04). The lesson is: in a single-worktree opencode Task batch, index-lock serialization makes the worst-case "sibling fan" outcome rare; the orchestrator can dispatch dependents in parallel with their providers and trust the lock to order them, then verify the actual `git log --pretty="%H %P"` chain after the wave settles. If a sibling-fan DOES appear (verify with `git log --pretty="%H %P"` — every commit's parent should equal the previous commit's hash, not the pre-batch HEAD), the recovery is a follow-up amend/rebase, not a retry of the same dispatch.
- **Concurrent dispatch with inter-group producer/consumer deps can yield a linear-but-wrong-order chain, not just a sibling-fan (2026-07-08 dmls review-3 batch, 3 concurrent commits, 0 lock contention, but the test commit landed before the fix commit).** A 3-group concurrent dispatch (`fix(dmls)` on `frontmatter.rs` + `substrate.rs` + `arena.rs`, `test(dmls)` on `level2_lsp_session.rs`, `docs(dmls)` on `review-3.md` + `spec.md`) was committed with index-lock serialization as predicted by the previous bullet — the chain was linear, every commit's parent equaled the previous commit's hash. **But** the order was wrong: the `test` commit (`3259aea03`) landed FIRST against the pre-batch HEAD (which lacked the `completable_atom` / `file_atom` / `inline_object_shape` / `is_schema_file_value` impl), then the `fix` commit (`7192a2b57`), then `docs` (`595dd80ce`). The test commit compiled fine (the new tests call public LSP API, not the new internal helpers), but its 4 new tests would fail at runtime because the impl was not yet present in the tree. This is distinct from a sibling-fan (where the chain *would* have shown multiple commits sharing the pre-batch HEAD as parent) — every parent's hash matched the previous commit's, so the simple `git log --pretty="%H %P"` "is it a sibling-fan?" check passed. The wrong-order check needs an *additional* read: `git log --pretty="%H %P %s"` and verify that each commit's parent equals the *correct previous* commit, not just *some* previous commit. Recovery is the same as the sibling-fan case: a follow-up rebase reorder. **Two reinforcing points.** (1) When dispatching producer/consumer groups concurrently despite the "inter-group deps should be sequential" warning on line 89, do NOT trust the index lock to pick the right semantic order — it serializes commits but the order it picks depends on whichever subagent's `git commit` first wins the lock, which is essentially random with respect to producer/consumer semantics. The dev-dep lesson above (line 104) is the same shape and recommends the same fix (wave 1 = producer, wave 2 = dependents). For non-dev-dep producer/consumer pairs, the same wave-split is the safer choice. (2) The non-interactive rebase reorder recipe is a `GIT_SEQUENCE_EDITOR` script plus a workspace-local todo file: write the desired reorder to `.git-rebase-tmp/todo` in the worktree (not `/tmp` — see the shell-gotcha lesson below), write a `cp .git-rebase-tmp/todo "$1"` script as the editor, then run `GIT_SEQUENCE_EDITOR="$(pwd)/.git-rebase-tmp/editor.sh" git rebase -i HEAD~N`. The repo GPG signs each rebased commit again (because the commits are re-applied), so all rebased commits remain signed; verify with `git verify-commit HEAD` after the rebase.

- **When one commit's tree depends on dev-deps added in another commit, use a 2-wave foundation-first dispatch (2026-06-19 claudine Phase 4 batch, 9 commits across 2 waves, 0 lock contention, 0 GPG hangs, clean linear chain).** The "trust the index lock" pattern above is fine when the dependent commits' missing identifier is a *production* import — if a sibling-fan does occur, `cargo build` fails loudly and the user can fix it. It is *not* fine when the dependency is a **dev-dep** (e.g. `tracing-test = "0.2"` for `#[tracing_test::traced_test]`-using test code, or `tracing-subscriber` for warning-capture tests): the production binary still builds, so a sibling-fan slip-through is invisible until someone runs the test target. The batch that prompted this lesson had 9 commits across 3 package areas: a `chore(claudine)` foundation that added `tracing-test` to `claudine/lib/Cargo.toml` (plus a `which = "8"` bump and the new `claudine/docs/dependencies.md`), and 8 dependent commits — of which 3 used `tracing_test::traced_test` in tests. Zero retries, zero GPG re-prompts (the foundation commit's signing primed the cache for the 8 dependents — see the GPG lesson above). The pre-flight dependency scan still matters: identify any group whose files reference an identifier or `#[macro]`/attribute introduced by another group, and put the producer in Wave 1 (or in the same group as its consumer). When the only cross-group dependency is a single Cargo.toml/`package.json` dev-dep addition, Wave 1 = that one foundation commit; when multiple groups depend on multiple new crates or modules, run several Wave 1 commits in series before opening Wave 2.
- **The 2-wave foundation-first dispatch generalizes from dev-deps to type-level cross-crate identifier dependencies (2026-07-06 claudine 10-commit batch, 1 Wave 1 + 9 Wave 2 parallel, perfectly linear chain).** The dev-dep-focused lesson immediately above covers dependencies that are invisible at production build time. Some batches need a third wave: when a **regenerated artifact** (committed JSON, generated Rust, schema-bumped doc) is produced by running a generator that picks up a behavior change shipped in Wave 2, the regen output's tree DEPENDS on the Wave 2 behavior commit. Verified in the 2026-07-06 model-metadata release-date batch: `feat(unchained-ai-gen)` (`48d7bb2c6`, Wave 2) tightened `release_date` validation to strict `YYYY-MM-DD` AND changed `models_dev_to_metadata` to a fallible `Result`. Three reinforcing points: (1) **don't combine the regen diff with the validation commit** — `chore` is the right operation for regen output and its body should make the *prior* commit the contract source of truth; combining them turns a focused behavior change into a mixed message that obscures what was validated; (2) **don't dispatch the regen in parallel with the validation commit** — both would land at the same parent (a sibling-fan), and any sibling-fan recovery (amend/rebase) is messier than just waiting for the validation to land first; (3) **identify chore-regen steps in the pre-flight dependency scan** — anywhere the staged set contains both a generator-behavior change AND its regenerated output, they must go in different waves with the regen sequenced after the behavior. The generalizable heuristic: when the staged set has both a `feat` that changes generator behavior AND a `chore` that captures the regen output of that behavior, that's a `Wave N → Wave N+1` chain by construction. Verified 6-commit chain `f9d58b02b → dc7758eb4 → 558457b63 → d4bd2a5d6 → 48d7bb2c6 → 8cde3a6d9`, all parents equal the previous commit's hash, zero retries, zero GPG hangs across all 6 (the Wave-1 commit's signing primed the cache for all 5 dependents — corroborates the GPG warm-cache lesson at line 16).

## Git Path Handling in Workspaces

- **A subagent can return with an empty `task_result` payload while its assigned files remain fully staged — the orchestrator MUST verify `git status --short` post-batch, not trust sibling-reported success (2026-06-30 darkmatter 3-commit batch, replace-expression feature).** In a 3-group concurrent commit batch on the darkmatter worktree, two of three subagents returned clean success reports and their commits landed (`docs(darkmatter)` `2738d82da`, `feat(prompts)` `9ef150c0c`). The third — assigned the darkmatter implementation files (`catalog.rs`, `functions.rs`, `darkmatter-expressions.md`) — returned with an empty `task_result` string. No commit landed for that group, no error surfaced, no diff reported. The orchestrator caught it only because the post-batch `git status --short` showed three `M ` entries it expected to be gone, and `git log --oneline -5` showed only the two siblings' commits. Root cause is opaque (swallowed subagent-internal error, aborted-but-exited process, missing report step) — don't burn tokens speculating. Recovery: the orchestrator commits the remaining files directly using the SAME recipe the subagent would have used (`git commit --only -F - -- <paths> <<'COMMIT_MSG' …`), re-running the brief's pre-flight checks inline (`git log --pretty=%s | grep -F <subject>` for collision, `git diff --cached -- <path>` for content sanity) and reusing the subject + body the brief had already vetted for that group. Verified 2026-06-30: the silent failure produced commit `79d2b0a66 feat(darkmatter): add replace, replace_first, and replace_last string mutations` via direct orchestrator commit, using the brief's suggested 66-char subject (already collision-checked at subagent-dispatch time) and the diff-derived bullet body. Three reinforcing points: (1) **never trust a subagent's returned payload without `git status --short`** — even when sibling groups in the same batch report success, one silent failure leaves its assigned files staged and the entire group uncommitted; (2) when the orchestrator takes over a silent-failure group, follow the subagent recipe EXACTLY (`--only` mandatory, single-quoted heredoc, no `--no-gpg-sign`, pathspec-only paths) — the orchestrator's ad-hoc scripts commonly drop `--only` and over-commit into sibling groups that already landed; (3) a `task_result` that contains an error string, a "I couldn't proceed" line, or any fields is a DIFFERENT (loud) failure mode and should be honored by re-dispatching or escalating — only an *empty* payload is the silent-failure case this rule addresses.
- When the worktree is a Cargo workspace member (e.g., running from `darkmatter/darkmatter/`), git interprets relative paths as relative to the current working directory, not the repo root. Use paths relative to the workspace member directory when committing from within a package subdirectory, not paths from the repo root like `darkmatter/lib/src/...`.

## Shell Gotchas

- In zsh, `$status` is read-only (an alias of `$?`). In a retry loop, capture the exit code immediately into another name (`rc=$?`); `status=$?` silently fails and breaks success/failure detection.
- Temp files for `git commit -F` must live inside the workspace temp dir, not global `/tmp`, which may be outside the allowed scope.
- **Heredoc on `git commit -F -` is consumed by the enclosing loop's stdin, not by `git commit`.** When you wrap a `git commit -F - -- <paths> <<'EOF' … EOF` invocation inside a `while … done` (or `until … done`) retry loop, the shell attaches the heredoc to the *loop*'s stdin, so `git commit -F -` sees an empty stream and aborts with `Aborting commit due to empty commit message.` The single-quoted delimiter does not change this — it only controls expansion. Fix: capture the message into a variable *outside* the loop (`MSG=$(cat <<'EOF' … EOF)`) and pipe it in inside the loop (`printf '%s' "$MSG" | git commit --only -F - -- <paths>`), or write to a temp file (`MSG_FILE=$(mktemp); cat >"$MSG_FILE" <<'EOF' … EOF`) and pass `git commit -F "$MSG_FILE"`. Apply the same fix to retry loops around `git commit --amend`, `git rebase --continue`, and any other command that reads a message from stdin.
- **`git commit --amend` without `--only` also commits ALL staged files** — it replaces the current commit with whatever is currently staged, not just the files originally in it. To amend while preserving only some staged files, use `git commit --only --amend -F - -- <paths>` or stage files one-at-a-time before amending.
- **The "MM must abort" lesson has a same-line-of-same-field exception (2026-06-20 claudine batch, `prompts/implement-suggestions.md`).** The existing bullet says "An `MM` (staged + WT) state on a path MUST abort the commit" — that is the safe default when the staged and WT deltas look unrelated, because a subagent cannot tell whether the WT change is a developer's active edit or an accidental drop. The exception: when the staged and WT deltas land on the **same line of the same field** of the same file and are clearly the same intent (e.g. a "collapse metadata" staged edit plus a "wrap the number in `**…**`" WT edit on the same `success.message:` line), the developer's active edit is the obvious complement of the orchestrator's snapshot, and capturing the union in a single commit is the right call. The orchestrator can resolve this: `git add <path>` to bring the index in sync with the WT, then `git commit --only -F - -- <path>` with a message that documents both deltas. Subagents should still abort on the cross-line/cross-field MM shape (e.g. staged change to field A plus unrelated WT change to field B) — the rule is "abort when in doubt, capture the union only when the two deltas are obviously one logical edit." Do NOT use `git restore` to discard the WT — that is destructive and the developer is actively editing; `git add` is forward-only and safe.
- **The "same intent" exception for MM/AM extends across multiple files when they implement one coordinated feature (2026-06-22 claudine lifecycle batch, `lifecycle_executor.rs` AM + `loop_control.rs` MM).** In the seven-event lifecycle batch, `claudine/lib/src/composition/lifecycle_executor.rs` was `AM` (added in index, modified in WT with a new `emit_top_level_for_signal` method) and `claudine/cli/src/commands/wrap/harness_orch/loop_control.rs` was `MM` (staged + WT edits adding a new `emit_lifecycle_top_level_only` helper that calls the new executor method). The two WT deltas were clearly one logical edit (adding a top-level-only emission path) spanning executor + CLI helper — both new symbols are useless without the other. The orchestrator pre-resolved by `git add`-ing both files to bring the index in sync with WT *before* dispatching subagents, so the lib commit landed with the new method and the CLI commit landed with the new helper that uses it. Both commits compiled cleanly in a 2-wave (1+4 parallel) batch. This is a broader interpretation of the existing "same intent" exception than the "same line of same field" wording — the underlying principle ("obviously one logical edit") is unchanged, but the scope can span multiple files when they implement/refine one coordinated feature. **Generalization:** when two or more files are in MM/AM state AND their WT deltas reference each other (or both implement the same named feature), the orchestrator can pre-`git add` them as a coordinated unit before dispatch. Without this pre-sync, the lib commit would land without the method and the CLI commit would land without the helper, leaving the committed code incomplete relative to the developer's intent (the staged snapshot alone references symbols that the developer intended to add in the WT).
- **Subagent self-recovery from a contaminated `--only` commit: `git revert <bad-hash>` is the always-safe path; `git reset --soft HEAD~1` worked once but is forbidden in general (2026-06-24 prompts implement-plan.md batch, subagent commit `0c11b44878` + dropped `0c11b44…^`).** A subagent assigned `prompts/implement-plan.md` skipped the pre-commit `git diff -- <path>` (WT-vs-index) check, ran `git commit --only -- prompts/implement-plan.md`, and swept in a developer's mid-batch WT edit (a `$schema:` reordering) alongside the briefed `initialize:` block. The first commit landed with 6 insertions + 1 deletion when the briefed staged diff was 6 insertions only. The subagent detected via `git show --stat <hash>` (stat-vs-briefed-stat mismatch), then recovered with: (1) `git reset --soft HEAD~1` to undo its own bad commit — note this is `git reset` which the prompt's "NEVER use commands like `git reset`!" rule forbids in general; it worked here ONLY because the bad commit was the subagent's own (so rewinding HEAD didn't pull in unrelated work) AND sibling subagents' commits had already landed (so the index had no other staged work to disturb — `--soft` would have preserved it but the recovery was running post-sibling-landing anyway); (2) `git checkout HEAD -- <path>` to restore the file to the pre-bad-commit version; (3) re-staged the original staged blob via `git ls-files --stage | grep <path>` + `git show <blob-hash> > <path>` + `git add <path>`; (4) re-committed with `--only` and verified 6 insertions / 0 deletions. The safer general recovery — which the subagent should have used instead — is `git revert <bad-hash>` (adds an inverse commit, never rewinds HEAD, works regardless of sibling-commit timing). The lesson consolidates three existing points into one recovery runbook: (a) the pre-commit `git diff -- <path>` check is the discipline that should have caught this BEFORE the bad commit (existing lesson, line ~86); (b) the post-commit `git show --stat <hash>` is the mandatory safety net and the subagent's correct escape valve here — do not treat "commit succeeded" as final without it; (c) when contamination is caught post-commit, prefer `git revert <bad-hash>` over `git reset --soft HEAD~1`, because the latter is a forbidden command that just happened to work in this specific context.
- **Orchestrator should project post-commit line numbers when a docs bullet cross-references a sibling commit's new symbol (2026-06-20 claudine batch).** In the cross-platform-test-helper batch, the docs-memory commit (`1e6ebaf80`) appended a bullet referencing the helper at `claudine/cli/tests/common/mod.rs:172` — but the helper did not yet exist in the index when the docs brief was written; it would only land at line 172 after the sibling chore commit (`95967a88f`) added 21 lines after line 168. The orchestrator had to read the sibling's `git show --stat` line count, project the post-merge line number, and put *that* into the bullet. A literal "use the current `git show` line number" approach would have written `:189` (the helper's pre-merge position) and produced a stale reference once the sibling commit landed. Generalize: any docs-memory / spec / review bullet that cites a line number in a file a sibling commit is about to modify must project the post-sibling-commit line number, not the pre-sibling one. The same rule applies to bullet cross-references to newly added types/functions/structs in any other file a sibling commit is about to introduce.
- **Orchestrator should `git add` an untracked file when it is the missing piece of a coordinated MM/AM scope, to keep cross-commit coherence (2026-07-03 claudine 2-commit batch, subagents summary + provider-metadata enrichment).** In the 2026-07-03 batch, the user listed 14 staged files: 11 skill-summary files in Group A and 3 provider-metadata spec/plan/triage files in Group B. By the time the orchestrator ran, the staged set had grown to 14 messy because three of Group B's files were `MM`/`AM` (staged + WT deltas reflecting "subagents summary is now complete as of 2026-07-03"), the SKILL.md had transitioned from `M ` to `MM` (the WT inserted `[Subagents](summaries/subagents.md)` into the Cross-provider Summaries list and dropped the "pending" note), AND a 15th file — `.claude/skills/claudine/summaries/subagents.md` — sat untracked in the working tree at 37653 bytes. The five signals pointed at one underlying event: the developer had finished the subagents summary and was mid-flight propagating that completion through several artifacts. The orchestrator extended scope via `git add` on all five — `claudine/features/.../{spec,implementation-plan,summary-triage}.md` to capture the WT deltas, `.claude/skills/claudine/SKILL.md` to capture the WT link/removed-pending-note, and `.claude/skills/claudine/summaries/subagents.md` to make the SKILL.md link resolve. Result: Group A committed 12 files (11 + the previously-untracked subagents summary, with SKILL.md now linking to it) and Group B committed 3 files; no broken links, no "five topics" vs "six topics" drift across commits. **Decision criterion for the orchestrator's scope expansion:** when one or more files in the listed set are `MM`/`AM` AND their WT deltas reference an untracked file (or another external artifact) that is necessary for the committed output to tell a coherent story — broken links, contradictory cross-references, "five" vs "six" counters that disagree — extend the scope by `git add`-ing those external artifacts into the appropriate group. Without this expansion, the alternative is to (a) commit the listed set literally with the `git add`-skip, leaving SKILL.md saying "subagents pending" while the spec says "complete" (cross-commit inconsistency), or (b) commit the listed set literally without touching WT deltas, requiring follow-up commits to resolve the multi-file WT drift. Two reinforcing guards: (1) **scope guard** — only extend scope when the untracked file is referenced by (and necessary for the coherence of) a file in the listed set; do not lump in unrelated untracked files; (2) **commit-message guard** — the expanded group's commit message should describe the now-complete state (e.g. "summaries, including the just-rendered subagents one, are now linked from SKILL.md"), NOT just the originally-listed-file delta. Verified 2026-07-03: both subagents committed cleanly on first try (no lock contention, no GPG hang), zero silent failures, and `sniff repo git-status` confirmed two new commits on the claudine worktree branch with a clean empty index.

## Pre-Flight STOP Reports Must Include the Diff

- **MM-state STOP reports must include the actual `git diff -- <path>` (WT-vs-index), not just "I stopped" (2026-06-26 claudine auto-complete batch, docs subagent STOP on `spec.md`).** The existing "MM must abort" lesson covers WHEN to abort but not WHAT to report — a subagent that fires the rule with a bare "STOP, MM detected" forces the orchestrator to either re-dispatch (costing one round-trip of latency) or guess at the WT delta. The fix is on the subagent side: when the pre-flight check trips on `MM`/`AM`, run `git diff -- <path>` (WT-vs-index) and include the actual hunk in the STOP report. In the auto-complete batch, subagent #3 reported `spec.md` as `MM` with the staged-side value (`review_iterations: 3`) and the WT-side value (`review_iterations: 4`) AND the full hunk, which let the orchestrator decide in a single round-trip whether to (a) re-dispatch with a wider brief, (b) use the stash dance to commit only the staged portion, or (c) split the bundle and ship the clean staged-adds separately. Without the diff in the report, the orchestrator would have re-dispatched once just to learn what `git status` alone could have told it. **Rule of thumb:** if the STOP trigger is "developer activity mid-batch" rather than "mechanical abort signal," include the WT diff so the orchestrator can disambiguate.
- **Developer activity mid-batch can push an MM file past the briefed staged value AND spawn related untracked files — force a post-dispatch bundle split (2026-06-26 claudine auto-complete batch).** The orchestrator staged `claudine/features/2026-06-14-auto-complete/spec.md` with `review_iterations: 1 → 3` alongside two clean staged-adds (`review-2.md`, `review-3.md`). During the dispatch window a developer (working in parallel on a related concern) bumped spec.md's WT to `review_iterations: 4` AND created an untracked `review-4.md` next to the staged review files. The result was `MM` on spec.md where the staged delta (`1→3`) and the WT delta (`3→4`) landed on the same line of the same field but to *different* final values — not the "same intent" exception (which requires "obviously one logical edit"). Three reinforcing points: (1) the "same intent" exception for MM does NOT apply when the staged and WT deltas are sequential value progressions rather than the same final value with different formatting — `1→3 staged vs. 3→4 WT` is two logical edits, not one; (2) when an MM file's WT delta extends past the briefed staged value AND a related untracked file appears, the right call is to **split the bundle**: ship the clean staged-add files in a docs commit that does NOT mention the MM file at all, leave the MM file and the untracked file for the developer to commit together. This mirrors the existing "When a semantic group has both MM and non-MM files, split the group at dispatch time" rule but applies *post-dispatch* when developer activity forces the split — the clean-staged-add commit goes out with a NOTABLE bullet explaining why spec.md is absent; (3) the bundle-split commit's message should explicitly note the deferred spec.md bump (e.g. "the spec.md `review_iterations` frontmatter bump that would normally accompany these review artifacts is being held back because the file is in `MM` state … the developer will land their own spec.md bump alongside `review-4.md`") so the next reviewer can trace why the spec counter still reads `3` after reviews 2 and 3 are in history.

## Claudine Lifecycle Architecture

- **A lifecycle key must be handled identically in both the loop execution path AND the composition path, because the parsing order splits them (2026-06-22 claudine lifecycle batch).** In the claudine lifecycle parser, `resolve_loop_config` (`claudine/lib/src/composition/loop_config.rs`) runs **before** lifecycle parsing in the loop execution path — so a top-level `loop.<key>` first hits `KNOWN_LOOP_KEYS` / `reject_unknown_loop_keys` in `loop_config.rs`, and only a key registered there reaches `parse_lifecycle_config` in `lifecycle.rs`. Any per-key decision therefore has to be made in BOTH files or `loop.<key>` silently diverges from the same key on an ordinary event block. The `stdout` channel is the worked example and shows the lesson is polarity-neutral: it was first *rejected* on both paths, then *reintroduced as a valid channel* (commit `f8f6129`) — which required adding `"stdout"` to `KNOWN_LOOP_KEYS` in `loop_config.rs` AND accepting it in `lifecycle.rs`, exactly mirroring the earlier paired rejection. Canonical paired L1 tests assert the *current* behavior on each path: `claudine/lib/src/composition/loop_config.rs::loop_stdout_is_accepted_as_lifecycle_concern` and `claudine/lib/src/composition/lifecycle.rs::parses_stdout_field_on_loop_block`. The lesson generalizes: any "this key must behave the same on every code path" rule requires (a) a call-site audit of the parser order and (b) a paired test asserting the behavior in each path.

## Testing Terminal-Rendering CLIs

- Non-TTY test contexts default to 80-column width, which can be too narrow for some tables. Tests should also accept the "could not be rendered" (or equivalent) error rather than only asserting a successful render, so they stay robust across CI environments.
- For biscuit-terminal table layouts that switch between single and split (two-column) views based on terminal dimensions, the established pattern in `biscuit-icon/cli/tests/cli.rs` is to drive a deterministic `Terminal` by passing `BISCUIT_TERM_WIDTH` and `BISCUIT_TERM_HEIGHT` env vars to the child process (parsed as `u32` inside the CLI), and to detect the layout by counting or scanning table-separator lines in the rendered output (e.g. `stdout.lines().filter(|l| l.starts_with('├')).count()` for the number of tables, or `any(|l| l.contains('┤') && l.contains('├'))` for the split case). This avoids snapshotting unstable ANSI styling while still asserting the layout branch.
- **Orchestrator subagent briefs must specify the worktree root, not the package-area subdirectory (2026-06-22 claudine 3-commit batch).** The system prompt's `<env>` block declares the worktree root as e.g. `/Users/ken/.claudine/worktrees/rusty-biscuit/claudine` — when the orchestrator builds a subagent brief it is tempting to "narrow" the scope by appending the package-area name (`.../claudine/claudine/`), but that path does not exist: the workspace root IS the worktree root, and the `claudine/` package-area directory is the first subdirectory under it. - **Cross-platform CLI integration tests can drop `#[cfg(unix)]` and still pass on Windows via a `PATHEXT` shim and a helper that branches internally (2026-06-20 claudine batch, `wrap_basics.rs::codex_dry_run_discovered_replace_system_prompt_*`).** The pair of dry-run tests for discovered `mode: replace` in `claudine/cli/tests/wrap_basics.rs` are **not** `#[cfg(unix)]`-gated — they compile and run on macOS, Linux, AND Windows.
