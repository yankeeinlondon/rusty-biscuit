## Goal

Close the remaining gap between the original architecture refactor and the actual runtime behavior observed in `integration-quality-review-part2.md`.

## Success Criteria

- `get_driver_metadata` for all three integrations includes a valid `setup_data_schema`
- the integrations accept setup messages and can add a device without restart
- setup persists both configured devices and per-Remote assignment data
- `get_available_entities` and `get_entity_states` only expose devices assigned to the requesting connection
- startup no longer blindly serves every configured device to every Remote
- Eversolo `--host` seeding reuses the safe helper path and preserves saved `device_name` / `driver_config`
- discovery captures stable identifiers and richer metadata where device APIs already expose them
- Eversolo and Sony entity options match live device capabilities instead of static placeholders

## Work Breakdown

### 1. Planning and Baseline

- Preserve the review document as the implementation contract
- Map each review finding to helper/runtime, integration handler, or discovery/driver changes
- Keep the touched docs aligned with the new runtime behavior in the same change

### 2. Helper Runtime and Assignment Filtering

- Extend `DeviceManager` with filtered inventory/state helpers keyed by a Remote/connection identifier
- Add helper methods that resolve assigned configured devices from `PersistentRegistry`
- Add runtime loading helpers so integrations can activate only the devices relevant to a specific Remote on demand
- Keep the global active-device pool, but make the serving path Remote-aware instead of global-only
- Preserve existing broadcast behavior unless it blocks correctness; prioritize truthful request responses first

### 3. End-to-End Setup Flow

- Add typed setup-session handling in the helper or integration layer so each WebSocket connection can:
  - start discovery
  - receive a `driver_setup_change` progress event
  - receive a selection schema for discovered/known/manual devices
  - submit user data
  - validate and persist the chosen device
  - bind the device to the current Remote/connection
  - activate the device in the runtime immediately
- Wire both `setup_driver` and `set_driver_user_data` in each handler
- Add `setup_data_schema` to each integration metadata payload
- Use direct `context.send(...)` calls for progress/change events when setup is specific to a single connection

### 4. Startup and Persistence Correctness

- Update each integration `main.rs` so startup:
  - still supports `--host` as a seed hint
  - does not overwrite persisted config when the hinted device already exists
  - does not pre-serve every configured device to every connection
- For Eversolo specifically, replace the bespoke `ConfiguredDevice` upsert path with the registry helper flow and merge WOL settings only when seeding a new device or when filling missing config safely

### 5. Stable Discovery Identity

- Update Arcam discovery to populate the best available stable identity or explicit fallback metadata from the probe path
- Update Eversolo discovery to query model/network details and fill `mac_address`, firmware, and extra fields from `get_model`
- Update Sony discovery to query system information and fill `mac_address`, firmware, model, and friendly name from the receiver
- Ensure helper discovery continues to fall back to `host:port` only when no better physical identifier exists

### 6. Truthful Dynamic Entity Options

- Eversolo:
  - make the driver advertise source list and volume steps from the live snapshot/catalog path
  - persist or cache enough catalog data so entity advertisement is not stuck with empty/static defaults
- Sony:
  - replace `SOURCE_CATEGORIES`-only advertisement with a list derived from live receiver inputs
  - reuse the same native/list-input resolution logic already used in command execution and snapshot mapping

### 7. Tests and Documentation

- Add or update tests for:
  - setup flow request handling
  - assignment-aware `get_available_entities` / `get_entity_states`
  - Eversolo seed preservation
  - stable discovery metadata extraction
  - truthful Eversolo/Sony entity options
- Update integration READMEs and helper README where public behavior changed
- Validate with `just -f homelab/justfile test`

## Execution Order

1. Add helper/runtime primitives for filtering and dynamic activation
2. Wire setup flow into one integration pattern, then apply the same pattern to the other two
3. Fix startup/seed correctness
4. Fix discovery identity and dynamic option modeling
5. Update docs and run the homelab test suite
