# Messenger Stage 1 & 2 Implementation Plan

**Date**: 2026-03-09
**Design doc**: `messenger/docs/messenger-design.md`
**Platform research**: `messenger/docs/platforms/{discord,slack,signal,whatsapp,telegram}.md`

## Current State

- `messenger/lib` and `messenger/cli` exist as empty scaffolds (boilerplate `add()` function and `Hello, world!`)
- Cargo.toml files have edition 2024, no meaningful dependencies yet
- Justfile is fully set up with standard build/test/lint recipes

## Overview

The plan is organized into 7 phases. Phases 1-4 cover Stage 1 (Discord + Slack). Phases 5-7 cover Stage 2 (Signal, WhatsApp, Telegram). Each phase is designed to produce a compilable, testable increment.

## Phase 2: Markdown Rendering Pipeline

**Goal**: Parse Markdown once into an internal AST, render to provider-specific formats.

### 2.1 Create markdown module

| File | Contents |
|------|----------|
| `markdown/mod.rs` | Public `render_for_provider()` entry point |
| `markdown/ast.rs` | Small rich-text AST: `RichNode` enum with `Text`, `Bold`, `Italic`, `Strikethrough`, `Code`, `CodeBlock`, `Link`, `List`, `Paragraph`, `Heading` |
| `markdown/parse.rs` | Parse `MessageBody::Markdown` string into `Vec<RichNode>` using `pulldown-cmark` |
| `markdown/plain_text.rs` | Render AST to plain text (strip all formatting) — used for providers that don't support rich text |
| `markdown/discord.rs` | Render AST to Discord Markdown (near pass-through, minor adjustments) |
| `markdown/slack_mrkdwn.rs` | Render AST to Slack `mrkdwn` format (`*bold*`, `_italic_`, `` `code` ``) |
| `markdown/telegram_html.rs` | Render AST to Telegram HTML (`<b>`, `<i>`, `<code>`, `<a>`) — gated behind `telegram` feature |

### 2.2 Add dependency

```toml
pulldown-cmark = "0.13"
```

### 2.3 Rendering strategy per provider

| Provider | Render target | BestEffort behavior | Strict behavior |
|----------|--------------|---------------------|-----------------|
| Discord | Discord Markdown | Pass-through, drop unsupported | Error on unsupported |
| Slack | Slack mrkdwn | Map to Slack equivalents, drop unsupported | Error on unsupported |
| Signal | Plain text | Strip all formatting | Error if formatting present |
| WhatsApp | Plain text | Strip all formatting | Error if formatting present |
| Telegram | HTML | Map to HTML tags | Error on unsupported |

### 2.4 Unit tests

- Parse known Markdown strings, assert AST structure
- Render AST to each format, snapshot test outputs
- BestEffort: formatting dropped silently
- Strict: formatting returns `UnsupportedFeature` error

### 2.5 Acceptance criteria

- `Message::markdown("**bold** and _italic_")` renders correctly for Discord, Slack, plain text, and Telegram HTML
- Round-trip: parse then render to plain text strips all formatting

## Phase 3: Provider Trait and Messenger Runtime

**Goal**: Define the `Provider` trait, build the `Messenger` coordinator, wire up dispatch routing.

### 3.1 Create provider module

| File | Contents |
|------|----------|
| `provider/mod.rs` | `Provider` trait definition (from design doc), `ProviderKind` resolution from `Target`, provider registry |

### 3.2 `Provider` trait

```rust
#[async_trait::async_trait]
pub trait Provider: Send + Sync {
    fn kind(&self) -> ProviderKind;
    fn capabilities(&self) -> CapabilitySet;
    async fn send(&self, dispatch: &Dispatch, message: &Message) -> Result<SendReceipt, MessengerError>;
}
```

### 3.3 `Messenger` struct

```rust
pub struct Messenger {
    providers: HashMap<ProviderKind, Box<dyn Provider>>,
}
```

Methods:
- `Messenger::new()` — empty
- `Messenger::register(provider)` — insert by `provider.kind()`
- `Messenger::send(dispatch, message)` — validate, resolve provider from target, delegate
- `Messenger::send_many(dispatches, message)` — send to multiple targets, collect results

### 3.4 Unit tests

- Register a mock provider, send a message, verify receipt
- Send to unregistered provider returns `MissingConfiguration`
- `send_many` with mixed success/failure

### 3.5 Acceptance criteria

- Mock provider tests pass
- Validation pipeline (validate → resolve → send) works end-to-end

## Phase 4: Discord and Slack Adapters (Stage 1 Complete)

**Goal**: Implement the two Stage 1 provider adapters with real API integration.

### 4.1 Discord adapter

**Crate**: `twilight-http` + `twilight-model` (modular, HTTP-only, no Gateway overhead)

Add to `Cargo.toml` (feature-gated):

```toml
twilight-http = { version = "0.15", optional = true }
twilight-model = { version = "0.15", optional = true }

[features]
discord = ["dep:twilight-http", "dep:twilight-model"]
```

| File | Contents |
|------|----------|
| `provider/discord.rs` | `DiscordProvider` struct, `DiscordConfig`, `DiscordOverrides` |

Implementation:
- `DiscordProvider::new(config: DiscordConfig)` — create `twilight_http::Client` with bot token
- `send()`:
  1. Render markdown to Discord format (or plain text)
  2. Build `CreateMessage` request
  3. Handle attachments via multipart upload
  4. Set `message_reference` if `reply_to` is `MessageRef::Discord`
  5. Execute request, map response to `SendReceipt` with `MessageRef::Discord`
- Rate limiting: delegated to `twilight-http` (built-in)
- Capabilities: `supports_markdown_rendering: true`, `supports_reply: true`, `supports_attachments: true`, `supports_location: false`, `supports_silent_delivery: false`, `supports_link_preview_control: false`

### 4.2 Slack adapter

**Crate**: `slack-morphism` (recommended by research, full Web API support)

Add to `Cargo.toml` (feature-gated):

```toml
slack-morphism = { version = "2.1", features = ["hyper"], optional = true }

[features]
slack = ["dep:slack-morphism"]
```

| File | Contents |
|------|----------|
| `provider/slack.rs` | `SlackProvider` struct, `SlackConfig`, `SlackOverrides` |

Implementation:
- `SlackProvider::new(config: SlackConfig)` — create Slack client with bot token
- `send()`:
  1. Render markdown to Slack mrkdwn format
  2. Build `chat.postMessage` request with `channel_id` and `text`
  3. Set `thread_ts` if `reply_to` is `MessageRef::Slack`
  4. Execute, map response `ts` to `SendReceipt` with `MessageRef::Slack`
- Rate limiting: respect `Retry-After` header on 429
- Capabilities: `supports_markdown_rendering: true`, `supports_reply: true`, `supports_attachments: false` (Stage 1 — Slack file upload is complex, defer), `supports_location: false`, `supports_silent_delivery: false`, `supports_link_preview_control: true`

**Note**: Slack Block Kit is explicitly out of scope for the shared API. `SlackOverrides` exists as an escape hatch for callers who need it.

### 4.3 Integration tests (wiremock)

For both providers, add `wiremock`-based tests that verify:

- Request serialization (correct JSON payload shape)
- Auth header presence
- Reply metadata included when `reply_to` is set
- Error mapping (auth failure → `Authentication`, rate limit → `RateLimited`, server error → `Transport`)

Add to dev-dependencies:

```toml
[dev-dependencies]
wiremock = "0.6"
serial_test = "3"
```

### 4.4 Smoke test module

Create `tests/integration.rs` with a `#[ignore]` test that sends a real message to each provider (requires env vars). This is for manual acceptance testing, not CI.

### 4.5 Acceptance criteria

- `just test` in `messenger/` passes all unit + wiremock integration tests
- `just lint` passes with no warnings
- Ignored smoke tests work when run manually with real credentials
- The ergonomic API from the design doc works:

```rust
let message = Message::markdown("**Deploy succeeded**");
messenger.send(Dispatch::to(Target::slack_channel("C012345")), &message).await?;
messenger.send(Dispatch::to(Target::discord_channel("123456")), &message).await?;
```

## Phase 5: Telegram Adapter

**Goal**: First Stage 2 provider. Simplest of the three — clean HTTP API with a well-maintained Rust crate.

### 5.1 Dependencies (feature-gated)

```toml
frankenstein = { version = "0.48", features = ["client-reqwest"], optional = true }

[features]
telegram = ["dep:frankenstein"]
```

### 5.2 Implementation

| File | Contents |
|------|----------|
| `provider/telegram.rs` | `TelegramProvider`, `TelegramConfig`, `TelegramOverrides`, `TelegramTarget`, `TelegramChatId` |

Key decisions:
- Render Markdown to HTML (not MarkdownV2) per design doc — MarkdownV2 escaping is too brittle
- Use `frankenstein::AsyncApi` for all sends
- Map `SendReceipt` with `MessageRef::Telegram { chat_id, message_id, thread_id }`
- Handle `reply_parameters` for replies
- Handle `message_thread_id` for forum topics
- Support `sendMessage`, `sendPhoto`, `sendDocument`, `sendVideo`, `sendLocation`
- Respect `retry_after` on 429

Capabilities: `supports_markdown_rendering: true`, `supports_reply: true`, `supports_attachments: true`, `supports_location: true`, `supports_silent_delivery: true`, `supports_link_preview_control: true`

### 5.3 Tests

- wiremock tests for request serialization
- Markdown → HTML rendering tests
- Location payload tests
- Attachment dispatch (correct API method selection based on `AttachmentKind`)

## Phase 6: WhatsApp Adapter

**Goal**: Cloud API integration using `reqwest` + `serde` (no SDK — per design doc, to avoid drift risk).

### 6.1 Dependencies (feature-gated)

```toml
reqwest = { version = "0.12", features = ["json", "multipart"], optional = true }

[features]
whatsapp = ["dep:reqwest"]
```

Note: `reqwest` may already be a transitive dependency. If so, just feature-gate the WhatsApp module.

### 6.2 Implementation

| File | Contents |
|------|----------|
| `provider/whatsapp.rs` | `WhatsAppProvider`, `WhatsAppConfig`, `WhatsAppOverrides`, `WhatsAppTarget` |
| `provider/whatsapp_api.rs` | Request/response structs for Cloud API serialization |

Key decisions:
- Render Markdown to plain text (WhatsApp does not support rich formatting in freeform messages)
- Send endpoint: `POST https://graph.facebook.com/{version}/{phone_number_id}/messages`
- Always include `messaging_product: "whatsapp"` in request body
- Reply via `context.message_id`
- Implement 24-hour messaging window awareness in validation (warn or error if attempting freeform send without knowing session state)
- Back off on 429 / 5xx
- Pin `api_version` in `WhatsAppConfig` (default `v23.0`)

Capabilities: `supports_markdown_rendering: false`, `supports_reply: true`, `supports_attachments: true`, `supports_location: true`, `supports_silent_delivery: false`, `supports_link_preview_control: false`

### 6.3 Tests

- wiremock tests for all message types (text, media, location, reply)
- Auth header verification
- 24-hour window validation behavior
- Error mapping from Graph API error responses

## Phase 7: Signal Adapter and CLI Foundation

**Goal**: Complete Stage 2 with Signal adapter. Begin CLI scaffolding.

### 7.1 Signal adapter

**Crate**: `signal-cli-jsonrpc-client` (per design doc — most practical integration path)

```toml
signal-cli-jsonrpc-client = { version = "*", optional = true }

[features]
signal = ["dep:signal-cli-jsonrpc-client"]
```

| File | Contents |
|------|----------|
| `provider/signal.rs` | `SignalProvider`, `SignalConfig`, `SignalOverrides`, `SignalTarget`, `SignalAddress`, `SignalThreadKey` |

Key decisions:
- Render Markdown to plain text (reserve UTF-16 body ranges for `SignalOverrides`)
- Connect to `signal-cli` daemon via JSON-RPC at `rpc_url`
- Send via `send` / `sendGroupMessage` methods
- Reply using author + timestamp quote metadata
- Serialize sends through the RPC client (no parallelism needed at this stage)
- `SignalTarget::NoteToSelf` maps to sending to own account

Capabilities: `supports_markdown_rendering: false`, `supports_reply: true`, `supports_attachments: true`, `supports_location: false`, `supports_silent_delivery: false`, `supports_link_preview_control: false`

### 7.2 Tests

- JSON-RPC request fixture tests (mock the socket/transport)
- SignalAddress enum serialization
- Reply quote metadata construction
- Error mapping from signal-cli error responses

## Risk Register

| Risk | Impact | Mitigation |
|------|--------|------------|
| `twilight-http` API churn (v0.15 → v1.0) | Medium | Pin version, feature-gate, isolate behind provider trait |
| `slack-morphism` complexity for simple sends | Low | Use only `chat.postMessage`; don't pull in Socket Mode |
| `signal-cli-jsonrpc-client` low maturity / maintenance | High | Evaluate at Phase 7; fallback to raw JSON-RPC over `reqwest` if needed |
| WhatsApp Cloud API version drift | Medium | Pin `api_version` in config, thin reqwest wrapper is easy to update |
| `frankenstein` version lag vs Bot API | Low | Currently tracks Bot API 9.5; thin wrapper makes migration straightforward |
| Markdown rendering fidelity across providers | Medium | Snapshot tests for each provider format; strict mode catches drift |
| Slack file upload complexity | Low | Deferred from Stage 1; `supports_attachments: false` initially |

## Execution Notes

- **Parallelism**: Phases 1-3 are sequential (each builds on the prior). Phase 4's Discord and Slack adapters can be developed in parallel. Phases 5, 6, 7 can be partially parallelized (Telegram and WhatsApp have no interdependencies).
- **Testing gate**: Each phase must pass `just test` and `just lint` before proceeding.
- **Skills to activate**: `rust`, `clap`, `thiserror`, `color-eyre`, `reqwest`, `markdown`, `pulldown-cmark`, `wiremock`, `rust-testing`, `inquire`, `monorepos`
- **Feature flags**: All providers are feature-gated so Stage 1 can ship without Stage 2 dependencies. Default features are `discord` + `slack`.
