# Schematic definition API: builders and typed registration

## Reading this draft

This is the builders-and-registration specification. Its sibling `2026-10-15-schematic-definition-vocabulary` adds further definition fields after this migration. “L1” means ordinary unit and integration tests that run without real provider services or terminal windows; “L2” means tests using real local terminal or browser infrastructure. Requirement labels are listed under Requirements; planning-default labels under Planning-time details; decision labels (D-numbers) come from section 15 of the parent review `2026-07-31-macro-review`. They are lookup aids, not substitutes for the contracts stated here.

**Inline review note (2026-10-11; prerequisite facts refreshed 2026-10-14).** The intended one-pass migration, typed registration, removal of unused OAuth scopes and endpoint pagination remain intact. This review corrects assumptions about Rust alias identity, descriptor validation after deserialization, registry ownership and migration ordering. The naming mechanism was ruled in D57 item 11 (`register` / `register_as` with `rust_path!`, R5). Runtime and pagination interfaces now exist; the delivered-interface map below records the pagination review's verified migration baseline.

**Author ruling note (2026-10-12).** The author ruling on `2026-10-11-schematic-generation-integrity` review 1, item 1 changes this spec in three places. (a) Endpoint identity is `(method, path)` permanently; REST selectors are withdrawn (D36 no longer applies), and no parameter, parameter location or parameter value ever distinguishes two endpoints. (b) The seven OpenAI `?beta=true` endpoints merge into their non-beta twins with an optional `beta` query parameter, and Gitea's `GetGitTreeRecursive` merges into Gitea `GetGitTree` with an optional `recursive` query parameter, following the GitHub precedent set by that ruling; fixed-value query declarations are therefore no longer needed and are not built (R29). (c) Every parameter declares its location, and a request body on `GET` fails validation (R31).

## Problem

An API is described today by a hand-written `fn define_x_api() -> RestApi` that returns one struct literal, and each endpoint is a fixed nine-field `Endpoint { .. }` literal (parent section 2). Three things are wrong, all verified in the parent review (July evidence, re-checked in part on 2026-10-11 by this draft):

1. **Ceremony without safety.** There are about 511 endpoint literals across the 18 REST APIs (OpenAI alone has 265; the parent's July figure of 253 is stale and is not used anywhere in this spec). The parent's July counts of defaulted fields (`oauth_scopes: None`, `headers: vec![]`, `params: None`, `request: None`, about 1,387 `.to_string()` calls) were taken on the smaller set and are re-measured at the start of the run (R18). The links between a definition and the Rust types it names are hand-typed strings: `ApiResponse::json_type("RepositoryInfo")` has no compile-time relationship to `pub struct RepositoryInfo`, and a parallel `SchemaRegistry` (`schematic/definitions/src/registry/mod.rs`) maps other hand-typed name strings to `schemars` schemas. `validate_completeness` compares one set of hand-written strings with another. The crate bends to fit strings (`pub type Commit = CommitInfo;` in `schematic/definitions/src/huggingface/types/stubs.rs` exists so a string resolves).
2. **Dead or doubtful surface.** `Endpoint::oauth_scopes` has no `Some` in any shipped definition; the only non-test reader copies it into the `x-schematic` operation extension (`schematic/define/src/openapi/export/paths.rs:88`). `RestApi::auth_policy` is `None` in every shipped definition, but the generator does read it through `effective_auth_policy()` (`schematic/gen/src/codegen/api_struct/mod.rs:77`, `helpers.rs:7`) and an API-variant path (`api_struct/variant.rs`), so the parent's phrase "zero codegen consumers" is not accurate for `auth_policy` (see Risks). Several definitions also write the same environment variable twice (`openai/mod.rs`: `env_auth` and `env_mapping`).
3. **A rewrite that must happen once.** The parent decided (D5, D42, D50) that the endpoint literals are rewritten in exactly one pass, and that the builder surface must already fit the response vocabulary of a later spec so no definition is rewritten twice. D52 (2026-10-11) split the original definition-API spec in two so that this pass, which is mechanical and large, is not entangled with the vocabulary work: this spec (4a) is the pass and the surface it needs; the vocabulary additions (typed path parameters, auth override, `deprecated`, rate limits, Basic shape, `oneOf` bodies, the self-contained by-name `Schema` serialization contract, OAuth2 grants, query-parameter fidelity) are the next spec, `2026-10-15-schematic-definition-vocabulary` (4b), and are added to the builders this spec creates as new methods and fields, so no definition is rewritten again.

**Not stated in the parent, found while drafting.** The `just import-openai` recipe regenerates `schematic/definitions/src/openai/{mod,types}.rs` through `schematic/gen/src/definition_gen.rs`, which emits `Endpoint { .. }` struct literals as source text (it also emits `oauth_scopes`). If only the hand-written definitions are rewritten, the next OpenAI re-import silently reintroduces literals. The emitter is therefore in scope here (R22).

**Also decided for this spec (D55, 2026-10-11).** Nine endpoints put `?` in the path template (Gitea `GetGitTreeRecursive`, GitLab's repository-file endpoint, seven OpenAI `/responses` endpoints with `?beta=true`). Spec 1 only warns. This spec adds the hard validation error and migrates all nine (R28, R29). Eight of the nine (Gitea and the seven OpenAI endpoints) have a twin on the same method and path without the `?` suffix; once the query moves out of the path they would collide under spec 1's `(method, path)` rule, so they merge into their twins rather than becoming separate endpoints (author ruling 2026-10-12).

## Goal and non-goals

**Goal.** After this spec, an API author (human or agent) writes a definition only with builders and a typed definition context. Every shipped definition is rewritten to that form in one pass, the old pagination types are gone, and generated output is unchanged except for differences explained in the implementation log.

**Non-goals (out of scope, with owner).**

- The vocabulary additions: typed path parameters, per-endpoint auth override, `deprecated`, rate-limit and retry vocabulary, retiring `env_auth[0]`, polymorphic `oneOf` bodies, the harder self-contained serialization (the by-name `Schema` contract and the bundle; the plain `Serialize`/`Deserialize` derives on `RestApi`, `Endpoint`, `EndpointParams` and `ParamDef` are this spec's, R17), OAuth2 per-grant payloads, and query-parameter `required`/`style`/`explode`/enum fidelity: spec 4b. This spec leaves a seam for them (R2, the builders' additive shape) and builds none of them.
- Response vocabulary v2 (success sets, error sets and status mapping, streaming, content types) and GraphQL: spec 5. REST selectors are withdrawn (author ruling 2026-10-12, `2026-10-11-schematic-generation-integrity` review 1, item 1); endpoint identity stays `(method, path)`. This spec only shapes the builder surface for it (R13).
- The pagination model, pagers, `collect_all`, `with_session`: spec 3 builds them. This spec moves each exception onto its endpoint and removes the old pagination types (R19, R20).
- The runtime package, envelope, credentials, redaction, redirect-following, cross-origin runtime: spec 2. This spec adds only the definition-side forms that name them (R14, R15).
- OpenAPI bridge fixes, `x-schematic` round trip, Postman example bodies, AsyncAPI, feature flags, the single generated API list, required constant headers as OpenAPI parameters, module-path resolver unification, generated-docs honesty pass, README doctests, and the accepted-gap ledger (D20): spec 7. Vendor pagination presets are not built anywhere: there is no shared preset layer (D55-4, R20).
- WebSocket definitions: spec 6. WebSocket reuses the shared types this spec touches (`ParamDef`, auth types, `EnvMapping`); this spec must not break the five WebSocket definitions' build, and does not rewrite them.
- The wider legacy-versus-modern auth dual-source cleanup, the optional-auth variant (the "Ollama ignores API keys but accepts them" case), invented HuggingFace stub shapes, and orphaned types: not done here beyond the minimum below. They are **accepted-gap candidates** for spec 7's ledger table (D20) and are listed in Risks and the Human review agenda so each is recorded rather than assumed fixed.
- Diagnostics for duplicate endpoint ids, duplicate `(method, path)`, and per-output validation: spec 1. The builders call the validation spec 1 delivers; this spec adds no second validator.

## Background: decisions this spec implements

Provenance: parent spec `schematic/reviews/2026-07-31-macro-review/spec.md` (section 15 holds the decisions, section 13a "Plan structure (D50)" the mapping, section 14 the criteria). Everything the implementer needs is restated here; the parent is evidence, not a prerequisite read.

- **D1 (scope).** Nothing is deferred. Every item the parent assigned to the definition-API work is built, in this spec or in 4b.
- **D2 (typed registration, explicit context).** `schematic-define` provides a definition context passed through each definition function in `schematic-definitions`. One call registers a type's schema and returns a descriptor carrying a validated generated Rust path. Containers such as `Vec<T>` reuse their element registrations. Rejected: descriptors carrying schema-producing callbacks, a deriving proc-macro, deferral.
- **D44 (naming rules, closes D2's details).** Defaults come from the type itself: the schema name comes from the type, the Rust path from a module the API states once (for example `types_in(...)`). Containers (`Vec`, `Option`, `HashMap`) reuse their element's registration. Free-form `serde_json::Value` registers no component. Aliases are stated explicitly (the parent illustrated this as `ctx.alias::<Commit, CommitInfo>()`, which cannot recover the alias spelling; D57 item 11 replaces it with `register_as`). Name collisions are reported when the definition is built. Left to planning: nested container and `HashMap` key registration, the format of collision reports (PD1, PD2).
- **D15 (no public `Default` on `Endpoint` and `RestApi`).** `Endpoint`, `RestApi` and their builders get constructors and builders and no public `Default`. Required facts go in constructors so an unusable definition cannot be written. Generated request types in `schematic-schema` keep their `Default`. D15 covers `Endpoint` and `RestApi`; it does not by itself cover related types such as `EndpointParams`, so `EndpointParams`'s `Default` is a separate, explicit allow-list decision (R8, PD6). Rejected: a public `Default`; `Default` behind a test feature.
- **D5, D42 (one pass).** The landing that introduces builders is the only pass over the endpoint definitions. Spec 3 puts the pagination exceptions in a table on each API definition; the builders move each exception onto its endpoint and the table is removed.
- **D43 (list recognition).** A GET endpoint returning `Vec<T>` is a list with no table entry; a POST returning an array is a list only when authored as one.
- **D30 (per-endpoint override).** The API-level `cross_origin` field and the redirect runtime land in spec 2. The per-endpoint `cross_origin` override lands here: an endpoint-level policy replaces the API-level one for that endpoint only. The policy has five values (D28): `same_origin` (default), `allow_origins([...])` exact scheme+host+port, `allow_without_credentials`, `allow_any` (explicit, clearly named opt-in; credentials sent), `deny`. Callers may tighten the policy at runtime, never loosen it.
- **D40 (secret marking).** Secrets are marked automatically from auth strategies, by an explicit `.secret()` marker on any header or parameter in the definition, and by a built-in list of well-known names. The redaction set is the union. Spec 2 owns the semantics, the API-level fields and the redaction tests; this spec supplies the builder sugar only.
- **D48 (envelope details, definition-side part).** The definition names the provider's request-id header (for example `request_id_header("x-github-request-id")`). The built-in list and the redaction are runtime work (spec 2).
- **D49 item 4 (`oauth_scopes` and `auth_policy`).** Ruled (D56-6): `auth_policy` is kept with a builder form and `oauth_scopes` is removed. Criterion, still checked by test: whichever is chosen, the field is either read by generator or exporter code and covered by a test, or it no longer exists; a field that is neither fails review.
- **D50 (plan structure).** The builders' surface (for example `.returns(...)` and `.errors(...)`) is shaped here for spec 5's response vocabulary, so the definitions are not rewritten twice. Each spec leaves the whole repo green on macOS, Linux, native Windows and WSL2; every dependent crate builds and passes its tests; an agent's terminal state is "implementation complete, ready for review". Pre-authorizations are items the author must confirm before the unattended run (D50 item 8).
- **D52 (split of the definition-API spec, approved 2026-10-11).** Eight specs: 1 generation-integrity, 2 runtime-envelope, 3 pagination, 4a definition-api (this), 4b definition-vocabulary, 5 response-model-graphql, 6 websocket, 7 fidelity-polish. The parent text for D52 may still be arriving; this spec restates what it needs.
- **D10 (backstop rule).** A declared feature must either reach the selected output or produce a diagnostic identifying the API, endpoint, feature and unsupported target; one output's gap never blocks another output.
- **D53 (no convenience methods; accepted gap).** Convenience methods on generated clients are not built; the omission is an accepted gap recorded in spec 7's ledger (D20). This spec adds no such methods to builders or generated output.
- **D54 (ownership clarifications).** Ownership of the definition-side forms and shared types follows the split above: this spec owns the builders, the context and the plain serde derives; 4b owns the vocabulary and the by-name `Schema` serialization contract; specs 2, 3 and 5 own the runtime, pagination and response models this spec only names.
- **D55 (rulings of 2026-10-11).** (1) `?` in a path template is a hard validation error added here, and the nine endpoints are migrated (R28, R29). (2) Definitions snapshot to JSON from the start via plain serde derives on `RestApi`, `Endpoint`, `EndpointParams`, `ParamDef`, replacing the sorted-`Debug` snapshot (R17, R24). (4) Vendor pagination constructors die with the old `PaginationStyle`; each API owns a small strategy function in its own module in `schematic-definitions`; there is no shared preset layer (R19, R20). (5) Inputs a pager manages are exempt from `required` fidelity (spec 4b's handling); the builders' query-parameter declaration can mark an input as adopted by a strategy (R30).
- **D56 (rulings of 2026-10-11, continued).** (6) `RestApi::auth_policy` is kept with a builder form and `Endpoint::oauth_scopes` is removed (R16, PD17); (7) the runtime trait is `EndpointSpec`.
- **D57 (rulings of 2026-10-11, second child-spec review).** (4) OpenAI pagination is authored in a hand-written overlay module (`openai_pagination::apply(api)`) that the importer never writes; the importer emits a call to it through a generic overlay hook, not an OpenAI-specific branch (R19, R22). (11) `ctx.register::<T>()` covers the common case with no names written; aliases, re-exports and foreign types use `ctx.register_as::<T>(rust_path!(path::Alias))`, where `rust_path!` fails to compile on an unresolvable path, with an optional `.schema_name("..")` component-name override (R1, R5, R6). (12) Container registrations such as `Vec<Commit>` are dropped: containers reuse the element's registration and export inline (`{"type":"array","items":{"$ref":"#/components/schemas/Commit"}}`), and the removal is a listed, explained change in R24 (R3, R6).
- **D8 (shared building blocks).** WebSocket reuses the REST parameter, auth-policy, env-mapping and header types. Changes made here to `ParamDef`, `AuthStrategy`, `EnvMapping` must not close that door (do not bake REST-only assumptions into them).
- **Parent recommendation 14 (pagination shrink).** Resolved here as **remove** (D55-4): spec 3 keeps `PaginationStyle`, `PaginationResponse`, `EndpointParams::with_pagination` and the `pagination`/`response_pagination` fields inert (its R8, and states that removal belongs here); this spec removes them and converts the 35 declared endpoints (R20).
- **D33/D38 (context only).** Error mapping is spec 5's; the placeholders in R13 must not make it harder.
- **D36 withdrawn (author ruling 2026-10-12, `2026-10-11-schematic-generation-integrity` review 1, item 1).** REST selectors are not built. An endpoint is `(method, path)`, permanently; one endpoint has one request type and, from spec 5, enumerates its possible success shapes as a tagged union. Parameter location (query, body, header) is transport mechanics, never identity (R31).

The runtime trait that generated clients implement is named `EndpointSpec` (Decided, D56), so this spec's struct `Endpoint` is unambiguous: `Endpoint` is the definition, `EndpointSpec` is the runtime trait.

## Requirements

Counts below were verified in the parent review (some in July) or at drafting and must be re-verified at the start of the run (R18 states the check). "Package" names the crate: `schematic-define` (`schematic/define`), `schematic-definitions` (`schematic/definitions`), `schematic-gen` (`schematic/gen`), `schematic-schema` (`schematic/schema`, generated).

### Definition context and typed registration (D2, D44)

**R1. A definition context exists and returns validated descriptors.** `schematic-define` exposes a context type (working name `DefinitionContext`) with a registration call that, for a type `T: JsonSchema` (plus whatever bound the Rust-path derivation needs), records `T`'s schema under a schema name derived from `T` and returns a descriptor holding the schema name and the generated Rust path (module stated once by `types_in(...)` plus the type identifier). A validated authoring descriptor comes from a context: no public constructor takes a bare string. Deserialization produces data that must be validated against the destination context before use (R7). Schema names and Rust paths are separate: `JsonSchema` can supply a schema name, but cannot prove that name is a public Rust identifier. The naming contract is D57 item 11: `ctx.register::<T>()` derives both with no names written, and `ctx.register_as::<T>(rust_path!(..))` states the Rust path explicitly for the exceptions (R5). Do not parse `std::any::type_name` as a stable generated path.
Validated by: L1 unit tests in `schematic-define` (registration returns the expected name and path); compile-fail test (trybuild or `compile_fail` doctest) showing a descriptor cannot be built from a string; the Rust path of every registered type compiles in the isolated generated crate (the spec 1 compile check, run from `schematic-gen` L1 against the rewritten definitions).

**R2. Descriptors can carry optional structural type information and derive serde from the start (author-approved constraint).** The descriptor type has an optional structural component (working name `structure: Option<TypeRef>`, where `TypeRef` is the existing structural type in `schematic-define`'s model; the exact carrier is Proposed) that is `None` for every registration this spec performs, and the descriptor derives `Serialize` and `Deserialize`. Nothing in this spec reads the structural component. It exists so that 4b can implement `oneOf`/`anyOf`/`allOf` bodies and the self-contained serialization without changing the descriptor type or any rewritten definition. The structural component has no public setter; deserialized values, including structural data, remain subject to R7 validation. The structural component is reserved data, not a second source of schemas in this spec.
Validated by: L1 test in `schematic-define` (a descriptor round-trips through `serde_json` with `structure: None`, and with a `Some` value built through a crate-internal test helper); the compile-fail test of R1 also covers the component; an L1 negative test proving that forged deserialized descriptor data cannot be accepted by a context.

**R3. Containers reuse the element's registration and preserve wire shape.** `Vec<T>`, `Option<T>`, `HashMap<K, V>` (and nesting such as `Option<Vec<T>>`) register the element type once; the descriptor's path renders the container around the element path (`Vec<RepositoryInfo>`). A container never becomes a component of its own (D57 item 12): the 36 hand-typed container registrations found at drafting (`register::<Vec<..>>("Vec<..>")` in the EMQX, GitHub, GitLab, ElevenLabs, Gitea and HuggingFace modules; re-count at the start) are dropped, and an endpoint returning a container exports it inline around the element's reference (`{"type":"array","items":{"$ref":"#/components/schemas/Commit"}}`). `HashMap` key types follow PD1. Primitive leaves (`String`, booleans and numbers) have their native Rust paths and inline schemas without creating invented components; support containers around them and around free-form JSON. Wrapper shape must survive lowering into the existing `ApiResponse` and `ApiRequest` storage even while the optional structural field of R2 remains unused.
Validated by: L1 unit tests in `schematic-define` (registry holds one entry for the element and none for the container; descriptor path text; nested containers; a non-supported key type is a build error); L1 in `schematic-gen`: the exported OpenAPI for an endpoint returning `Vec<Commit>` carries the inline array schema with an `items` reference to `Commit` and no `Vec<Commit>` component (D57 item 12).

**R4. Free-form JSON registers no component.** `serde_json::Value` (and type aliases that resolve to it) yields a descriptor with path `serde_json::Value` and adds nothing to the registry.
Validated by: L1 unit test in `schematic-define`; the exported OpenAPI for an endpoint returning it carries an inline free-form schema, as today (L1 in `schematic-gen`).

**R5. Aliases are explicit and collisions are reported when the definition is built (D57 item 11).** Rust erases a `type A = B` alias, so a generic call cannot recover the alias spelling; the parent's illustrative `ctx.alias::<A, B>()` is therefore not used. Ordinary types use `ctx.register::<T>()`, which writes no names. Aliases, public re-exports and foreign types use `ctx.register_as::<T>(rust_path!(path::Alias))`: `rust_path!` takes an actual Rust type path, fails to compile when the path does not resolve, and records the authored spelling as the descriptor's Rust path. An optional `.schema_name("..")` on that registration overrides the component name; it never stands in for the Rust path. Whether `rust_path!` also proves that the path names `T` itself, and how it treats generic paths, is Proposed and logged; `register_as` names a non-container type, and containers of it reuse that registration (R3). Registering the same canonical type repeatedly is idempotent; two distinct types claiming the same schema name are collected as build errors, with all collisions reported in the format of PD2. An alias is not permission to merge distinct types with incompatible schemas. Historical component names that differ from the canonical schema name are preserved explicitly with `.schema_name("..")` and checked by the baseline tests, rather than silently renamed.
Validated by: L1 unit tests in `schematic-define` (an alias registration emits the alias's Rust path, not the canonical type's; `.schema_name` overrides the component name and leaves the Rust path unchanged; missing alias reports a collision; two same-named types in different modules; a renamed schema, a public re-export, an external type and nested containers of an aliased type); a trybuild compile-fail case in `schematic-define` showing a misspelled `rust_path!` path does not compile (D57 criterion); the HuggingFace `Commit`/`CommitInfo` and Ollama `PushModelProgress`/`PullModelProgress` aliases in `schematic-definitions` are migrated using `register_as` (L1 in `schematic-definitions`); the isolated compile check proves each emitted path is accessible from the generated crate.

**R6. The context replaces the hand-typed registry strings and the string-vs-string check.** After the rewrite, no definition in `schematic-definitions` uses an untyped string reference to register or select a request/response schema; explicit exceptional naming (`rust_path!` and `.schema_name`, R5) remains attached to a typed registration, `SchemaRegistry::register::<T>("Name")` is no longer how registries are filled, and `validate_completeness` no longer compares two hand-written string sets. The registries returned by `get_registry`, `get_registries_for_module` and each module's `openapi_registry()` are produced from the context, with the same entries in the same insertion order as before, except that the container entries dropped by D57 item 12 (R3) are removed; that removal is a listed, explained change in R24. Explicit typed registrations preserve components not directly named by endpoints and preserve the old ordering; do not prune or reorder the registry merely because endpoint discovery encounters types differently. The context stores provider-neutral schema registrations in `schematic-define`; conversion into the existing `SchemaRegistry` remains an adapter in `schematic-definitions`, avoiding a dependency from `schematic-define` back to `schematic-definitions`. Use the existing OpenAPI-compatible schema settings and nested-definition extraction behavior.
Validated by: source-scan L1 test in `schematic-definitions` (no `register::<..>("` call and no `json_type("` string literal remain); the equivalence tests of R10 and R24 prove registry content and order are unchanged; `openapi_strict_completeness` in `schematic-gen` still passes.

**R7. Every endpoint reference is validated against its destination context.** Private descriptor fields prevent direct string construction, but do not alone prevent moving a descriptor between contexts or forging it through `Deserialize`. The API build step checks each request and response reference against the module group's registrations, including its schema name, generated path and container shape. Foreign or deserialized descriptors are accepted only when they resolve to a matching registration; otherwise the build returns a validation error naming API, endpoint and type. Imported in-memory definitions receive the same check; primitives and free-form JSON are explicit non-component cases. No process-local context identity is serialized.
Validated by: compile-fail test for direct string construction; L1 negative tests for a reference from a context missing that registration and for a forged JSON descriptor; positive tests for matching deserialized data and a shared module-group registration, in `schematic-define`.

### Builders (D15)

**R8. Endpoint and API builders exist; `Endpoint` and `RestApi` have no public `Default`; `EndpointParams`'s `Default` is explicitly allow-listed.** `Endpoint` gets method constructors (`Endpoint::get(id, path)` and the other verbs, names per PD8); `RestApi` gets a builder whose constructor takes the required facts (PD7). Neither `Endpoint`, `RestApi` nor their builders implement `Default` publicly (this is D15, which covers exactly those). `EndpointParams` derives `Default` today (`schematic/define/src/params/mod.rs`) and D15 does not cover it: it **keeps** its `Default` as a recorded allow-list entry because an endpoint with no parameters is a normal, valid endpoint (PD6). The audit also lists every other public definition type that derives `Default` today; each is either given a constructor and loses its public `Default`, or is added to the allow-list with the reason an empty value is valid. Generated request types in `schematic-schema` keep their `Default` (unchanged).
Validated by: compile-fail test in `schematic-define` (`Endpoint::default()` and `RestApi::default()` do not compile); an L1 audit test listing the public definition types and asserting the `Default` set equals the recorded allow-list (which names `EndpointParams`).

**R9. A builder cannot produce an endpoint missing a required fact.** Required facts (PD7) are enforced by the type system (typestate), not by a runtime check: `.build()` (or the conversion into `Endpoint`) is unavailable until the description and the success shape are set.
Validated by: compile-fail tests in `schematic-define` (missing description; missing success shape; missing API description or auth choice).

**R10. A built value preserves the literal it replaces.** `Endpoint` and `RestApi` already derive `PartialEq`/`Eq`. For each of the 18 APIs, the builder-built definition matches the pre-rewrite JSON baseline under a narrow, documented normalization for removed fields, new defaults and intentional changes. A baseline cannot be deserialized directly into a changed struct and assumed equivalent: that could silently discard removed fields. Compare JSON values first; compare `PartialEq` values only where the representation is unchanged. Each normalization names the API, endpoint and field; a general ignore rule for request, response, parameters or schemas is forbidden. This is the primary migration check; R24 backs it up.
Validated by: L1 equivalence test in `schematic-definitions` or `schematic-gen` (R24 states how the baseline is captured).

**R11. The `RestApi` builder takes each fact once.** One authoring call declares authentication and sets the fields that must agree (`auth`, and the environment-variable names for it as the current model stores them), so a definition cannot contradict itself (the `openai/mod.rs` double write of `OPENAI_API_KEY` becomes impossible to write). The builder leaves `env_mapping` and `auth_policy` for the explicit forms that need them. An explicit mapping conflicting with values set by the auth call is a build error, independent of setter order; it cannot silently win by being called last. Authentication choices cannot overwrite one another silently. An explicit `AuthPolicy` remains authoritative for the existing multi-method case; validate its associated environment mapping without treating that intended case as a contradiction. The shape of the stored auth types is unchanged (4b changes `Basic`). Output must be unchanged.
Validated by: L1 test in `schematic-define` (one auth call yields the same `RestApi` fields the literal wrote); R10 per API.

**R12. `Endpoint` and `RestApi` are `#[non_exhaustive]` (PROPOSED, beyond D15).** D15 requires no public `Default` and required facts in constructors; it does not require `#[non_exhaustive]`. ## Design

"Decided" means the parent decided it (cite). Everything else is **Proposed**: the implementer adopts it unless a Planning-time default (below) or a better fit found in the code says otherwise, and logs the choice.

| Symbol | Package | What it does | Status |
|---|---|---|---|
| definition context (`DefinitionContext`) | `schematic-define` | owns the registry for one module group; registers types, resolves aliases, reports collisions at build; replaces the registry-name strings | Decided that a context exists and is passed through definition functions (D2); name and exact signature Proposed |
| `ctx.types_in("path")` | `schematic-define` | states the module that holds the API's types once | Decided as the mechanism (D44, "for example `types_in(...)`"); exact name Proposed |
| `ctx.register::<T>()` -> descriptor | `schematic-define` | records schema and returns a validated name+path descriptor with no names written; containers reuse element registrations and never become components | Decided (D2, D44, D57 items 11 and 12) |
| `ctx.register_as::<T>(rust_path!(path::Alias))` with optional `.schema_name("..")` | `schematic-define` | registers an alias, re-export or foreign type under a compile-checked authored Rust path; optional component-name override | Decided (D57 item 11); whether `rust_path!` also checks the path names `T`, and generic paths, Proposed |
| descriptor type (`TypeDesc`) with optional structure, serde derives | `schematic-define` | schema name + Rust path + optional structural type; authored through the context, deserialized data validated on use | Proposed (D2 says "a descriptor"); the optional structure and serde derives are an author-approved constraint (2026-10-11), unused in this spec |
| definition-time error (`DefinitionError`) | `schematic-define` | collisions, unregistered refs, placeholder rejections | Proposed |

Sketch of the intended authoring shape (names illustrative, Proposed). Build endpoints before borrowing the context for the API builder; registration methods receive that context explicitly. Both build steps return errors rather than panicking on invalid authored data:

```rust
pub fn define_github_api(
    ctx: &mut DefinitionContext,
) -> Result<RestApi, DefinitionError> {
    ctx.types_in("schematic_definitions::github");
    let repository = Endpoint::get("GetRepository", "/repos/{owner}/{repo}")
        .describes("Get repository metadata including default branch")
        .returns_json::<RepositoryInfo>(ctx)
        .build()?;
    let tags = Endpoint::get("ListTags", "/repos/{owner}/{repo}/tags")
        .describes("List repository tags")
        .returns_json::<Vec<TagInfo>>(ctx)
        .build()?;

    RestApi::builder(ctx, "GitHub", "https://api.github.com")
        .describes("GitHub REST API v2022-11-28")
        .bearer_env(["GITHUB_TOKEN", "GH_TOKEN"])
        .request_id_header("x-github-request-id")
        .endpoints([repository, tags])
        .build()
}
```

The exact fallible signatures are established during planning and applied to registry lookup, generator entry points and the import emitter together. Errors identify the API and endpoint; provider definitions do not use unchecked `unwrap()` to conceal registration failures. The API build aggregates module-group collisions even when endpoint construction has succeeded.

Everything 4b adds (`.path_param(..)`, `.public()`, `.deprecated()`, `.rate_limit(..)`, `oneOf` registration) is a new method on these builders; the sketch above does not change when it lands.

### Module-group assembly and request coverage

One definition context belongs to one generated module group. APIs sharing a module, such as the Ollama and EMQX pairs, share registrations and collision checks; isolated groups may reuse schema names without conflict. Repeated registration of the same canonical type does not change insertion order. Registry lookup and definition lookup use the same assembly function, returning the definitions and their registry together; no global mutable registry or second manually maintained registration list is introduced. The existing [SchemaRegistry](../../definitions/src/registry/mod.rs) in `schematic-definitions` preserves insertion order and extracts nested schemas during export. The context adapter preserves both behaviors, and module-group collisions fail validation instead of relying on last-write-wins merging.

The builder migration covers every currently authored HTTP method, not only the five method constructors shown in the design table. Request builders cover JSON, multipart forms and URL-encoded forms with their field names, optionality and file metadata preserved. Text and binary request descriptors retain their present model behavior; any runtime body-carrying gap stays reported under the existing output-specific validation and is not accidentally treated as fixed by new builder syntax. Give each supported request form a focused generation/compile fixture. Endpoint-level query defaults, headers and API parameter inheritance retain their current precedence.

Query values moved out of path templates by the migration become ordinary optional caller-set query parameters (R29); there is no fixed-value query declaration. Compare name and decoded value for general query equivalence, and separately check encoding of reserved characters and repeated keys. OpenAPI and Postman output represent the new parameters like any other query parameter. Imported query-bearing paths are normalized by the shared import path before builder construction. Reject an ambiguous or malformed query expression with an endpoint-specific diagnostic rather than guessing a value. The vendored OpenAI source is unchanged; any required transform is part of repeatable import tooling and tested by re-importing twice.

## Planning-time details assigned to this spec

**PD1 (D44): nested container and `HashMap` key registration.** Default if not ruled before planning: containers recurse to the element or value type; `HashMap<K, V>` registers `V` only. ## Open Questions

- *How does typed registration name Rust aliases and public re-exports?* Ruled in D57 item 11 (`register` / `register_as` with `rust_path!` and `.schema_name`); see R5.

### Should external struct literals be prohibited by the compiler?

`#[non_exhaustive]` is still a proposal beyond the parent's builder requirement. It affects generator fixtures and downstream users as well as shipped definitions. The recommended option is the default if the author has not ruled before planning (D51 item 5).

1. **Recommended: apply `#[non_exhaustive]` after the migration.** Pros: the compiler enforces builder-only construction and later field additions do not require another literal rewrite. Cons: forces existing external literal consumers to migrate. Recommended because this young repository can absorb the change once and it directly supports the one-pass goal.
2. **Keep public literals and check shipped definitions only.** Pros: smaller immediate fixture migration. Cons: does not protect external callers from subsequent field additions, and source scans cannot enforce the public contract. If chosen, revise the builder-only acceptance wording and explicitly record the weaker guarantee.

## Risks and failure modes

- **Hidden behavior change in the rewrite.** A mistyped path or description in about 511 conversions is silent. Mitigation: R10, R24 and per-API batching (PD19). A conversion that cannot be verified by equality must fail the batch, not be waved through.
- **Typed registration changes names.** The Rust identifier derived from `T` may differ from the string the old definition used (serde `rename` on a container changes the `schemars` name; an alias; a re-exported type). Unverified at drafting for all registered types. Mitigation: the equivalence tests compare descriptor-derived names with the old strings; mismatches become `register_as` registrations with `rust_path!` or `.schema_name` (D57 item 11) or PD2 collisions, each logged.
- **Registered set must not grow.** Registering nested types automatically would add components to OpenAPI output. Default: preserve the old explicit registrations and their order, plus the existing nested `$defs` extraction behavior (R6). Suppressing nested components already exported today would itself be a regression; additions are explained diffs and review items. The one ruled exception is the container components (`Vec<..>`), dropped by D57 item 12 and listed per API in R24.
- **`#[non_exhaustive]` is beyond D15 and causes churn.** Many in-repo test literals (R12) must move to builders or a helper. Fallback stated in R12; the construction guarantee is an Open Question with a default.
- **Removing the old pagination types can break dependents and generated controls.** The 35 legacy declarations remain, but the generated pager surface already uses authored `.page(..)` and `.page_size(..)` controls instead of adopted request fields. Mitigation: R20's byte comparison and dependent builds; preserve the delivered controls and `fetch_page()` result type rather than restoring removed request setters.
- **Descriptor constraint may be wrong.** The optional structural component is designed before 4b exists. If 4b needs a different carrier, the descriptor type changes but no definition does (definitions never name the descriptor's fields). 4b's refresh checks this.
- **Parent inaccuracy about `auth_policy`.** The parent says `auth_policy` has zero codegen consumers; the generator reads `effective_auth_policy()`. Removing the field would remove the way a definition states "several explicit auth methods". Ruled: keep it (D56-6).
- **JSON snapshot ordering.** Map-like fields must serialize in a stable order or false diffs appear. Mitigation: sort when rendering the snapshot.
- **GitLab request type change breaks dependents.** Making `ref` a caller-set query field changes a generated request type (R29). Mitigation: inventory dependents first, migrate them in this spec, build all dependents (R25).
- **Merged endpoints may differ in the wire form.** With the new optional parameter set, a merged endpoint must send the same query string as the removed `?`-suffixed endpoint did (ordering with other query parameters, encoding). Mitigation: URL assertions in R29.
- **An OpenAI beta schema is not a superset of its twin.** Then the pair cannot merge without losing data or inventing an indistinguishable union. Mitigation: the R29 schema gate stops that pair, logs it for the author, and keeps R28's hard error disabled until the author rules.
- **Pagination migration can change resolved behavior.** The delivered-interface map below records the actual exceptions table, resolution/adoption functions, coverage, and tests. Preserve these results while changing their authoring location; legacy declarations alone do not establish that an endpoint is paginated.
- **Spec 2's definition-side interface is unverified.** `CrossOrigin`, redaction sets, the request-id field and the harness may exist in some other form (R14, R15, PD3, PD4).
- **Placeholders may not fit spec 5.** `Success`/`ErrorSet` are guesses at spec 5's needs (R13). Mitigation: `#[non_exhaustive]`, a single stored lowering point, and the refresh after review 1 of this spec before spec 5 is planned.
- **Import regeneration may lose hand edits.** R22's reproduce-first proof guards against it.
- **Unassigned adjacent gaps (not done here; accepted-gap candidates for spec 7's ledger table, D20).** (a) The optional-auth variant (the Ollama "ignores API keys but accepts them" case, parent section 4.5); (b) the legacy-versus-modern auth dual-source cleanup (`auth`/`env_auth`/`env_username` versus `auth_policy`/`env_mapping`), of which only the `env_auth[0]` retirement is done, in 4b; (c) invented HuggingFace stub shapes (parent section 4.5); (d) orphaned types (parent section 4.6). Listed so nobody assumes they were fixed; each needs a close-or-accept decision by spec 7.
- **Long unattended run.** The rewrite is the largest mechanical change in the whole plan; a context-window or time failure mid-batch must leave the tree green: commit-free, so each batch ends only when tests pass, and the log records the last completed API.

The three author rulings in pagination review 1 are migration invariants:

- **Session opening:** reject partitions combined with `Session::opened_by_first_page()` as `partitioned-first-page-session`. Separately opened shared sessions with rotating handles remain supported; unpartitioned first-page sessions remain supported.
- **Response callbacks:** paging runs the global JSON callback before extracting items and continuations, and skips the endpoint-specific typed callback. Ordinary sends still run both.
- **Failure recovery:** retain specific errors and their evidence, allow explicit retry after every category, replace evidence on a failed retry, and preserve the failed position without redelivering earlier items. This ruling superseded the pagination snapshot's retry exclusion. Automatic retry policies are follow-up work, not part of this builder migration.
