# Schematic Package Code Review

**Date:** 2026-02-06
**Reviewer:** Claude (Opus 4.5)
**Focus Areas:** Documentation quality, URL metadata exposure, From/TryFrom ergonomics, builder patterns

## Executive Summary

The schematic package demonstrates excellent foundational work with comprehensive rustdoc documentation in `schematic/define`, well-structured code generation in `schematic/gen`, and clean generated output in `schematic/schema`. The codebase follows Rust best practices with extensive testing and thoughtful API design.

However, there are several opportunities to improve ergonomics and documentation completeness, particularly around exposing API documentation URLs as runtime-accessible properties and expanding `From`/`TryFrom` implementations for improved caller ergonomics.

---

## Must Fix

### 1. Documentation URLs Not Exposed as Runtime Properties

**Location:** Generated API clients in `schematic/schema/src/*.rs`

**Issue:** The `docs_url` is captured in `RestApi` definitions and rendered as a Markdown link in module-level documentation, but it's not exposed as a runtime-accessible constant or method on the generated API client structs.

**Current behavior:**

```rust
// schematic/schema/src/openai.rs (line 3-5)
/*! Generated API client for [OpenAI](https://platform.openai.com/docs/api-reference).
 OpenAI REST API for model management*/
```

**Expected behavior:**

```rust
impl OpenAI {
    /// Base URL for the API.
    pub const BASE_URL: &'static str = "https://api.openai.com/v1";

    /// Official API documentation URL.
    pub const DOCS_URL: Option<&'static str> = Some("https://platform.openai.com/docs/api-reference");

    // Or as a method for consistency:
    /// Returns the official API documentation URL, if available.
    pub fn docs_url() -> Option<&'static str> {
        Some("https://platform.openai.com/docs/api-reference")
    }
}
```

**Files to modify:**

- `schematic/gen/src/codegen/api_struct.rs:55-265` - Add `DOCS_URL` constant generation

**Impact:** High - this is explicitly requested functionality for programmatic access to API docs

### 2. Missing `From<String>` and `From<&str>` for Request Path Parameters

**Location:** Generated request structs in `schematic/schema/src/*.rs`

**Issue:** Path parameter fields require explicit `.into()` calls or owned `String` values. While `new()` accepts `impl Into<String>`, there's no direct `From` implementation allowing natural struct construction.

**Current behavior:**

```rust
// Must use new() or manually construct
let req = RetrieveModelRequest::new("gpt-4");
// or
let req = RetrieveModelRequest { model: "gpt-4".to_string() };
```

**Suggested improvement for single-parameter requests:**

```rust
impl From<&str> for RetrieveModelRequest {
    fn from(model: &str) -> Self {
        Self { model: model.to_string() }
    }
}

impl From<String> for RetrieveModelRequest {
    fn from(model: String) -> Self {
        Self { model }
    }
}
```

**Files to modify:**

- `schematic/gen/src/codegen/request_structs.rs` - Add `From` impls for single-field request structs

**Impact:** Medium - improves ergonomics for simple request construction

## Suggested Improvements

### 3. Add Builder Pattern for Request Bodies

**Location:** `schematic/definitions/src/*/types.rs`

**Current behavior:** Body types like `CreateMessageBody` use `..Default::default()` pattern:

```rust
let body = CreateMessageBody {
    model: "claude-sonnet-4-5-20250514".into(),
    messages: vec![Message::user("Hello")],
    max_tokens: 1024,
    ..Default::default()
};
```

**Suggested improvement:** Add builder-style methods to complement the existing `new()` + `with_*()` pattern:

```rust
// Already exists (good!)
CreateMessageBody::new("claude-sonnet-4-5-20250514", messages, 1024)
    .with_system("You are a helpful assistant")
    .with_temperature(0.7)

// Consider also adding a full builder for more complex cases:
CreateMessageBody::builder()
    .model("claude-sonnet-4-5-20250514")
    .messages(messages)
    .max_tokens(1024)
    .system("You are helpful")
    .build()
```

**Note:** The Anthropic types already have excellent builder-style methods (`with_system`, `with_tools`, etc.). This is a positive observation - consider documenting this pattern more prominently or applying it consistently across all API definitions.

**Impact:** Low - existing pattern works well, this is enhancement

### 4. Add `TryFrom` for Validated Conversions

**Location:** `schematic/define/src/types.rs`, `schematic/define/src/auth.rs`

**Issue:** Some conversions that could fail (like parsing REST methods from strings) only use `FromStr` but lack `TryFrom<String>`.

**Current behavior:**

```rust
// Uses strum's FromStr
let method = RestMethod::from_str("POST").unwrap();
```

**Suggested improvement:**

```rust
impl TryFrom<String> for RestMethod {
    type Error = strum::ParseError;
    fn try_from(s: String) -> Result<Self, Self::Error> {
        s.parse()
    }
}

impl TryFrom<&str> for RestMethod {
    type Error = strum::ParseError;
    fn try_from(s: &str) -> Result<Self, Self::Error> {
        s.parse()
    }
}
```

**Files to modify:**

- `schematic/define/src/types.rs` - Add `TryFrom` impls for `RestMethod`

**Impact:** Low - improves consistency with Rust idioms

### 5. Missing Documentation on `Schema` Module Path Resolution

**Location:** `schematic/define/src/schema.rs:59-159`

**Issue:** The `Schema::with_path()` method is documented, but there's no guidance on when to use module paths vs. bare type names, or how the generator resolves these paths.

**Suggested improvement:** Add a "## Usage Guide" section:

```rust
/// ## Usage Guide
///
/// Use `Schema::new()` when:
/// - The type is defined in the same generated module
/// - The type will be re-exported via `pub use`
///
/// Use `Schema::with_path()` when:
/// - The type is defined in a different crate or module
/// - You need explicit qualification to avoid naming conflicts
///
/// ## Code Generation Behavior
///
/// The generator uses `full_path()` to produce import statements:
/// - `Schema::new("Foo")` → `Foo` (no import generated, assumed in scope)
/// - `Schema::with_path("Foo", "crate::models")` → `use crate::models::Foo;`
```

**Impact:** Medium - improves developer experience when defining new APIs

### 6. Generate `#[must_use]` Attributes on Request Methods

**Location:** Generated client code in `schematic/schema/src/*.rs`

**Issue:** Async request methods like `request<T>()` should have `#[must_use]` to warn if the future is accidentally discarded.

**Current behavior:**

```rust
pub async fn request<T: serde::de::DeserializeOwned>(
    &self,
    request: impl Into<OpenAIRequest>,
) -> Result<T, SchematicError>
```

**Suggested improvement:**

```rust
#[must_use = "this returns a Future that must be awaited"]
pub async fn request<T: serde::de::DeserializeOwned>(
    &self,
    request: impl Into<OpenAIRequest>,
) -> Result<T, SchematicError>
```

**Files to modify:**

- `schematic/gen/src/codegen/client.rs:205-230` - Add `#[must_use]` to generated methods

**Impact:** Low - catches a class of bugs at compile time

### 7. Improve Error Type Documentation with Examples

**Location:** `schematic/schema/src/shared.rs:17-57`

**Issue:** `SchematicError` variants are well-documented individually, but lack examples showing how to handle them.

**Suggested improvement:**

```rust
/// Errors that can occur when making API requests.
///
/// ## Error Handling Examples
///
/// ```rust,ignore
/// match client.request::<Response>(req).await {
///     Ok(response) => { /* success */ }
///     Err(SchematicError::MissingCredential { env_vars }) => {
///         eprintln!("Set one of: {:?}", env_vars);
///     }
///     Err(SchematicError::ApiError { status: 429, .. }) => {
///         // Rate limited - implement backoff
///     }
///     Err(e) => return Err(e.into()),
/// }
/// ```
#[derive(Debug, thiserror::Error)]
pub enum SchematicError { ... }
```

**Files to modify:**

- `schematic/gen/src/codegen/error.rs` - Add examples to error enum generation

**Impact:** Low - improves documentation quality

### 8. Add `From<Body>` for Request Structs with Bodies

**Location:** Generated request structs

**Issue:** Requests with bodies require explicit `Request::new(body)` even when there are no path parameters.

**Current behavior:**

```rust
let req = CreateMessageRequest::new(body);
```

**Suggested improvement:**

```rust
impl From<CreateMessageBody> for CreateMessageRequest {
    fn from(body: CreateMessageBody) -> Self {
        Self { body }
    }
}

// Now supports:
let req: CreateMessageRequest = body.into();
// or in method call context:
client.request::<Response>(body.into()).await?;
```

**Files to modify:**

- `schematic/gen/src/codegen/request_structs.rs` - Generate `From<Body>` for request-only structs

**Impact:** Medium - significantly improves ergonomics

## Nits (Optional)

### 9. Inconsistent Module Documentation Style

**Observation:** Module-level docs use `//!` in library code but generated code uses `/*! */` blocks.

```rust
// schematic/define/src/lib.rs uses:
//! Schematic Definition Library

// schematic/schema/src/openai.rs uses:
/*! Generated API client for [OpenAI](...) */
```

Both are valid, but consistency improves readability. Consider standardizing on `//!` throughout.

---

### 10. Generated Code: Multiple `impl` Blocks

**Location:** Generated request structs

```rust
// Current: Two impl blocks for same struct
impl RetrieveModelRequest {
    pub fn new(model: impl Into<String>) -> Self { ... }
}
impl RetrieveModelRequest {
    pub fn into_parts(self) -> Result<RequestParts, SchematicError> { ... }
}
```

Consider merging into a single `impl` block for cleaner generated output. This is purely cosmetic.

---

### 11. Consider `#[non_exhaustive]` for Enums

**Location:** `schematic/define/src/auth.rs`, `schematic/define/src/request.rs`, `schematic/define/src/response.rs`

Adding `#[non_exhaustive]` to public enums like `AuthStrategy`, `ApiRequest`, `ApiResponse` would allow future variants to be added without breaking changes.

## Positive Observations

### Excellent Documentation in schematic/define

The `schematic/define` crate has exemplary documentation:

- Every public type has clear rustdoc with `## Examples` sections
- Doc tests are present and would catch documentation drift
- The module-level docs in `lib.rs` provide excellent orientation

**Highlight:** `schematic/define/src/request.rs:83-106` - The `FormField` builder pattern is well-designed with clear, chainable methods:

```rust
let field = FormField::text("nickname")
    .optional()
    .with_description("User's preferred nickname");
```

### Strong `From` Trait Usage

The existing `From` implementations are well-placed:

- `impl From<Schema> for ApiRequest` (backward compatibility)
- `impl From<XxxRequest> for ApiRequest` (request enum ergonomics)

### Comprehensive Test Coverage

The test suites in `schematic/gen/src/codegen/` are thorough:

- All HTTP methods tested
- Auth strategies validated
- Generated code syntax verification with `syn::parse2`
- Edge cases like empty APIs handled

### Well-Designed Type Definitions

The Anthropic types in `schematic/definitions/src/anthropic/types.rs` demonstrate excellent API design:

- Builder methods on `CreateMessageBody`, `Message`, `ContentBlock`
- Helper constructors like `Message::user()`, `ContentBlock::text()`
- Semantic methods like `StopReason::should_continue()`
