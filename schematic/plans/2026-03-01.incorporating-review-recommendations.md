## Objective

Implement the recommendations from `ws-review.md` to close functional gaps in generated WebSocket runtimes, improve ergonomics, and add runtime confidence through E2E tests.

## Non-Goals

- Multi-endpoint socket multiplexing (future optimization only).
- Full binary/pooled zero-copy pipeline rewrite across all frame types in this pass.
- Backward-compatible API overloading for all connect signatures (Rust does not support overloads).

## Phase 1 (WS-1): URL Construction + Typed Connection Parameters

## Scope

Implement typed path/query connection parameter handling in generated `connect_*` methods.

## Implementation Tasks

1. Extend WS plan model:
   - Replace `connection_param_count` in `EndpointPlan` with structured metadata:
     - `path_params: Vec<PathParamPlan>`
     - `query_params: Vec<QueryParamPlan>`
   - Derive `path_params` using `extract_path_params(&ep.path)` from `parser.rs`.
   - Classify each `ConnectionParam`:
     - If name appears in path placeholders -> path param
     - Otherwise -> query param
2. Add lowering diagnostics:
   - Error when a path placeholder has no typed source.
   - Warning when a `ConnectionParam` duplicates a path placeholder but has conflicting expectations.
   - Warning when unknown placeholders remain after planned substitution.
3. Generate typed connect signatures in `ws_codegen/client.rs`:
   - Required path params become required method args.
   - Optional/typed query params are passed via generated endpoint-specific params struct.
4. Generate URL assembly helpers:
   - Path substitution with `urlencoding::encode` for path segment safety.
   - Query assembly using deterministic key ordering and URL encoding.
5. API shape decision (recommended):
   - For endpoints with path params and optional query params:
     - `connect_<endpoint>(&self, <required path args...>, params: <Endpoint>ConnectionParams, options: WsClientOptions)`
   - For endpoints with no query params:
     - Omit `params` argument.
6. Regenerate schema outputs and verify `elevenlabs_ws.rs` now emits e.g.:
   - `connect_text_to_speech(&self, voice_id: impl Into<String>, params: TextToSpeechConnectionParams, options: WsClientOptions)`

## Phase 4 (WS-3): Reconnect Supervisor Loop

## Scope

Implement policy-driven reconnect behavior after unexpected disconnects.

## Implementation Tasks

1. Introduce a connection supervisor model in generated client runtime:
   - Separate dial lifecycle from reader/writer loops.
   - Detect unexpected reader termination and classify disconnect reason.
2. Apply `ReconnectPolicy`:
   - Backoff progression: `initial_backoff -> multiplier -> capped at max_backoff`.
   - Jitter application per attempt.
   - `max_attempts` enforced when set.
3. State transitions:
   - `Ready -> Disconnected -> Connecting -> Ready` on success.
   - `Ready -> Disconnected -> Closed` when attempts exhausted.
4. Pending request handling during reconnect:
   - Fail all pending correlation waiters on disconnect (do not hold stale waiters).
5. Ensure manual `close()` disables reconnect attempts and exits supervisor cleanly.

## Files

- `schematic/gen/src/ws_codegen/client.rs`
- `schematic/gen/src/ws_codegen/shared.rs` (state/error additions only if required)
- Generated WS clients in `schematic/schema/src/*_ws.rs`

### Exit Criteria

- Configured reconnect policy materially changes behavior after connection loss.
- Manual close and unexpected disconnect are distinguishable and tested.

2. Make framing decision respect API/runtime `FrameFormat` hints.
3. Benchmark-level validation (lightweight):
   - Add micro-benchmark or targeted unit measurements (if benchmark infra already available).

## Risks and Mitigations

1. Breaking change risk in `connect_*` signatures.
   - Mitigation: Document migration in release notes and README examples; keep signatures stable for endpoints with no connection params.
2. Reconnect complexity can destabilize send/request semantics.
   - Mitigation: Land reconnect after URL/timeout/config work, with explicit state machine tests.
3. Transport config behavior may vary by platform/TLS stack.
   - Mitigation: Prefer behavior-based integration tests over implementation-only assertions.
4. Optional optimization work (WS-5) can increase complexity.
   - Mitigation: Gate by frame format and ship incremental allocation improvements first.
