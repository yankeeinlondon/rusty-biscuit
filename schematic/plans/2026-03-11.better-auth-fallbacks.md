# Better Auth Fallbacks Plan

## Goal

Support the following credential precedence for generated REST clients:

1. Explicitly passed API key
2. Explicitly passed OAuth token or explicit OAuth kickoff path
3. Environment-variable API key fallback
4. Descriptive error when none of the above are available

This must work for APIs that support both OAuth and API-key auth without forcing authors to choose a single `AuthStrategy` at definition time.

## Current State

### What already works

- Explicit bearer auth overrides env fallback.
- Explicit basic auth overrides env fallback.
- OAuth2 definitions can accept an explicitly injected bearer token.

### What does not work

- Explicit API key does not count as an auth override.
- A single generated client cannot model "explicit API key or explicit OAuth, else env API key fallback".
- REST auth resolution still reads `env_auth` and `env_username` directly instead of using the generated `EnvMapping`.
- Errors only describe missing env vars or missing OAuth token injection, not the full set of valid explicit auth options.

## Review Findings

### 1. Explicit API key is not treated as an explicit auth override

`Headers::use_api_key()` writes a custom header, but `Headers::has_authorization()` remains false for API keys. The generated REST client only skips auth fallback when `has_authorization()` is true. As a result, an explicitly provided API key can still trigger env lookup and fail with `MissingCredential`.

Affected areas:

- `/Volumes/coding/personal/rusty-biscuit/schematic/define/src/headers.rs`
- `/Volumes/coding/personal/rusty-biscuit/schematic/gen/src/codegen/client.rs`

### 2. REST auth is modeled as one strategy, not multiple accepted strategies

`RestApi` currently exposes one `auth: AuthStrategy`. Generated clients hard-switch on that single strategy at runtime. This blocks a client from expressing "either API key or OAuth is valid, with env fallback only for API key".

Affected area:

- `/Volumes/coding/personal/rusty-biscuit/schematic/define/src/types.rs`

### 3. `EnvMapping` exists but is not authoritative for REST request auth

`schematic-gen` embeds `EnvMapping` into generated `Headers`, but REST request execution does not resolve auth through that path. Instead, generated request code reads `self.env_auth` and `self.env_username` directly, bypassing the richer `EnvMapping` model.

Affected areas:

- `/Volumes/coding/personal/rusty-biscuit/schematic/define/src/types.rs`
- `/Volumes/coding/personal/rusty-biscuit/schematic/gen/src/codegen/api_struct.rs`
- `/Volumes/coding/personal/rusty-biscuit/schematic/gen/src/codegen/client.rs`

### 4. Error reporting is too narrow

The current runtime error model can report:

- missing env credentials
- missing OAuth bearer injection

It cannot report a combined requirement such as:

"Pass an API key explicitly, pass an OAuth token explicitly, or set one of these env vars for fallback."

Affected area:

- `/Volumes/coding/personal/rusty-biscuit/schematic/gen/src/codegen/error.rs`

## Proposed Design

### 1. Split accepted auth methods from env fallback sources

Replace the current "one auth strategy implies one credential source" model with an explicit auth policy.

Possible shape:

```rust
pub struct AuthPolicy {
    pub explicit: Vec<AuthMethod>,
    pub env_fallback: Option<EnvAuthFallback>,
}

pub enum AuthMethod {
    BearerToken {
        header: Option<String>,
    },
    ApiKey {
        header: String,
    },
    Basic,
    OAuth2(OAuth2Config),
}
```

Key properties:

- `explicit` defines what the client may accept programmatically.
- `env_fallback` defines what may be loaded from environment variables if nothing explicit was provided.
- OAuth metadata remains available without forcing the client into OAuth-only runtime behavior.

### 2. Make explicit auth tracking generic

`Headers` should distinguish:

- whether an `Authorization` header is present
- whether any explicit auth has already been supplied

Add something like:

```rust
pub fn has_explicit_auth(&self) -> bool
```

This should return true for:

- `use_bearer_token()`
- `use_basic_auth()`
- `use_api_key()`
- any future explicit auth helpers

Keep `has_authorization()` only for cases that specifically care about the `Authorization` header shape.

### 3. Centralize auth resolution in one runtime path

Generated REST clients should stop manually matching `self.auth_strategy` against env vars. Instead, request execution should resolve auth through a single runtime path using:

- explicit headers/auth attached to `Headers`
- generated-client explicit credential setters
- `EnvMapping` fallback
- auth policy metadata

Target precedence:

1. Explicit auth already set on `Headers`
2. Explicit auth set through generated client APIs
3. Env fallback from `EnvMapping`
4. `AuthenticationRequired` error

### 4. Make `EnvMapping` the source of truth

For REST generation:

- `env_auth` and `env_username` should become authoring compatibility inputs only
- `RestApi::default_env_mapping()` should normalize those legacy fields once
- generated code should resolve runtime fallback from `EnvMapping`, not from raw legacy fields

Also fix legacy conversion so `AuthStrategy::ApiKey` can produce `EnvMapping.api_key`, not just bearer/basic-style mapping.

### 5. Add explicit credential injection helpers to generated clients

Generated clients should expose first-class methods for explicit auth:

```rust
.api_key("key")
.bearer_token("token")
.basic_auth("user", "pass")
.oauth_token("token")
```

These should all feed the same explicit-auth state.

For OAuth kickoff:

- prefer integration with `schematic-oauth`
- generated clients should expose provider metadata and a clean handoff point
- avoid embedding full provider-specific OAuth execution logic into every generated client

### 6. Replace narrow auth errors with one descriptive requirement error

Add a runtime error variant that can explain all acceptable auth inputs.

Possible shape:

```rust
AuthenticationRequired {
    explicit_methods: Vec<AuthMethodHint>,
    env_fallback_vars: Vec<String>,
}
```

This error should describe:

- which explicit auth methods are accepted
- which env vars are valid fallback sources
- whether OAuth requires the user to obtain a token via `schematic-oauth`

### 7. Preserve compatibility while migrating

Migration approach:

- keep current `AuthStrategy` support temporarily
- introduce the new policy model alongside it
- translate legacy definitions into the new model during generation
- deprecate direct runtime dependence on `env_auth` / `env_username`

This avoids forcing a flag day across all existing definitions.

## Implementation Plan

### Phase 1: Fix the explicit API key precedence bug

Scope:

- make explicit API keys count as explicit auth
- stop env fallback when any explicit auth is present

Tasks:

- add `Headers::has_explicit_auth()`
- track explicit API key usage in `Headers`
- update generated REST auth setup to check `has_explicit_auth()` instead of `has_authorization()`
- add tests covering explicit API key vs env fallback precedence

Expected outcome:

- explicit API key, bearer, and basic credentials all override env fallback

### Phase 2: Route REST env fallback through `EnvMapping`

Scope:

- stop reading raw `env_auth` / `env_username` during request execution

Tasks:

- update generated REST clients to resolve fallback credentials via the embedded `Headers`/`EnvMapping`
- update `RestApi::default_env_mapping()` so legacy API-key definitions normalize correctly
- remove duplicated env-resolution logic from generated request code

Expected outcome:

- one fallback implementation for bearer, basic, and API-key auth
- richer env configuration is actually honored at runtime

### Phase 3: Introduce a multi-method auth policy

Scope:

- allow one API definition to accept multiple explicit auth methods

Tasks:

- add a new auth policy type in `schematic-define`
- support compatibility translation from legacy `AuthStrategy`
- update generator data model and emitted client structs
- add generated-client helpers for explicit API key / bearer / basic / OAuth token

Expected outcome:

- one client can accept explicit API key or explicit OAuth token without changing auth strategy

### Phase 4: Improve auth errors and OAuth handoff

Scope:

- produce descriptive auth errors
- expose a clearer OAuth integration path

Tasks:

- add unified `AuthenticationRequired` error
- include accepted explicit auth methods and env fallback vars
- update OAuth-only and dual-auth clients to point to `schematic-oauth`
- revise generated docs and READMEs

Expected outcome:

- errors explain exactly what the caller can do next

## Test Plan

Add or update tests in both `schematic-define` and `schematic-gen`.

### `schematic-define`

- explicit API key marks auth as explicit
- env fallback does not overwrite explicit API key
- env fallback still fills API key when no explicit auth exists
- explicit bearer/basic behavior remains unchanged

### `schematic-gen`

- generated API-key client uses explicit API key when env is absent
- generated API-key client uses explicit API key when env is present
- dual-auth client accepts explicit OAuth token
- dual-auth client accepts explicit API key
- env API key is used only when no explicit auth is present
- missing auth produces descriptive `AuthenticationRequired`
- backward-compatible bearer/basic clients still behave as before

## Recommended Order

1. Phase 1: explicit API key precedence fix
2. Phase 2: unify runtime fallback on `EnvMapping`
3. Phase 3: introduce multi-method auth policy
4. Phase 4: improve errors and docs

## Recommendation

Do not add more OAuth-flavored API definitions until at least Phase 1 and Phase 2 are complete.

Reason:

- current precedence behavior is incorrect for explicit API keys
- current runtime plumbing cannot faithfully express "OAuth or API key, env as fallback"

Once Phase 3 lands, forge-style APIs like GitLab, Gitea, and Bitbucket can be modeled much more accurately.
