# GitLab And Gitea Unified OAuth Plan

## Goal

Add OAuth capabilities to the existing `GitLab` and `Gitea` REST API definitions without creating parallel `*OAuth` definitions.

Each definition should support:

1. Explicit API-key / PAT-style auth
2. Explicit OAuth token auth
3. Existing environment-variable API-key / PAT fallback
4. A descriptive runtime error when neither explicit auth nor env fallback is available

This plan assumes the same endpoint surface is available regardless of whether the caller uses API-key auth or OAuth.

## External Constraints

### GitLab

- GitLab REST authentication officially supports OAuth 2.0 tokens via `Authorization: Bearer <token>`.
- GitLab personal, project, and group access tokens are documented with `PRIVATE-TOKEN`, and GitLab also documents bearer-style use for those tokens.
- GitLab’s OAuth provider supports Authorization Code with PKCE, Authorization Code, Device Authorization Grant, and refresh tokens.
- For the current read-only definition surface, `read_api` is the best default OAuth scope. `read_repository` is not broad enough for merge requests, issues, group projects, and releases.

### Gitea

- Gitea accepts OAuth access tokens via `Authorization: Bearer ...` and query parameters.
- Gitea PAT-style auth currently uses `Authorization: token <pat>`.
- Gitea’s OAuth provider supports Authorization Code with PKCE.
- Gitea’s granular scopes map cleanly to the current endpoint surface:
  - `read:repository` for repository, tree, raw content, PR, tags, and releases
  - `read:issue` for issues, comments, and timeline
  - `read:organization` for `ListOrgRepos`

## Design Decisions

### 1. Do not add `GitLabOAuth` or `GiteaOAuth`

Use one `RestApi` per provider and express the dual auth behavior through `auth_policy`.

This preserves:

- one module path
- one request enum
- one set of response models
- one generated client type per provider

### 2. Preserve current API-key / PAT behavior as the env fallback

The existing API-key / PAT auth path is already in use and should remain the default environment-variable fallback.

That means:

- GitLab env fallback remains `PRIVATE-TOKEN`
- Gitea env fallback remains `Authorization: token <pat>`

OAuth is additive, not a replacement.

### 3. Use OAuth only as an explicit programmatic auth method

Generated clients should accept OAuth tokens through `.oauth_token(...)`.

This plan does not require generated clients to acquire tokens automatically at request time. Token acquisition remains the responsibility of `schematic-oauth`.

### 4. Prefer endpoint-compatible scope metadata

Because both current definitions are read-only, scope modeling should remain minimal and read-oriented.

Recommended rule:

- GitLab: use `read_api` as the API-level default scope
- Gitea: use a read-only union at the API level and more precise endpoint-level `oauth_scopes` where useful

## Proposed Definition Shapes

### GitLab

Keep the legacy auth field for backward compatibility, but add an explicit auth policy:

```rust
RestApi {
    auth: AuthStrategy::ApiKey {
        header: "PRIVATE-TOKEN".to_string(),
    },
    auth_policy: Some(AuthPolicy {
        explicit: vec![
            AuthMethod::ApiKey {
                header: "PRIVATE-TOKEN".to_string(),
            },
            AuthMethod::OAuth2(OAuth2Config {
                grant_type: OAuth2GrantType::AuthorizationCodePkce,
                authorization_url: Some("{base}/oauth/authorize".to_string()),
                token_url: "{base}/oauth/token".to_string(),
                revocation_url: Some("{base}/oauth/revoke".to_string()),
                device_authorization_url: None,
                default_scopes: vec!["read_api".to_string()],
                pkce: PkceRequirement::Required,
                client_auth: OAuth2ClientAuthMethod::None,
            }),
        ],
        env_fallback: Some(EnvAuthStrategy::ApiKey {
            header: "PRIVATE-TOKEN".to_string(),
        }),
    }),
    env_auth: vec![
        "GITLAB_TOKEN".to_string(),
        "GITLAB_PRIVATE_TOKEN".to_string(),
    ],
    // ...
}
```

Notes:

- The env fallback remains the existing `PRIVATE-TOKEN` path.
- OAuth tokens are bearer tokens and should be injected only through `.oauth_token(...)` or `Headers::use_bearer_token(...)`.
- `client_auth: None` is the safest PKCE-first default for public clients, but see “Open Questions” below.

### Gitea

Use one client that accepts either a PAT-style authorization header or an OAuth bearer token:

```rust
RestApi {
    auth: AuthStrategy::ApiKey {
        header: "Authorization".to_string(),
    },
    auth_policy: Some(AuthPolicy {
        explicit: vec![
            AuthMethod::ApiKey {
                header: "Authorization".to_string(),
            },
            AuthMethod::OAuth2(OAuth2Config {
                grant_type: OAuth2GrantType::AuthorizationCodePkce,
                authorization_url: Some("{base}/login/oauth/authorize".to_string()),
                token_url: "{base}/login/oauth/access_token".to_string(),
                revocation_url: None,
                device_authorization_url: None,
                default_scopes: vec![
                    "read:repository".to_string(),
                    "read:issue".to_string(),
                    "read:organization".to_string(),
                ],
                pkce: PkceRequirement::Required,
                client_auth: OAuth2ClientAuthMethod::None,
            }),
        ],
        env_fallback: Some(EnvAuthStrategy::ApiKey {
            header: "Authorization".to_string(),
        }),
    }),
    env_auth: vec!["GITEA_TOKEN".to_string()],
    // ...
}
```

Notes:

- This is the more interesting case because both auth methods use the `Authorization` header but with different value shapes:
  - PAT: `token <pat>`
  - OAuth: `Bearer <access_token>`
- The generated client should expose both `.api_key(...)` and `.oauth_token(...)`.
- Existing env behavior stays unchanged: `GITEA_TOKEN` must still contain the full PAT-formatted header value unless a future ergonomics change is planned separately.

## OAuth Metadata And Env Mapping

Both definitions should explicitly populate OAuth runtime env hints in `env_mapping` instead of relying only on legacy auth fields.

Recommended variables:

### GitLab

- `GITLAB_CLIENT_ID`
- `GITLAB_CLIENT_SECRET`
- `GITLAB_REDIRECT_URI`

### Gitea

- `GITEA_CLIENT_ID`
- `GITEA_CLIENT_SECRET`
- `GITEA_REDIRECT_URI`

Recommended shape:

```rust
env_mapping: Some(EnvMapping {
    api_key: Some(ApiKeyEnv {
        names: EnvList::new(existing_env_auth.clone()),
        header: existing_pat_header.to_string(),
    }),
    oauth_client_id: Some(EnvList::single("...CLIENT_ID")),
    oauth_client_secret: Some(EnvList::single("...CLIENT_SECRET")),
    oauth_redirect_uri: Some(EnvList::single("...REDIRECT_URI")),
    ..Default::default()
}),
```

Rationale:

- PAT fallback remains authoritative for runtime auth fallback
- OAuth app credentials become discoverable and serializable in the definition layer
- `schematic-oauth` gets consistent provider-specific env conventions

## Scope Strategy

### GitLab

Because every current GitLab endpoint is a read-only REST API endpoint, use:

- API-level default: `read_api`
- no endpoint-level overrides in the first pass

Why:

- `read_api` is broad enough for repositories, merge requests, issues, releases, pipelines, and groups
- endpoint-specific scope tuning adds little value for the current slice

### Gitea

Use a mixed strategy:

- API-level default scopes:
  - `read:repository`
  - `read:issue`
  - `read:organization`
- endpoint-level `oauth_scopes` for clarity and future tooling:
  - repository/tree/raw/PR/tag/release endpoints → `["read:repository"]`
  - issue/comment/timeline endpoints → `["read:issue"]`
  - `ListOrgRepos` → `["read:organization"]`

Why:

- Gitea already exposes granular route-family scopes
- the endpoint surface splits neatly across those route families
- the extra metadata will improve generated docs and any future runtime scope selection

## Risks

### 1. `OAuth2ClientAuthMethod` may be too rigid

Both GitLab and Gitea support public-client PKCE and confidential-client flows, but `OAuth2Config` currently carries a single `client_auth` default.

Risk:

- choosing `None` favors PKCE-first public clients
- choosing `ClientSecretPost` favors confidential apps
- either choice may be too opinionated

Recommendation:

- treat `None` as the provider default in the definition layer
- allow `schematic-oauth::OAuth2RuntimeConfig` to override client-auth behavior at runtime if needed

### 2. Gitea PAT ergonomics remain stringly

The current PAT path expects `GITEA_TOKEN` to include the `token ` prefix.

Risk:

- users may confuse `.api_key("abc")` with `.oauth_token("abc")`

Recommendation:

- document this clearly in module docs and README
- consider a later ergonomics improvement such as `.personal_access_token(...)` if confusion becomes common

### 3. GitLab bearer-token ambiguity

GitLab also accepts some non-OAuth access tokens via bearer headers.

Risk:

- users may use `.oauth_token(...)` with a PAT and still succeed

Recommendation:

- accept that runtime wire behavior may overlap
- keep the semantic distinction in docs:
  - `.api_key(...)` means PAT-style auth
  - `.oauth_token(...)` means OAuth-acquired token

## Open Questions

1. Should GitLab also expose endpoint-level `oauth_scopes`, or is `read_api` alone sufficient for the current read-only surface?
2. Should Gitea’s default scopes be the full read-only union, or should the API-level default be left empty with endpoint-level scopes only?
3. Should `schematic-oauth` get provider helper constructors for GitLab and Gitea runtime config, or should this remain purely definition-driven?

## Recommendation

Implement GitLab first, then Gitea.

Why:

- GitLab is the simpler migration because PAT and OAuth use different header names in the recommended path
- Gitea is the better stress test afterward because both auth modes share `Authorization` but use different value formats

If GitLab lands cleanly under the unified policy, Gitea becomes a focused follow-up instead of debugging two variables at once.
