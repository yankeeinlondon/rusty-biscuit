# Review: OAuth Primitives & Better Auth Fallbacks

**Date:** March 11, 2026
**Plans Evaluated:**

- `@schematic/plans/2026-03-10. oauth primitives.md`
- `@schematic/plans/2026-03-11.better-auth-fallbacks.md`

## 1. Functionality Delivery

The implementation successfully fulfills the core requirements laid out in both plans:

- **OAuth Primitives (`schematic-define`):** Added `OAuth2Config`, `OAuth2GrantType`, `PkceRequirement`, and `OAuth2ClientAuthMethod` correctly. `AuthStrategy::OAuth2` was introduced without breaking existing legacy types.
- **OAuth Runtime (`schematic-oauth`):** The crate was successfully bootstrapped with token lifecycle management (`OAuth2Manager`), token stores (`MemoryTokenStore`, `FileTokenStore`), and thorough `tokio`-backed tests.
- **Generator Updates (`schematic-gen`):** Generated code now appropriately handles dual-auth APIs using `AuthPolicy`. Explicit auth helpers (`bearer_token`, `api_key`, `basic_auth`, `oauth_token`) are cleanly generated based on the policy.
- **OpenAPI Round-Tripping:** Import and export mappings successfully translate between OpenAPI `SecurityScheme::OAuth2` and `AuthStrategy::OAuth2`.
- **Better Auth Fallbacks:** Fallback logic cleanly transitioned to `EnvMapping`, giving precedence to explicit auth configurations. `AuthPolicy` structures explicit vs. environment credentials effectively.

## 2. Recommended Improvements

While the implementation is robust, a few ergonomic, idiomatic, and cleanup improvements can be made:

### A. Remove Obsolete Error Variant

In `schematic/gen/src/codegen/error.rs`, the `SchematicError` enum contains `OAuthAuthenticationRequired`:

```rust
#[error("OAuth2 authentication required: {message}")]
OAuthAuthenticationRequired { message: String },
```

The "Better Auth Fallbacks" plan introduced the unified `AuthenticationRequired` variant (lines 100-108 in `error.rs`), which handles all credential requirements, including OAuth instructions. The generator successfully uses the unified error in `client.rs` (via `authentication_required_error()`). The `OAuthAuthenticationRequired` variant is now obsolete code and should be removed entirely to avoid confusion.

### B. Graceful Degradation in OpenAPI Import

In `schematic/define/src/openapi/import/mappings.rs`, when mapping a `SecurityScheme::OAuth2`:

```rust
} else if flows.implicit.is_some() {
    Err("Implicit OAuth2 flow is not supported...".to_string())
} else if flows.password.is_some() {
    Err("Resource Owner Password Credentials flow is not supported...".to_string())
}
```

Currently, this returns an `Err(String)`, which likely aborts the entire endpoint or API import. Instead of a hard error, it would be more resilient to push an `OpenApiDiagnostic::warn` and return `Ok(AuthStrategy::None)`. This allows the user to still generate the REST client (which they can authorize manually using `.variant_with_headers()`) rather than blocking the code generation entirely because of an unsupported security scheme.

### C. Performance & Ergonomics: `Headers` Cloning

The explicit auth helpers generated in `api_struct.rs` (e.g., `bearer_token`, `api_key`) call `.clone()` on `self.headers`:

```rust
pub fn api_key(&self, key: impl Into<String>) -> Self {
    self.variant()
        .headers_builder(self.headers.clone().use_api_key(key, "X-API-Key"))
        .build()
}
```

While perfectly acceptable for a builder pattern, creating deeply nested variants could result in excessive cloning. Providing mutable builder methods on `Headers` or optimizing its internal representation (e.g., `Arc` for environment mappings since they rarely change) could yield micro-optimizations down the line.

## 3. Test Coverage

The test coverage is very strong across all modified crates:

- **`schematic-define` / `schematic-gen`**: Over 460 passing tests and 165 doc tests. Explicit checks exist for `api_key_uses_runtime_auth_matching`, `dual_auth_generates_descriptive_authentication_required_error`, and `bearer_token_uses_runtime_auth_matching`.
- **`schematic-oauth`**: 22 passing tests covering configurations, CSRF checks, PKCE builds, and mocked token exchanges.
- **OpenAPI Mapping**: Thorough assertions across `map_security_scheme` for HTTP, API Keys, and various OAuth 2.0 flows.

**Conclusion:**
The feature integration was seamless, respects backward compatibility, and achieves a much cleaner separation of explicit credentials vs. environment variables. Applying the minor cleanup items (particularly removing the dead error variant and preventing hard-errors on OpenAPI mapping) will polish the release.
