# Model Citizen CLI Code Structure and Testing Review

This is a review of the `model-citizen-cli` package based on the best practices outlined in `@biscuit-terminal/docs/cli-testing-best-practices.md`.

## 1. Module Breakdown

### Current State

- **`commands/` module:** You have correctly decoupled the execution logic of different subcommands into their own handlers (`list.rs`, `run.rs`, `download.rs`, etc.). This is a great starting point.
- **`main.rs`:** It acts as a router but is decidedly **not** a thin wrapper. It currently houses the entire `Clap` definition (the `Cli` struct, `Commands` enum, and `SortOrder` enum), shell completions documentation, and the global routing match block. It spans roughly 200 lines.
- **`args.rs`:** Does not exist.
- **`output.rs` (or `format.rs`):** Does not exist. Presentation logic (e.g., configuring and formatting the `Table` utilizing `biscuit_terminal` in `list.rs`) and standard output printing (`println!`) are tightly coupled within the command execution routines.

### Recommendations

- **Create `src/args.rs`:** Extract the `Cli`, `Commands`, and `SortOrder` definitions from `main.rs` and place them entirely within an `args.rs` file. This isolates the CLI interface definition.
- **Thin out `src/main.rs`:** Refactor `main.rs` so it only handles environment initializations (`color_eyre::install()`, `CompleteEnv`) and delegating the parsed arguments from `Cli::parse()` directly to the handlers in `commands.rs`.
- **Create `src/output.rs` or `src/format.rs`:** Extract data structuring and visual formatting (such as table construction and JSON serialization) out of `commands/list.rs` and other handlers. The commands should orchestrate fetching data from the library and return a result that is passed to the output module.

## 2. Library Interaction

### Current State

- The CLI depends on `model-citizen = { path = "../lib" }`, properly demonstrating a clear split between the CLI frontend and the core library.
- Subcommands (like `list.rs`) correctly initialize and orchestrate the `ModelRegistry` scanners rather than reinventing the core scanning logic inside the CLI.

### Recommendations

- Keep up this pattern! Further separate concerns by ensuring that `commands/*.rs` functions return unformatted core data structures that get passed to a unified output formatter, keeping I/O side effects isolated.

## 3. Effective Testing of the CLI Stack

### Current State

- **Unit Testing:** There are several unit tests implemented in `src/commands/run.rs` and `src/commands/download.rs`. However, without an `args.rs`, testing `clap` argument validations securely requires larger e2e runs.
- **Integration Testing:** Although `assert_cmd` and `predicates` are present in `Cargo.toml` under `[dev-dependencies]`, the `tests/` directory is missing entirely. End-to-end command execution is not being verified.
- **Snapshot Testing:** The project lacks `insta`. Tabular and visual outputs are not being snapshot tested, making regressions hard to catch.
- **Environment and TTY Testing:** `expectrl` (or `ptyprocess`) is missing. The CLI includes conditional outputs (`json` flags vs `is_empty()` paths vs full terminal tables) and interactive prompts (using `inquire`), which cannot be tested thoroughly without a pseudo-terminal.
- **Property-based Testing:** `proptest` is not currently used.

### Recommendations

- **Write Integration Tests:** Create a `tests/integration_test.rs` file utilizing `assert_cmd::Command` to spawn the compiled binary and assert on stdout/stderr, successful exit codes, and failure states for missing/incorrect arguments.
- **Implement Snapshot Testing:** Add `insta` to your `[dev-dependencies]`. Pipe the complex output formats (such as the JSON output or the tabular outputs generated by `biscuit_terminal`) into `insta::assert_snapshot!` to prevent structural regressions.
- **Simulate Terminal Sessions:** Add `expectrl` to your `[dev-dependencies]` to test features relying on a true TTY session, especially `inquire` interactive prompts or terminal width boundaries.
- **Unit Test Argument Parsing:** Once `args.rs` is established, add unit tests targeting the `Parser` implementations using arrays of strings. This validates flag overrides, conflicts, and `ValueEnum` mappings without hitting `main`.
