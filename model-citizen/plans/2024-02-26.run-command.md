# Plan: `model run` Subcommand

## Goal

Add `model run` to `model-citizen-cli` so users can launch a downloaded GGUF model in `llama.cpp` server mode and immediately use the browser-based GUI.

## Success Criteria

1. `model run <model>` resolves a local GGUF model and starts `llama-server` with that file.
2. `model run` (no model argument) supports interactive model selection when multiple GGUF models exist.
3. The command can open the browser GUI URL after the server is reachable.
4. Failure paths are explicit (missing `llama-server`, no GGUF models, invalid model selection, port in use).
5. Docs and help output are updated in the same change.

## Current State

- CLI commands currently: `list`, `info`, `search`, `download`, `remove`, `completions`.
- Model discovery already exists via `ModelRegistry` + scanners.
- GGUF candidates exist across:
  - `LlamaCppScanner` (real `.gguf` paths)
  - `LmStudioScanner` (real `.gguf` paths + MLX dirs)
  - `OllamaScanner` (records manifest paths, not directly runnable GGUF files)
- No command currently launches runner processes.

## Proposed UX

### Primary command

```bash
model run [model]
```

### Proposed flags (MVP)

```text
--runner <ollama|lmstudio|llamacpp>   # optional source filter
--host <HOST>                          # default: 127.0.0.1
--port <PORT>                          # default: 8080
--ctx-size <TOKENS>                    # optional pass-through
--threads <N>                          # optional pass-through
--n-gpu-layers <N>                     # optional pass-through
--api-key <KEY>                        # optional pass-through to llama-server
--llama-server-bin <PATH>              # optional binary override
--no-browser                           # disable auto browser open
--dry-run                              # print resolved command, do not execute
```

### Behavior rules

1. If `model` is omitted:
- Prompt user to select from runnable GGUF models.
- If no runnable GGUF exists, exit with a clear error.

2. If `model` is provided and matches multiple models:
- Interactive selection in TTY mode.
- Non-interactive mode returns ambiguity error.

3. Runnable model filter:
- Only include entries with `ModelFormat::Gguf`.
- Require resolved file path to a `.gguf` file (or valid GGUF header if extension is absent).
- Exclude Ollama manifest-only entries unless they resolve to real GGUF files.

4. GUI behavior:
- Start `llama-server`.
- Wait for health endpoint readiness (`/health` preferred, fallback timeout strategy).
- Open browser at `http://<host>:<port>` unless `--no-browser`.

5. Process behavior:
- Child process inherits stdio for live logs.
- Ctrl-C should terminate child cleanly.

## Technical Design

### Command Wiring

- Add `Run` variant to `Commands` enum in `cli/src/main.rs`.
- Add `pub mod run;` to `cli/src/commands/mod.rs`.
- Implement command in new `cli/src/commands/run.rs`.

### Model Resolution

- Reuse current scanner bootstrap pattern (`Config::load`, `ModelRegistry`, enabled scanners).
- Build helper to collect candidate runnable models:
  - optional runner filter
  - GGUF-only filter
  - path validity checks
- Reuse/port selection UI pattern from `info.rs`.

### `llama-server` Command Construction

- Resolve binary in this order:
  1. `--llama-server-bin`
  2. PATH lookup (`llama-server`)
- Build argument list from selected model + flags.
- Add compatibility gate for web UI related flags by inspecting `llama-server --help` (best effort) so behavior works across llama.cpp versions.

### Browser Opening

- Prefer a cross-platform launcher abstraction in `run.rs`.
- If adding dependency (`open` crate), update package dependency docs in the same change.
- Browser launch failure should warn but not kill server.

### Readiness Check

- Poll `http://<host>:<port>/health` for a bounded window (example: up to 15s).
- Continue running even if health probe fails; still print URL for manual access.

Deliverables:

- Filtering logic for runnable GGUF models.

Exit criteria:

Deliverables:

## Test Strategy

### Unit Tests (new in `run.rs`)

1. Command argument builder includes expected flags.
2. Runnable model filter excludes non-GGUF and invalid paths.
3. Model matching behavior for exact/single/multiple/none cases.
4. Binary resolution precedence (`--llama-server-bin` over PATH).

### Integration Tests (CLI)

1. `model run --dry-run ...` prints deterministic command.
2. Ambiguous model selection error in non-interactive mode.
3. Missing llama-server binary returns non-zero with clear message.

### Manual Smoke Tests

1. Start server with explicit model and open browser.
2. Start server with `--no-browser` and verify URL output.
3. Interrupt with Ctrl-C and confirm child server exits.

## Risks and Mitigations

1. Ollama path mismatch (manifest vs GGUF file)
- Mitigation: strict runnable-file validation and explicit warning.

2. llama.cpp CLI option drift across versions
- Mitigation: runtime capability probing (`--help`) + conservative defaults.

3. Port conflicts
- Mitigation: clear bind error surface and suggestion to use `--port`.

4. Browser open behavior varies by OS/session type
- Mitigation: non-fatal browser launch failures and always print URL.

## Out of Scope (MVP)

- Long-running detached/background process manager.
- Managing multiple simultaneously served models.
- Full llama-server flag parity for every advanced option.
- Downloading/building llama.cpp binaries automatically.
