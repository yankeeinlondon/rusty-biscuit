## Findings

1. Medium: the new `--` validator will warn on valid OpenCode prompts that start with `-`, which is the main case the separator was added to support. [`claudine/cli/src/commands/wrap/profile.rs:1966`](/Users/ken/.claudine/worktrees/rusty-biscuit/claudine/claudine/cli/src/commands/wrap/profile.rs:1966) treats every post-`--` arg beginning with `-` as a misplaced flag, but OpenCode intentionally emits `["--", prompt]` and already has a regression test proving bullet-list prompts are valid at [`claudine/cli/src/commands/wrap/profile.rs:2562`](/Users/ken/.claudine/worktrees/rusty-biscuit/claudine/claudine/cli/src/commands/wrap/profile.rs:2562). Because the validator is now called in both the direct-wrap and composition paths at [`mod.rs:1192`](/Users/ken/.claudine/worktrees/rusty-biscuit/claudine/claudine/cli/src/commands/wrap/mod.rs:1192) and [`composition.rs:537`](/Users/ken/.claudine/worktrees/rusty-biscuit/claudine/claudine/cli/src/commands/wrap/composition.rs:537), valid OpenCode runs can produce false warning noise. The validator needs prompt awareness, or at minimum it should ignore the first positional after `--`.

2. Medium: the new OpenCode model-resolution tests are currently broken/flaky because they mutate global process state without serialization. [`claudine/cli/src/commands/wrap/profile.rs:2477`](/Users/ken/.claudine/worktrees/rusty-biscuit/claudine/claudine/cli/src/commands/wrap/profile.rs:2477) and [`claudine/cli/src/commands/wrap/profile.rs:2495`](/Users/ken/.claudine/worktrees/rusty-biscuit/claudine/claudine/cli/src/commands/wrap/profile.rs:2495) both change `HOME` and/or `OPENCODE_MODEL`, but unlike the adjacent `resolve_opencode_model` tests they are not marked `#[serial_test::serial]`. Running `cargo test -p claudine-cli wrap::profile -- --nocapture` in the current worktree finished `80 passed; 2 failed`, with those two tests failing inside `apply_opencode_model_resolution(...)` on the "No model specified!" path. Given the spec’s expectation of strong unit coverage, the targeted suite should be green and deterministic.

3. Low: the regression coverage for the original direct-wrap bug is still much weaker than the composition-path coverage. The new checks in [`claudine/cli/src/commands/wrap/profile.rs:2965`](/Users/ken/.claudine/worktrees/rusty-biscuit/claudine/claudine/cli/src/commands/wrap/profile.rs:2965) only exercise a local simulation helper that re-implements the pipeline rather than calling `run_provider_wrapper_inner`, and the main end-to-end direct-wrap test at [`claudine/cli/tests/wrap_commands.rs:3338`](/Users/ken/.claudine/worktrees/rusty-biscuit/claudine/claudine/cli/tests/wrap_commands.rs:3338) is a dry-run smoke test that never spawns the child or inspects argv order. By contrast, the composition path has a concrete OpenCode argv-order assertion at [`claudine/cli/tests/wrap_commands.rs:2317`](/Users/ken/.claudine/worktrees/rusty-biscuit/claudine/claudine/cli/tests/wrap_commands.rs:2317). I would add direct-wrap integration tests that capture real child argv for OpenCode and Goose and assert:
   `--model`, `--format json`, and YOLO flags all appear before `--`
   exactly one `run` is present for Goose
   an OpenCode prompt beginning with `-` is delivered after `--` with no extra flags after it

## Follow-Up Suggestions

- `mod.rs` and `composition.rs` now share the same effective ordering, but they still duplicate most of the pipeline assembly logic. Extracting a shared builder/helper would reduce drift risk and let the tests validate one implementation instead of a hand-written simulation.
- `apply_opencode_model_resolution` is easier to test if model discovery is injected rather than read from global env/filesystem state. Passing in a resolved config/env snapshot would remove the need for `HOME` mutation in unit tests and let those tests run in parallel.
