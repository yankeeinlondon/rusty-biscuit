## Scan patterns

The six D8 shapes, as scanned for this inventory:

| # | Shape | Command |
|---|---|---|
| A | formatted-report construction | `rg -e 'eyre!\([^)]*\{[a-z_]+[:}]'` |
| B | `to_string()` map_err | `rg -e 'map_err' -A1 \| rg 'to_string\(\)'` |

## Classification key

| Cat | Meaning | Disposition |
|---|---|---|
| **0** | Scan false positive — the interpolated binding is **not** an error (an id, slug, key, or path). | Not a lossy site. Phase 6's Rust-aware guard **must not** flag these; they are the reason a grep guard is insufficient. |

### Pre-existing contract violation found while characterizing

Spec Existing Contract 7 states `err.msg` is "escape-free, single-line,
non-empty, and capped at approximately 240 characters". **It is not single-line
on `HEAD`.** The post-start setup-failure route (a malformed `exit_expressions`
regex, the same case `level2_lifecycle_control.rs:1563` drives) projects:

```text
finalize-msg=protect rule parse error for pattern `[`: regex parse error:
    [
    ^
error: unclosed character class
```

Four lines, reaching the lifecycle `err` global and therefore TTS/messaging.

This is a **pre-existing defect, not a regression this feature introduces**, and
it is recorded here so Phase 5 reads it correctly. Phase 5's L1 task ("every
`err.msg` is escape-free, single-line, non-empty, within the ~240-char cap") is
therefore a **fix**, and its test will fail on `HEAD` before it passes — which is
the correct shape for a regression test per the testing requirements.

**Consequence for the characterization baseline:** the suite must **not** pin
`err.msg` *content*, because that content is documented to change (D10:
"the documented `err.msg` change to the effective diagnostic's concise message
projection"). It pins only what must stay identical — exit code, lifecycle event
order, and emission count.

**Assessment.** Every repo-owned consumer asserts `err.msg` is **non-empty**,
**single-line**, and (for provider failures) **contains the exit code**. None
match on `err.msg` *content* beyond the provider-exit-code substring, which
`harness::failure_message` precedence preserves. The change is therefore safe
for these consumers provided Phase 5 keeps that precedence — which Checkpoint 5
and the `level1_structured_error_message.rs` gate both enforce.
