# PolicyEngine Implementation Plan

Primary inputs:

- `claudine/features/2026-03-30-permissions-engine/spec.md`
- `claudine/features/2026-03-30-permissions-engine/policy-engine-design.md`
- `claudine/features/2026-03-30-permissions-engine/opinion.md`
- provider research in `claudine/docs/research/permissions/`
- current Protect implementation in `claudine/lib/src/services/protect.rs`
- current provider metadata in `claudine/lib/src/events/` and `claudine/lib/src/agents/`

## Summary

`PolicyEngine` should be implemented as a new library-first subsystem at `claudine/lib/src/permissions/` that becomes Claudine's source of truth for provider permission state.

The implementation should be sequenced in layers:

1. scaffold the subsystem and public API
2. land the canonical policy, query, explanation, and mutation-plan models
3. add engine and backend plumbing
4. implement high-value providers first: Claude, Codex, Gemini, OpenCode
5. complete query and mutation support on top of those backends
6. add Qwen and Roo with explicit fidelity warnings
7. add Goose and Kimi as partial or unsupported backends that fail clearly rather than guessing

The most important architectural constraint is to keep `PolicyEngine` separate from `ProtectService`. `PolicyEngine` owns permission truth. Protect remains a runtime decision layer that can consume `PolicyEngine` later.

## Scope

This plan covers:

- a new `claudine::permissions` subsystem
- configured and effective policy resolution
- canonical cross-provider policy modeling
- rich query results with explanation and provenance
- persistent and one-shot mutation planning
- explicit apply support for plans generated by the engine
- layered tests and fixtures

This plan does not require:

- a new CLI command in this phase
- Protect refactoring in the same change set
- full parity across all providers on day one

## Implementation Principles

1. Preserve provider fidelity over false uniformity.
2. Separate configured policy from effective policy everywhere in the API and tests.
3. Return structured answers, not booleans.
4. Keep mutation planning separate from mutation execution.
5. Parse provider-native configs into typed structures before canonicalization.
6. Prefer explicit unsupported or best-effort answers over silent guessing.
7. Keep v1 library-first so future CLI and Protect consumers can build on stable types.

## Deliverables

At the end of the initial rollout, the library should provide:

- `PolicyEngine`
- `ProviderPolicyHandle`
- `PolicyContext`
- `ConfiguredPolicySnapshot`
- `EffectivePolicySnapshot`
- `PolicyQuery`, `QueryResult`, and typed convenience helpers
- `PolicyChange` and `PolicyMutationPlan`
- provider backends for Claude, Codex, Gemini, and OpenCode
- partial backends for Qwen and Roo
- explicit unsupported or degraded behavior for Goose and Kimi

## Phase 1: Scaffolding And Public Surface

Goal: make the crate compile with a stable skeleton and no provider logic yet.

### Tasks

1. Add `pub mod permissions;` to `claudine/lib/src/lib.rs`.
2. Create `permissions/mod.rs` that re-exports the intended public surface.
3. Define the top-level module tree and empty provider modules.
4. Add initial error variants to `ClaudineError` or introduce a dedicated internal `PolicyEngineError` bridged into `ClaudineError`.
5. Add compile-ready placeholder backend registration in `engine.rs`.
6. Add compile-ready placeholder types for:
   - `PolicyContext`
   - `PolicySource`
   - `CanonicalPolicy`
   - `ConfiguredPolicySnapshot`
   - `EffectivePolicySnapshot`
   - `PolicyQuery`
   - `QueryResult`
   - `PolicyChange`
   - `PolicyMutationPlan`

### Acceptance Criteria

- `claudine/lib` compiles with the new module present.
- No existing modules break due to new exports.
- Public names match the design closely enough that downstream code can start targeting them.

## Phase 2: Core Domain Types

Goal: land the data model before any provider-specific logic.

### `context.rs`

Implement:

- `PolicyContext`
- `ProjectTrustContext`
- `TrustSource`
- `CliPolicyInput`

Key decisions:

- `cwd` required
- `repo_root`, `home_dir`, `system_root` optional
- `env` owned for deterministic tests
- trust state represented explicitly as known or unknown

### `canonical.rs`

Implement the canonical model:

- `CanonicalPolicy`
- `PolicyMode`
- `CanonicalPolicyAxes`
- `FilesystemPolicy`
- `CommandPolicy`
- `NetworkPolicy`
- `McpAccessPolicy`
- `AgentPolicy`
- `RuntimePolicy`
- rule structs for paths, commands, domains, MCP, subagents, runtime modes
- `PolicyEffect`
- `PolicyCertainty`
- `MappingFidelity`
- `TernaryState`
- provenance and warning types

### `query.rs`

Implement:

- `PolicyQuery`
- `PathQuery`
- `PathKindHint`
- `CommandQuery`
- `DomainQuery`
- `QueryResult`
- `QueryStability`
- `MatchedRule`
- snapshot helper methods such as `can_read`, `can_write`, `can_execute`

### `explain.rs`

Implement:

- `PolicyExplanation`
- `ExplanationReason`
- optional helper renderers for concise summaries

### `change.rs`

Implement:

- `PolicyChange`
- `PolicyChangeOp`
- `PolicyChangeTarget`
- `PolicyPersistence`
- convenience builders for common operations

### `mutation.rs`

Implement:

- `PolicyMutationPlan`
- `PersistentMutationPlan`
- `OneShotMutationPlan`
- `ConfigEditPlan`
- `AppliedMutationReport`

### `native.rs`

Implement shared native-layer envelope types:

- `PolicySource`
- `PolicySourceKind`
- `NativePolicyLayer`
- `NativeEffectivePolicy`
- `ProviderCliOverrides`

Use provider-specific payload enums or boxed backend-owned structs rather than prematurely forcing one shared native schema.

### `matchers.rs`

Implement shared primitives only:

- path equality and prefix
- workspace and special-path classification helpers
- glob matching
- regex helpers
- command raw or executable matching
- domain exact and wildcard matching

Do not centralize provider precedence here. Backends own precedence.

### Acceptance Criteria

- All major types compile and have basic constructors or helpers.
- Query and mutation types are usable in tests without any provider backend loaded.
- Types derive only what is actually needed; avoid overcommitting to `Serialize` or `Deserialize` unless immediate tests or reporting need it.

## Phase 3: Engine And Backend Plumbing

Goal: make snapshots and backend dispatch work end-to-end.

### `backend.rs`

Define `ProviderPolicyBackend` with responsibilities from the design:

- discover sources
- load native layers
- parse CLI overrides
- compose native policy
- canonicalize
- plan change

Also add lightweight capability metadata so callers and tests can inspect support level per provider and axis.

### `engine.rs`

Implement:

- `PolicyEngine::new()`
- backend registry keyed by `Provider`
- `provider(&self, provider: Provider) -> ProviderPolicyHandle`
- `configured(...)`
- `effective(...)`
- provider handle convenience methods
- `plan_change(...)`

### Snapshot Construction

Configured pipeline:

1. discover sources
2. load native layers
3. compose without CLI overrides
4. canonicalize
5. return `ConfiguredPolicySnapshot`

Effective pipeline:

1. run configured steps
2. parse CLI overrides
3. compose with CLI overrides
4. canonicalize
5. return `EffectivePolicySnapshot`

### Caching

Do not build a sophisticated cache in v1. Add only internal seams so an in-memory cache can be layered later.

### Acceptance Criteria

- Engine returns clean backend-unavailable errors for unsupported providers.
- One fake or stub backend can drive configured, effective, query, and plan-change paths in unit tests.
- Snapshot helper methods delegate through the canonical query layer rather than duplicating logic.

## Phase 4: Provider Discovery And Native Modeling For High-Value Providers

Goal: implement the four most valuable providers first.

## Phase 4A: Claude Backend

Target fidelity: high.

### Tasks

1. Discover Claude config layers:
   - user config
   - repo config where relevant
   - managed or local overrides if present in research
2. Model Claude-native permission state in typed structs.
3. Parse sandbox, permission arrays, domain controls, MCP-related controls, and subagent-related permissions if present.
4. Parse CLI/runtime override inputs.
5. Compose configured and effective native policy using Claude precedence.
6. Canonicalize with provenance retained per native rule.
7. Implement mutation planning for:
   - read and write path permissions
   - command approval rules
   - network or domain permissions where supported
   - approval and sandbox mode changes
8. Support one-shot CLI mapping when Claude can express the change via launch flags.

### Tests

- fixture tests for layer precedence
- path read and write queries
- sandbox and bypass behavior
- mutation plan preview tests

## Phase 4B: Codex Backend

Target fidelity: medium-high.

### Tasks

1. Discover Codex config layers:
   - user `config.toml`
   - repo config if present
   - enterprise requirements if readable
2. Model Codex native concepts separately:
   - sandbox mode
   - approval policy
   - command rules
   - writable roots
   - trust-sensitive repo config
   - MCP controls
3. Parse effective CLI overrides such as:
   - `--sandbox`
   - `--ask-for-approval`
   - `--dangerously-bypass-approvals-and-sandbox`
   - `--full-auto`
4. Compose native policy with explicit warnings where multiple enforcement axes contribute to one canonical answer.
5. Canonicalize without collapsing shell sandbox and MCP policy into one axis.
6. Implement mutation planning for:
   - writable roots
   - command rules
   - sandbox mode
   - approval policy
7. Produce one-shot argv when changes can be expressed through launch flags instead of file edits.

### Tests

- workspace vs external write queries
- protected path behavior
- trust-state ambiguous behavior
- `yolo` and `full-auto` effective overrides
- command-rule planning and explanation snapshots

## Phase 4C: Gemini Backend

Target fidelity: high.

### Tasks

1. Discover settings and policy TOML layers in correct precedence order.
2. Model native rule files, approval mode, sandbox state, and permanent tool approval behavior.
3. Parse CLI overrides including `--approval-mode`, deprecated `--yolo`, and `--sandbox`.
4. Compose native policy using Gemini precedence:
   - CLI
   - env
   - project or user config
   - policy rules
5. Canonicalize with explicit rule provenance.
6. Implement mutation planning for:
   - approval mode
   - sandbox mode
   - rule-level allow or deny operations
   - MCP and domain cases where policy engine supports them

### Tests

- mode-specific rule behavior
- sandbox effect on filesystem and network answers
- permanent approvals vs policy rules
- one-shot CLI mapping

## Phase 4D: OpenCode Backend

Target fidelity: high.

### Tasks

1. Discover OpenCode config and plugin-permission sources.
2. Model explicit ask, allow, and deny permission structures.
3. Parse CLI overrides and session-only permission changes if available.
4. Compose the effective permission model.
5. Canonicalize with warnings that OpenCode permissions are guardrails, not a hard OS boundary.
6. Implement mutation planning for:
   - path and command permissions
   - MCP permissions
   - domain or network permissions if supported

### Tests

- allow vs ask vs deny precedence
- persistent config edits
- advisory warnings in explanation payloads

### Exit Criteria For Phase 4

- Claude, Codex, Gemini, and OpenCode can all produce configured and effective snapshots.
- Each of the four supports at least:
   - path read query
   - path write query
   - command query
   - mutation planning for one filesystem or mode-changing operation

## Phase 5: Canonical Query Completeness

Goal: make the query surface complete and consistent across implemented providers.

### Tasks

1. Finalize path-classification logic:
   - workspace
   - outside workspace
   - home
   - temp
   - provider config
   - system path
2. Finalize command tokenization and executable extraction.
3. Implement network and domain queries.
4. Implement MCP server and tool queries.
5. Implement subagent and mode-switch queries.
6. Implement `can_modify_own_config`.
7. Ensure all query helpers route through one generic `query(&PolicyQuery)` implementation.
8. Add explanation summaries and matched-rule evidence consistently across all query types.

### Acceptance Criteria

- Snapshot helper methods all exist on both configured and effective snapshots.
- Query results always include effect or an explicit unknown state with reasons.
- Stability correctly distinguishes configured ambiguity from effective certainty.

## Phase 6: Mutation Planning And Apply

Goal: make policy changes inspectable and safely executable.

### Tasks

1. Finalize `PolicyChange` operation coverage for recurring axes.
2. Implement provider-specific persistent targeting rules.
3. Resolve `PolicyChangeTarget::Auto` semantics:
   - prefer repo config when current policy source is repo scope and trust is established
   - otherwise prefer user config
4. Build `ConfigEditPlan` preview generation:
   - before preview
   - after preview
   - source description
5. Implement `PolicyMutationPlan::apply()` only for engine-generated plans.
6. Make apply atomic where practical, following existing config-writing patterns in `claudine/lib/src/config/`.
7. Emit degraded fidelity when a requested operation must be broadened or narrowed.

### Acceptance Criteria

- Every supported provider can produce a structured plan even when apply is unsupported.
- Unsupported mutations fail as structured results, not silent no-ops.
- Apply path is covered by tempdir-based round-trip tests.

## Phase 7: Qwen And Roo

Goal: extend practical coverage while preserving honesty about fidelity.

## Phase 7A: Qwen

Target fidelity: medium-high.

### Tasks

1. Discover settings and policy sources.
2. Model approval-mode defaults, allow and deny tool rules, sandbox state, and trusted MCP server behavior.
3. Parse CLI overrides like `--approval-mode`, `--yolo`, and `--sandbox`.
4. Canonicalize with explicit warnings for unstable or evolving behavior.
5. Implement mutation planning where the mapping is stable enough.

## Phase 7B: Roo

Target fidelity: medium.

### Tasks

1. Discover mode, approval, MCP, and protected-file sources.
2. Model native layers separately:
   - mode tool surface
   - auto-approval categories
   - protected files
   - workspace boundary
   - MCP approvals
3. Parse runtime overrides like `--require-approval` and `--mode`.
4. Canonicalize with explanations that multiple native layers contribute to one answer.
5. Implement mutation planning only where the source model is stable and edit targets are clear.

### Acceptance Criteria

- Qwen and Roo backends produce meaningful query answers with fidelity metadata.
- Unsupported operations return `Unknown` or unsupported-mutation warnings instead of fabricated certainty.

## Phase 8: Goose And Kimi

Goal: provide honest partial support rather than leaving gaps in the registry.

### Tasks

1. Implement backend stubs that discover obvious config where it exists.
2. Support only clear query surfaces backed by documented native behavior.
3. Return backend-specific warnings for incomplete or non-authoritative axes.
4. Delay broad mutation support until stronger research exists.

### Acceptance Criteria

- Engine can answer whether support is partial.
- Consumers get structured warnings instead of missing-backend failures.

## Testing Plan

Use `just test` from the repository root or `claudine/` package area once tests are added.

### Test Layers

1. Backend fixture tests
   - source discovery order
   - native parsing
   - CLI override parsing
   - composition precedence
2. Canonicalization tests
   - effect mapping
   - provenance
   - fidelity
   - warning emission
3. Query contract tests
   - read path in workspace
   - write external path
   - command requiring approval
   - denied MCP tool
   - network or domain denial
4. Mutation planning tests
   - correct file targeting
   - one-shot argv correctness
   - degraded mapping surfaced explicitly
5. Round-trip apply tests
   - load fixture
   - plan mutation
   - apply
   - reload
   - verify changed query outcome
6. Explanation snapshot tests
   - summary text
   - reason list
   - source IDs and native references

### Fixture Strategy

Create provider-specific fixture directories under `claudine/lib/tests/fixtures/permissions/` or provider-local test modules, depending on the existing project test style.

Fixtures should include:

- user-only config
- repo-only config
- combined layered config
- trust-known and trust-unknown cases
- CLI override cases
- expected canonical outputs and query expectations

## Integration Readiness After Initial Rollout

Once Phases 1 through 6 are complete, the subsystem should be ready for:

- future `claudine permissions ...` CLI commands
- Protect consuming effective policy snapshots
- reporting or audit views that need permission explanations
- wrapper-level checks before launching a provider CLI

Protect integration should be a follow-on change, not bundled into the initial `PolicyEngine` landing.

## Key Open Decisions To Resolve Early

Resolve these before deep provider work begins:

1. `ClaudineError` integration strategy
   - dedicated nested error type converted into `ClaudineError`
   - or direct top-level variants
2. Test fixture location
   - unit-style in module files
   - or integration fixtures under `claudine/lib/tests`
3. Native policy representation shape
   - enum wrapper over provider-native structs
   - or backend-owned trait objects hidden behind `NativeEffectivePolicy`
4. Mutation apply guardrails
   - whether apply is available in the initial provider rollout or one release later
5. Trust discovery ownership
   - how much lives in backend discovery versus caller-supplied `PolicyContext`

## Suggested Execution Order

1. Phase 1 and Phase 2 in one change set.
2. Phase 3 with one fake backend and full unit coverage.
3. Phase 4A through 4D provider-by-provider, each with fixture tests.
4. Phase 5 query completeness once the first four providers are stable.
5. Phase 6 mutation planning and apply.
6. Phase 7 and Phase 8 as follow-on provider expansion.

This keeps the subsystem shippable at multiple points:

- after Phase 3 as an internal scaffold
- after Phase 4 as a useful query engine for four providers
- after Phase 6 as a full v1 policy engine

## Definition Of Done For `PolicyEngine` V1

`PolicyEngine` v1 is done when all of the following are true:

- the new `claudine::permissions` module is exported and documented enough for internal consumers
- configured and effective snapshots exist and are tested
- Claude, Codex, Gemini, and OpenCode support real configured and effective queries
- the canonical policy model covers filesystem, commands, network, MCP, agents, and runtime axes
- query results include explanation, provenance, certainty, and stability
- mutation planning works for the high-value providers
- apply is either implemented and tested for supported plans or explicitly deferred behind a documented boundary
- Qwen and Roo return meaningful partial support with fidelity warnings
- Goose and Kimi fail clearly with structured limitations rather than pretending support
