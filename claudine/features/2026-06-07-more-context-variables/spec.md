# Claudine Context Catalogs

## Summary

`claudine context` exposes Darkmatter's runtime context variables, read-only
expression functions, and mutating side-effect capabilities as human-readable
terminal reports.

This feature updates all context reports to use typed runtime metadata owned by
Darkmatter, incorporates the context variables and functions introduced by
Darkmatter's `more-context-variables` feature, adds the side-effect capability
report, and makes the reports follow one consistent terminal layout contract.

The reports describe Darkmatter's runtime surface. They are not generated by
parsing Darkmatter's Markdown documentation.

## Goals

- Display every context variable exposed by Darkmatter.
- Display every expression function exposed by Darkmatter.
- Display every side-effect capability exposed by Darkmatter.
- Keep catalog data synchronized with the runtime implementation through one
  typed source of truth.
- Produce readable output from narrow terminals through terminals wider than
  the report's maximum width.
- Render inline code and unordered lists consistently using
  `biscuit-terminal`.
- Preserve the distinction between read-only expression functions and
  externally mutating side effects.

## Scope

### In Scope

- The output of:
  - `claudine context`
  - `claudine context --values`
  - `claudine context --expressions`
  - `claudine context --side-effects`
- Public, typed Darkmatter catalog descriptors required by those reports.
- Removal of Markdown parsing as Claudine's catalog source.
- Catalog completeness and drift tests.
- Table sizing, inline-code styling, list rendering, report wording, and
  related terminal tests.
- Documentation updates required to describe changed public CLI behavior or a
  new public Darkmatter metadata API.

### Out of Scope

- Adding new context variables, expression functions, or side effects beyond
  those implemented by Darkmatter.
- Invoking a side effect from `claudine context`.
- Integrating side effects into Claudine lifecycle actions.
- Determining whether a side effect is currently authorized, configured, or
  invocable.
- Changing Darkmatter's mutation-root, network allowlist, auto-rehash, or other
  safety policies.
- Adding full-file overwrite or deletion side effects.
- Changing expression parsing, evaluation, or composition semantics.
- Adding machine-readable output such as `--json`.
- Redesigning unrelated Claudine reports or terminal components.

## Source of Truth

Darkmatter runtime metadata is authoritative for all three catalogs:

- context variables
- expression functions
- side-effect capabilities

Darkmatter must expose public typed descriptors sufficient for Claudine to
render each catalog without parsing prose. A descriptor must provide the
semantic data needed by its report, including:

- canonical name
- category or section
- display type or callable signature, as applicable
- description
- safety constraints, when applicable
- stable ordering information, or an API that returns entries in display order

The descriptors must represent the same runtime entries accepted or produced
by Darkmatter. Adding, removing, or renaming a runtime catalog entry must cause
a completeness test to fail until its descriptor is updated.

Darkmatter's Markdown documentation remains explanatory documentation. Its
headings, tables, lists, and prose are not an API and must not determine
Claudine output. Claudine must not retain embedded documentation parsers or
hand-maintained copies of the catalogs.

Display-only transformations, such as prefixing a context variable with
`ctx.`, coloring a type, or grouping descriptors into tables, belong to
Claudine.

## Command Behavior

`claudine context` accepts exactly one of `--values`, `--expressions`, or
`--side-effects`. The flags are mutually exclusive, and invalid combinations
must fail validation before rendering begins.

All reports write their primary report content through Claudine's established
data-output path. Informational usage hints continue to use the established
message-output path.

### `claudine context`

The default report displays the complete context-variable catalog grouped by
the categories and subsections supplied by Darkmatter metadata.

Each section contains a table with these columns:

| Column | Content |
| --- | --- |
| `Property` | The canonical variable name prefixed with `ctx.` |
| `Type` | The descriptor's display type |
| `Description` | The descriptor's description |

The report must include all newly introduced variables, including the repo
scope, dependency, UTC time, document, OS, and hardware variables represented
by the Darkmatter catalog.

The report does not capture live host values. Its footer may direct the user to
`--values`, `--expressions`, and `--side-effects`, but must describe side
effects as Darkmatter capabilities rather than as automatically available
Claudine operations.

### `claudine context --values`

The values report uses the same sections, ordering, `Property` column, `Type`
column, and global column widths as the default report. It replaces
`Description` with `Value`.

Values are captured using Darkmatter's runtime context API. The property names
used for lookup must come from the same descriptors used to render the rows.
Every catalog entry must produce one row even when its captured value is null
or unavailable.

Values use the established plain terminal representation:

- strings render as their string value
- booleans and numbers render textually
- arrays render as a comma-separated sequence
- objects render as a compact serialized object
- null or unavailable values render as a visibly dimmed `null`

This command may perform the host and repository discovery required to capture
the complete context. It must not perform duplicate capture work per section or
per row.

### `claudine context --expressions`

The expression report displays the expression-language overview and the
complete typed expression-function catalog.

The function tables contain:

| Column | Content |
| --- | --- |
| `Function` | Canonical function signature |
| `Description` | Function description |

Expression functions must come from Darkmatter metadata. Explanatory sections
about operators, precedence, truthiness, variable access, interpolation, and
condition behavior may remain Claudine-owned presentation content, but must
not be parsed from Markdown as a substitute for typed function metadata.

The "Interpolation vs. Condition Mode" introduction must read:

> The parser supports two modes with different operator behavior:

The mode table or list must then explain the behavior and consequences without
an immediately adjacent second introductory line ending in a colon.

### `claudine context --side-effects`

The side-effects report displays Darkmatter's complete side-effect capability
catalog. It is independent of active Claudine authorization, policy,
configuration, lifecycle integration, or current invocability.

The report title and introductory prose must explicitly use the term
"capabilities." The report must not include an availability/status column and
must not claim that any listed capability is currently enabled.

The report groups capabilities using Darkmatter metadata and displays:

| Column | Content |
| --- | --- |
| `Capability` | Canonical side-effect signature |
| `Description` | Behavior and return-value summary |
| `Safety` | Applicable mutation, network, re-hash, or other enforced constraint |

The report must communicate these catalog-wide constraints:

- the report is documentation only and does not invoke side effects
- only an external orchestrator invokes side effects
- filesystem writes are restricted to the configured mutation root
- network operations are restricted by the host allowlist, which is deny-all
  by default
- Markdown mutations honor Darkmatter's auto-rehash behavior
- capability catalog membership does not imply authorization or availability

The report must include every side effect represented by the authoritative
Darkmatter metadata, including all supported signatures of overloaded
capabilities.

## Shared Rendering Requirements

### Table Width

Every table:

- fills the available terminal width
- has a 1ch left margin and a 1ch right margin
- has a total maximum rendered width of 140ch
- counts both margins, borders, separators, and table content within that
  140ch maximum

Therefore, at terminal widths of at least 140ch, no rendered table row may
exceed 140 visible terminal cells. At widths below 140ch, the table uses the
available terminal width without intentional horizontal overflow.

Width calculations must use visible terminal cells rather than byte length or
raw styled-string length.

### Context Columns

For the default and values reports, Claudine computes intrinsic widths across
the complete visible context catalog before rendering any section:

- `Property` width is the maximum intrinsic visible width of the `Property`
  header and every displayed property.
- `Type` width is the maximum intrinsic visible width of the `Type` header and
  every displayed type.
- Those two computed widths are reused for every context section table.
- `Property` and `Type` are independently computed and are not required to be
  equal to one another.
- The final column receives the remaining width and wraps as needed.

### Function and Capability Columns

The first column of an expression-function or side-effect-capability table has
an intrinsic width capped at 40ch. The remaining width is allocated to the
descriptive columns.

Long signatures wrap according to established `Table` behavior; they must not
force the table beyond its width contract.

### Narrow Terminals

At widths too narrow to preserve all intrinsic column widths, reports rely on
the established `biscuit-terminal` table behavior for constrained layouts:

- cell content wraps rather than causing deliberate horizontal overflow
- configured margins remain 1ch where the component can represent them
- descriptive content remains present
- no Claudine-specific truncation marker or alternate narrow layout is
  introduced by this feature

The implementation must not panic for a positive terminal width supported by
the terminal and table components.

### Inline Code

Backtick-delimited inline code is a presentation hint. The literal backticks
must not appear in styled terminal output.

The enclosed content must render through `Prose` using inverse styling in
styled output, equivalent to:

```text
<inverse>content</inverse>
```

This applies to prose, list items, table cells, function signatures, variable
references, operators, and examples in all four reports. Multiple inline-code
spans in one string must be handled independently. Text outside the spans must
retain its surrounding prose styling.

In plain output, `NO_COLOR`, or `--plain` mode, inline code must render with
visible backticks. Unmatched backticks must not cause a panic. Until a product
decision is made for malformed metadata, they may render as literal text.

### Unordered Lists

Every unordered list in these reports must:

- use `biscuit_terminal::components::list::UnorderedList`
- use the `- ` marker
- provide each item as `Prose`
- preserve the component's hanging indentation for wrapped continuation lines
- reserve a 1ch right margin for list content
- have exactly one blank line before and exactly one blank line after the list

The renderer must not manually prefix list items with `-`, `*`, `•`, or any
other marker.

## Failure Behavior

- Catalog rendering must not read or parse external or embedded Markdown
  documentation at runtime.
- A catalog descriptor that cannot be represented by the report is a
  development-time contract failure and must be covered by tests; it must not
  be silently omitted.
- `--values` follows Darkmatter's context-capture semantics. A missing
  individual value renders as `null` and does not remove its catalog row.
- Rendering malformed inline-code markup must not panic.
- Plain output preserves visible inline-code backticks.
- Terminal rendering failures continue to follow the error and exit behavior
  of Claudine's existing output pipeline; this feature does not introduce a
  separate fallback renderer.
- `--side-effects` performs no capability execution, policy probe, filesystem
  mutation, or network request.

## Compatibility Expectations

- The command name and report selections remain available.
- Human-readable compatibility is semantic only: canonical names and report
  selection are stable, while layout, prose, styling, and wording may change.
- Canonical Darkmatter names and signatures must be displayed without
  Claudine-specific renaming.
- Catalog ordering must be deterministic.
- No new machine-readable compatibility contract is created by this feature.

## Performance

No numeric latency budget is established by the available requirements.
Implementation and review must nevertheless preserve these constraints:

- default, expression, and side-effect reports consume static typed metadata
  and must not capture runtime context
- `--side-effects` must not instantiate or probe an effect engine merely to
  render metadata
- `--values` captures runtime context once per command invocation
- report rendering must not perform per-entry filesystem, repository,
  hardware, or network discovery
- catalog traversal and intrinsic-width calculation should be linear in the
  number and text size of descriptors

Existing Darkmatter context benchmarks must remain free of material regression.
If this change alters a benchmarked capture path, the implementation must
update or add regression coverage rather than relaxing the benchmark without
explanation.

## Implementation Guidance

The requirements above define behavior. The following guidance is
non-normative unless needed to satisfy them:

- Prefer immutable descriptor slices or equivalent typed catalog APIs in
  Darkmatter.
- Keep metadata adjacent to runtime registration or derive both from one
  declaration so parity is mechanically enforceable.
- Use `biscuit-terminal` `Table`, `TableColumn`, `Prose`, and `UnorderedList`
  rather than manual spacing or raw terminal escape sequences.
- Use ANSI-aware visible-width utilities for intrinsic measurements and test
  assertions.
- A shared report-layout helper is appropriate if it enforces the same
  140ch-inclusive width and margin contract across all tables.

## Acceptance Criteria

1. Claudine obtains all three catalogs exclusively from public typed
   Darkmatter metadata.
2. No Claudine context report parses `context-variables.md`,
   `darkmatter-expressions.md`, `side-effects.md`, or another Markdown document
   to discover catalog entries.
3. The default and values reports contain exactly one row for every
   Darkmatter context-variable descriptor.
4. The expression function report contains every Darkmatter
   expression-function descriptor.
5. The side-effects report contains every Darkmatter side-effect descriptor
   and supported signature, labels them as capabilities, explains safety
   constraints, and presents no availability status.
6. Context `Property` and `Type` widths are independently computed across the
   complete catalog and reused by every context section.
7. Every table uses the available width up to 140 visible cells total,
   including both 1ch margins.
8. Expression function and side-effect capability first columns never exceed
   40ch before wrapping.
9. Backtick-delimited inline code renders with inverse styling in styled
   output and visible backticks in plain output.
10. Unordered lists use `UnorderedList`, `- `, `Prose`, hanging indentation, a
    1ch right margin, and exactly one surrounding blank line.
11. The "Interpolation vs. Condition Mode" introduction uses the corrected
    wording and does not contain consecutive introductory lines ending in
    colons.
12. `--values` captures context once and renders null or unavailable entries
    without dropping rows.
13. `--side-effects` performs no side effects or availability probes.
14. All affected tests and repository-prescribed Claudine checks pass.

## Required Tests

### Catalog Contract Tests

- Assert exact parity between runtime context variables and context
  descriptors.
- Assert exact parity between callable expression functions and expression
  descriptors.
- Assert exact parity between dispatchable side effects, overloads, and
  side-effect descriptors.
- Assert deterministic category and entry ordering.
- Assert that no report depends on Markdown headings, tables, or lists.
- Assert `clap` rejects combined `--values`, `--expressions`, and
  `--side-effects` invocations.

### Rendering Tests

- Render every report below, at, and above the 140ch cap.
- Assert visible row width never exceeds the applicable terminal width or
  140ch, whichever is smaller.
- Assert both 1ch table margins are included in the 140ch limit.
- Assert every context section uses the same computed `Property` and `Type`
  widths.
- Assert context `Property` and `Type` widths are not forced to be equal.
- Assert function and capability first-column widths are at most 40ch.
- Assert narrow output wraps without panic and retains descriptive content.
- Assert inline code emits inverse styling in styled output, restores visible
  backticks in plain output, and renders correctly in prose, list items, and
  table cells.
- Assert unordered lists use `- `, hanging indentation, a 1ch right margin,
  and exactly one blank line on each side.
- Assert the corrected interpolation/condition wording.

### Command Tests

- Verify each report selection renders its intended catalog.
- Verify `--values` performs one capture and includes every context row.
- Verify the side-effects report describes capability rather than availability
  and performs no mutation or network access.
- Verify footer hints do not claim that side effects are enabled, exempt from
  allowlisting, or provided without configuration.

## Definition of Done

The feature is complete when:

- the authoritative typed metadata APIs exist in Darkmatter
- Claudine's four context reports satisfy this specification using those APIs
- the Markdown catalog parsers and side-effects placeholder are removed
- catalog parity, layout, inline-code, list, narrow-terminal, command, and
  no-side-effect tests pass
- relevant public documentation is updated for the metadata API and CLI
  behavior
- no unresolved open question has been decided implicitly in code
- repository-prescribed checks for the changed Darkmatter and Claudine crates
  pass
