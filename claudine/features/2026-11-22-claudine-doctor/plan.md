# Claudine doctor implementation plan

## Summary and Definition of Done

Implement `claudine doctor [--fix] [--json]` as a passive, non-interactive route that works with missing or broken setup. A single invocation reports seven ordered checks for the captured home and launch repository. Both output modes use the same redacted rows. Help and completion advertise the command. Report exit codes are 0 for a final report without errors and 1 for a report with errors. Usage errors exit 2.

An inspection leaves the filesystem as found and performs no network requests or speech synthesis. Repairs are limited to the Claudine host registration and eligible Darkmatter permissions handoffs. They share the production publisher and configuration writer, preserve unrelated configuration and comments, report partial changes, and converge to a no-op on a second successful run. All features ship together after `2026-11-22-host-registration-v2`. Completion includes L1 proof through the public diagnostics and the shipped CLI, updated reference and topic docs, and the published caller skill.

## Phase 1 — Passive configuration and report foundations

### Necessary Rules

1. **Use the existing startup snapshot and an early return.** Add `Commands::Doctor(DoctorArgs)` in `claudine/cli/src/args.rs`. In `main.rs::dispatch`, handle it after ordinary launch directory capture, `request::initialize`, and `log::set_plain`, before telemetry and anywhere the route could call `request::darkmatter_config`, `ensure_config_exists`, or a setup or publication routine. Pass the returned `RequestSnapshot` into `claudine::doctor::run`. Use `composition::capture_file_resolution_context` once, including its Sniff repository discovery and Claudine magic roots. Run context-independent checks even when context construction fails and issue a `config` error. This follows `request.rs::initialize` and `composition/resolve.rs::capture_file_resolution_context`; the normal config accessor uses `MigrateLegacy`. Root help and completion retain their existing early routes.
2. **Keep the check registry and all finding policy in the library.** Expose `claudine::doctor::run(snapshot: &RequestSnapshot, fix: bool) -> Vec<DoctorRow>` and public `DoctorRow`/`Severity` in `claudine/lib/src/doctor/mod.rs`. Keep one static ordered list of descriptors for `config`, `registration`, `darkmatter-permissions`, `repo-config`, `stray-config-keys`, `tts`, `path`, with IDs, titles, check callbacks, and optional repair callbacks. Keep the CLI adapter in `commands/doctor.rs`. Use private injected passive probes for deterministic L1 tests. Collect reusable observations once for the initial pass. Run repairs in registry order from fresh on-disk evidence for each repair, allowing the registration edit to precede a permissions edit of the same file. Re-read each attempted row and its prerequisites after the attempt. Keep a failed attempt at error with the reason and recorded changes even when the new disk state would otherwise pass.
3. **Aggregate by finding impact.** Use `error > warn > info > ok` and fixed scope order (user before repository) and deterministic path order for multiple paths. A scope skipped for unavailable prerequisites is informational. A row with no problems and an applicable successful check is OK, with exceptions explicitly specified for informational observations. Derive `fixable` from at least one eligible remaining repair in the reported row, independent of the flag; successful repairs clear it for resolved findings. A failed operation can remain fixable when a fresh read shows an eligible retry. Concatenate per-file details and remedies with newlines. Emit no progress on stdout. The command and report section of the spec defines the stable JSON fields and exit policy.
4. **Report safe diagnostic facts.** Build findings from typed categories, file paths from the inspection or publication inventory, schema locations, and fixed remedies. Display unknown key names with their locations as the explicit exception for user-authored text. Use canonical provider labels and named operations with I/O kind or status. Drop raw YAML/serde/regex errors, reference strings, arbitrary map-key segments of other diagnostic pointers, shell output, and writer refusal text from output and logs. Normalize control characters in dynamic display text and escape Prose markup. For a permissions target, report the declaring file and setting, keeping its authored and resolved reference private. `config/load.rs::describe`, Darkmatter `config/load/entries.rs`, and `ConfigWriteError::ValidationFailed` can all embed authored values. For partial writes use the writer's structured published-path list.
5. **Observe the four working files and distinguish absence from failure.** Use the paths produced by `config/setup.rs::claudine_config_path` and Darkmatter `config/init.rs::config_path`. Use the setup comparison based on `PathIdentity` and `canonicalize_simplified` for each user/repository pair. Report a repository alias as present and already judged in user scope. Skip the repository permissions pair with an explanation when a repository file aliases its user counterpart to prevent editing a user file as a repository file. Report an unreadable existing repo Claudine file as present with validation failure, a dangling config symlink as unreadable, and other I/O failures with the affected path. Missing repo files stay optional. Only a missing user YAML file with a neighboring `config.json` gets the legacy migration remedy; document the existing normal startup conversion or setup flow. Never open or convert the legacy JSON in doctor. `dispatch/loader.rs::load_claudine_config_with_notices` already suppresses duplicate validation, and `config/json_conversion.rs::prepare_scope` is the writing migration boundary.
6. **Reuse semantic checks without migration or dispatch.** Load Claudine through `config::load::read_document` and `ClaudineConfig::from_effective` / `RepoOverrideConfig::from_effective`. Apply `merge_repo_override` and `ClaudineConfig::validate` to the effective pair. Apply user validation alone when the repo file is absent, aliased, or unusable. Share the passive binding checks in `dispatch/loader.rs` for regex action mappers that `compile_canonical_runtime` rejects. Matchers that the existing compiler tolerates stay tolerated. Report a semantic failure with the responsible file, or name both files for an interaction such as a repo `active_messenger` selection with no matching user route. Assess user-only semantics separately for TTS and existing-file handoff validation, without duplicating user-only problems in `config` when the valid merged pair supersedes them. Reuse the normal load's merge and validation ordering in `load_claudine_config_with_notices`. Compile only passive runtime validators. Leave lifecycle dispatch, configuration rendering, and committed repository policy outside the diagnostic path.
7. **Share Darkmatter's passive one-file validation.** Expose `darkmatter::config::load::inspect_working_file(context, scope) -> Result<ConfigFile, ConfigError>`, using `read_worktree` and `observe_file` with `User` or `RepositoryWorktree`. Add crate-private `read_working_file(context, scope) -> Result<(Option<Vec<u8>>, ConfigFile), ConfigError>`; `init::observe` retains the bytes for the writer, and `inspect_working_file` projects the file. Surface whole-file failure, inline permission validation errors, and all `ConfigFile::registration_findings` under `config`. Report reference syntax errors under `config` and `darkmatter-permissions` when the pair exists. Failed resolution of an otherwise valid permissions reference belongs to the permissions row. The inspect API never selects committed policy, creates defaults on disk, or reads installed registrations. `load.rs::Observe::file` stores field-specific problems inside a successful result and `init::observe` already uses `follow_on_disk` for setup's reference state. Keep the user registration repair independent of a broken but syntactically valid permission reference.
8. **Carry structured unknown-key findings and key locations.** Add a `ConfigProblemKind` field to Claudine's `ConfigProblem` constructors in `config/load.rs`, with `UnknownKey`, `Syntax`, and `InvalidSetting`. Extract each key using `ValidationProblemCode::UnknownKey` and `offending_properties` (singular fallback), and use `LoadedYaml::byte_range` with a single-key unknown problem so `PositionMap` selects the key token. Sort and deduplicate by file and key pointer, retaining the existing flat-form migration diagnostic in `config` and its genuine unknown keys for `stray-config-keys`. Keep both kinds of evidence in the passive loader and keep normal error formatting for established callers. A YAML/document-level failure names the uninspectable file in the stray row. Unknown Claudine keys keep `config` at error with a pointer to the stray row and appear by name only there. Darkmatter keys belong to `config`. Imported permissions keys use the Claudine validator when present in a Claudine file.
9. **Recover nested union key diagnostics in the existing validator.** Extend `simplified-schema/lib/src/validate.rs::build_problems` at the `AnyOf` branch. Recurse through same-path unions, exclude arms that reject the instance type at that node, and retain a same-node unknown key only when every remaining arm rejects that key at that node. A structurally applicable arm with no such rejection contributes an empty set. Combine the resulting structured problems with the existing deeper/nullable diagnostics and preserve the generic union failure when neither yields a problem. This exposes common unknown keys without labeling a known key from a different arm as stray. The current drill-down drops same-path `AdditionalProperties` because its instance path names the parent. Prove the change through public SimplifiedSchema validation and exercise the Claudine `tts` mapping, imported permissions mapping, and a keyed action or route union with an extra key. Keep legitimately open mappings and admitted keys governed by the shipped schemas.
10. **Treat registration inspection as a byte comparison plus targeted profile validation.** Use the v2 `RegistrationInventory` from `claudine/lib/src/composition/registration.rs` for the expected manifest and members. Compare exact byte digests using `biscuit_hash::blake3_hash_bytes`; the hidden CLI's XXH64 is its listing fingerprint. Probe the fixed manifest and expected members without following links inside the managed tree. Inspect extras recursively and both known legacy paths with no-follow metadata. Missing, unreadable, or nonregular expected paths and a missing user entry are errors. An unreadable directory scan, obstructing link, or other special file in the removal set is an error with a manual remedy. Changed artifact bytes, extra removable files/directories, and unobstructed legacy paths are warnings. A changed manifest also goes through Darkmatter's v2 loader against only the fixed expected manifest, using `load_entries` with `md_owned_names` and requiring the Claudine profile. Loader refusal is an error. An unchanged manifest with only changed present artifacts retains the spec's warning classification for those artifacts and the detail explains that v2 will refuse mismatched digests. Use `manifest_identity` against user `ConfigFile::registrations()` anchored to the declaring file; an equivalent entry suffices. Treat other hosts' targets and repository `register` entries as outside this repair. Where a valid user Darkmatter file is unavailable, still report managed disk findings where home is available and name why entry verification is blocked. Use an informational row when home is unavailable and there is no registration evidence to inspect. Use an error for a blocked entry check when disk inspection independently finds a required file missing or invalid.
11. **Keep one publisher lock and separate authorized cleanup policy.** Refactor v2 `composition/registration.rs::publish` to delegate to private operations under an owned lock guard. Add crate-private `repair_registration(context, inventory)`, sharing the v2 `config/setup.rs::setup_claudine` sequence for publish, verify, `replace_manifest_registration`, verify, and legacy cleanup. Plain publish keeps the dependency's extras policy. Setup keeps its permissions handoff between publish and register and its existing handling of destination conflicts. Doctor keeps the lock through publication, verification, user entry edit, and cleanup. Preflight the complete deletion/replacement set, including the lock path, fixed tree components, registration config edit destination and lock sidecar, and both legacy trees, with the v2 symlink/reparse guard. Use the shared guard immediately at mutations, including internal removals and before acquiring or reusing a sidecar lock. Use metadata without following links, inspecting Windows reparse attributes as well as Unix symlink type. Resolve the trusted home anchor once, and walk descendants from it. Use the existing Darkmatter lock and source-expectation path for the user configuration. On versions of the observation where `register` is valid but has no equivalent entry, constrain replacement or deduplication to entries with the new and known legacy identity as in the v2 plan. Obstructions are manual findings. Within the fixed directory delete extras deepest first, retaining expected folders, and clean the two exact legacy paths only after the new inventory and user entry verify. A publish or verification failure preserves legacy paths, and a config write failure keeps the verified published inventory for retry. Report actions already taken from a structured operation log and the incomplete state from fresh inspection. Require existing valid user Darkmatter YAML, including a valid `register` field, before altering publication files. Add `replace_manifest_registration_existing(context, scope, reference, old_path: &Path)` to the v2 writer through `config/init.rs`, delegating to the same edit planner with an existing-file requirement and an observed-byte expectation through `ConfigTransaction`. Setup uses the create-capable entry point. Preserve unrelated entries and comments. This follows the publisher's stable lock, manifest-last contract, and v2 setup migration ordering.
12. **Share the permissions decision and the writer.** Extract crate-private `plan_permissions_handoff` and `commit_permissions_handoff` from `claudine/lib/src/config/setup.rs::setup_with_darkmatter`. Use `darkmatter::config::init::observe`, the setup file identity comparison, and `effective_permissions` for inline conflict and retry detection. A reference is usable only when its `BlockState::Reference.block` succeeded. A reference to Claudine passes, a valid third-party target is informational, and all broken references require manual correction, including a self-reference with no usable block. Keep setup's ability to complete its own newly authored config and initialize missing files. Doctor requires existing valid distinct files, recognizes omitted and explicit-null Darkmatter permissions as requests for handoff with defaults, and treats omitted/null Claudine permissions as no authored block. An inline block facing a different effective authored block or a Claudine-side reference is a conflict. For an omitted/null Darkmatter setting, an existing valid Claudine inline mapping is reused; a Claudine-side reference is a manual conflict because publishing a reference to that file would require a second hop. Validate the selected mapping with Darkmatter's scoped runtime rules so an authored Claudine mapping that would yield a broken reference is manual. `init::observe` currently classifies explicit null as inline, `effective_permissions` compares only mappings, and `referenced_block` requires a mapping. Preserve those normal default semantics while making the shared handoff planner explicit about null and reference states.
13. **Limit permission edits to the handoff and keep policy live across partial writes.** In doctor use only YAML `permissions` edits against the observed bytes. Build the Darkmatter edit with `TargetChange::edit` and `published_last`; `init::setup_change` also fills omitted top-level settings and stays the setup-only route. Check both in-memory candidates with Claudine `validate_config_text` and Darkmatter `init::commit_checked`, including the referenced mapping's scoped runtime check. Validate the explicit target scope even when home equals the repo root. Reuse the no-follow guard for write destinations and lock sidecars; proven read aliases remain valid for reporting. A failed second write leaves the inline block in effect. Retry recognizes an effectively equal authored block and completes the reference without rewriting Claudine's file. Keep registration findings independent of permissions fixability; the permissions writer still refuses invalid candidates. After a successful edit verify through the same setup observation that the reference resolves to the matching Claudine mapping. `config/write.rs::ConfigTransaction::commit` stages all candidates and exposes completed replacements on failure.
14. **Use runtime speech order and report only local availability.** Derive hook enablement and the provider string from `dispatch::loader::bridge_tts_settings` on the validated user-only config. Use `biscuit_speaks::detection::{get_available_providers, parse_provider_name, provider_base_quality}` with the runtime's `SpecificProvider` membership semantics from `get_providers_for_strategy`. Apply the spec's enabled/disabled severity table, selecting the first runtime candidate on equal quality and naming the actual first candidate when it differs from the highest-rated one. An unrecognized configured name is a warning floor and uses automatic candidates. Suppress the raw name. Report settings unavailable as info for a failed user validation. Explain that disabled hook speech still permits lifecycle `say` and that detection only checks local prerequisites. The bridge and `composition/lifecycle/audio.rs` establish these runtime distinctions. Never construct or prewarm a speech engine.
15. **Use Sniff for executable and shell discovery.** The current process uses exactly `ExecutableIndex::build_path_only().find("claudine")`, inheriting its executable mode and native suffix handling. Add a focused native Windows `sniff::programs::windows_shells` detector. Use a full `ExecutableIndex` for `pwsh`, `powershell`, `git`, and a PATH or indexed `bash` candidate. Fall back to `SystemRoot/System32/WindowsPowerShell/v1.0/powershell.exe`. Classify Bash executables by adjacent `msys-2.0.dll` or `cygwin1.dll` to exclude Windows' WSL launcher. Check the Git for Windows root derived from Sniff's Git launcher layouts and `ProgramFiles/Git/usr/bin/bash.exe`, then `SystemDrive/msys64/usr/bin/bash.exe` and `SystemDrive/msys32/usr/bin/bash.exe`. For Cygwin, consult read-only HKCU then HKLM `SOFTWARE\\Cygwin\\setup` `rootdir` in native and 32-bit views and the `SystemDrive/cygwin64` and `cygwin` layouts. Check each root's `bin/bash.exe`. Interpret `SystemDrive` as an absolute volume root by appending the root separator before joining. Prefer Git Bash over standalone MSYS2 for the shared family, then prefer the PATH match within each family. Thread the launch working directory to the shell command and let the shell inherit the process PATH. Deduplicate by existing path identity. Sniff's executable index stores one location per name and its generic Windows fallback only walks standard install roots shallowly, so it cannot identify both Bash families by asking for `bash` twice. Discovery probes local metadata and registry only.
16. **Bound shell probes and suppress all startup code.** In Sniff, retain the existing process supervisor and add a private flags-aware core behind `process::run_command_with_timeout`; the existing callers retain their flags. The native-Windows shell probe uses `TreeConfig::windows_creation_flags(WINDOWS_CREATE_NO_WINDOW)` through that core, null stdin, drained stdout/stderr, and a 2-second deadline per shell. Use PowerShell `-NoLogo -NoProfile -NonInteractive -Command` with a fixed script that disables module auto-loading and uses module-qualified `Get-Command -CommandType Application -Name claudine -ErrorAction SilentlyContinue`. Use Bash `--noprofile --norc -p -c`, remove `BASH_ENV` and `ENV`, and run the fixed builtin `type -P -- claudine` check. Both scripts translate found/missing to exit 0/3. Reject any other exit or terminated process as probe failure. Launch the discovered absolute executable and never run `claudine` or source shell profiles. Spawn failures and timeouts are warnings like shell lookup misses but carry distinct remedies. Omit absent shells. Include the shell name and startup-free condition in the detail. Native Windows only runs those probes; WSL follows Linux behavior. Evidence is `sniff/lib/src/process.rs::run_command_with_timeout`, `process/tree.rs::TreeConfig`, and the spec's subprocess contract.
17. **Use one output path per mode.** Render human rows with an `UnorderedList` of `Prose` entries containing a styled severity label, descriptor title and summary, with hard line breaks for details. Use `log::terminal` for capability and width, forcing color off on redirected stdout even under `FORCE_COLOR` and on `--plain`. Buffer the finished report, then call `std::io::stdout().lock().write_all` with one trailing newline and return the I/O error through existing CLI dispatch. This route has no wrapper output worker, and `terminal_gate::write` discards direct write errors. Serialize the same rows to a single JSON array plus newline with `serde_json`. Put `doctor` immediately after `config` within Administration in both `commands/help.rs::groups` and `completion/root_menu.rs`. Use clap definitions for its flags through the existing completion engine delegation. Update both dispatch exhaustiveness and `telemetry.rs::command_name`. Keep help usable with invalid configuration and no process fixture writes.
18. **Use fixed, hermetic verification with no runtime spike.** Every open behavior follows a spec rule or a traced source seam. The Windows timeout is a production bound exercised by a short injected test timeout, with no separate performance measurement. The working tree has the v2 planning artifact and still uses `HostRevision` and `refresh_host_registration`; implement this plan on the completed v2 code, with no v1 compatibility branch. Regular cross-OS CI supplies remote coverage under the repository's existing scheduling. The declared remote hosts are macOS, native Windows, and WSL2. The local cross-check recipe internally creates a throwaway commit, so leave it out of this implementation's local verification. No new CI cells or test tiers are required.

### Input Robustness Matrix

Invalid input produces an error with the failing file and field location where available, and triggers zero action execution or repair writes for that invalid document and its dependent operations. Unrelated eligible repairs can proceed during `--fix`. The matrix concerns Claudine and Darkmatter YAML plus the existing v2 manifest. Legacy JSON is existence-only. Use the public diagnostic rows or the shared crate's public validation result in-process, with a valid tool-authored fixture and one edited field per case.

- **Admitted YAML.** Claudine and Darkmatter working files share `simplified_schema::yaml_documents::load_yaml_document`. Test duplicate key, trailing nonsense, malformed syntax, second YAML document, and non-string mapping key once at the doctor boundary. Treat `key:` as explicit null, test BOM/comment acceptance, and distinguish an empty document from the accepted `{}` default mapping. Reuse the v2 manifest loader's document-shape coverage and add one differential doctor case for digest mismatch and one for a manifest whose document shape the loader refuses.
- **Claudine TTS.** Missing, explicit null, and false yield disabled hook speech with documented lifecycle eligibility. True and an explicit empty settings object each enable automatic speech. Wrong whole type errors. Missing or null `provider` selects automatic candidates, empty string and wrong type error, and a nonempty unrecognized string warns while preserving the enabled/no-candidate error.
- **Claudine settings and overrides.** Exercise the existing optional/default and nullable schema families through `actions`, `matchers`, and a repo override with an explicit null versus empty mapping. Null inherits for declared nullable overrides. An empty mapping fails a `not-empty` override. A null event entry is unset in the user file and inherits in the repository. An empty event action list is invalid. Use one mixed and one all-invalid action array. Exercise `active_messenger`, a semantic conflict that appears only after merging, and one typed or semantic runtime error from a single file. Use existing schema cases for the remaining unchanged validator families, with one wrong shape on any load-bearing field newly projected by doctor. Keep root, nested, wrong-scope, and imported `permissions` cases distinct.
- **Darkmatter and imported permissions.** Omitted and explicit null invoke scope defaults and are both repairable handoff states on a valid existing file. Empty mapping is an explicit valid inline policy with defaults. Wrong scalar, blank reference, wrong collection type, and mixed and all-invalid entries are errors. Exercise the shared rules array through `shell-commands`: omitted and null use defaults, empty explicitly grants no commands, and both invalid-element shapes are refused. Give `file-read` and `network` a control and one invalid value each, plus `file-read: []` to assert the current `not-empty` refusal and a scope-invalid reference/glob case. A referenced `permissions: {}` mapping uses scope defaults, while a missing, null, or nonmapping block in the target is a broken reference. Darkmatter's `check_permissions_text` requires an authored mapping for a reference target.
- **Darkmatter registration.** Absent and null `register` default to an empty list; authored `[]` is a valid empty list. All three leave the Claudine entry unregistered and retain their source distinction for edit selection and testing. Wrong whole type, mixed elements, all-invalid elements, and invalid local-reference syntax produce located config errors and forbid updates to that file. Preserve a valid third-party entry in the fixture. V2 manifest field shapes stay covered by its existing public-profile tests; doctor delegates the validity verdict.
- **Process proof.** Through `CliProcessFixture` run a valid control and two invalid cases for shared YAML (duplicate key and a nested stray key). Assert the path, coordinates, no synthesis/agent launch, and an unchanged filesystem. Use the registration command fixture to obtain valid v2 bytes and corrupt that fixture for one doctor CLI refusal case. Review load-bearing parse paths for new `#[serde(default)]`, `Option<T>` collapsing null and absence, unchecked `filter_map`, `unwrap_or_default()`, and `.ok()`. When a finding concerns a matrix cell, enumerate the other shapes for that field validator and the other fields sharing that validator.
