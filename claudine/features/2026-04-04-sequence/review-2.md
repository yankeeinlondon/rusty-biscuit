# Sequence Review 2

## Findings

1. `[P1]` `@` and `!` external sequence references still resolve from the process CWD, not from the source document's location.
`resolve_sequence_reference()` routes magic/package references through `FileReference::resolve()` in [sequence.rs](/Users/ken/.claudine/worktrees/rusty-biscuit/feat-claudine-composition/claudine/lib/src/composition/sequence.rs#L75), but `FileReference::resolve()` builds its context from `std::env::current_dir()` via [`ResolutionContext::from_ambient()`](/Users/ken/.claudine/worktrees/rusty-biscuit/feat-claudine-composition/biscuit-file/lib/src/file_reference/context.rs#L13). That means `sequence: "@fixtures/steps.yaml"` and `sequence: "!foo.yaml"` are resolved relative to wherever the user launched `claudine`, not relative to the Markdown source file, even though the docs explicitly say sequence file references are resolved relative to the source document in [composition.md](/Users/ken/.claudine/worktrees/rusty-biscuit/feat-claudine-composition/claudine/docs/topics/composition.md#L206). The current integration test for magic references in [sequence_cli.rs](/Users/ken/.claudine/worktrees/rusty-biscuit/feat-claudine-composition/claudine/cli/tests/sequence_cli.rs#L420) sets `current_dir` to the repo root, so it misses this case entirely. A user invoking `claudine sequence /abs/path/to/repo/prompts/seq.md` from some unrelated directory can still get the wrong file or a spurious "not found".
Recommendation: the durable fix is an API improvement in `biscuit-file`, not just more Claudine-side conditionals. `FileReference` needs an explicit source-aware resolution entrypoint such as `resolve_from(base: &Path)` or `resolve_with_context(ctx: ResolutionContext)`, with the current ambient `resolve()` remaining as a convenience wrapper. Claudine can then resolve external sequence refs using the source document's directory/repo/package context instead of the process CWD.

2. `[P2]` The new approval-reuse test does not actually verify the shared approval cache path.
The implementation now threads a shared approval cache through the sequence runner and wrapper, which is the right fix. But [sequence_reuses_shell_approvals_across_steps()](/Users/ken/.claudine/worktrees/rusty-biscuit/feat-claudine-composition/claudine/cli/tests/sequence_cli.rs#L587) only uses a whitelisted `echo` command. Whitelisted commands succeed on every step even if the shared cache is broken, so this test cannot catch regressions in the "allow once" reuse logic it claims to cover. The comment at [sequence_cli.rs](/Users/ken/.claudine/worktrees/rusty-biscuit/feat-claudine-composition/claudine/cli/tests/sequence_cli.rs#L588) says the shared cache is populated on step 1 and hit on step 2, but that is not what this setup proves. A targeted test needs to exercise a non-whitelisted command with a reusable approval cache or a mocked approval handler; ideally one test should also cover the harness-command path, since the review requirement was whole-sequence reuse rather than template-only reuse.
