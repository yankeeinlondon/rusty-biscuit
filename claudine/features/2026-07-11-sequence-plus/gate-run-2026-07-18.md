### Is the `terminate-after = 6` grant adequate or marginal?

**Adequate, with comfortable margin.** The grant is not close to binding.

The bespoke override in `.config/nextest.toml`:

```toml
[[profile.default.overrides]]
filter = 'test(=level2_prompt_idle_flush_keeps_the_task_bar_in_tmux)'
slow-timeout = { period = "30s", terminate-after = 6 }
```

| | Value |
|---|---|
| Termination cap (`30s × 6`) | **180 s** |
| Measured duration | **78.128 s** |
| Fraction of cap consumed | **43.4 %** |
| Absolute headroom | **101.9 s** |
| Multiple of measured duration the cap allows | **2.30×** |

For comparison, the test's own in-test `run_in_pane_within` deadline is
`Duration::from_secs(150)`, of which it consumed **52.1 %**. The in-test deadline
binds before the nextest cap does, which is the correct ordering — a blown
deadline surfaces as an assertion failure with a pane dump rather than an opaque
`TMT`.

Two caveats against reading this as unlimited comfort:

1. It was measured at load `9`–`10`. The ~80 s floor is structural (a hardcoded
   30 s `SILENCE_WINDOW` at `cli/src/commands/wrap/exec/watchdog/spawn.rs:58`
   plus a ticker of the same cadence, cleared only on the *second* tick) and will
   not shrink on a fast host, but the pane-setup and capture overhead around it
   will grow on a loaded one. The 2.30× headroom is what absorbs that, and at the
   load this session peaked at (197), 2.30× is not obviously enough.
2. Because the test is 72.7% of the tier and the tier runs its L2 tests
   concurrently at `min(cores, 8)`, this single test now sets the L2 tier's floor.
   No amount of parallelism can bring `just test-l2` below ~80 s again.

Budget for that before adding another stall-shaped L2 test.

- **AC8 (cross-platform Ctrl+C) is unblocked, not met.** This is the most
  important limitation in this document and it should not be softened. **No
  Windows runtime evidence exists.** The Windows suites — `termination/windows.rs`'s
  `#[cfg(all(test, windows))]` Job-object regressions and
  `cli/tests/level2_windows_sequence_ctrl_c.rs` — now *type-check* via
  `just check-windows` (`cargo check --tests --target x86_64-pc-windows-gnu`).
  They have **never executed**. Type-checking proves a typo or signature drift
  would be caught; it proves nothing about `GenerateConsoleCtrlEvent`,
  `TerminateJobObject`, or kill-on-close behavior at runtime. The strongest
  Windows evidence remains *source audit plus production cross-compile*. Only a
  native Windows run closes this.
- **AC1's L3 OS-keyboard evidence is not refreshed for this round.** L3 was
  guard-blocked. The macOS Ctrl+C fan-out contract rests on the review-3 round's
  green, against an older tree.
- **Linux is not re-run here.** The Linux evidence in `validation-matrix.md` still
  dates from the review-3 round.
- **The 3 `level2_context_*_at_140` failures remain unresolved.** They are
  pre-existing and unrelated to sequences, but "pre-existing" is not "green" —
  the L2 tier does not return `0`.
- **L1 timing on this host is fragile.** The 12-test compose/opencode/perf family
  consumes ~55% of its 30 s cap even in isolation on a busy host. This run does
  not certify that the L1 tier passes on a loaded machine; it certifies that it

- **Nothing here speaks to review-4 findings 1, 2, 5, 6, 7 or 8 on the merits.**
