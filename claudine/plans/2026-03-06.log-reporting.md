# Plan: Implement `claudine logs` Reporting

## Goal

Implement the reporting system described in `claudine/docs/log-reporting.md` as a library-first feature set:

- raw `EventMeta` JSONL remains the audit trail and source of truth
- SQLite becomes a derived local index/cache for fast reporting
- the CLI only parses arguments, triggers sync/query operations, and renders typed results

This plan is intentionally more concrete than the design doc. It also tightens a few parts of the design that are currently too vague to implement safely.

## Current State

- `claudine/lib/src/dispatch/runner.rs` already writes `EventMeta` JSONL files to `~/.claudine/logs/` with optional daily rotation.
- `claudine/lib/src/events/event_meta.rs` already contains almost all fields required by the reporting doc.
- There is no `reporting` module in the library today.
- There is no `logs` subcommand in `claudine/cli`.
- The design doc proposes aggregate SQLite tables only, but several requested reports need raw event-level access.

## Required Design Tightening

Before implementation starts, treat these as settled decisions unless new evidence forces a change.

### 1. Keep JSONL as the canonical source

- SQLite is an index/cache, not the canonical store.
- Deleting `metrics.db` must never lose data because it can be rebuilt from JSONL.
- `logs sync` must be idempotent and safe to rerun.

### 2. Add a raw `events` table

The design doc currently jumps straight to daily aggregate tables. That is not enough for:

- `logs errors` with event context
- `logs sessions` with duration and per-session counts
- file-read / edit / bash-command drilldowns
- derived metrics like retry recovery and research-vs-action ratios
- future features that need event-level slices without another schema rewrite

Implementation should therefore start with indexed raw events plus a small amount of session metadata. Aggregate tables can come later if profiling proves they are necessary.

### 3. Use views or query-time aggregation first

Given the observed size in the doc is roughly 66k events across 15 days, the first implementation should prefer:

- indexed raw tables
- SQL views for common rollups
- Rust-side post-processing for derived metrics

Do not start with a wide set of eagerly maintained rollup tables. That adds complexity, makes incremental sync harder, and creates more ways for the database to drift from the JSONL source.

### 4. Define a stable event identity

Each ingested event should be uniquely keyed by:

- `source_file`
- `source_offset`

This makes incremental ingestion deterministic, avoids double-counting on reruns, and gives the library a reliable way to rebuild a single file if it is truncated or replaced.

### 5. Define a conservative session-key strategy

`session_id` is nullable for some providers and events. Reporting still needs a non-dropping strategy.

Use this order:

1. `provider + session_id` when present
2. provider-specific stable fallback from `extra` when available, such as transcript/session path fields
3. anonymous fallback using `provider + source_file + source_offset`

That last fallback is intentionally conservative. It preserves all events without pretending unrelated anonymous events belong to the same session.

### 6. Reporting must not dump sensitive payloads by default

Raw logs contain prompts, tool input, and tool output. Terminal reports should therefore default to:

- truncation for long prompts and commands
- omission of full `tool_response` bodies
- brief error context, not raw payload dumps

`--json` may return fuller structured data, but the typed output model should still separate summaries from raw payload fields.

### 7. Read commands should perform best-effort sync

For good UX, read-oriented commands should not require a manual `logs sync` first.

Recommended behavior for v1:

- `claudine logs sync` performs explicit ingest and prints a sync summary
- read commands run a lightweight sync over the relevant file/date range before querying
- later, a `--no-sync` flag can be added if startup cost becomes noticeable

## Architecture

## Library Responsibilities

All business logic belongs in `claudine/lib/src/reporting/`:

- default log/db path resolution
- SQLite connection management
- schema creation and migrations
- JSONL file discovery and incremental ingestion
- typed query functions
- derived metric computation
- filtering by date/provider/repo

## CLI Responsibilities

All CLI-only work belongs in `claudine/cli/src/commands/logs.rs`:

- `clap` argument parsing
- choosing the correct reporting query
- calling best-effort sync before read commands
- rendering tables, badges, sparklines, and JSON
- writing machine output to stdout and status/progress to stderr

## Proposed Library File Layout

```text
claudine/lib/src/
├── lib.rs
├── error.rs
└── reporting/
    ├── mod.rs
    ├── paths.rs
    ├── schema.rs
    ├── ingest.rs
    ├── queries.rs
    ├── metrics.rs
    └── types.rs
```

### `reporting/mod.rs`

Public facade for the reporting subsystem. Expose a small surface such as:

- `ReportingStore::open_default()`
- `ReportingStore::sync(...)`
- `ReportingStore::daily_summary(...)`
- `ReportingStore::sessions(...)`
- `ReportingStore::tools(...)`
- `ReportingStore::errors(...)`
- `ReportingStore::repos(...)`
- `ReportingStore::trends(...)`

### `reporting/paths.rs`

Single source of truth for:

- default JSONL directory
- daily JSONL file naming
- default SQLite database path
- date-to-file-path resolution

`dispatch::runner` should use these helpers too so log writing and log reading never diverge.

### `reporting/schema.rs`

Own:

- schema creation
- schema version tracking
- forward-only migrations
- indexes and views

Use a simple schema-version table or `PRAGMA user_version`. The important part is explicit migration ownership, not which variant is chosen.

### `reporting/ingest.rs`

Own:

- log file discovery
- ingestion state lookup
- incremental parsing from byte offsets
- per-file rebuild when a file shrinks or is replaced
- session metadata upserts
- sync summaries and ingest diagnostics

### `reporting/queries.rs`

Own:

- all SQL for report queries
- row-to-typed-model mapping
- filtering and ordering logic

### `reporting/metrics.rs`

Own:

- autonomy ratio
- research-vs-action ratio
- error recovery rate
- session efficiency
- context pressure index

These should consume typed query results rather than embed SQL in multiple places.

### `reporting/types.rs`

Define stable result types for both terminal and JSON output. Likely types:

- `SyncSummary`
- `DailySummary`
- `DailyToolStat`
- `SessionInfo`
- `ErrorRecord`
- `RepoActivity`
- `TrendPoint`
- `ProviderSplit`
- `TopToolTrend`
- `ReportingFilters`

## Proposed SQLite Shape

## Core Tables

### `schema_meta`

Tracks schema version and any future metadata needed for maintenance.

### `ingestion_state`

Tracks file progress and rebuild decisions:

- `source_file`
- `file_size`
- `modified_at`
- `byte_offset`
- `last_event_timestamp`
- `last_synced_at`

### `events`

This is the foundation table.

Recommended columns:

- source identity: `source_file`, `source_offset`, `source_date`
- core event fields: `timestamp`, `provider`, `event`, `session_key`, `session_id`
- common filters: `cwd`, `repo_name`, `repo_org`, `branch`, `primary_language`
- common report fields: `tool_name`, `agent_type`, `notification_type`, `error`
- promoted `extra` fields used frequently in reports: `model`, `permission_mode`, `head_sha`, `is_dirty`, `memory_available_bytes`
- raw payload columns: `prompt_text`, `tool_input_json`, `tool_response_json`, `extra_json`, `env_json`

Primary key:

- `(source_file, source_offset)`

Key indexes:

- `(source_date)`
- `(timestamp)`
- `(provider, source_date)`
- `(repo_name, source_date)`
- `(session_key, timestamp)`
- `(tool_name, source_date)`
- `(event, source_date)`

### `sessions`

Small summary table keyed by `session_key` for fast session listings.

Recommended columns:

- `session_key`
- `session_id`
- `provider`
- `started_at`
- `ended_at`
- `cwd`
- `repo_name`
- `repo_org`
- `branch`
- `model`
- `permission_mode`
- `hostname`
- `primary_language`
- `event_count`
- `turn_count`
- `tool_call_count`
- `tool_error_count`
- `turn_error_count`
- `subagent_count`

This table should be updated incrementally from ingested events rather than recomputed from scratch on each query.

## Views

Instead of materialized aggregate tables in v1, create views for common groupings:

- `daily_event_totals_v`
- `daily_tool_usage_v`
- `daily_subagent_usage_v`
- `daily_repo_activity_v`

Queries can read from these views and still join back to raw events when a report needs detail.

- `daily_summary`

- `sessions`
  - duration from first to last event in the selected range
  - turns, tool calls, errors, repo, provider, model

  - count per tool
  - error rate per tool

- `errors`
  - list `tool_error` and `turn_error`

  - repo activity counts
  - branch usage
  - distinct `head_sha` count

- `trends`
  - per-day events, sessions, turns, errors

Completion criteria:

## Risks and Mitigations

### Risk: duplicate or drifting aggregates

Mitigation:

- start from raw events plus views
- delay materialized rollups until profiling says they are needed

### Risk: corrupted JSONL breaks the index

Mitigation:

- per-file transaction boundaries
- fail and roll back that file on malformed JSON
- keep source JSONL untouched

### Risk: sessions without IDs distort session reports

Mitigation:

- explicit `session_key` fallback strategy
- surface anonymous fallback counts in sync summaries
- avoid pretending anonymous events are one session unless there is real evidence

### Risk: terminal output leaks sensitive payloads

Mitigation:

- truncate by default
- omit large payload bodies from terminal summaries
- keep richer data in structured JSON output only when necessary

## Deferred Items

These should not block the first usable implementation:

- pruning old SQLite rows with `--prune-before`
- hourly and weekday heatmaps
- memory-pressure correlation beyond simple daily summaries
- materialized rollup tables
- advanced retry-chain reconstruction across long sessions
- export to HTML or Markdown reports
