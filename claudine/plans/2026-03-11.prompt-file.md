# Plan: Prompt File Switch For Wrapper Sessions

## Goal

Add a universal `--prompt-file` / `-p` wrapper flag that lets any wrapped provider session source its initial prompt from a Markdown file. The file is resolved with repo/package awareness, composed through Darkmatter's transform pipeline, and the result split into a prompt body (injected into the provider) and residual frontmatter (exported as child-session environment variables).

This gives Claudine a composable, repo-aware prompt-file system instead of a raw file-reading shortcut.

## Scope

This plan covers:

- wrapper arg parsing for `--prompt-file` / `-p`
- path resolution with `@`, `./`, bare filename, and absolute path semantics
- Markdown-only validation
- Darkmatter library composition (body + residual frontmatter extraction)
- frontmatter-to-env-var normalization, collision detection, and protected-name rejection
- per-provider prompt delivery via a new `WrapperProfile` trait method
- mutual exclusion with other prompt sources
- dry-run reporting of resolved path and injected env names
- interactive confirmation/selection for ambiguous bare-name matches
- unit and integration tests
- help text and snapshot updates

This plan does not cover:

- changes to `--system-prompt` semantics
- non-Markdown prompt sources
- Darkmatter composition semantics themselves (we consume, not change)
- follow-on documentation updates to `claudine/cli/README.md` or `claudine/docs/cli/commands.md`

- MCP tag extraction at `mod.rs:517-649` finds prompt location and mutates args in place
- `find_prompt_location()` at `mod.rs:590-649` handles Codex, Gemini, OpenCode positional/flag prompts
- Dry-run output at `output.rs:111-180` shows command, env changes, and MCP info
- Integration tests at `claudine/cli/tests/wrap_commands.rs` use `assert_cmd`, `insta`, and `tempfile`

Darkmatter library API:

- `Markdown::try_from(Path)` loads and parses a file
- `md.transform_with(TransformOptions)` returns `(Markdown, TransformReport)`
- `TransformOptions::new().with_source_file(path)` sets transclusion context
- `transformed.content()` → composed body string
- `transformed.frontmatter().as_map()` → `HashMap<String, serde_json::Value>`
- Error type: `MarkdownError` / `MarkdownResult<T>`

## Design Direction

### 1. New module for all prompt-file logic

Add `claudine/cli/src/commands/wrap/prompt_file.rs` to encapsulate resolution, composition, env derivation, and prompt-source conflict detection. Keep `mod.rs` orchestration-focused.

### 2. Provider prompt delivery as a trait method

Add `apply_prompt_body()` to `WrapperProfile` so each provider declares how a composed prompt body reaches the agent. This parallels the existing `apply_system_prompt()`, `apply_model()`, etc.

### 3. Stdin seeding for Claude and Kimi

Claude and Kimi require stdin-based prompt delivery. The child execution path must support optional stdin seeding, which is a new capability for `exec.rs`.

### 4. Frontmatter env vars are child-session overrides

Prompt-file-derived env vars sit between explicit wrapper flags and inherited process env in precedence. They are added to the child environment through the same `env_overrides` vector already used by providers.

### 5. MCP tag extraction runs after prompt-file injection

The composed body must be visible to `extract_tags_from_child_args()` so `#tag` references inside prompt files work identically to inline prompts.

## Phase 2: Path Resolution

### Tasks

1. Create `claudine/cli/src/commands/wrap/prompt_file.rs` with the following structs and functions.

2. Define `PromptResolutionContext`:
   ```rust
   pub(crate) struct PromptResolutionContext {
       pub cwd: PathBuf,
       pub repo_root: Option<PathBuf>,
       pub package_root: Option<PathBuf>,
       pub interactive: bool,
   }
   ```
   `interactive` is true only when stdin is a terminal AND stdout is a terminal AND `--non-interactive` is not set.

3. Define `ResolvedPromptFile`:
   ```rust
   pub(crate) struct ResolvedPromptFile {
       pub original: String,
       pub resolved_path: PathBuf,
   }
   ```

4. Implement `resolve_prompt_file(input: &str, ctx: &PromptResolutionContext) -> Result<ResolvedPromptFile>`:

   a. **Extension validation**: Check that the input ends with `.md` or `.markdown` (case-insensitive). Reject immediately otherwise.

   b. **`@` prefix**: Strip `@`, join remainder against `ctx.repo_root`. Error if `repo_root` is `None`.

   c. **`./` prefix**: Strip `./`, join remainder against `ctx.package_root`. Error if `package_root` is `None`.

   d. **Absolute path**: Use as-is.

   e. **Path with directory separators** (but no special prefix): Resolve relative to `ctx.cwd`.

   f. **Bare filename** (no directory separators): Search in order:
      1. `ctx.cwd / filename`
      2. `ctx.package_root / filename` (if available)
      3. `ctx.repo_root / filename` (if available)
      4. Repo-wide leaf-name search (if repo_root available)

5. Implement repo-wide search (`search_repo_for_filename`):
   - Walk `repo_root` for exact leaf-name matches with `.md` or `.markdown` extension.
   - `0` matches → error with "not found" message.
   - `1` match:
     - interactive → confirm with user via `inquire::Confirm`
     - non-interactive → error, print the single suggested path
   - `>1` matches:
     - interactive → `inquire::Select` prompt
     - non-interactive → error, print candidate list

6. After resolution, verify the file exists on disk. Error if not.

7. Build `PromptResolutionContext` from existing wrapper state:
   - `cwd` from `std::env::current_dir()`
   - `repo_root` from the same `sniff::filesystem::git::detect_git()` call already used in `env.rs`
   - `package_root` from the same monorepo package selection already used to populate `PACKAGE`
   - `interactive` from terminal detection and `--non-interactive` flag

### Files touched

- `claudine/cli/src/commands/wrap/prompt_file.rs` (new)
- `claudine/cli/src/commands/wrap/mod.rs` — `mod prompt_file;` declaration, context construction

### Dependencies

## Phase 3: Darkmatter Composition

### Tasks

1. Add `darkmatter` as a dependency of `claudine-cli` (it may already be available via `claudine` lib; check workspace deps).

2. Define `ComposedPrompt`:
   ```rust
   pub(crate) struct ComposedPrompt {
       pub resolved_path: PathBuf,
       pub body: String,
       pub env_overrides: Vec<(String, String)>,
       pub env_names: Vec<String>,
   }
   ```

3. Implement `compose_prompt_file(resolved: &ResolvedPromptFile) -> Result<ComposedPrompt>`:

   a. Load the file: `Markdown::try_from(resolved.resolved_path.as_path())?`

   b. Build transform options:
      ```rust
      let options = TransformOptions::new()
          .with_source_file(&resolved.resolved_path);
      ```

   c. Run composition: `let (transformed, _report) = md.transform_with(options)?;`

   d. Extract body: `transformed.content().to_string()`

   e. Extract frontmatter: `transformed.frontmatter().as_map().clone()`

   f. Convert frontmatter to env vars via `frontmatter_to_env()` (Phase 4).

   g. Return `ComposedPrompt` with all fields populated.

4. Map `MarkdownError` into the wrapper's error type with actionable messages:
   - "Darkmatter compose failed for '{path}': {error}"

## Phase 4: Frontmatter To Environment Variables

### Tasks

1. Implement `frontmatter_to_env(map: &FrontmatterMap) -> Result<Vec<(String, String)>>`:

   a. **Name normalization** (`normalize_env_name`):
      1. Uppercase the key
      2. Replace any non-`[A-Z0-9]` character with `_`
      3. Collapse repeated `_`
      4. Trim leading and trailing `_`
      5. If result starts with a digit or is empty, prefix `PROMPT_FILE_`

   b. **Value serialization** (`serialize_env_value`):
      - `Value::String(s)` → `s.clone()`
      - `Value::Number(n)` → `n.to_string()`
      - `Value::Bool(b)` → `"true"` / `"false"`
      - `Value::Null` → `""`
      - `Value::Array(_)` / `Value::Object(_)` → `serde_json::to_string(&v)?` (compact JSON)

   c. **Collision detection**:
      - Track normalized names. If two distinct frontmatter keys normalize to the same env var name, error with both original keys and the colliding name.

   d. **Protected env rejection**:
      - Define a `PROTECTED_ENV_NAMES` set: `HOME`, `PATH`, `SHELL`, `USER`, `AGENT`, `YOLO`, `INTERACTIVE`, `AGENT_PARAMS`, `CLAUDINE_SESSION_ID`, `PACKAGE`, `PACKAGE_AREA`, `REPO_ROOT`, `NON_INTERACTIVE`
      - If any normalized name matches a protected name, error with the specific key and name.

2. Return `Vec<(String, String)>` of `(normalized_name, serialized_value)` pairs.

### Files touched

- `claudine/cli/src/commands/wrap/prompt_file.rs`

### Tests

- `model` → `MODEL`
- `agent-type` → `AGENT_TYPE`
- `target.env` → `TARGET_ENV`
- `2026_plan` → `PROMPT_FILE_2026_PLAN`
- Empty key → `PROMPT_FILE_`
- `foo-bar` and `foo_bar` in same frontmatter → collision error
- `path` in frontmatter → protected env error
- String value → raw string
- Number value → decimal string
- Bool value → `"true"` / `"false"`
- Null value → `""`
- Array value → compact JSON
- Object value → compact JSON

## Risks And Decisions

### Risks

1. **`-p` collision with provider-native flags**: Gemini and Qwen both use `-p` natively. Users who currently pass `-p` through to the provider will need to use `--` passthrough or the provider's long-form flag. This is an intentional breaking change for the wrapper layer.

2. **Stdin seeding complexity**: Claude and Kimi use stdin for prompt delivery. The child process must have its stdin written to and then closed before the session begins. This requires careful handling of the pipe lifecycle, especially under timeout and signal-forwarding scenarios.

3. **Repo-wide search performance**: Walking the entire repo for a bare filename could be slow in large repositories. Mitigate by respecting `.gitignore` (use `ignore` crate if available) and bailing early on match count thresholds.

4. **Darkmatter dependency coupling**: Adding `darkmatter` as a dependency of `claudine-cli` increases the build graph. Verify this doesn't create circular dependencies in the workspace.

### Open decisions

1. **Should `apply_prompt_body` be fallible or return `Option<String>` for warnings?** The design doc suggests `Result<()>`, which is cleaner. Warnings can go through the existing `deferred_warnings` pattern only if needed.

2. **Should stdin seeding write the full prompt and close, or should it leave stdin open for interactive use?** For `--non-interactive` with `--prompt-file`, closing stdin after seeding is correct. Interactive use with stdin-based providers and prompt files is not supported per the design doc.

3. **Should repo-wide search use `ignore` crate (respects `.gitignore`) or `walkdir`?** Prefer `ignore` if already in the dependency tree; otherwise `walkdir` with manual `.git` directory exclusion.

1. **Phase 4** (frontmatter-to-env) — pure logic, no dependencies on other phases, highly testable

8. **Phase 8** (testing) — integration tests run last but unit tests should be written with each phase

Unit tests should be developed alongside each phase. Integration tests are consolidated in Phase 8 but should be written incrementally as each phase lands.
