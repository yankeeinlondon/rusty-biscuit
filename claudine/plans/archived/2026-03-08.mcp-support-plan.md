# Plan: Implement MCP Support

## Goal

Implement the MCP (Model Context Protocol) support described in `claudine/prompts/mcp-support.md` as a library-first feature set:

- a global catalog of normalized MCP server definitions
- user-scope and repo-scope defaults for the active server set
- structured provider-state tracking for import provenance and sync ownership
- import from native provider configs via `claudine mcp init`
- sync/export back to provider-native configs via `claudine mcp sync`
- runtime session composition via `--mcp` on wrapped provider commands
- `#tag` prompt activation and `--use` explicit server selection at launch time

This plan is intentionally more concrete than the design spec. It settles open questions, assigns every piece of work to a specific file, and sequences phases so that each one produces a testable, usable increment.

## Current State

- Claudine has no MCP-related code today.
- The wrapper system (`cli/src/commands/wrap/`) already handles shadow-home environments, env injection, and provider-specific flag mapping.
- The configurator trait (`lib/src/config/trait_def.rs`) manages hook registration per provider but has no MCP awareness.
- Research docs exist for 6 of 8 providers in `claudine/docs/mcp/` (Claude, Codex, Gemini, OpenCode, Qwen, Roo). Goose and Kimi are missing.
- The `Provider` enum, adapter pattern, and wrapper profile pattern are all well-established and extensible.

## Required Design Decisions

Before implementation starts, treat these as settled unless new evidence forces a change.

### 1. Catalog is the single source of truth

The catalog at `~/.claudine/mcp/catalog.json` is the only place full server definitions live. Defaults files reference catalog IDs only. Provider-state tracks provenance only. No duplication of server definitions across files.

### 2. Fingerprinting uses normalized content hash

A server fingerprint is computed from the sorted, normalized definition (transport, command, args, env, url, headers) using a stable hash. The `metadata`, `aliases`, `provider_overrides`, and `id` fields are excluded from the fingerprint. This makes deduplication reliable across providers that configure the same server differently.

### 3. Repo defaults replace, not merge

When a repo has `.claudine/mcp.json`, its `defaults` array replaces the user defaults entirely. This matches the spec and Claudine's broader repo-isolation posture. The `--use` flag adds to whichever set is active.

### 4. Runtime injection is provider-specific and phase-gated

Only providers with verified injection strategies get `--mcp` support. Phase 1 covers OpenCode, Codex, and Gemini. Claude gets import/sync only. Roo gets sync/export only. Qwen, Goose, and Kimi are blocked until research docs are complete.

### 5. `#tag` is launch-time only

Tags are extracted from the prompt before the provider sees it. Mid-session tag activation is not supported in v1. Interactive sessions without an initial prompt must use `--use`.

### 6. Secrets stay in the catalog

v1 does not introduce secret management. Env vars and headers are stored as-is in the catalog. Display commands redact values by default.

## Normalized Server Schema

The catalog schema must be a superset that covers all known provider formats.

```rust
pub struct McpServer {
    pub id: String,
    pub aliases: Vec<String>,
    pub transport: McpTransport,        // Stdio | Http | Sse
    pub command: Option<String>,        // for Stdio
    pub args: Vec<String>,              // for Stdio
    pub cwd: Option<PathBuf>,           // for Stdio
    pub env: HashMap<String, String>,   // for Stdio
    pub url: Option<String>,            // for Http | Sse
    pub headers: HashMap<String, String>,
    pub enabled_tools: Vec<String>,
    pub disabled_tools: Vec<String>,
    pub required: bool,
    pub metadata: McpServerMetadata,
    pub provider_overrides: HashMap<String, Value>,
}

pub struct McpServerMetadata {
    pub description: Option<String>,
    pub created_from: Option<String>,   // "codex:user", "gemini:repo", etc.
    pub fingerprint: String,            // content hash
    pub created_at: DateTime<Utc>,
    pub updated_at: DateTime<Utc>,
}

pub enum McpTransport {
    Stdio,
    Http,
    Sse,
}
```

## Phase 5: Import from Native Provider Configs

Files:

- `claudine/lib/src/mcp/import.rs`
- `claudine/lib/src/mcp/mod.rs`

Tasks:

- implement `McpImporter`:
  - `import_all(repo_root: Option<&Path>) -> Result<ImportReport>`
  - `import_provider(provider: Provider, repo_root: Option<&Path>) -> Result<ImportReport>`
- implement per-provider parsers (one function per provider):
  - `parse_claude_mcp(config_path: &Path) -> Result<Vec<McpServer>>` — parse `~/.claude/settings.json` and `.claude/settings.local.json` mcpServers objects
  - `parse_codex_mcp(config_path: &Path) -> Result<Vec<McpServer>>` — parse `~/.codex/config.toml` `[mcp_servers.*]` tables
  - `parse_gemini_mcp(config_path: &Path) -> Result<Vec<McpServer>>` — parse `~/.gemini/settings.json` mcpServers object
  - `parse_opencode_mcp(config_path: &Path) -> Result<Vec<McpServer>>` — parse `~/.config/opencode/config.json` or env-based config mcpServers
  - `parse_roo_mcp(config_path: &Path) -> Result<Vec<McpServer>>` — parse `.roo/mcp.json` mcpServers array
  - `parse_qwen_mcp(config_path: &Path) -> Result<Vec<McpServer>>` — parse `~/.qwen-code/config.json` mcpServers (when research is complete)
- implement the import algorithm from the spec:
  1. discover native config files for the current machine and repo
  2. parse each provider's MCP definitions into normalized `McpServer`
  3. compute fingerprint
  4. if fingerprint exists in catalog: reuse entry, add alias if native name differs
  5. if fingerprint is new: create new catalog entry with stable slug ID
  6. record provenance in provider-state
  7. return `ImportReport` with imported, merged, conflicted, and skipped counts
- implement stable slug ID generation from server name (lowercase, hyphens, dedup)
- implement conflict rules:
  - same fingerprint + different names → merge with alias
  - same name + different fingerprint → new ID with disambiguation suffix, flag to user
  - alias collision with existing ID → reject alias, warn

`ImportReport` type:

```rust

    pub merged: Vec<MergedEntry>,
    pub conflicts: Vec<ConflictEntry>,
    pub skipped: Vec<SkippedEntry>,
    pub errors: Vec<ImportError>,
}
```

Completion criteria:

- `import_all` scans all detected providers and produces a complete report
- importing twice is idempotent (fingerprint dedup)
- import never mutates native provider configs

  - `compute_session_set(repo_root: Option<&Path>, explicit_use: &[String], prompt_tags: &[String]) -> Result<SessionSet>`
  - algorithm:
    1. start with effective defaults (repo replaces user)
    2. add explicit `--use` values
    3. add `#tag` values
    4. resolve all IDs/aliases through the catalog
    5. deduplicate
    6. return resolved `SessionSet` with full `McpServer` definitions
- implement tag extraction from prompt text:
  - `extract_tags(prompt: &str) -> (String, Vec<String>)` — returns (cleaned prompt, extracted tags)
  - tags are `#word` tokens where `word` matches a catalog ID, alias, or fuzzy match
  - strip matched tags from the outgoing prompt
- implement tag resolution with the 5-tier priority:
  1. exact catalog ID
  2. exact alias
  3. normalized exact match (case-insensitive, `-`/`_` equivalent)
  4. prefix match
  5. substring match
- ambiguity handling:
  - interactive TTY: could prompt user (defer to CLI layer)
  - non-interactive: fail with `McpAmbiguousMatch`

## Risks and Mitigations

### Risk: native provider config formats change

Mitigation:

- parsers are isolated per provider and can be updated independently
- import never mutates native configs, so a parse failure is non-destructive
- fingerprinting makes re-import safe after format changes

### Risk: shadow-home injection breaks provider features

Mitigation:

- Codex and Gemini injection creates minimal config files, not full replacements
- test with OAuth files, project configs, and trusted-project behavior
- OpenCode avoids the problem entirely via env var injection

### Risk: alias/ID namespace collisions across providers

Mitigation:

- strict collision rules: alias cannot match existing ID
- import generates disambiguated slugs for same-name different-fingerprint conflicts
- resolution priority is deterministic and documented

### Risk: secrets exposed in catalog or CLI output

Mitigation:

- terminal display redacts env vars and headers by default
- `--json` output includes full values (user explicitly opted in)
- catalog file permissions should be user-read-only (0600)

### Risk: incomplete provider research blocks implementation

Mitigation:

- phase-gated rollout: only providers with completed docs get runtime support
- import/sync can still work for partially-researched providers
- `McpProviderNotSupported` error gives clear guidance

## Deferred Items

These should not block the first usable implementation:

- mid-session MCP hot-reload for providers that support dynamic reloading
- secret manager integration (1Password, system keychain)
- `claudine mcp add` interactive wizard for creating new servers
- `claudine mcp test <id>` to verify a server is reachable
- Qwen, Goose, and Kimi runtime injection (blocked on research)
- Claude runtime injection (blocked on scope precedence modeling)
- MCP server health monitoring and auto-disable
- tag activation in interactive wrapped sessions
- catalog sharing/export for team workflows
