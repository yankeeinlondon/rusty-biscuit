# Plan: Refactor MCP Mode To Match The New CLI Specification

## Goal

Bring Claudine's shipped MCP implementation into alignment with the newer CLI-oriented specification in:

- `claudine/docs/cli/mcp-mode.md`
- `claudine/docs/cli/mcp-catalog.md`

without throwing away the useful substrate that already exists in the library:

- normalized MCP catalog types
- provider-state tracking
- provider import/export logic
- runtime injectors for Codex, Gemini, and OpenCode
- wrapper integration for `--mcp` and `--use`

This should be treated as a refactor and product-shaping pass, not a greenfield rewrite.

## What Exists Today

- `claudine/lib/src/mcp/` already contains a real subsystem: `catalog.rs`, `defaults.rs`, `state.rs`, `import.rs`, `export.rs`, `session.rs`, `inject.rs`, and `types.rs`.
- `claudine/cli/src/commands/wrap/mod.rs` already wires `--mcp` and `--use` into wrapper execution.
- `claudine/cli/src/commands/mcp.rs` already ships `init`, `show`, `default`, `alias`, `remove`, and `sync`.
- `claudine/cli/tests/mcp_cli.rs` already covers the current command and wrapper behavior.

That means the work is mostly about:

- changing semantics where the current behavior diverges from the spec
- finishing missing UX and command surface
- tightening the library API so the CLI can express the spec cleanly
- deciding where the new spec is still too vague or internally inconsistent

## Primary Gaps Against The New Spec

### 1. Command semantics do not match the new spec

The new spec expects:

- `claudine mcp` to mean `list`
- `claudine mcp add local`
- `claudine mcp add remote`
- `claudine mcp alias <name> <alias>`
- `claudine mcp remove <name_or_alias>`
- `claudine mcp config <name_or_alias>`
- `claudine mcp check`
- `claudine mcp sync` to re-evaluate agent configs and refresh the catalog

The current CLI instead exposes:

- `show` instead of `config`
- `alias add/remove` instead of the simpler spec form
- no `add` or `check`
- `sync <provider> [--scope] [--apply]`, which is provider export, not catalog refresh

This is the biggest product-level mismatch.

### 2. Initialization flow is missing the behavior the spec centers on

The spec describes two init paths:

- proactive init through `claudine mcp init`
- reactive bootstrap the first time a wrapped run uses `--mcp`

The current implementation only imports provider configs during `mcp init`. It does not:

- prompt for user defaults
- prompt for repo defaults
- create the "mini help" re-entry flow
- reactively bootstrap state when a wrapper first uses `--mcp`

### 3. Wrapper tag behavior is only partially implemented

The spec expects inline `#tag` activation in both interactive and non-interactive flows, with precise lexical rules and fallback behavior.

The current implementation:

- only extracts tags when the wrapper is in non-interactive mode
- couples lexical extraction to catalog resolution
- leaves unmatched tags in the prompt instead of stripping and warning
- has no `--strict` mode
- does not offer ambiguity handling that matches the spec
- uses a prefix match tier that the spec does not define

### 4. Matching and naming rules are underspecified in code

The new spec requires:

- exact match
- case-insensitive exact match
- case-insensitive substring match
- launcher-aware name derivation for unnamed servers
- xxHash fallback when no meaningful name can be derived

The current code has useful matching support, but it does not implement the spec's full naming pipeline, and its match ordering is not identical to the new doc.

### 5. CLI UX is still far thinner than the spec

The spec expects:

- interactive add flows
- interactive alias/remove prompting when args are omitted
- `TerminalTable` list output
- alias filtering
- bold emphasis for defaults
- OSC8 links in init re-entry help
- safer remove behavior that distinguishes server deletion from alias deletion

The current CLI is functional, but it is still closer to an engineering tool than the product described in the new docs.

### 6. Storage and command docs are now in conflict

The new spec documents different file locations and default-file shapes than the currently shipped subsystem. There is also a direct conflict around the meaning of `mcp sync`.

That conflict should be resolved deliberately before more code is added. Otherwise we will keep shipping behavior that no single document describes correctly.

### 7. Provider behavior needs hardening before the UX is expanded

Even if the command surface were updated today, the provider layer still needs tightening around:

- native-name round-tripping
- managed ownership bookkeeping
- config overlay vs full replacement
- reactive shadow-home creation for providers that need session-scoped config
- preservation of known provider-specific fields through `provider_overrides`

## Recommended Direction

### 1. Treat the new docs as authoritative for user-facing behavior

The wrapper and `claudine mcp` UX should be driven by the new CLI spec.

### 2. Keep the current library substrate and refactor on top of it

Do not replace the MCP subsystem wholesale. The catalog, defaults, provider-state, import, export, session, and inject modules are the right decomposition. They need semantic cleanup, not removal.

### 3. Split "catalog refresh" from "native provider export"

The new spec uses `mcp sync` to mean "discover/import into the catalog." The current implementation uses `mcp sync` to mean "export Claudine defaults back into a provider config."

Recommended resolution:

- make `claudine mcp sync` mean catalog refresh/import
- introduce `claudine mcp export <provider> [--scope user|repo] [--apply]` for the current write-back behavior
- keep `claudine mcp sync <provider> ...` as a deprecated compatibility alias for one release if compatibility matters

This preserves the existing value while letting the public command surface match the new spec.

### 4. Separate lexical tag parsing from catalog resolution

The wrapper should:

1. lex `#tags` from the prompt according to the doc's start/end-token rules
2. strip those tags from the outgoing prompt regardless of whether they resolve
3. resolve the extracted tag strings against the catalog
4. warn or error according to match outcome and strictness

This is cleaner than the current "only strip if it already resolves" behavior.

### 5. Keep provider rollout unchanged during this refactor

Do not expand provider support as part of this work. The refactor should keep the current rollout:

- runtime injection: Codex, Gemini, OpenCode
- import/export support: Claude, Codex, Gemini, OpenCode, Roo
- no new runtime promises for Goose, Kimi, or Qwen

The focus is spec alignment and product polish, not widening the support matrix.

## Decisions To Settle Before Coding

These are the few places where the new docs are not precise enough, or directly conflict with shipped behavior.

### 1. Canonical storage layout

The new docs describe flat files such as:

- `~/.claudine/mcp-catalog.json`
- `~/.claudine/user-mcp-defaults.json`
- `~/.claudine/repo-mcp-default.json`

The shipped implementation already uses:

- `~/.claudine/mcp/catalog.json`
- `~/.claudine/mcp/defaults.json`
- `~/.claudine/mcp/provider-state.json`
- `<repo>/.claudine/mcp.json`

Recommendation:

- keep the current nested `~/.claudine/mcp/` layout and repo-local `.claudine/mcp.json` as canonical
- update the spec docs to match that layout
- if compatibility is desired, add read support for the flat-file names but do not make them the long-term write target

Reason:

- provider-state already fits naturally in the nested layout
- repo-local defaults are more consistent with Claudine's repo-scoping story than a single global repo-default map
- changing paths now adds migration churn without improving the product behavior the new spec is trying to define

### 2. Ambiguous-tag behavior in non-interactive runs

The spec says ambiguity should prompt interactively by default, unless `--strict` is used.

That does not work in non-interactive runs.

Recommendation:

- in interactive wrapper runs with a TTY: prompt to disambiguate
- in non-interactive wrapper runs: treat ambiguity as a hard error
- `--strict` forces hard-error behavior in both modes

### 3. CLI alias command shape

The spec prefers `claudine mcp alias <name> <alias>`. The current CLI has `alias add` and `alias remove`.

Recommendation:

- add the spec-shaped `alias <name> <alias>` path
- keep `alias add` and `alias remove` as compatibility aliases until docs and scripts are updated

## Phase 1: Tighten The Library API Around Spec Semantics

Files:

- `claudine/lib/src/mcp/catalog.rs`
- `claudine/lib/src/mcp/session.rs`
- `claudine/lib/src/mcp/import.rs`
- `claudine/lib/src/mcp/types.rs`
- `claudine/lib/src/mcp/mod.rs`
- optionally new helpers under `claudine/lib/src/mcp/`

Tasks:

- introduce a clear separation between:
  - lexical tag parsing
  - catalog resolution
  - session composition
- replace the current "resolve or preserve" parser with a tag lexer that follows the doc exactly:
  - `#` at start of string or after whitespace
  - alphabetic character immediately after `#`
  - tag body limited to alphanumeric, `-`, `_`
  - terminates on whitespace or end-of-line
- replace the current match ordering with spec ordering:
  - exact ID
  - exact alias
  - case-insensitive exact
  - case-insensitive substring
- remove the current standalone prefix tier unless the team explicitly decides to document it
- add a richer resolution result type, for example:
  - `Resolved`
  - `Ambiguous { candidates }`
  - `Missing`
- add a server-name derivation helper for imported or manually added unnamed entries:
  - prefer explicit name when present
  - derive from executable when local
  - strip launcher prefixes like `uv`, `npm`, `npx`, `pnpm`, and similar
  - fall back to xxHash of normalized JSON when no good name exists
- add a validation API that can power `mcp check`
  - invalid transport-field combinations
  - duplicate aliases
  - defaults pointing to missing IDs
  - provider-state pointing to missing catalog entries

Completion criteria:

- the library can express every match outcome the new wrapper UX requires
- tag parsing is spec-compliant and independent of the current catalog contents
- name derivation is deterministic and documented
- validation results are available to the CLI as structured data

## Phase 2: Rebuild Session Composition For The New Wrapper Contract

Files:

- `claudine/lib/src/mcp/session.rs`
- `claudine/cli/src/commands/wrap/mod.rs`
- `claudine/cli/src/commands/wrap/env.rs`
- `claudine/cli/src/output.rs`

Tasks:

- make wrapper MCP mode work for both interactive and non-interactive prompt-bearing launches
- add `--strict` to wrapper args
- treat `--mcp`, `--use`, and prompt tags as three separate inputs to the session set
- change wrapper behavior to:
  1. ensure MCP state exists, bootstrapping reactively if necessary
  2. parse and strip tags from the initial prompt
  3. resolve defaults, `--use`, and tags
  4. warn or error according to the outcome
  5. inject runtime config only when the provider supports it
- make unresolved tags follow the spec:
  - strip from prompt
  - warn to stderr
  - continue unless strict mode is active
- make ambiguous tags follow the spec-tightened rule:
  - interactive + TTY: prompt to choose
  - non-interactive: hard error
  - `--strict`: hard error
- improve dry-run and wrapper output to show:
  - active servers
  - which came from defaults, `--use`, or tags
  - cleaned prompt
  - injected env vars and temp files
  - warnings for unmatched tags

Completion criteria:

- `claudine codex "#calendar"` works as an interactive initial prompt
- `claudine codex --non-interactive "#calendar fix this"` works and strips the tag before forwarding
- unmatched tags never leak through to the provider prompt in normal MCP mode
- strict mode produces predictable failures

## Phase 5: Implement The Interactive `mcp init` Product Flow

Files:

- `claudine/cli/src/commands/mcp.rs`
- `claudine/cli/Cargo.toml`
- any prompt helpers under `claudine/cli/src/commands/`

Tasks:

- add `inquire`-based multi-select flow for proactive init
- init flow should:
  1. import/refresh the catalog
  2. prompt for user defaults, defaulting to none selected
  3. if inside a git repo, prompt for repo defaults
  4. save defaults
  5. show the catalog entries
  6. show short usage help for tags, aliases, and list/config commands
- implement re-entry behavior:
  - if user defaults exist and repo defaults for the current repo do not: remind the user of user defaults and offer repo-default selection only
  - otherwise: show a mini-help report with file locations and management commands
- add OSC8 links in the re-entry help output

Completion criteria:

- `claudine mcp init` feels like the product described in the new docs rather than a thin importer
- re-running init is context-aware and not repetitive

## Suggested Implementation Order

1. Phase 0 spec-tightening decisions
2. Phase 1 library semantics cleanup
3. Phase 2 wrapper/session refactor
4. Phase 3 reactive bootstrap
5. Phase 4 command-surface refactor
6. Phase 5 interactive init flow
7. Phase 6 provider hardening
8. Phase 7 output polish
9. Phase 8 docs
10. Phase 9 tests and final verification

This order keeps the high-risk semantics work in the library and wrapper first, then reshapes the CLI surface on top of that.

## Success Criteria

- `claudine mcp` behaves like the new CLI spec, not like the older implementation plan
- `--mcp` remains opt-in and context-efficient
- prompt tags work in both interactive and non-interactive launches
- ambiguous and missing tags behave predictably
- initialization feels intentional and discoverable
- provider runtime injection remains limited to the providers Claudine can genuinely support
- current useful export/apply functionality is preserved, but no longer conflicts with the public meaning of `mcp sync`
- the docs, tests, and shipped behavior all describe the same product
