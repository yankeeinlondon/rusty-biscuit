# Plan: Capture Token And Cost Metrics For Codex, Kimi, And Qwen

## Goal

Extend Claudine's provider adapters and logging path so `Codex`, `Kimi Code`, and `Qwen Code` emit usable token and cost telemetry into `EventMeta.extra`, matching the direction already established for Gemini and OpenCode.

The output of this work should make these metrics available in the JSONL logs without requiring provider-specific post-processing every time we want to report on usage.

## Scope

This plan covers:

- adapter parsing for provider-native usage payloads
- normalization of provider-specific token/cost fields into a stable shape
- preservation of provider-native raw payloads where useful
- tests proving the metrics survive parsing into `EventMeta`
- small documentation updates where the current behavior description would otherwise drift

This plan does not cover:

- SQLite/reporting rollups over these new metrics
- backfilling old logs
- changing provider support levels or adding new hook surfaces
- trying to infer costs for providers that only expose token counts

## Current State

- OpenCode already writes normalized `token_usage` and `cost_usd` into `meta.extra`.
- Gemini already preserves `llm_response`, which can contain `usageMetadata`, but the adapter does not normalize it into a shared `token_usage` shape.
- Codex upstream exposes turn usage, but the current adapter only preserves a `token_usage` field and appears to miss the documented `usage` payload shape.
- Kimi upstream exposes both `context_usage` and `token_usage` on `StatusUpdate`, but the current adapter does not retain either.
- Qwen upstream exposes `usage` in headless `assistant` and `result` events, but the current adapter does not retain it.

## Design Direction

### 1. Normalize the common fields we actually need

For all three providers, prefer a shared structure in `meta.extra`:

- `token_usage`
- `cost_usd` when the provider gives us real cost data
- `context_usage` when the provider gives us real context-window utilization
- `model`, `provider_id`, `model_id` when present and cheap to preserve

Recommended normalized `token_usage` keys:

- `total`
- `input`
- `output`
- `reasoning`
- `cache_read`
- `cache_write`

Not every provider will fill every key. Sparse output is fine. Missing keys are better than fabricated values.

### 2. Keep provider-native payloads too

Normalization helps reporting, but it should not replace raw provider payloads. Keep the original usage-bearing fields under their native names when they are available and useful, for example:

- Codex `usage`
- Kimi `token_usage`
- Qwen `usage`

This reduces future schema churn if we later decide to expose more provider-specific detail.

### 3. Do not infer costs unless the provider provides them

Only write `cost_usd` when the upstream event includes an actual cost value. Do not estimate from token counts, model names, or cached pricing tables in this phase.

### 4. Treat Kimi `context_usage` as first-class

Kimi is the clearest current source for context-window utilization. That field should be preserved directly as `context_usage` instead of being buried in raw event JSON.

## Provider Plans

## Codex

### Upstream shape

The documented non-interactive JSON stream emits `turn.completed` with:

- `usage.input_tokens`
- `usage.cached_input_tokens`
- `usage.output_tokens`

### Current gap

The adapter currently preserves `token_usage` if present, but not the documented `usage` field. That means real Codex usage can be silently dropped depending on which event surface we ingest.

### Implementation tasks

- Update [codex.rs](/Volumes/coding/personal/rusty-biscuit/claudine/lib/src/adapters/codex.rs) to read both `usage` and `token_usage`.
- Normalize Codex usage into:
  - `token_usage.input`
  - `token_usage.output`
  - `token_usage.cache_read`
  - `token_usage.total` when it can be computed safely
- Preserve the original `usage` object in `meta.extra` when present.
- Verify whether `turn.completed` arrives through the existing Codex non-hook path without additional event mapping changes. If not, fix the event-path assumption before finalizing.

### Notes

For Codex, `total` can be computed as `input_tokens + output_tokens` because `input_tokens` already includes cached input in the documented payload. If the actual payload proves otherwise in real runs, drop `total` rather than writing an incorrect number.

## Kimi Code

### Upstream shape

The documented `StatusUpdate` notification includes:

- `context_usage`
- `token_usage.input_other`
- `token_usage.output`
- `token_usage.input_cache_read`
- `token_usage.input_cache_creation`

### Current gap

The adapter maps `StatusUpdate` to `Notification`, but it does not retain either `context_usage` or `token_usage`.

### Implementation tasks

- Update [kimicode.rs](/Volumes/coding/personal/rusty-biscuit/claudine/lib/src/adapters/kimicode.rs) to capture:
  - raw `context_usage`
  - raw `token_usage`
  - normalized `token_usage`
- Normalize Kimi fields into:
  - `token_usage.input` from `input_other + input_cache_read + input_cache_creation` only if we want total input
  - `token_usage.output`
  - `token_usage.cache_read`
  - `token_usage.cache_write`
  - `token_usage.total` only when derived unambiguously
- Write top-level `context_usage` into `meta.extra`.
- Confirm whether `StatusUpdate` payloads arrive nested under a `payload` object in our actual wrapper path. If so, teach the adapter to parse both flat and nested variants.

### Notes

Kimi is the only target in this plan that clearly exposes context-window utilization. That is useful enough to promote directly into normalized metadata even if we do nothing with it yet.

## Qwen Code

### Upstream shape

The documented headless stream emits:

- `assistant` events with `usage`
- `result` events with usage stats and completion info

### Current gap

The adapter currently retains only a few control-plane fields such as approval data and subagent identifiers. It does not preserve `usage`.

### Implementation tasks

- Update [qwen.rs](/Volumes/coding/personal/rusty-biscuit/claudine/lib/src/adapters/qwen.rs) to capture raw `usage` from both assistant-message and result-style payloads.
- Normalize Qwen usage into the shared `token_usage` shape.
- If Qwen exposes actual monetary cost in some result variants, write `cost_usd`; otherwise only keep token counts.
- Verify whether the wrapper emits provider events as `StreamAssistantMessage` / `StreamResult` with usage flattened into the root object or nested inside a child object. Support both if necessary.

### Notes

Qwen is the riskiest of the three because its public CLI surfaces are still moving. The implementation should therefore preserve raw `usage` even if the normalized mapping is initially conservative.

## Shared Implementation Work

## Phase 1: Add a small normalization helper

Introduce a shared internal helper pattern similar to the OpenCode adapter's usage normalization, but do not over-generalize too early.

Recommended options:

- a private helper inside each adapter if field names remain very different
- or a small shared helper in `claudine/lib/src/adapters/mod.rs` or a new internal utility module if duplication becomes obvious

The priority is clarity, not abstraction.

## Phase 2: Tighten adapter parsing

For each provider:

- parse both documented and observed field shapes
- preserve raw provider-native usage objects
- emit normalized `token_usage`
- emit `context_usage` and `cost_usd` when real upstream values exist

## Phase 3: Test the adapter contracts

Add focused unit tests for each provider adapter that assert:

- the event still maps to the correct `AgenticEvent`
- raw usage-bearing fields are preserved
- normalized `token_usage` is present with the expected keys
- `context_usage` is preserved for Kimi
- `cost_usd` is only present when the source payload includes a true cost value

## Phase 4: Validate end-to-end logging behavior

Use `claudine dry-run` or direct adapter tests where possible, then run package tests to ensure no regressions in unrelated provider handling.

## Risks And Decisions

### 1. Real payload shape may differ from the research docs

This is most likely for Qwen and least likely for Kimi. The implementation should prefer defensive parsing and preserve raw objects to reduce churn if live payloads differ.

### 2. `total` token counts can be ambiguous

Some providers expose distinct cached and uncached inputs without an explicit total. Only compute `total` where the arithmetic is clearly correct from the payload semantics.

### 3. Cost semantics may vary

If a provider exposes "cost" in a non-USD unit or in a mixed object, do not flatten it into `cost_usd` unless the unit is clearly USD. Preserve the raw field and defer normalization.

### 4. Event timing differs by provider

Codex usage appears at turn completion, Kimi can report usage mid-turn through notifications, and Qwen can expose usage on message and result events. Logging will therefore remain event-oriented, not session-summary-oriented, in this phase.

## Recommended Delivery Order

1. Fix Codex first.
   It is the smallest and most certain patch, and it closes an actual mismatch between documented payloads and current parsing.
2. Add Kimi next.
   It has the highest-value new field because `context_usage` is directly available.
3. Add Qwen last.
   It is the most likely to require payload-shape adjustment after first implementation.

## Completion Criteria

This plan is complete when:

- Codex logs token usage from documented `turn.completed` payloads.
- Kimi logs normalized token usage and raw `context_usage`.
- Qwen logs normalized token usage from its headless events.
- Unit tests cover all three providers' usage extraction.
- The work is verified with `cargo test -p claudine --lib`, plus `claudine/just` verification as far as unrelated failures allow.
