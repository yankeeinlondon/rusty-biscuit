## Scope

This topic should be handled as **authorized scraping**: content you own, content the site explicitly permits you to access, or content you can access through a legitimate account/session/API. The techniques below are for detecting and handling authentication requirements, not bypassing access controls, paywalls, MFA, CAPTCHA, bot defenses, or terms-of-service restrictions.

## Detecting Auth Requirements

A naive browser or scraper can get fairly complete coverage by treating auth detection as a layered check rather than a single status-code test.

### HTTP Status And Challenge Headers

The clearest signal is `401 Unauthorized` with a `WWW-Authenticate` header. HTTP authentication servers use `WWW-Authenticate` to advertise acceptable auth schemes such as Basic, Digest, or Bearer, and clients reply with an `Authorization` header. See MDN: [`401 Unauthorized`](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Status/401), [`WWW-Authenticate`](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/WWW-Authenticate).

Also inspect:

- `403 Forbidden`: often means credentials are absent, invalid, insufficient, blocked, or not entitled, even when no formal challenge is sent. See MDN: [`403 Forbidden`](https://developer.mozilla.org/en-US/docs/Web/HTTP/Status/403).
- `407 Proxy Authentication Required`: proxy auth rather than origin-site auth.
- `WWW-Authenticate`, `Proxy-Authenticate`, `Authorization`, `Proxy-Authorization`.
- Bearer-token errors such as expired or invalid token challenges.
- Response bodies that say “login required,” “access denied,” “forbidden,” or “not authorized.”

### Redirect Patterns

Many sites do not return `401`; they redirect anonymous users to login.

Detect:

- `301`, `302`, `303`, `307`, `308` redirects to paths like `/login`, `/signin`, `/session/new`, `/auth`, `/oauth`, `/sso`, `/account`.
- Query parameters such as `next=`, `returnUrl=`, `redirect_uri=`, `continue=`.
- Cross-origin redirects to an identity provider.
- Redirect loops caused by missing cookies or blocked session state.

MDN’s redirect guide is useful for the mechanics: [HTTP redirections](https://developer.mozilla.org/en-US/docs/Web/HTTP/Redirections).

### Login Form And Auth UI Detection

When the final HTTP response is `200 OK`, parse the HTML.

Look for:

- `<form>` elements containing password inputs.
- Inputs named like `username`, `email`, `password`, `csrf`, `token`, `otp`, `mfa`.
- Buttons or links with labels like “Sign in,” “Log in,” “Continue with Google,” “SSO,” “Magic link.”
- Hidden CSRF fields.
- OpenID Connect or OAuth URLs.
- CAPTCHA or anti-automation widgets.
- “subscribe,” “upgrade,” “trial expired,” “member only,” or “paywall” text.

A simple static parser can detect many server-rendered login pages. A headless browser is needed when the login UI is generated by JavaScript.

### Cookie And Session Clues

Authentication is usually maintained by cookies or bearer tokens.

Detect:

- `Set-Cookie` on login, challenge, or redirect responses.
- Session-like cookie names: `session`, `sid`, `auth`, `token`, `jwt`, `csrf`, `xsrf`.
- `HttpOnly`, `Secure`, and `SameSite` attributes.
- Whether the same URL returns different content with and without cookies.
- Whether authenticated cookies are scoped to another domain or subdomain.

MDN documents cookie behavior here: [`Set-Cookie`](https://developer.mozilla.org/en-US/docs/Web/HTTP/Headers/Set-Cookie).

### Content Comparison

For high-confidence detection, fetch the same target in multiple states:

- anonymous request
- request with stored cookies
- request with expired/invalid cookies
- request with known-valid credentials, when authorized
- browser-rendered page versus raw HTTP response

Compare:

- final URL
- status
- redirect chain
- title
- canonical URL
- major headings
- content length
- visible text
- structured data
- presence of target selectors

This catches “soft auth” pages that return `200 OK` but contain a login wall instead of the desired content.

### JavaScript And Browser-State Checks

Some auth gates are invisible to raw HTTP clients.

A more complete detector should optionally run a real browser and observe:

- network requests after page load
- XHR/fetch calls returning `401` or `403`
- client-side redirects
- localStorage/sessionStorage usage
- service worker behavior
- iframe-based SSO flows
- post-login route guards
- shadow DOM login widgets

### Anti-Automation And Challenge Detection

Auth-required content is often protected by bot-management systems. Detection should flag, not bypass:

- CAPTCHA, Turnstile, reCAPTCHA, hCaptcha
- Cloudflare or similar challenge pages
- device/browser fingerprint checks
- repeated challenge loops
- rate-limit responses
- bot-score denials

Cloudflare documents Turnstile challenge behavior and bot-like detection signals in its Turnstile troubleshooting docs: [Cloudflare Turnstile challenge solve issues](https://developers.cloudflare.com/turnstile/troubleshooting/challenge-solve-issues/). OWASP also treats scraping, credential stuffing, and bot activity as automated-threat categories: [OWASP Bot Management and Anti-Automation Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Bot_Management_and_Anti-Automation_Cheat_Sheet.html).

## Obstacles Auth-Required Content Presents

### Session State

Obstacle: authenticated pages depend on cookies, CSRF tokens, local storage, refresh tokens, or browser-managed state.

Solutions:

- maintain a cookie jar
- persist authorized sessions securely
- replay only authorized session state
- refresh tokens through supported OAuth/OIDC flows
- detect expiry and re-authenticate through an approved path

### CSRF And Dynamic Form Tokens

Obstacle: login and mutation forms often require per-request tokens.

Solutions:

- load the form page first
- parse hidden token fields
- submit exactly the fields the server expects
- preserve cookies between form fetch and submit
- avoid fabricating tokens

### JavaScript-Rendered Auth

Obstacle: raw HTML may not contain the login form, target data, or post-login route state.

Solutions:

- use a headless browser
- wait for selectors or network idle
- inspect XHR/fetch responses
- extract rendered DOM after scripts run
- prefer official APIs when available

### SSO, OAuth, And OpenID Connect

Obstacle: authentication may involve redirects across identity providers, consent screens, PKCE, device codes, MFA, and callback URLs.

Solutions:

- use protocol libraries for OAuth/OIDC
- use provider-supported device-code or authorization-code flows
- store tokens securely
- do not scrape identity-provider login pages unless explicitly authorized
- prefer service accounts or API credentials when the provider supports them

### MFA, CAPTCHA, And Human Challenges

Obstacle: MFA and CAPTCHA intentionally require human or out-of-band proof.

Solutions:

- treat them as a stop condition
- use official API access, service accounts, or pre-authorized sessions
- require human login once and reuse the resulting authorized session where permitted
- do not automate CAPTCHA bypass or MFA circumvention

### Authorization Versus Authentication

Obstacle: being logged in does not imply access to every resource.

Solutions:

- distinguish `401` from `403`
- detect entitlement/paywall messages
- compare expected content selectors
- track account role, subscription tier, tenant, and scopes
- fail closed when the target data is unavailable

### Rate Limits And Abuse Controls

Obstacle: auth-required sites often apply tighter limits because authenticated scraping can look like account abuse.

Solutions:

- honor documented rate limits
- use backoff and retry budgets
- identify the client clearly when appropriate
- cache aggressively
- prefer batch/export/API endpoints

### Browser Fingerprinting And Bot Detection

Obstacle: some sites inspect TLS behavior, JavaScript APIs, timing, headers, IP reputation, device properties, and automation fingerprints.

Solutions:

- use real browsers for authorized workflows that require browsers
- keep request rates low and human-compatible
- avoid header spoofing as a substitute for authorization
- ask the site owner for API access or allowlisting
- stop when the site presents anti-automation challenges

### Data Visibility

Obstacle: post-login pages may expose only partial data, virtualized lists, paginated APIs, or data embedded in scripts.

Solutions:

- inspect network calls made by the authorized browser session
- use documented API endpoints where available
- handle pagination and lazy loading
- validate extraction by checking expected fields, not just page success

## Rust Crates That Help

### `reqwest`

URLs:

- Repo: <https://github.com/seanmonstar/reqwest>
- Docs: <https://docs.rs/reqwest>
- Crates.io: <https://crates.io/crates/reqwest>

Functional footprint:

`reqwest` is the default high-level Rust HTTP client for this kind of work. It handles async and blocking requests, headers, status codes, redirects, proxies, TLS, forms, JSON, multipart bodies, and optional cookies. Its docs explicitly cover redirect policy and cookie-store support.

Overlap with this topic:

- detect `401`, `403`, `407`, redirects, and auth headers
- submit login forms when authorized
- carry bearer tokens or Basic auth headers
- configure redirect handling to inspect login redirects
- use cookie support for session continuity

Pros versus bespoke:

- mature, widely used, ergonomic
- avoids hand-writing HTTP/TLS/redirect behavior
- integrates with Tokio
- enough control for most non-browser scraping

Cons versus bespoke:

- not a browser
- does not execute JavaScript
- limited for SSO pages, browser fingerprinting, service workers, or rendered DOM
- cookie persistence usually needs extra setup

### `cookie_store`

URLs:

- Repo: <https://github.com/pfernie/cookie_store>
- Docs: <https://docs.rs/cookie_store>
- Crates.io: <https://crates.io/crates/cookie_store>

Functional footprint:

`cookie_store` stores and retrieves cookies according to RFC6265-style domain/path matching rules. Its docs point to `reqwest_cookie_store` for integration with `reqwest`.

Overlap with this topic:

- preserve session cookies
- model browser-like cookie scope rules
- distinguish missing-cookie auth failures from real authorization failures

Pros versus bespoke:

- avoids subtle domain/path/expiry bugs
- better than manually concatenating `Cookie` headers
- useful when session continuity matters

Cons versus bespoke:

- only covers cookies, not full browser storage
- does not handle localStorage/sessionStorage
- persistence format and concurrency strategy are still application concerns

### `reqwest_cookie_store`

URLs:

- Repo: <https://github.com/pfernie/reqwest_cookie_store>
- Docs: <https://docs.rs/reqwest_cookie_store>
- Crates.io: <https://crates.io/crates/reqwest_cookie_store>

Functional footprint:

`reqwest_cookie_store` adapts `cookie_store` to `reqwest::cookie::CookieStore`.

Overlap with this topic:

- makes authorized session reuse practical with `reqwest`
- supports login-then-fetch flows
- helps avoid redirect loops caused by dropped cookies

Pros versus bespoke:

- straightforward integration
- less error-prone than custom cookie jars
- suitable for raw HTTP scraping behind session cookies

Cons versus bespoke:

- still not equivalent to a browser profile
- does not solve CSRF, JavaScript, SSO, or MFA alone

Overlap with this topic:

- detect login forms

Pros versus bespoke:

Cons versus bespoke:

- no JavaScript execution
- no browser layout, events, shadow DOM interaction, or network observation

### `oauth2`

URLs:

- Docs: <https://docs.rs/oauth2>

### `openidconnect`

URLs:

- Repo: <https://github.com/ramosbugs/openidconnect-rs>
- Docs: <https://docs.rs/openidconnect>
- Crates.io: <https://crates.io/crates/openidconnect>

Functional footprint:

Overlap with this topic:

- avoids hand-rolled token parsing and validation

- more setup than raw form scraping
- only applies when the target supports OIDC or exposes enough provider metadata
- does not bypass MFA or consent requirements

## Practical Architecture

For static, authorized pages:

1. Use `reqwest` with explicit redirect handling.
2. Store cookies with `reqwest_cookie_store`.
3. Parse HTML with `scraper`.
4. Detect auth by status, challenge headers, redirect chain, login form markers, and missing target selectors.
5. Store credentials/tokens with `keyring`; hold in-memory secrets with `secrecy`.

For OAuth/OIDC-backed access:

1. Prefer API access over page scraping.
2. Use `oauth2` or `openidconnect`.
3. Persist refresh tokens securely.
4. Treat expired tokens as a refresh workflow, not as a scraping failure.
5. Fall back to browser automation only for an authorized interactive login bootstrap.

For JavaScript-heavy authenticated pages:

1. Use `thirtyfour`, `fantoccini`, `chromiumoxide`, or `headless_chrome`.
2. Log the redirect chain, final URL, cookies, rendered title, and target selectors.
3. Detect CAPTCHA/MFA/bot challenges as stop conditions.
4. Extract data from documented APIs or authorized browser-observed endpoints where permitted.
5. Keep raw browser automation as the slow path, not the default path.

## Core Recommendation

Use a **tiered scraper**:

1. Start with raw HTTP detection using `reqwest`.
2. Add cookie persistence and static HTML parsing.
3. Add OAuth/OIDC protocol support where applicable.
4. Escalate to browser automation only when the page genuinely requires browser execution.
5. Treat CAPTCHA, MFA, bot challenges, paywalls, and entitlement failures as explicit non-bypassable states.
6. Prefer official APIs, exports, service accounts, or allowlisted access whenever available.
