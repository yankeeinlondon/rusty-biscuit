# Scratch-repository fixture, 2026-09-12

A disposable public repository under Ken's account, `rusty-biscuit-ci-scratch`
(id 1367089197), carrying a reduced `ci.yml` whose shape mirrors the real one:
`pull_request` with no branch filter, `push` to `main`, `workflow_dispatch`,
a cancel-in-progress concurrency group, a `scope` job that reads
`.ci-scenario.json`, two area jobs skipped through `if:` when unselected, an
advisory job with `continue-on-error: true`, and no policy job. Every ruleset
write happened here; none touched `rusty-biscuit`. The repository was deleted on 2026-09-12 once this
record was captured; the run and pull-request numbers below are historical.

## Finding 1 — OQ3 Option C is unavailable; Option B is the mechanism

`POST /repos/{owner}/{repo}/rulesets` with a `workflows` rule was rejected
with HTTP 422, "Invalid rule 'workflows': Invalid parameter workflows:
Workflow error at index 0:" (empty reason), in five spellings: path plus
repository id alone; with `ref: refs/heads/main`; with `ref: main`; with the
head `sha`; and with `enforcement: evaluate`. The workflow was registered and
had a completed run at the time. The enterprise-cloud documentation for
available ruleset rules states that ruleset workflows "can be configured at
the organization or enterprise level" only. `rusty-biscuit` is user-owned,
so the rule cannot be applied there. The Chrome extension was not connected,
so the settings page was not inspected; the API refusal plus the
documentation is the evidence.

Option B was then proven: a `ci-gate` job, `needs` every area job plus the
advisory job, `if: always()`, whose only step folds `needs.*.result` and
fails unless every result is `success` or `skipped`. Ruleset
`require-ci-gate` (id 23024971) on the default branch requires the single
status check context `ci-gate` with `strict_required_status_checks_policy:
false`.

## Finding 2 — Option B semantics, one pull request per case

| PR | Scenario | Run | ci-gate | Merge state |
|---|---|---|---|---|
| 4 | s1: every selected area passes (control) | 34682478318 success | success | CLEAN |
| 1 | s2: a selected area fails | 34682460508 failure | failure | BLOCKED |
| 1 | s2 after a fix push | 34682623385 success | success | CLEAN |
| 2 | s3: an area unselected (`if:` skipped job) | 34682463490 success | success | CLEAN |
| 3 | s4: advisory job fails under `continue-on-error` | 34682465836 success | success | UNSTABLE |
| 5 | s5: workflow without the `ci-gate` job | 34682626552 success | never reported | BLOCKED |
| 6 | s6: cancel submitted after every job finished | 34682627617 cancelled | success | CLEAN |
| 9 | s6b: cancel while an area job runs | 34682772764 cancelled | failure | BLOCKED |
| — | `workflow_dispatch` on `main` | 34682621626 success | — | no PR affected |

Observations the spec depends on:

- **A failed selected area blocks** (s2). **An unselected area creates no
  pending requirement** (s3): its job is `skipped`, the fold accepts it.
- **Missing required coverage blocks** (s5): a head whose workflow never
  produces the `ci-gate` check sits at BLOCKED with the check "expected".
- **Cancellation blocks when it interrupts work** (s6b): the cancelled area
  reports `cancelled`, `always()` still runs the gate, the fold fails.
  Cancellation after the gate reported does not retract it (s6): the run's
  conclusion becomes `cancelled` while the required check stays `success`.
  Under Option B the run conclusion is not the gate; the check run is.
- **`continue-on-error` hides a failure from the fold** (s4): the job's
  check shows `failure`, but `needs.advisory.result` is `success` (logged by
  the gate), so the gate passes. GitHub marks the PR UNSTABLE, which is the
  "some checks were not successful" merge-box state, but merging is allowed.
  Every advisory job must therefore carry `continue-on-error` deliberately,
  and the fold must never be given a job whose failure should block.
- **A fix push replaces the verdict** (s2 rerun): the new head's run reports
  a fresh `ci-gate` and the PR clears. **`workflow_dispatch` runs touch no
  pull request.**
- **MISSING detection cannot live in the gate.** `needs` names static job
  ids; a matrix that never created an area's job yields `skipped`, which the
  fold accepts by design. The per-area rollup and the scope job own MISSING,
  as spec section 5 already requires.
- `reuse_validation.py` and `release-plz.yml` key on the run conclusion and
  are unaffected; s6 shows the conclusion can be `cancelled` with a green
  gate, which errs toward not reusing, the safe direction.

## Finding 3 — OQ4 presentation of synthetic check runs

A job with `permissions: checks: write` created check runs through
`POST /repos/{owner}/{repo}/check-runs` on the pull request head with
`status: completed`, a `details_url`, and an `output` title, summary, and
text carrying the ACCEPTED GAP wording.

| PR | Synthetic conclusions | Run conclusion | ci-gate | Merge state |
|---|---|---|---|---|
| 7 | `neutral`, `cancelled`, `skipped` together | 34682629707 success | success | UNSTABLE |
| 8 | `neutral` alone | success | success | CLEAN |

- **A synthetic check run never alters the enclosing run's conclusion**
  (both success), so the release and reuse consumers are unaffected.
- **`neutral` alone leaves the PR CLEAN.** The UNSTABLE state on PR 7 is
  caused by the `cancelled` check. This confirms the premise of the OQ4
  ruling: `cancelled` would have put every accepted-gap PR into the
  "some checks were not successful" state; `neutral` does not.
- The check appears in the PR checks list under its own name with the
  supplied title and summary, attributed to the `github-actions` app.
