# Baseline — the schedule before the cutover

Task 7.4 re-measures against this document on the **same** test identities,
feature arguments, and cache conditions. A number recorded here that Phase 7
cannot reproduce under the same conditions is not a baseline, so every field
below names exactly how it was produced.

## Status of this document

The instrumentation is complete, tested, and lint-clean, and its local
behavior is recorded below. **The hosted cold and warm observations have not
been collected.** Collecting them requires dispatching `ci.yml` with
`measure-compiler-work: true` six times per environment (three cold, three
warm) on each of two revisions, which is outside what these sessions may do:
they were instructed not to commit or push, and three consecutive green hosted
runs per environment cannot be produced any other way.
[deferred-performance-measurements.md](deferred-performance-measurements.md)
records that deferral in full.

The tables below are therefore written with their schema, their exact
collection procedure, and empty observation rows. Task 1.6 stays **unchecked**
in the plan until those rows are filled. Nothing downstream of Phase 1 reads
this document, so Phases 2 and 3 are not blocked by the gap; Task 7.5's
measured architecture gate is.

## The revision these rows are collected on

Review 2 found that this document had no revision to run: the instrumentation
and the ownership cutover arrived as one working-tree change, so dispatching
`feat/single-os` measures the post-cutover schedule and the merge base
`8aa105e7c` has no instrument at all. Neither can produce the pre-cutover
observations the comparison needs.

`scripts/ci/build_baseline_revision.py` constructs the missing revision. It
replays the Phase 1 instrumentation of plan Tasks 1.4 and 1.5 — the
compiler-work counter, its two `just` recipes, and the per-cell measurement
publication — onto the merge base and nothing else:

```sh
python3 scripts/ci/build_baseline_revision.py --explain
```

The output is `fb8681b86902bc3bfe67dfee76bb35727b611eee`, an unreferenced
commit parented on `8aa105e7c`. It is reproducible: the author, committer, and
dates are fixed, so re-running the script yields that same id as long as the
counter tool is unchanged. Should the counter change, refresh every document
that names the id in one step:

```sh
python3 scripts/ci/build_baseline_revision.py --update-documents
```

`scripts/ci/test_build_baseline_revision.py` fails until the documents and the
script agree, so a stale hash cannot survive to send someone dispatching a
commit that does not exist.

Three properties make it usable as an acceptance baseline rather than as an
approximation, and each is enforced by that test suite:

- **The instrument is the same object.** `scripts/ci-build*.rs`,
  `scripts/Cargo.toml`, and `scripts/Cargo.lock` are copied byte for byte from
  the post-cutover tree, so `counter_setup_seconds` is the same cost on both
  sides and cancels exactly.
- **The measured commands are byte-identical to the merge base's.** Timing is
  taken by sibling steps and the wrapper arrives through the gate step's `env:`
  mapping; no `run:` body is rewritten.
- **The cutover is provably absent.** Every line of the merge base's
  workflows and `just/devops.just` survives — the construction removes exactly
  one line, `workflow_dispatch: {}`, which has to grow an input — so no owner
  job, build record, or archive production can be hiding in it.

To dispatch it, push the constructed commit under a throwaway ref (it is
unreferenced until someone names it) and dispatch `ci.yml` on that ref:

```sh
git push origin fb8681b86902bc3bfe67dfee76bb35727b611eee:refs/heads/baseline/ac8-pre-cutover
```

## How to collect the observations

Run this procedure twice: once with `REF=baseline/ac8-pre-cutover` for the rows
below, and once with `REF=feat/single-os` for Task 7.4's. Nothing else differs
between the two collections — same switch, same cache control, same download —
which is what makes them matched.

1. Publish the revision under test. For the pre-cutover half that is the
   `git push` of the constructed commit above; for the post-cutover half it is
   the branch itself. Do **not** rely on the push's own run: `ci.yml` exposes
   `measure-compiler-work` on `workflow_dispatch` only, so a pull-request or
   push run cannot turn it on.
2. For each of the three **cold** observations, delete every Cargo cache entry
   the run would restore, then dispatch. Cold is controlled by that deletion
   and by nothing else; a run is cold only if no `package-ci-*` key existed for
   it at dispatch time:

   ```sh
   REF=baseline/ac8-pre-cutover
   env HOME=/Users/ken gh cache list --limit 100 --json key,id \
       --jq '.[] | select(.key | startswith("package-ci-")) | .id' \
     | while read -r id; do env HOME=/Users/ken gh cache delete "$id"; done
   env HOME=/Users/ken gh workflow run ci.yml --ref "$REF" \
       -f measure-compiler-work=true
   ```

3. For each of the three **warm** observations, dispatch again **without**
   clearing the cache, immediately after a green run on the same revision, so
   `Swatinem/rust-cache` restores the key that run saved. Warm is defined by
   that restore, not by wall-clock speed — which is exactly why the compiler
   invocation count, not the duration, is the primary column below.
4. Identify the three consecutive green runs per environment. "Consecutive"
   is ordered by `run_number` on the one revision, with no intervening
   dispatch of the same condition on that revision; "green per environment"
   means every `{package, environment, gate}` cell of that environment
   concluded `success` in the run. A red or cancelled run does not become the
   first of the next three — it restarts the count for every environment it
   touched, and a re-run of a failed attempt is a new observation, not a repair
   of the old one:

   ```sh
   env HOME=/Users/ken gh run list --workflow ci.yml --branch "$REF" \
       --json databaseId,number,conclusion,createdAt --limit 20 \
       --jq 'sort_by(.number) | .[] | [.number, .databaseId, .conclusion] | @tsv'
   ```

5. Download the measurements and the run timings:

   ```sh
   env HOME=/Users/ken gh run download <run-id> -p 'measurement-*' -D ./measurements
   env HOME=/Users/ken gh api repos/yankeeinlondon/rusty-biscuit/actions/runs/<run-id>/jobs \
       --paginate --jq '.jobs[] | {name, started_at, completed_at}'
   ```

   Each `measurement-<package>-<gate>-<environment>/measurement.json` carries
   `schema_version: 1`, the cell identity, `run_id`, `run_attempt`,
   `job_started_epoch`, `runner_os`, `runner_image`, a `timings` object, and the
   `compiler_work` document `ci-build report --json` produced.
6. `queued_seconds` is **not** in the document, deliberately: parsing a run's
   ISO start needs GNU `date -d` on Linux and BSD `date -jf` on macOS. Compute
   it once, in Python, as `job_started_epoch` minus the run's `run_started_at`
   from the API call above.

## WSL2 is reported as two rows, never one

The plan requires it and the instrumentation enforces it. The `archive` job on
`ubuntu-latest` owns the compile; the guest owns the execution and has no
compiler at all. The archive job's measurement is published as
`measurement-<package>-L1-wsl2-ubuntu` — the compile belongs to that cell even
though another machine performed it — and its `timings` carry
`archive_seconds` separately from `setup_seconds`. This is the only path where
compile and archive are already separable stages; every native tier runs one
Nextest invocation containing both, which is why `gate_seconds` there is not a
compile time.

| Stage | Where it is measured today |
|---|---|
| Linux producer compile + archive | `_wsl-ci.yml` `archive` job, `archive_seconds` |
| Artifact upload | not separately timed before the cutover |
| Guest download / extraction | not separately timed before the cutover |
| Guest test execution | `_wsl-ci.yml` `wsl` job |

Task 7.1 adds the upload, download, and extraction stages. They are listed here
as explicit gaps rather than omitted, so the Phase 7 comparison cannot quietly
fold transfer cost into test time.

## Total runner compute and critical path

Both are properties of the **run**, not of a cell, so they come from the jobs
API rather than from any measurement document:

- **Total runner compute** — sum over every job of
  `completed_at - started_at`. Report Windows separately; its minutes are
  billed at a different multiplier and mixing them hides a regression.
- **End-to-end critical path** — the run's own `run_started_at` to the last
  job's `completed_at`.

## Noise band

A delta within **15%** is noise, per the specification. A regression above that
range requires an explicit design ruling under Task 7.5 and may not be
explained away by transfer time, fewer tests, or a warm cache. Neither a first
hosted run nor merging the branch closes Task 7.4 or Task 7.5; the ruling is a
separate, recorded act.
[deferred-performance-measurements.md](deferred-performance-measurements.md)
carries the full rule and the deferral it is currently blocked behind.
