This is **not new drift**. `.github/ci/README.md` already states it plainly:
"The durable fix for the R11 contract suite (`tools/test-toolkit`,
`gates = false` promotion-pending, expiry 2026-10-31) is its promotion to a
gating package", and the reuse-boundary paragraph is careful to say only that
"the *Python* suite also runs in preflight … and in the CI-tooling job". The
documentation is accurate; no correction is needed.

What is new is the **weight** now resting on it. Confirmed mechanically:

- `test-toolkit` declares `gates = false`, so neither an area job nor the
  pre-push hook schedules it — visible in this head's plan as the `tools` area
  being *selected with zero cells*.
- The `ci-tooling` job runs the nine Python suites and the `ci-rollup` and
  `ci-plan` Nextest bins, and has no `-p test-toolkit` step.

`ci_workflow_contracts.rs` (82 tests) is now the primary evidence behind AC10,
AC11, AC14, AC15, AC16, and AC17, including Phase 8's documentation guard. It
passed 82/82 today only because it was invoked by hand. A workflow or
documentation regression that it would catch can still merge undetected, so six
of this fix's own acceptance criteria are guarded only by whoever remembers to
run it.

## Hosted regression owed for the producer-normalization change

Review 6, finding 1 was implemented locally on 2026-09-12 (every gate command
in `_package-ci.yml` and `_wsl-ci.yml` is a step-level `continue-on-error`
whose outcome the status step folds into the cell's `result`; the area's
rollup is the only path from a failed test, lint, or compile command to
`ci-gate`). The review also demands that this be shown at the hosted
workflow boundary, which needs a commit and a push of a throwaway branch —
forbidden in the implementing session. Run this once a push is authorized,
and record the result as a fixture beside `fixtures/scratch-2026-09-12.md`.

**Reduce the run to one area.** Branch from the implemented tree; touch only
one small package with L1 tests, no L2/browser tier, and `wsl = false` (so
the plan resolves to three native L1 cells and, only if it declares examples
or benches, three `check` cells) plus `.github/ci/ci-baseline.toml`. Nothing
else changes, so the affected scope selects that area alone. Do not dispatch
a full-scope run merely to exercise this small fixture. Its WSL omission is
a fixture cost choice, not a product execution ban. Open a
draft PR from the branch so the run is a `pull_request` run and the merge box
exists. Push each case as its own commit and wait for the run to complete
before pushing the next.

Four cases, in order:

1. **Baselined producer failure.** Add a deterministic failing test gated to
   one environment (`#[cfg(target_os = "linux")]`), and an exact
   `[[failure]]` entry for `{package, ubuntu-latest, L1}` with owner,
   reason, `source_run`, and an unexpired `expiry`. Assert: the job
   `area-ci (<area>) / <package> / test (ubuntu-latest)` concludes
   `success` with the `L1 tests` step red and one `::error` annotation on the
   check run; the artifacts `junit-<package>-L1-ubuntu-latest` (failing
   testcase present) and `status-<package>-L1-ubuntu-latest`
   (`"result":"failure"`) exist; the area's `rollup` grid shows the cell
   `FAIL` with a `baseline-accepted` finding; `area-ci (<area>) / rollup`
   concludes `success`; `area-ci` and `ci-gate` conclude `success`.
2. **The same failure unaccepted.** Remove the baseline entry. Assert: the
   producer job is unchanged (`success`, red step, annotation); `rollup`
   concludes `failure` with a `cell-failed` finding; `area-ci` and `ci-gate`
   conclude `failure`; the PR is BLOCKED.
3. **A missing report.** Keep the baseline entry from case 1 and make the L1
   command fail before nextest can write a report (a `compile_error!` under
   the same `cfg`, so `just _test` exits 101 with no JUnit). Assert: the
   producer job still concludes `success` with the annotation; the status
   artifact says `failure`; the cell is `MISSING`, the baseline does not
   excuse it, `rollup` fails with `cell-missing`, and `ci-gate` fails.
4. **The equivalent failure reused from local evidence.** Restore case 1's
   tree (failing test plus baseline entry) and, on this host, run
   `just ci-local` for that package so the failed L1 cell is recorded and
   published under `refs/notes/ci-local/<environment>`; then push. This
   depends on review-6 finding 2 (a complete failing strict run must publish
   its note) having landed — without it no note reaches the remote and the
   cell simply executes again. Assert: the plan resolves the cell to reuse
   (no `test (ubuntu-latest)` job is scheduled for it), the rollup grid shows
   the reused cell `FAIL` with origin `local` and `baseline-accepted`, and
   `ci-gate` concludes `success` — the same verdict as case 1.

What to read for each case: `gh run view <run-id> --json jobs` for every
job's `conclusion`; `gh api repos/{owner}/{repo}/check-runs/<job-id>/annotations`
for the producer's `::error`; `gh run download <run-id> -n status-<package>-L1-ubuntu-latest`
and `-n ci-results-<slug>` for the folded `result` and the cell's `state`
and findings; `gh pr view <n> --json mergeStateStatus` for the merge box.
Until ruleset `protect-your-bacon` names `ci-gate` instead of `ci-verdict`,
`mergeStateStatus` stays BLOCKED in every case (the required context is
never reported), so the load-bearing assertion is the `ci-gate` check run's
conclusion; note the merge-box state beside it for the record.

The lost-runner path is not part of this regression: `runner_loss.py` reads
job conclusions, a normalized producer concludes `success`, and
`test_a_normalized_gate_failure_is_neither_lost_nor_a_failure` pins that it
