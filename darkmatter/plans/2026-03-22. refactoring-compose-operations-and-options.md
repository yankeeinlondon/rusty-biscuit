# Refactoring Compose Operations and Options

## Motivation

The current compose pipeline has several structural issues:

1. **`Stage1Stages` / `Stage2Stages`** — meaningless names that encode execution order rather than purpose. The documentation uses "Inline Mutation (Pre/Post)" and "Transclusion", which are far more descriptive.

2. **Nested option structs** — `ComposeOptions` contains `Stage1Stages`, `Stage2Stages`, `TransclusionOptions`, and `ShellExpansionOptions` as separate typed structs. This forces callers to understand the internal architecture. A flat key/value approach with well-named, well-documented properties is simpler.

3. **Code/doc ordering mismatch** — the pipeline documentation defines the flow as `Inline Pre → Transclusion → Inline Post → Rendering`, but the code runs cleanup and normalization (post-transclusion ops) *before* transclusion. Page blocks are documented as "Inline Pre" but coded in "Stage 2".

4. **No operation enumeration** — operations are controlled by boolean fields on two separate structs. There is no single type that enumerates all compose operations.

5. **Serial transclusion** — the documentation describes concurrent transclusion (multiple `::file` directives resolved in parallel), but the implementation processes them serially.

|-------|--------------------|--------------------------|------------------|

| 9     | FM Transclusion    | `stage2.fm_transclusion` | Transclusion     |

## Target Pipeline Execution Order (Per Documentation)

```
Inline Pre (serial) → Transclusion (concurrent) → Inline Post (serial) → Rendering
```

## Design

### 1. `ComposeOperation` Enum

A single enum that enumerates every operation in the pipeline, regardless of group or execution phase.

```rust
/// Every discrete operation in the compose pipeline.
///
/// Operations are grouped into three phases for execution:
/// - **Inline Pre**: serial, runs before transclusion
/// - **Transclusion**: concurrent, recursive document inclusion
/// - **Inline Post**: serial, runs after transclusion
#[derive(Debug, Clone, Copy, PartialEq, Eq, Hash)]
pub enum ComposeOperation {
    /// Applies the frontmatter `replace` map to substitute text
    /// patterns throughout the document body.
    TextReplacement,

    /// Evaluates `::block when="..."` / `::end-block` conditional
    /// regions and removes blocks whose conditions are false.
    PageBlocks,

    /// Expands `{{variable}}` handlebars expressions using frontmatter,
    /// environment variables, and context variables.
    Interpolation,

    /// Executes approved `::shell` directives and replaces them
    /// with the command's stdout output.
    ShellExpansion,

    /// Validates all hyperlinks and image references on the page,
    /// reporting broken or unreachable targets.
    LinkValidation,

    /// Resolves `::file` and `::url` directives by including the
    /// referenced markdown document (recursively composed).
    BlockTransclusion,

    /// Resolves `prologue` and `epilogue` frontmatter references
    /// by prepending/appending the referenced documents.
    FrontmatterTransclusion,

    /// Resolves `::code` directives by including file content
    /// as a fenced code block.
    CodeTransclusion,

    /// Expands `::toc-linking` directives by generating a linked
    /// table of contents from an external document's headings.
    TocLinking,

    /// Normalizes markdown formatting: injects blank lines between
    /// block elements and aligns table columns.
    Cleanup,

    /// Adjusts heading levels to ensure a valid hierarchy
    /// (e.g., no H3 before an H2).
    Normalization,
}
```

Add a method that returns the default phase for each operation:

```rust
/// The execution phase an operation belongs to.
#[derive(Debug, Clone, Copy, PartialEq, Eq)]
pub enum ComposePhase {
    /// Serial operations before transclusion.
    InlinePre,
    /// Concurrent recursive document inclusion.
    Transclusion,
    /// Serial operations after transclusion.
    InlinePost,
}

impl ComposeOperation {
    /// Returns the default phase this operation belongs to.
    pub fn phase(&self) -> ComposePhase {
        match self {
            Self::TextReplacement
            | Self::PageBlocks
            | Self::Interpolation
            | Self::ShellExpansion
            | Self::LinkValidation => ComposePhase::InlinePre,

            Self::BlockTransclusion
            | Self::FrontmatterTransclusion
            | Self::CodeTransclusion
            | Self::TocLinking => ComposePhase::Transclusion,

            Self::Cleanup
            | Self::Normalization => ComposePhase::InlinePost,
        }
    }

    /// Returns all operations in their default execution order.
    pub fn default_order() -> &'static [ComposeOperation] {
        &[
            // Inline Pre (serial)
            Self::TextReplacement,
            Self::PageBlocks,
            Self::Interpolation,
            Self::ShellExpansion,
            Self::LinkValidation,
            // Transclusion (concurrent)
            Self::BlockTransclusion,
            Self::FrontmatterTransclusion,
            Self::CodeTransclusion,
            Self::TocLinking,
            // Inline Post (serial)
            Self::Cleanup,
            Self::Normalization,
        ]
    }
}
```

### 2. Flat `ComposeOptions`

Replace the nested structs with a single flat struct. Every field gets a doc comment. Fields that benefit from examples include them.

```rust
/// Configuration for the compose pipeline.
///
/// Controls which operations run, how transclusion resolves references,
/// and provides external state for interpolation and replacement.
///
/// ## Examples
///
/// ```
/// use darkmatter::markdown::compose::ComposeOptions;
///
/// // Default: all operations enabled
/// let options = ComposeOptions::new();
///
/// // Disable cleanup and normalization
/// let options = ComposeOptions::new()
///     .disable(ComposeOperation::Cleanup)
///     .disable(ComposeOperation::Normalization);
///
/// // Only run specific operations
/// let options = ComposeOptions::new()
///     .only(&[ComposeOperation::TextReplacement, ComposeOperation::Interpolation]);
/// ```
#[derive(Clone)]
pub struct ComposeOptions {
    // ── Operation control ──────────────────────────────────────────

    /// Set of operations to execute.
    ///
    /// Defaults to all operations. Use `disable()` or `only()` to
    /// restrict which operations run.
    pub enabled_operations: HashSet<ComposeOperation>,

    // ── Error handling ─────────────────────────────────────────────

    /// When `true`, the pipeline returns an error on the first failure.
    /// When `false` (default), failures are recorded as warnings and
    /// the pipeline continues with remaining operations.
    pub fail_fast: bool,

    // ── Source context ─────────────────────────────────────────────

    /// Source location of the document being composed.
    ///
    /// Required for transclusion to resolve relative `::file` paths.
    /// Set via `with_source_file()` or `with_source_url()`.
    ///
    /// ## Example
    ///
    /// ```
    /// let options = ComposeOptions::new()
    ///     .with_source_file("./docs/README.md");
    /// ```
    pub source: ComposeSource,

    // ── State and data ─────────────────────────────────────────────

    /// External state merged with frontmatter for interpolation and
    /// replacement. Missing or null frontmatter keys are filled from
    /// this value using deep-merge semantics.
    ///
    /// ## Example
    ///
    /// ```
    /// let options = ComposeOptions::new()
    ///     .with_external_state(serde_json::json!({
    ///         "version": "1.2.0",
    ///         "author": "Ken"
    ///     }));
    /// ```
    pub external_state: Option<serde_json::Value>,

    /// Override values that unconditionally overwrite frontmatter keys.
    ///
    /// Unlike `external_state` which only fills missing/null keys,
    /// these values always win regardless of what the frontmatter says.
    pub set_overrides: Option<serde_json::Value>,

    // ── Transclusion ───────────────────────────────────────────────

    /// Maximum recursive transclusion depth before the pipeline
    /// returns an error. Prevents infinite `::file` chains.
    /// Default: 16.
    pub max_transclusion_depth: usize,

    /// Whether `::url` remote transclusion is allowed.
    ///
    /// Disabled by default for security. When false, `::url` directives
    /// are skipped (or error if `fail_fast` is true).
    pub allow_remote_transclusion: bool,

    /// Whether `::file` can include local markdown documents.
    /// Default: true.
    pub allow_local_markdown: bool,

    /// Whether `::code` can include local text files as code blocks.
    /// Default: true.
    pub allow_local_code: bool,

    /// Language tag applied to `::code` blocks when the file extension
    /// is unknown or unmapped. Default: `"txt"`.
    pub code_fallback_language: String,

    /// Overrides the default behavior for invalid transclusion references.
    ///
    /// - `None`: use the document's frontmatter `ignore_invalid` setting
    /// - `Some(true)`: silently skip invalid references
    /// - `Some(false)`: treat invalid references as errors
    pub ignore_invalid_references: Option<bool>,

    /// Whether `@`-prefixed paths resolve to the git repository root.
    /// Default: true.
    ///
    /// ## Example
    ///
    /// When enabled, `::file @/docs/shared.md` resolves relative to
    /// the repository root rather than the current document.
    pub resolve_repo_root: bool,

    // ── Shell expansion ────────────────────────────────────────────

    /// Maximum execution time for a single `::shell` command.
    /// Default: 30 seconds.
    pub shell_timeout: std::time::Duration,

    /// Root directory for shell expansion policy files.
    ///
    /// When set, only commands matching an approval policy in this
    /// directory (or its ancestors) are allowed to execute.
    pub shell_policy_root: Option<PathBuf>,

    /// Working directory for `::shell` command execution.
    ///
    /// When `None`, commands run in the directory of the source file
    /// (if known) or the current working directory.
    pub shell_working_directory: Option<PathBuf>,

    /// Callback for interactive shell command approval.
    ///
    /// When set, commands that require approval call this handler
    /// before execution. When `None`, unapproved commands are skipped.
    pub shell_approval_handler: Option<Arc<dyn ShellApprovalHandler>>,

    // ── Cleanup ────────────────────────────────────────────────────

    /// Controls how blank lines between list items are handled
    /// during the cleanup operation. Default: `Normal`.
    pub list_spacing: ListSpacingMode,

    /// Number of spaces per nesting level for list indentation
    /// during cleanup. Default: 4.
    pub indent_size: usize,

    // ── Internal (crate-private) ───────────────────────────────────

    /// Runtime context captured at construction time (timestamps,
    /// environment variables).
    context: ComposeContext,

    /// When true, external `replace` keys override document `replace`
    /// keys (used during recursive transclusion to inherit parent
    /// replacements).
    pub(crate) replace_parent_wins: bool,

    /// One-off replace map applied only to this document's replacement
    /// stage, never propagated to children.
    pub(crate) one_off_replace: Option<serde_json::Map<String, serde_json::Value>>,
}
```

Builder methods on the new `ComposeOptions`:

```rust
impl ComposeOptions {
    pub fn new() -> Self { /* all operations enabled, context captured */ }

    /// Disables a single operation.
    pub fn disable(mut self, op: ComposeOperation) -> Self {
        self.enabled_operations.remove(&op);
        self
    }

    /// Enables only the specified operations, disabling everything else.
    pub fn only(mut self, ops: &[ComposeOperation]) -> Self {
        self.enabled_operations = ops.iter().copied().collect();
        self
    }

    /// Returns true if the given operation is enabled.
    pub fn is_enabled(&self, op: ComposeOperation) -> bool {
        self.enabled_operations.contains(&op)
    }

    // Existing with_* builders remain (with_source_file, with_external_state, etc.)
    // but with_stages() and with_stage2() are removed.
}
```

### 3. Pipeline Executor Redesign

The `run_compose_pipeline_internal` method should be restructured to follow the documented flow:

```rust
fn run_compose_pipeline_internal(
    &mut self,
    options: ComposeOptions,
    runtime: &mut PipelineRuntime,
) -> MarkdownResult<ComposeReport> {
    let mut report = ComposeReport::new();

    // Merge external state and build effective state (unchanged)
    let effective_state = self.build_effective_state(&options);

    // Phase 1: Inline Pre (serial)
    for &op in ComposeOperation::default_order() {
        if op.phase() != ComposePhase::InlinePre || !options.is_enabled(op) {
            continue;
        }
        self.run_operation(op, &effective_state, &options, runtime, &mut report)?;
    }

    // Phase 2: Transclusion (concurrent)
    self.run_transclusion_phase(&effective_state, &options, runtime, &mut report)?;

    // Phase 3: Inline Post (serial)
    for &op in ComposeOperation::default_order() {
        if op.phase() != ComposePhase::InlinePost || !options.is_enabled(op) {
            continue;
        }
        self.run_operation(op, &effective_state, &options, runtime, &mut report)?;
    }

    report.max_transclusion_depth = runtime.transclusion.deepest_seen;
    Ok(report)
}

### 4. Concurrent Transclusion Design

#### Rayon vs Tokio

| Factor | Rayon | Tokio |
|--------|-------|-------|
| Local file I/O | Good (thread pool handles blocking) | Needs `spawn_blocking` or `tokio::fs` |
| Remote `::url` | Poor (blocks thread pool) | Native async HTTP |
| Recursive compose | Simple (just call recursively) | Needs `block_in_place` or restructuring |
| Already in deps | Yes | Yes |
| Shared mutable state | `Mutex` or collect-then-apply | Same |

**Recommendation: Rayon for the initial implementation.**

Reasoning:

- The vast majority of transclusions are local file reads (`::file`)
- Remote transclusion (`::url`) is disabled by default and rare
- The compose pipeline is CPU-bound (parsing, replacement, interpolation) not I/O-bound
- Rayon's `par_iter` maps naturally to "process N directives, collect results, apply in order"
- Tokio would require making `run_compose_pipeline_internal` async, which cascades through the entire API
- When remote transclusion is needed, Rayon can spawn a `reqwest::blocking` call without issue

If remote transclusion becomes the common case later, we can revisit with a hybrid approach (Rayon for the pipeline, Tokio for HTTP fetches via `tokio::runtime::Handle::current().block_on()`).

#### Concurrent Transclusion Implementation

```rust
fn run_transclusion_phase(
    &mut self,
    state: &EffectiveState,
    options: &ComposeOptions,
    runtime: &mut PipelineRuntime,
    report: &mut ComposeReport,
) -> MarkdownResult<()> {
    // 1. Parse all directives from the current content
    let directives = self.collect_transclusion_directives(options);

    if directives.is_empty() {
        return Ok(());
    }

    // 2. Resolve each directive concurrently with Rayon
    //    Each resolution runs the full compose pipeline on the child document.
    //    The runtime (depth tracker) needs thread-safe access.
    let runtime_mutex = Mutex::new(runtime);

    let results: Vec<(usize, Result<TransclusionResult, MarkdownError>)> = directives
        .par_iter()
        .enumerate()
        .map(|(idx, directive)| {
            let mut local_runtime = {
                let rt = runtime_mutex.lock().unwrap();
                rt.clone_for_child()
            };
            let result = self.resolve_directive(
                directive, state, options, &mut local_runtime,
            );
            // Merge child runtime stats back
            {
                let mut rt = runtime_mutex.lock().unwrap();
                rt.merge_child(&local_runtime);
            }
            (idx, result)
        })
        .collect();

    // 3. Apply results in source order (reverse to preserve offsets)
    let mut sorted = results;
    sorted.sort_by_key(|(idx, _)| *idx);
    for (_idx, result) in sorted.into_iter().rev() {
        match result {
            Ok(resolved) => {
                self.apply_transclusion(resolved, report);
            }
            Err(e) if !options.fail_fast => {
                report.add_warning(ComposeWarning::new("transclusion", e.to_string()));
            }
            Err(e) => return Err(e),
        }
    }

    Ok(())
}
```

**Key design decisions for concurrency:**

- `PipelineRuntime` needs a `clone_for_child()` method that creates an independent depth tracker sharing the same cycle-detection set (via `Arc<Mutex<HashSet<String>>>`)
- Results are collected eagerly, then applied in reverse source order so string offsets remain valid
- The `Mutex` around runtime is coarse-grained but contention is low (lock is held only for the brief clone/merge operations, not during the actual compose work)

## Migration Strategy

### Phase 1: Add `ComposeOperation` and `ComposePhase` enums

- Add the new types to `types.rs`
- No behavioral changes
- Existing code untouched

### Phase 2: Flatten `ComposeOptions`

- Inline all fields from `Stage1Stages`, `Stage2Stages`, `TransclusionOptions`, and `ShellExpansionOptions` into `ComposeOptions`
- Replace `stages` and `stage2` with `enabled_operations: HashSet<ComposeOperation>`
- Add `disable()`, `only()`, `is_enabled()` methods
- Add comprehensive doc comments to every field
- Keep `with_source_file()`, `with_external_state()`, etc. — they're ergonomic

### Phase 3: Fix operation ordering

- Move Page Blocks from after Stage 1 to Inline Pre (between Replacement and Interpolation)
- Move TOC Linking from Stage 1 to the Transclusion phase
- Move Cleanup and Normalization to after Transclusion
- Restructure `run_compose_pipeline_internal` into three explicit phases

### Phase 4: Concurrent transclusion

- Refactor `PipelineRuntime` for thread safety (`clone_for_child` / `merge_child`)
- Collect all transclusion directives (block, frontmatter, code, TOC linking)
- Resolve concurrently with `rayon::par_iter`
- Apply results in source order

### Phase 5: Remove dead types

- Delete `Stage1Stages`, `Stage2Stages`, `TransclusionOptions`
- Move `ShellExpansionOptions` fields into `ComposeOptions` (already done in Phase 2)
- Update all 3 production call sites:
    - `darkmatter/cli/src/commands.rs`
    - `claudine/lib/src/composition/prepare.rs`
    - `claudine/cli/src/commands/wrap/prompt_file.rs`
- Update tests (bulk of the work — ~90 call sites in test code)

### Phase 6: Documentation sync

- Update `darkmatter/docs/darkmatter-compose-pipeline.md` if any design decisions diverge from current docs
- Update `darkmatter/docs/structs/Markdown.md` compose section
- Update the darkmatter skill file

## Open Questions

> NOTE: all open questions have the agreed upon decisions attached now; these are no longer "open"

1. **Caching** — the pipeline doc mentions caching as important for transclusion performance. This plan does not design a cache. That should be a separate plan once the pipeline shape is stable. **VALIDATED**. CACHING COMES LATER AND IS SEPARATE.

2. **Reference Validation** — included in the enum as a placeholder. Its implementation is a separate feature (`darkmatter/features/2026-03-22. link-validation/`). Should it be a no-op variant now, or should we wait until it's implemented to add it? **DECISION**: WAIT UNTIL IT'S IMPLEMENTED.

3. **Code Transclusion** — currently `::code` is handled inside the block transclusion stage. Should it be split into its own `ComposeOperation::CodeTransclusion` variant now (matching the doc's separation) or kept bundled with block transclusion? **DECISION**: SEPARATED AS IT'S OWN OPERATION VARIANT.

4. **Rendering phase** — the pipeline doc shows Rendering as a fourth phase. Should `ComposeOperation` include rendering operations (table rendering, YouTube embedding, etc.) or should rendering remain a separate concern outside the compose pipeline? **DECISION**: THE COMPOSE PIPELINE SHOULD INCLUDE BOTH INLINE MUTATION PHASES AS WELL AS THE TRANSCLUSION PHASE BUT IT SHOULD **NOT** INCLUDE RENDERING. RENDERING WILL BE DOCUMENT AND SEEN AS IT'S OWN PIPELINE PROCESS BUT THIS PLAN DOES NOT NEED TO ADDRESS THE RENDERING PIPELINE.
