# Renderable Refactor Plan (2026-02)

## Summary

Refactor `biscuit-terminal`'s `Renderable` trait so the intuitive API is the correct one:

- Remove current `render(term_width: Option<u32>)`.
- Rename current `fallback_render(term: &Terminal)` to `render(term: &Terminal)`.
- Keep `display(term)` as the newline-safe terminal output method.
- Preserve optimistic rendering via an explicit helper path (instead of overloading `render`).

This is a breaking API change by design.

## Problem

Current API shape causes repeated misuse:

- Developers call `render(...)` by default because it appears primary.
- In most real CLI output paths, terminal-aware rendering is correct.
- The current naming makes the safe/default path look secondary (`fallback_render`).

## Goals

1. Make terminal-aware rendering the default, first-class API.
2. Keep width-constrained/optimistic rendering possible for composition and tests.
3. Eliminate ambiguity between "render for real terminal" and "render optimistic".
4. Minimize behavioral regressions in wrapping, nested layout, and block-level composition.

## Non-Goals

1. Removing `display(term)`.
2. Reworking all component layout semantics.
3. Changing style/theme behavior beyond call-path migration.

## Proposed API

### Trait surface (`biscuit-terminal/lib/src/components/renderable.rs`)

Replace current pair:

- `render(term_width: Option<u32>)`
- `fallback_render(term: &Terminal)`

With:

- `render(&self, term: &Terminal) -> String` (new primary method; old `fallback_render`)
- `render_optimistic(&self, term_width: Option<u32>) -> String` (provided helper)
- `display(&self, term: &Terminal) -> String` (unchanged behavior; delegates to `render`)

Optional helper to reduce repeated width-override boilerplate:

- `render_in_width(&self, term: &Terminal, width: u32) -> String`
  - Clone terminal, set `fixed_width`, call `render(&child_term)`.

## Implementation Phases

## Phase 1: Trait + Core Contract

1. Update `Renderable` trait method signatures.
2. Move doc comments so terminology is consistent (`render` = terminal-aware).
3. Rewire `display()` to call new `render(term)`.
4. Add `render_optimistic()` default implementation using `Terminal::new_optimistic(width)`.

## Phase 2: Component Implementations

Update all `impl Renderable` in `biscuit-terminal/lib/src/components/**`:

1. Rename `fallback_render` implementations to `render`.
2. Convert old optimistic `render(term_width)` logic into:
   - component-local helper (`render_with_width(...)`), or
   - trait-level `render_optimistic(...)` usage.
3. For components that render nested components with relative width:
   - stop calling old `component.render(Some(child_width))`.
   - call `component.render(&child_term_with_fixed_width)`.
4. Priority files for relative-width correctness:
   - `block_quote.rs`
   - `list.rs`
   - `section.rs`
   - `two_column.rs`
   - `compose.rs` / `inline_content.rs` (composition entry points)

## Phase 3: Workspace Call-Site Migration

Migrate all consumers from:

- `.fallback_render(&term)` -> `.render(&term)`
- `.render(None)` / `.render(Some(...))`:
  - If real terminal context exists or should exist: use `.render(&term)`.
  - If intentionally optimistic rendering is required: use `.render_optimistic(...)`.

Expected high-impact packages:

- `biscuit-terminal` (lib + cli + examples)
- `darkmatter/lib`
- `sniff/cli`
- `claudine/lib` and `claudine/cli`
- `homelab/cli`
- `model-citizen/cli`
- `playa/cli`

4. Ensure no stale references remain:

## Risk Register

## R1: Nested width regressions

- Risk: Child components overflow quote/list/column containers.
- Mitigation: use fixed-width child terminals for nested render calls.

## R2: Behavior drift from optimistic to terminal-aware rendering

- Risk: output changes in places that previously forced optimistic capabilities.
- Mitigation: explicitly use `render_optimistic(...)` where deterministic optimistic output is required (tests, badges, static templates).

## R3: Silent newline behavior changes

- Risk: Call sites switch away from `display` and lose newline guarantees.
- Mitigation: keep `display` contract unchanged; verify direct `print!` paths.

## R4: Documentation mismatch

- Risk: guidance remains split between old/new method names.
- Mitigation: include docs sweep in same PR.

## Acceptance Criteria

1. No `fallback_render(` references remain in workspace source/docs (except migration notes).
2. No compile errors from old `render(Option<u32>)` signature.
3. All targeted package tests pass.
4. Direct terminal output paths still use `display()` where newline normalization is required.
5. Relative-width containers (`BlockQuote`, lists, columns, sections) render nested content with terminal-aware behavior and correct wrapping.

## Suggested PR Sequence

1. PR 1: Trait refactor + component implementation migration in `biscuit-terminal`.
2. PR 2: Cross-package call-site migration + docs drift cleanup.
3. PR 3 (optional): Follow-up normalization (prefer `display` for direct `print!` call sites).
