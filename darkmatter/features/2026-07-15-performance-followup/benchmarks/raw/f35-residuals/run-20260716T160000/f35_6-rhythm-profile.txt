Interpretation
--------------
`strip_escape_codes` takes `Into<String>`, so the pre-change predicate allocated
TWICE per output line: an owned `String` copy of the line, then the regex's
replacement output. Driving the same canonical `ANSI_ESCAPE_RE` directly over the
borrowed `&str` returns a `Cow` that BORROWS when the line carries no escape
code, and hoisting the `\x1b[48` background-fill test ahead of the strip decides
every filled row without touching the regex at all (`&&` over two pure operands,
so the reorder is result-preserving).

Every case improved; there is no regression, including the escape-free body,
which the candidate now handles with zero allocations (-30.3%).

End-to-end: the pass accounted for ~164.8 us of a decorated `toc_medium` render;
the same render now spends 14.8 us there. Reconstructing the baseline render as
582.5 + (164.8 - 14.8) = ~732.5 us, the rhythm pass fell from ~22.5% of a
decorated render to 2.55%, i.e. the decorated render path itself is ~20% faster.
This clears the declared 10% floor by a wide margin on the target operation AND
on the operation that contains it.

Disposition: ACCEPTED (implementation win).

Cross-platform classification: OS-IDENTICAL, confirmed from the actual diff.
The change is a pure in-memory string/regex predicate: one `Cow`-returning
`replace_all` and a reordered `&&`. No `cfg`, no filesystem, no terminal I/O, no
OS-divergent behavior. The regex is the same shared `ANSI_ESCAPE_RE` static that
`strip_escape_codes` already used on every platform. Windows compile + the macOS
behavioral run + ordinary Linux CI are sufficient per the Verification Matrix.
