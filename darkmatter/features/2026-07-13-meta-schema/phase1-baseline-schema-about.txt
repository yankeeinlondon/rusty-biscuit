 SimplifiedSchema Language Reference

 A SimplifiedSchema describes the frontmatter a Markdown file expects. Put it
 under $schema to name required fields, allowed types, defaults, and simple
 constraints. Darkmatter uses that schema when you run md schema validate and
 during compose, so invalid frontmatter fails early and common string values
 can be coerced before the page is rendered.

 Use this as a quick authoring reference: what shapes are allowed, which type
 keywords exist, which constraints can be attached, and what Darkmatter does
 with values during compose.

 Schema Shapes

 A $schema value can use any of these forms. Choose the simplest shape that
 describes the frontmatter you expect.

 - Single object. Use this for the common case: property names mapped to type
   expressions.
   - Example: title: string(required)
 - Root-level union. Use this when a document may follow one of several
   schema alternatives.
   - Example: - title: string\n- ./schemas/post.yaml
 - Property-level union. Use this when one property may have one of several
   allowed types.
   - Example: data: [string, "{ foo: string }"]
 - Inline object literal. Use this to validate a nested object without
   creating a separate schema file.
   - Example: { foo: string(required), bar: number }
 - Nested mapping object. Use a YAML mapping as a property value to declare a
   nested object shape. Equivalent to the inline object literal for the
   cases both forms can express; the mapping form additionally permits
   sequence union arms without quoting.
   - Example: addr:\n  street: string\n  zip: number

 Any of the above types can be made into an array by adding [] to the end of
 the type:

                                                                         yaml 
                                                                              
  $schema:                                                                    
      # a string type                                                         
      foo: string                                                             
      # can be made into a string array                                       
      bar: string[]                                                           
                                                                              

 All types listed here, including those with the [] array modifier, can add
 constraints to the type by putting parentheses after the type. Multiple
 constraints are always delimited by the ; character. As an example:

                                                                         yaml 
                                                                              
  $schema:                                                                    
    foo: string(required)                                                     
    bar: "number(required; min(0); max(10))"                                  
    baz: "string[](min(1))"                                                   
                                                                              

 In this example, constraints are added to a string, a number, and an array
 of strings. The next section lists the available constraints.

 ▐   Note: the values in schemas must be valid YAML strings. In some cases
 ▐   you won't need to put single or double quotes around them, but you can
 ▐   always quote the string and then you don't need to think about it.

 Constraint Vocabulary

 Constraints go inside (...) after a type, separated by commas or semicolons.
 They narrow what a value may contain or provide metadata such as defaults.

 Trigger Schemas

 Trigger schemas activate an object-schema payload for matching documents.
 Their match language is pure and side-effect-free.
 - Envelope. kind: trigger-schema — Claims a discovered YAML file as a
   trigger envelope; $schema is its merge-compatible object-schema payload.
 - Property condition. property: type-expr — A bare expression is an optional
   guard; required makes it a presence gate. Present values must satisfy
   the type and match-safe constraints.
 - $path. $path: glob | \[glob, ...\] — Matches the case-sensitive, boundary-
   relative path with / separators. Basename globs match in any directory
   and ! patterns exclude.
 - all. all: \[condition, ...\] — Matches when every child condition matches.
 - any. any: \[condition, ...\] — Matches when at least one child condition
   matches.
 - none. none: \[condition, ...\] — Matches when no child condition matches.
 - min-match. min-match: { count: N, of: \[condition, ...\] } — Matches when
   at least N of the child conditions match.
 - Outer OR arms. match: \[arm, ...\] — A mapping is one arm; a sequence of
   arm mappings is OR'd. Mixing property and structural keys in one mapping
   is invalid.
 - Vacuous-arm lint. each arm requires a positive gate — Every satisfiable
   arm must require presence through required or $path, outside none; an
   arm that could match every document is rejected.
 Match-safe constraints only: required, <members>, pattern, min, max,
 integer, not-empty, unique, min-keys, max-keys. Constraints such as default,
 generated, suggest, eager, match, and scheme are rejected because trigger
 evaluation cannot transform values or consult external state.
