## Findings

### 1. [Medium] Reference-analysis persistent cache still does not match compose cache semantics

Relevant code:

- `darkmatter/lib/src/markdown/reference/graph.rs:37-45`
- `darkmatter/lib/src/markdown/compose/mod.rs:203-206`
- `darkmatter/lib/src/markdown/compose/cache/store.rs:44-58`
- `darkmatter/lib/src/markdown/reference/validate.rs:398-407`
- `darkmatter/lib/tests/reference_integration.rs:513-565`

`make_cache()` now attaches a persistent `RunLocalCache`, which is an improvement, but it still does not resolve the cache path the same way the compose pipeline does.

Current behavior:

- reference analysis uses `cache.with_persistent(root.clone())`
- compose uses `FileStore::resolve_cache_root(Some(root), options.cache_namespace.as_deref())`

That means the reference-analysis path and the compose path can still point at different persistent cache roots for the same `ComposeOptions`, and `cache_namespace` is still ignored on the reference-analysis side.

Impact:

- `reference_graph()` / `validate_references()` may not share the same persistent cache tree as `compose_with()`
- branch/profile namespace isolation is still not honored consistently
- the new cache tests only prove “works when `cache_root` is set”, not that the intended persistent cache location is actually reused

Recommendation:

- construct the analysis cache using the same `resolve_cache_root(...)` logic as compose
- honor `cache_namespace` when building the reference-analysis runtime
- strengthen the cache tests to assert cache-path parity or observable cache reuse, not just successful execution

### 2. [Medium] `set_meta_tag()` only updates a narrow string shape of existing valid meta tags

Relevant code:

- `darkmatter/lib/src/markdown/reference/meta.rs:143-215`
- `darkmatter/lib/src/markdown/reference/meta.rs:297-364`

The new `set_meta_tag()` implementation works for the exact shapes covered by the tests, but `replace_existing_meta_tag()` is still a literal substring matcher. It only recognizes tags that begin with one of these exact prefixes:

- `<meta name="key"...`
- `<meta property="key"...`
- `<meta charset="...`

That misses many valid existing tags, for example:

- reordered attributes: `<meta content="Alice" name="author">`
- extra spaces: `<meta   name="author" content="Alice">`
- additional attributes before the key attribute
- uppercase tag/attribute spellings

In those cases the public contract is wrong: instead of updating the existing tag, `set_meta_tag()` will append a second meta tag at the end of the document.

Recommendation:

- drive updates from parsed tag structure rather than raw substring search
- at minimum, add tests for reordered attributes, extra whitespace, and additional attributes so the current limitations are explicit

### 3. [Low] `transclusions().resolved_target` still does not use the same resolution semantics as graph/validation

Relevant code:

- `darkmatter/lib/src/markdown/reference/mod.rs:76-90`
- `darkmatter/lib/src/markdown/reference/mod.rs:131-155`

`transclusions()` now fills `resolved_target`, but it still does so with a simple `base_path.parent().join(...)`. The graph builder and validator were upgraded to use `biscuit_file::FileReference` semantics, but the local transclusion query was not.

Impact:

- `resolved_target` can still be wrong for repo-root `@...` paths
- the local query can disagree with graph/validation resolution for the same directive

Recommendation:

- resolve `TransclusionRef.resolved_target` through the same `FileReference` path logic used elsewhere
- add a test for an `@repo-root/...` target once that behavior is wired in

## Test Coverage

The new tests materially improved confidence, and they do cover the big issues from `review-2`.

The main remaining coverage gaps are now very specific:

- cache tests should verify actual persistent-cache reuse/parity, not just success with `cache_root` set
- meta-tag tests should cover real-world existing tag shapes, not only the canonical forms generated by `build_meta_tag_html()`
- transclusion-resolution tests should verify `resolved_target` correctness, not just presence

## Overall

I do not see any remaining high-severity blockers on the original `review-2` scope. The implementation is close.

The remaining work is mostly about consistency and robustness:

1. make persistent-cache behavior line up exactly with compose
2. harden `set_meta_tag()` against valid existing HTML
3. make `transclusions().resolved_target` use the same path semantics as the rest of the subsystem
