## Unblocked Findings

### R9-F1 (high) — Equivalent recursive declarations conflict when one is written inline

**Authority.** Section 6 says “Resolve named types and object composition before comparing declarations” and “Coalesce identical resolved declarations.” The acceptance criteria require both equivalence and strict narrowing to work. The defect class is using the depth at which a named type was expanded as part of the comparison. Darkmatter expands each side until that side encounters its own reference cycle. When the two declarations start at different depths, the equality check meets a remaining reference on one side and an equivalent inline object on the other, and rejects the pair. Both the strict-narrowing rule check and root-union ownership use that equality check. [Spec §6](spec.md#6-when-two-of-a-hosts-triggers-declare-the-same-property), [Darkmatter expansion](../../lib/src/config/registration/merge.rs#L332), [recursive equality](../../lib/src/config/registration/merge.rs#L777), [narrowing](../../lib/src/config/registration/merge.rs#L525), [arm ownership](../../lib/src/config/registration/merge.rs#L871).

Publish Claudine under a temporary home, register its manifest there, and edit the installed `composition.yaml` and `inline-composition.yaml`. Give both the match `prompt: string(required)` and the same local type. This is the tree shape already used by the registered merge suite. Use `review-model: Node` in one payload and `review-model: "{ name: string, children: Node[] }"` in the other.

```yaml
types:
    Node: "{ name: string, children: Node[] }"
```

Refresh the two manifest digests with biscuit-hash. In a document with `prompt: Say hello`, set `review-model: { name: root, children: [{ name: leaf }] }`. With either trigger alone the document validates, and changing the child's name to a list produces a child type error. With both triggers, preparation fails with `dm.host.trigger_conflict` on `review-model` and says their equivalent types differ in a nested declaration. The same result occurs when both declarations refer to a single shared library type and one writes its outer object inline. Recursive types are realistic registration input. Claudine already ships recursive sequence and lifecycle declarations. [Existing tree fixture](../../lib/tests/l1/host_trigger_merge.rs#L186), [Claudine sequence types](../../../claudine/registration/sequence.yaml), [Claudine lifecycle types](../../../claudine/registration/lifecycle-events.yaml).

## Recurrence

R9-F1 belongs to the comparison class in [review 8's R8-F1](review-8.md#unblocked-findings), with the earlier strict-narrowing and alternative-pairing work in [review 7](review-7.md#unblocked-findings) and [review 6](review-6.md#unblocked-findings). The review-8 cases used nonrecursive inline equivalents or recursive references on both sides. The newly found sibling pairs a recursive reference with an inline unfolding. For the plain-object case the source before the repair series could open a plain reference against an inline type and then compare the two child references as a pair. The review-8 repair log records removing that mixed-reference branch. Current code rejects the surviving mixed pair after separately expanding the two trees. The comparison change should have swept recursive named-versus-inline operands through equivalence, strict narrowing, ownership, and the nested collection sites that use the same equality check. No older ledger case reproduced this input. The acceptance criteria explicitly require equivalence and strict narrowing, so those cases belong in one bounded comparison repair. [Repair log](log.md#implementation-of-review-findings-8), [current comparator](../../lib/src/config/registration/merge.rs#L777).
