# Review

## Findings

1. High: quoted property-form JSON5 payloads are parsed as plain strings, so spec examples like `set.author='{name: null}'` and `set.a='{y:2}'` do not work as designed. In [darkmatter/lib/src/markdown/compose/transclusion/parser.rs:194](../../lib/src/markdown/compose/transclusion/parser.rs#L194) the property path treats any quoted RHS as `Value::String` instead of parsing the stripped contents as JSON5. That directly contradicts the spec's property-form grammar and null/deep-merge examples. I verified this end to end with:

   ```bash
   cargo run -q -p darkmatter-cli -- compose "$tmpdir/parent.md"
   ```

   where `parent.md` contained `::file ./child.md set.author='{name: null}'`; the composed output was `{name: null}`, meaning the child received a string instead of an object and the merge semantics never happened.

2. High: the permissive-mode feature from the spec/plan is not implemented end to end. The library has `ComposeOptions` fields/builders for `allow_invalid_frontmatter_assignment` and `allow_reassigned_frontmatter_property` in [darkmatter/lib/src/markdown/compose/types.rs:296](../../lib/src/markdown/compose/types.rs#L296) and [darkmatter/lib/src/markdown/compose/types.rs:692](../../lib/src/markdown/compose/types.rs#L692), and `BlockOptions` even has `deferred_set_errors` in [darkmatter/lib/src/markdown/compose/transclusion/types.rs:77](../../lib/src/markdown/compose/transclusion/types.rs#L77), but none of that is wired into the parser or engine. The parser still hard-errors immediately on invalid/duplicate setters in [darkmatter/lib/src/markdown/compose/transclusion/parser.rs:215](../../lib/src/markdown/compose/transclusion/parser.rs#L215) and [darkmatter/lib/src/markdown/compose/transclusion/parser.rs:233](../../lib/src/markdown/compose/transclusion/parser.rs#L233), so sibling-valid clauses cannot survive, right-most-wins is impossible, and the engine never resolves deferred errors before applying overlays in [darkmatter/lib/src/markdown/compose/mod.rs:1496](../../lib/src/markdown/compose/mod.rs#L1496). On top of that, the CLI surface from the spec is missing entirely: `md compose --help` has no `--allow-invalid-frontmatter-assignment` or `--allow-reassigned-frontmatter-property`, which matches the absence of those args in [darkmatter/cli/src/args.rs:79](../../cli/src/args.rs#L79) and the lack of plumbing in [darkmatter/cli/src/commands.rs:193](../../cli/src/commands.rs#L193) and [darkmatter/cli/src/commands.rs:421](../../cli/src/commands.rs#L421).

3. Medium: test coverage is much lighter than the spec and plan called for. There is good parser coverage in [darkmatter/lib/src/markdown/compose/transclusion/parser.rs:453](../../lib/src/markdown/compose/transclusion/parser.rs#L453) and pure merge coverage in [darkmatter/lib/src/markdown/compose/state.rs:756](../../lib/src/markdown/compose/state.rs#L756), but I could not find end-to-end library or CLI tests for the important behavior this feature adds: overlay-first page-block evaluation, child interpolation through `set.*`, `replace:` observing overrides, child `::shell` seeing overrides, grandchild isolation, cache-key partitioning by overlay, strict-vs-permissive handling, or the worked example from the spec. The compose CLI section in [darkmatter/cli/tests/cli.rs:386](../../cli/tests/cli.rs#L386) still only covers generic compose behavior plus top-level `--set`; nothing there exercises transclusion-level setters.

4. Medium: the warning/output/docs/skill work described in the plan was not finished, which leaves the feature hard to discover even where the happy path works. CLI warning emission is still the generic `Status::from_prose` loop in [darkmatter/cli/src/commands.rs:737](../../cli/src/commands.rs#L737), not the `Status + BlockQuote` presentation with context/hyperlinking specified in the plan/spec. The user docs still enumerate `replace`, `quotation`, `disclosure`, `exclude`, and `when` only in [darkmatter/docs/transclusion/block-transclusion.md:96](../../docs/transclusion/block-transclusion.md#L96), with no `set` option at all; the compose-pipeline doc similarly has no note about parent-side interpolation passthrough in [darkmatter/docs/darkmatter-compose-pipeline.md:39](../../docs/darkmatter-compose-pipeline.md#L39), and the skill still lists transclusion capabilities without mentioning `set` in [.claude/skills/darkmatter/SKILL.md:47](../../../.claude/skills/darkmatter/SKILL.md#L47).

## Ergonomics / Performance Notes

- The current overlay application in [darkmatter/lib/src/markdown/compose/mod.rs:1559](../../lib/src/markdown/compose/mod.rs#L1559) does an extra clone/collect into a temporary `Map`, then clears and reinserts into the child frontmatter. An owned `apply_set_overrides_owned(Map, ...) -> Map` API would be simpler and avoid one full map rebuild per transclusion.
- `deferred_set_errors` currently reads as unfinished design residue: it is documented in [darkmatter/lib/src/markdown/compose/transclusion/types.rs:77](../../lib/src/markdown/compose/transclusion/types.rs#L77) but never populated or consumed. Either wire the deferred path fully or remove the field until permissive mode actually exists.
