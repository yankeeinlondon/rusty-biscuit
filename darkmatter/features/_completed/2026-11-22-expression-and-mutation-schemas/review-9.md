### R9-F2 (high) The shared review schema accepts a plan as its specification

**Authority (regression).** For a Markdown file using `schemas/review-fix-cycle.yaml`, start with the same valid review input and change only `spec: ./spec.md` to `spec: ./plan.md`. Both files exist and the plan is easy to select because it sits beside its specification. The schema at `HEAD` rejects the edit at `/spec`. The worktree schema accepts it, and the Level 1 corpus test fails before it exercises any Markdown input. [Shared cycle schema](../../../schemas/review-fix-cycle.yaml#L16), [Corpus test](../../lib/tests/l1/shipped_schema_corpus.rs#L1096)

In a single mapping, the same rule guides completion. A bare or explicit spelling of the real specification should both validate. Replacing it with an existing non-specification filename should fail. A temporary copy exporting `- $extends: cycle-inputs` as its only arm restored the refusal, with the revised field definitions still in place. [Simplified Schema file contract](../../../simplified-schema/docs/topics/language/types.md#files), [Schema lowering](../../../simplified-schema/lib/src/simplified/convert.rs#L2200)

### R9-F1 (medium) Library entry points can lose the root document's checkout

**Authority (defect).** A Rust caller following Darkmatter's documented relative-source example can open `vendor/review.md` from the project directory and pass that same relative path to `ComposeOptions::with_source_file`. If `vendor` is a separate checkout with its own `schemas/review.yaml`, schema preparation fails. Loading the same file and preparing the same request with absolute paths succeeds. A library reference graph also fails against the bare schema when the already-loaded Markdown is the only source of the absolute file path. [Darkmatter request example](../../docs/topics/compose-requests.md#preparing-a-request), [Source admission](../../lib/src/markdown/compose/context/options.rs#L175), [Root handling in the reference graph](../../lib/src/markdown/reference/graph.rs#L117)

The defect class is assigning a file's checkout from how the caller supplies its source instead of from the resolved document. A relative path with a captured launch directory and an absolute path to the same document must yield the same checkout. An unresolved schema name must still fail. With distinct files at `app/marker.md` and `app/vendor/marker.md`, `&marker.md` in the component must pick the component file.

The probes used a launch repository named `app`, a nested Git-file checkout at `app/vendor`, and a second nested checkout under a different repository. Each component had a schema requiring `description`, a type library, and a note with `description: Review heading` and a heading rendered from it. I ran a Rust program linked to the worktree library from the launch directory. For the relative input it used `with_source_file("vendor/review.md")` and loaded the same relative Markdown path. The other variants used an absolute request and document path, an absolute document with a relative request path, or the loaded absolute document with no source on the request.
