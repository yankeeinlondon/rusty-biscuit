# Review: Shell Expansion in Frontmatter

## Findings

1. High: frontmatter shell expansion stores combined `stdout` + `stderr`, not `stdout` only.
   The spec defines frontmatter shell expansion as "run shell commands whose STDOUT content will be placed into this Frontmatter property". The current implementation reuses the body shell executor, which combines `stdout` and `stderr` on success in [`darkmatter/lib/src/markdown/compose/shell_expansion/executor.rs:171`](../../lib/src/markdown/compose/shell_expansion/executor.rs#L171), and frontmatter expansion writes that combined string back into frontmatter in [`darkmatter/lib/src/markdown/compose/frontmatter_shell_expansion.rs:234`](../../lib/src/markdown/compose/frontmatter_shell_expansion.rs#L234). A command that succeeds but writes warnings to `stderr` will pollute the frontmatter value, which is outside the design contract.

2. High: malformed or rejected frontmatter shell expressions are silently ignored instead of failing compose.
   `parse_shell_value()` returns `Option` and collapses every parse/validation failure into `None` in [`darkmatter/lib/src/markdown/compose/frontmatter_shell_expansion.rs:65`](../../lib/src/markdown/compose/frontmatter_shell_expansion.rs#L65), including invalid timeout suffixes, tokenizer failures, and executable-token interpolation rejection. `scan_frontmatter()` then just skips those values in [`darkmatter/lib/src/markdown/compose/frontmatter_shell_expansion.rs:162`](../../lib/src/markdown/compose/frontmatter_shell_expansion.rs#L162). That means `$({{cmd}} arg)`, `$(echo)::timeout:0`, or other malformed values remain as inert strings instead of producing the hard failure the design implies for invalid/rejected frontmatter shell directives. This is also a security problem: the "executable may not come from interpolation" rule is currently enforced as a silent no-op.

3. Medium: the required concurrent execution of top-level frontmatter shell commands is not implemented.
   The design explicitly calls for concurrent execution because top-level frontmatter shell expressions are independent. The implementation executes candidates in a plain `for` loop in [`darkmatter/lib/src/markdown/compose/frontmatter_shell_expansion.rs:220`](../../lib/src/markdown/compose/frontmatter_shell_expansion.rs#L220). This is both a spec gap and a performance issue for documents with multiple expensive shell calls.

4. Medium: discovery/preflight is not using the same frontmatter preparation path as real compose, so approvals can drift from execution.
   Real compose applies external-state merge and `--set` overrides before frontmatter interpolation and shell expansion in [`darkmatter/lib/src/markdown/compose/mod.rs:307`](../../lib/src/markdown/compose/mod.rs#L307). `collect_shell_commands()` does not do that; it clones the document, optionally interpolates frontmatter, and scans immediately in [`darkmatter/lib/src/markdown/compose/shell_expansion/discovery.rs:93`](../../lib/src/markdown/compose/shell_expansion/discovery.rs#L93). It also calls `scan_frontmatter(..., None)` in [`darkmatter/lib/src/markdown/compose/shell_expansion/discovery.rs:104`](../../lib/src/markdown/compose/shell_expansion/discovery.rs#L104), so discovery does not enforce the executable-provenance rule that runtime compose uses. In Claudine's pre-approved flow, this can miss commands introduced by external state or `--set`, and it can ask approval for commands that runtime compose will later reject or skip.

5. Medium: `--allow-shell-timeout` / `ShellTimeoutBehavior::EmptyString` never emits the required warning.
   The design says timeout-to-empty-string should still emit a warning so stalled commands do not disappear silently. The executor currently returns `Ok(String::new())` directly for timeout fallbacks in [`darkmatter/lib/src/markdown/compose/shell_expansion/executor.rs:224`](../../lib/src/markdown/compose/shell_expansion/executor.rs#L224). Neither the body shell stage in [`darkmatter/lib/src/markdown/compose/mod.rs:969`](../../lib/src/markdown/compose/mod.rs#L969) nor the frontmatter shell stage in [`darkmatter/lib/src/markdown/compose/frontmatter_shell_expansion.rs:252`](../../lib/src/markdown/compose/frontmatter_shell_expansion.rs#L252) has any side channel for turning that into a `ComposeWarning`. So the fallback mode is implemented as silent data loss.

## Test Coverage Gaps

- `darkmatter/lib/src/markdown/compose/frontmatter_shell_expansion.rs:278` through [`darkmatter/lib/src/markdown/compose/frontmatter_shell_expansion.rs:505`](../../lib/src/markdown/compose/frontmatter_shell_expansion.rs#L278) is almost entirely happy-path coverage. I did not find tests for non-zero exits, blacklisting, approval denial, timeout override behavior, timeout-warning behavior, or malformed frontmatter expressions becoming hard errors.
- The integration coverage in [`darkmatter/lib/src/markdown/compose/mod.rs:3823`](../../lib/src/markdown/compose/mod.rs#L3823) through [`darkmatter/lib/src/markdown/compose/mod.rs:3912`](../../lib/src/markdown/compose/mod.rs#L3912) only exercises positive compose flows. There is no integration test for the security rule around interpolated executables, no test for frontmatter timeout fallback, and no test that multiple frontmatter commands execute concurrently.
- The CLI exposes `--timeout` and `--allow-shell-timeout` in [`darkmatter/cli/src/args.rs:142`](../../cli/src/args.rs#L142), but I could not find corresponding end-to-end coverage in `darkmatter/cli/tests/cli.rs`. There should be CLI tests that prove timeout errors, timeout-to-empty behavior, and warning emission actually work from the user surface.
- There is no coverage showing preflight symmetry for frontmatter commands introduced via `external_state` or `--set`, even though the runtime path supports those inputs.

## Ergonomics / Performance Suggestions

- Refactor frontmatter shell parsing to return a real `Result<FrontmatterShellDirective, ShellExpansionError>` once a value matches the `$()` shape. That would make invalid syntax and rejected executable interpolation fail loudly instead of being skipped, and it would align discovery and execution on one parser contract.
- Move the pre-EffectiveState frontmatter preparation into a shared helper used by both compose and discovery. The design already recommends this, and it would eliminate the current approval/runtime drift.
- Execute frontmatter shell directives concurrently and keep write-back deterministic by collecting `(key, result)` pairs and applying them in source-map iteration order after all executions finish.
- Make frontmatter parsing robust to `)` inside quoted arguments. The current `find(')')` approach in [`darkmatter/lib/src/markdown/compose/frontmatter_shell_expansion.rs:75`](../../lib/src/markdown/compose/frontmatter_shell_expansion.rs#L75) will misparse otherwise valid commands like `$(printf ')')`.
