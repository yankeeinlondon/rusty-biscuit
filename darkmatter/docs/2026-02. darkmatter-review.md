# Darkmatter package code review (2026-02)

## Skills used

- rust
- darkmatter
- biscuit-terminal
- clap

## Scope

- Reviewed: `darkmatter/lib` and `darkmatter/cli`
- Commands run:
    - `cargo test -p darkmatter -p darkmatter-cli`
    - `cargo test -p darkmatter-cli`
    - `printf '# T\n' | cargo run -q -p darkmatter-cli -- - --clean-save`

## Findings (highest severity first)

### 1) HIGH — `--clean-save` treats stdin marker `-` as a literal output filename

- Evidence: `load_markdown()` correctly interprets `-` as stdin (`darkmatter/cli/src/main.rs:229`), but `--clean-save` only checks whether `input` exists and then writes directly to that path (`darkmatter/cli/src/main.rs:105`, `darkmatter/cli/src/main.rs:110`).
- Repro: `printf '# T\n' | cargo run -q -p darkmatter-cli -- - --clean-save` exits `0` and writes to a file literally named `-`.
- Impact: unexpected write target; users can accidentally create or overwrite an unintended file.
- Recommendation: reject `input == "-"` for `--clean-save` with a clear error.

### 2) HIGH — advertised frontmatter CLI flags are currently no-ops that exit successfully

- Evidence: flags are exposed in CLI help (`darkmatter/cli/src/lib.rs:225`, `darkmatter/cli/src/lib.rs:229`), but execution only parses JSON, prints debug output, and returns without mutating markdown (`darkmatter/cli/src/main.rs:82`, `darkmatter/cli/src/main.rs:90`).
- Impact: users believe frontmatter operations were applied, but no document changes occur.
- Recommendation: either implement `Markdown::fm_merge_with` / `Markdown::fm_set_defaults` integration or hide these flags until implemented.

### 3) HIGH — image path traversal boundary is documented but not enforced

- Evidence: docs claim path traversal prevention (`darkmatter/lib/src/markdown/output/terminal.rs:386`), but implementation accepts absolute paths (`darkmatter/lib/src/markdown/output/terminal.rs:417`) and joins relative paths without canonical boundary enforcement (`darkmatter/lib/src/markdown/output/terminal.rs:420`). Constructor comments also explicitly avoid boundary enforcement (`darkmatter/lib/src/markdown/output/terminal.rs:331`).
- Impact: when image rendering is supported/enabled, markdown can reference images outside the intended base directory.
- Recommendation: canonicalize and enforce `candidate.starts_with(canonical_base)` when `base_path` is set; reject absolute paths unless explicitly allowed.

### 4) MEDIUM — hyperlink capability fallback is bypassed in terminal renderer

- Evidence: `Link::to_terminal()` contains capability-aware fallback logic (`darkmatter/lib/src/render/link.rs:321`), but terminal rendering bypasses it via `to_terminal_unchecked()` for table links (`darkmatter/lib/src/markdown/output/terminal.rs:990`) and unconditional OSC8 emission for inline links (`darkmatter/lib/src/markdown/output/terminal.rs:1024`, `darkmatter/lib/src/markdown/output/terminal.rs:2104`).
- Impact: terminals without OSC8 support may receive raw control sequences instead of readable fallback text.
- Recommendation: gate OSC8 emission behind capability detection or route link rendering through `Link::to_terminal()` consistently.

### 5) MEDIUM — library code writes directly to stderr on recoverable image paths

- Evidence: `ImageRenderer::render_image()` uses `eprintln!` in normal error/fallback paths (`darkmatter/lib/src/markdown/output/terminal.rs:412`, `darkmatter/lib/src/markdown/output/terminal.rs:426`, `darkmatter/lib/src/markdown/output/terminal.rs:442`, `darkmatter/lib/src/markdown/output/terminal.rs:457`).
- Impact: noisy/unstructured side effects for library consumers; difficult to integrate in quiet or structured logging contexts.
- Recommendation: replace direct stderr writes with `tracing` events and let applications choose logging sinks/levels.

### 6) MEDIUM (test reliability) — terminal tests are environment-coupled and fail under NO_COLOR/dumb TERM

- Evidence: renderer auto-detects color depth (`darkmatter/lib/src/markdown/output/terminal.rs:644`) and short-circuits to raw markdown when `ColorDepth::None` (`darkmatter/lib/src/markdown/output/terminal.rs:647`), while many tests assume styled output from `TerminalOptions::default()` (`darkmatter/lib/src/markdown/output/terminal.rs:2455`).
- Observed: `cargo test -p darkmatter -p darkmatter-cli` failed with 95 failures in `markdown::output::terminal::*` in this environment (`NO_COLOR=1`, `TERM=dumb`).
- Recommendation: make tests deterministic by setting explicit render options and controlling environment variables in test scope.

## Residual risk / gaps

- `darkmatter-cli` currently has no unit tests (`cargo test -p darkmatter-cli` runs 0 tests), so CLI argument interaction regressions are easy to miss.
