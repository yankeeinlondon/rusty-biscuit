# Implementation Log — Disable persistent compose cache until ContentPolicy exists

## Phase 1

Phase 1 covers rulings, investigation spikes, and a baseline. No source code was
changed; the only edits are to `plan.md`, `spec.md`, and this log.

### Rulings

- **R-Q1:** already owner-ruled (Ken, 2026-09-17, more-context R36): option 1,
  keeping the transport-cache exception.
- **R-Q2, R-Q3:** no owner ruling was available (non-interactive session). The
  plan's stated defaults (option 1 for each) were adopted, recorded in `spec.md`
  as "Adopted default … awaiting owner confirmation", and raised in
  `human_review_items`.
- **R-A … R-I:** stated defaults adopted. Each checkbox in `plan.md` carries a
  "Decision (Phase 1)" bullet. Two decisions gained caveats from the spikes:
  - R-E: `read_cached` requires both manifest and blob, so the `no-store` purge
    must read the manifest independently.
  - R-I: the store directory name embeds `CACHE_VERSION`, so after the bump a
    `v1/` entry is never read again, which undermines the R-E purge of old
    `no-store` entries unless Phase 4 handles it explicitly.

### Spike S1 — headers

- `FetchResponse` carries only `status`, `body`, `etag`, `last_modified`, and
  `cache_control`. For this fix `Cache-Control` is the only header that matters
  (`Pragma`, `Age`, and `Vary` are moot for a URL-keyed private cache).
- **Escalation:** `biscuit-file` reads `Cache-Control` via `HeaderMap::get`,
  which returns the first field line only. I confirmed this with a throwaway
  wiremock test in `biscuit-file/lib/tests/` (created, run, and deleted in the
  same command; no residue): a response with `max-age=3600` and a second
  `no-store` line yielded `Some("max-age=3600")`.
- A matching darkmatter bug: `parse_max_age` stops at the first recognized
  directive, so `max-age=3600, no-store` on one line is treated as a 3600 s TTL.

### Spike S2 — harness

- The lib wiremock harness is sufficient (`append_header` is available in
  wiremock 0.6.5).
- The CLI fixture already satisfies acceptance criterion 3 via
  `test_compose_cache_root_never_replays_composed_local_output`. An optional
  CLI `no-cache` test needs only an `etag` field on `MockHttpResponse` (13
  literal sites to update).

### Spike S3 — filesystem side effects

- The only writer under the cache root is `FileStore`, and the eager effect is
  exactly `FileStore::new`'s two `create_dir_all` calls. `atomic_write` is
  already lazy.
- No tracing file sinks. The `dirs::cache_dir()` read is in an unreachable
  branch (R-C).
- A portable `snapshot_tree` helper sketch is recorded in the plan.
- Drift found: `store.rs:11` claims lock files that do not exist. Left for
  Phase 2, which owns that file (this phase makes no source edits).

### Spike S4 — deletion inventory

- GitNexus was unusable. Every darkmatter lookup, including `FileStore`, came
  back "not found"; the CLI fallback gave the same result. `.gitnexus/` holds an
  `analyze.lock` and a `lbug.staging.*` directory from an earlier run. I did not
  start a re-index, in case another session holds the lock.
- The inventory was therefore built with `rg`, checking call sites one by one.
  It is recorded in `plan.md` as a keep/delete table.
- Notable findings:
  - `PersistentContext` and `OperationPersistentContext` are constructed on the
    production transclusion path. The run-local keys reuse the same hash inputs,
    so the hash functions stay and only the wrapper types go.
  - `::code` and `::toc-linking` perform an extra `std::fs::read` of the source
    purely for a dead `source_content_hash`.
  - `effective_state_hash` already has zero callers.
  - Deleting `CacheFreshnessMode` makes acceptance criterion 2's "legacy
    `CacheFreshnessMode`" wording vacuous; it needs restating in a later phase.

### Implementation (2A)

- `cache/store.rs`
  - `FileStore::new(root) -> io::Result<Self>` (two eager `create_dir_all`)
    is replaced by the infallible `FileStore::at(root) -> Self`, which records
    the path only. `atomic_write`'s `create_dir_all(parent)` is now the store's
    only directory-creation point, for both `write_blob` and `write_manifest`
    (verified by `first_blob_write_creates_only_the_blob_fanout`).
  - R-C: `resolve_cache_root(cache_root: &Path, namespace)` is no longer
    optional. The `dirs::cache_dir()` / `/tmp` fallback and
    `resolve_cache_root_without_workspace` are deleted. `dirs` stays in
    `Cargo.toml`, because `util.rs`, `link_normalization.rs`,
    `path_projection.rs`, `resolve_ctx.rs`, and `options.rs` still use
    `dirs::home_dir()`.
  - Doc drift fixed: the module doc claimed "cross-process safety uses
    filesystem-level lock files". No lock files exist; safety comes from
    tempfile+rename. The module doc now states that and the lazy-creation
    contract.
- `context/options.rs` — `build_remote_fetch_runtime` does no filesystem I/O
  now. It wraps `FileStore::at(resolve_cache_root(..))` directly, so the silent
  `.ok()` is gone. The error it swallowed now surfaces at write time.
- `cache/remote_cache.rs` — `write_cached` already dropped
  `write_artifact` errors (`let _ =`). A WHY comment now records that this is
  where an unusable root (unwritable, or a regular file) first fails, and that
  the fetch stays network-only. Observable behavior matches the old
  `.ok()` path: compose succeeds and nothing is cached. The one difference is
  that reads are now attempted against the unusable root; they return
  `NotFound`, which counts as a cache miss. **For Phase 3:** route this write
  failure into the new `cache_warnings` channel (R-F) together with the
  no-store purge failures.
- `cache/runtime.rs` — the `#[cfg(test)]` `with_persistent` uses `FileStore::at`;
  the `tracing::warn!` fallback it had is gone because construction can no
  longer fail.
- Audit: after the change, `rg "FileStore::new"` finds nothing in the package
  area. No other eager writer exists, as S3 established.

### Implementation

- **3A: directive model** (`cache/remote_cache.rs`)
  - `parse_max_age` is deleted. In its place, `ResponseDirectives { no_store,
    no_cache, max_age }` is parsed once from the whole `Cache-Control` value.
    - The comma split is quote-aware, so `private="no-store, x"` does not
      produce `no-store`.
    - Names are case-insensitive.
    - `no-cache="field"` counts as `no-cache`.
    - `max-age` may be quoted. The first valid value wins, and it saturates at
      2^31 s (RFC 9111 §1.2.2).
    - An invalid `max-age` is ignored, which leaves the entry stale.
    - `max-age=0` is a real zero lifetime and is storable, distinct from
      `no-store`.
  - Structural TTL precedence: `ResponseDirectives::storable()` returns
    `Option<StorableDirectives>`, which is `None` for `no-store`. Both
    `write_cached` and `compute_expires_at` take only `StorableDirectives`, so
    no TTL override can reach storage with a `no-store` response.
  - `compute_expires_at` precedence: `no-cache` gives `None` (never fresh),
    then the TTL override, then `max-age`. It now uses `checked_add`, because
    `SystemTime + Duration` could panic on a huge `max-age`.
- **3B: storage and reuse**
  - One `store_response` gate serves all three write sites (the 304 metadata
    refresh, the revalidated 200, and `FetchFresh`). A `no-store` response
    writes nothing.
  - **Decision beyond the plan:** when a *revalidation* (304 or 200) comes
    back `no-store`, the superseded entry is **purged**, not just left
    unrefreshed. Otherwise `Optimistic` would keep serving a body the origin
    has since marked `no-store`. Pinned by
    `revalidation_that_turns_no_store_purges_the_entry`.
  - `read_cached` reads the manifest before the blob (the R-E constraint).
    When the manifest records `no-store`, it calls `purge_cached` and returns
    absent. The R-E WHY comment sits at the blob removal.
  - `FileStore::remove_manifest` / `remove_blob` treat `NotFound` as success.
    They never create or prune directories.
  - `decide_action(cached: Option<&ResponseDirectives>, within_ttl, cfg)`: a
    `no-cache` entry revalidates in every mode.
  - R-G: in the revalidation `Err` arm, `Fallback` serves stale only when
    `!directives.no_cache`.
- **3C: warning channel**
  - `fetch_with_cache` takes a `&mut Vec<String>` warning sink.
  - The fetch task appends the sink to `RemoteFetchStats::cache_warnings`
    under the stats mutex, on success and error alike.
  - The root pipeline (`pipeline/mod.rs`) projects those entries into
    `report.warnings` through `RemoteFetchStats::cache_compose_warnings()`.
  - Each projected warning has stage `remote_cache` and code
    `dm.remote_cache.io_failure`, exposed as `CACHE_WARNING_STAGE` /
    `CACHE_WARNING_CODE`.
  - **Deviation:** the plan said `stage = "remote-cache"`. I used snake_case to
    match every existing stage (`schema_validation`, `file_links`, ...).
  - Counters are untouched, so the `remote:` summary does not change.
  - The CLI already prints `report.warnings` to stderr.
  - The Phase 2 `let _ = store.write_artifact(..)` is now routed into this
    channel.
  - Warning text names the entry by key hex, never by URL, so no userinfo or
    query can leak before Phase 4's R-H redaction exists.

### Implementation

- **R-H redaction** (`cache/manifest.rs`)
  - The new `redact_url(&Url)` returns `scheme://host[:port]/path` with
    userinfo and fragment removed, and any query (even an empty `?`) replaced
    by the literal `?<redacted>`.
  - It builds that string by hand, because `Url::set_query` would
    percent-encode the marker.
  - `RemoteUrlManifest.url` is replaced by `redacted_url`.
  - `source_id_hash` (the entry key) is still `xx_hash` of the **full** URL.
  - The redaction doc comment says the rule applies only to persisted
    artifacts. User-facing errors may keep the URL the user supplied.
- **R-I versioning. Decision: decouple the directory version from the
  manifest version.**
  - `CACHE_VERSION` 1→2 is now the manifest schema version.
  - The new `STORE_LAYOUT_VERSION = 1` names the `v{N}` directory.
    `FileStore::resolve_cache_root` uses it.
  - Why decouple: the Phase 1/3 handoff pointed out that bumping a shared
    constant would move new writes to `v2/`. That strands every v1 entry,
    including its cleartext URL and any v1 `no-store` body, in a tree that is
    never read again.
  - With the directory fixed, a v1 manifest sits at the same path as its v2
    successor, which has two effects:
    - The R-E purge still finds a v1 `no-store` entry.
    - A storable re-fetch overwrites a v1 entry with the redacted v2 shape, so
      the cleartext URL leaves the disk the next time that URL is cached.
  - No cache tree is ever deleted wholesale.
- **Reading a legacy manifest.** I did not use the plan's preferred "optional
  legacy `url` field". Instead, `read_cached` parses the manifest file once as
  `serde_json::Value`, then reads `RemoteUrlManifestHeader`
  (`cache_version`, `cache_control`, `body_blob_hash`, the fields every
  version shares), in this order:
  1. A `no-store` entry is purged, whatever its version.
  2. Any other version is a miss and is left on disk.
  3. Only then is the full `RemoteUrlManifest` deserialized.

  This keeps `RemoteUrlManifest` strict: there is no `#[serde(default)]` on
  the required v2 field and no dead legacy field. Before this change nothing
  checked `cache_version` on read at all.
- **Warnings.** Cache warnings now add the redacted URL after the key hex (per
  the Phase 3 handoff note), for example
  `failed to write remote cache entry {key:016x} (https://host/p?<redacted>): …`.
  `purge_cached` and `read_cached` take `&Url` for this.
- **Dormant runtime path** (`runtime.rs`, `resolve_dependency_closure_hash`,
  `RemoteUrl` arm)
  - It used to re-parse `manifest.url` to revalidate through the live fetch
    runtime, and that URL no longer exists.
  - It now fails closed: it returns `None` (the parent recomputes and fetches
    live) when a fetch runtime is attached or the version differs.
  - Only `#[cfg(test)]` code can reach it, and Phase 5A deletes it.
- **Leak sweep** (4A):
  - Nothing in `remote_fetch.rs`, `remote_cache.rs`, or `remote.rs` calls
    `tracing` with a URL. The `runtime.rs` debug lines log keys and paths from
    the dormant path.
  - `RemoteReadError::InvalidUrl` keeps the URL and `DeniedByPolicy` keeps the
    host. Both reach the user and are never persisted, so they stay as they
    are.
  - The only production writer under the cache root is still `FileStore`
    (Phase 1 S3).

### 5C — structural guard (AC8)

`lib/tests/semantic_results_never_persist.rs`. It borrows the shared
comment/literal sanitizer with `#[path = "../../cli/tests/common/source_scan.rs"]`,

under `lib/src`:

- `#[cfg(test)]` and `#[cfg(all(test, ..))]` items and statements are blanked.
- Test modules declared out of line (`mod x;`, including with `#[path]`) are

It enforces three rules:

1. The one `struct RunLocalCache` names neither `FileStore` nor
   `RemoteFetchRuntime`. If the struct is missing, that is itself a failure,
   so the guard cannot rot.
2. `FileStore` appears only in the five transport-cache files, with exact
   counts. A new file, a changed count, or an allowlisted file that no longer
   uses it is a failure (the stale-exemption check).
3. None of the 16 deleted persistence symbols reappears.
