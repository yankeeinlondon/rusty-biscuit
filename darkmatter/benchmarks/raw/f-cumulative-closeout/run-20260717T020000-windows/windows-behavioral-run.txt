  *** SCOPE OF THIS EVIDENCE -- read before citing ***

  This IS a real Windows host executing real Win32/NT syscalls. It is NOT Wine, and it is
  NOT a cross-compile-only result. `shared_child`'s wait lowers to the genuine Windows
  `WaitForSingleObject` family here, and F22's traversal runs the genuine
  `FindFirstFileW`/`FindNextFileW` behind `std::fs::read_dir`.

  Two honest qualifications:

    1. This is ARM64 Windows running an x86_64 binary under Prism emulation. The emulation
       is at the *instruction* level; the Win32/NT layer is the real OS, so process-wait,
       pipe, kill/reap and directory-traversal semantics are Windows' own. This is not an
       API reimplementation -- which is precisely what a Wine run would have been, and why
       Wine was rejected as evidence for these two findings.
    2. Not driven through `just test` / `cargo nextest` on the guest: the guest has no Rust
       toolchain. The test binaries were built on the host and invoked directly, so this is
       libtest's own runner -- same binaries, same assertions, same filters.

  Transfer artifact worth knowing (NOT a defect, NOT Windows behavior): `cargo_bin_cmd!("md")`
  bakes the compile-time host path of `md.exe` into the CLI test binary. Cross-compiled on
  macOS that path is `/Users/ken/.../debug/md.exe`. Windows resolves a leading `/` against
  the current drive, so staging a copy at `C:\Users\ken\...\debug\md.exe` satisfies it.
  Without that staging all 15 F22 CLI tests fail with ERROR_PATH_NOT_FOUND (code 3) at spawn.
  A native Windows `cargo test` would not need the staging step.
