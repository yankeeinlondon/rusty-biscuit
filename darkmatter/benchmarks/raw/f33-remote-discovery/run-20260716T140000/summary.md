### Control movement — investigated, not waved through

Both controls moved **−19 %**, which a code change confined to the target path
should not cause. A second full candidate run reproduced every figure within its
CI (target −82.4 %, controls −19.1 % / −20.0 %), so this is systematic, not
noise. Two distinct causes, neither a regression:

- **Control 2 is a genuine, intended win.** The new early return fires when the
  document parses no expression, which now happens *before* the
  `ComposeSource::File` → `PathBuf` clone that the old code performed
  unconditionally ahead of the loop. Skipping that allocation is real work
  removed, so −19 % on a 9.4 µs path is expected.
- **Control 1 is a build-layout artifact.** Its path is byte-for-byte unchanged
  code (`if !content.contains("http") { return Vec::new(); }` is still the first
  statement). Baseline and candidate are separate compilations, and restructuring
  the enclosing function changes inlining/code layout around a 2.3 µs
  `memchr`-dominated scan. This flatters *every* benchmark in the binary,
  including the target.

**Effect on the verdict.** Discounting the entire −19 % as build drift rather
than attributing any of it to the change, the target's code-specific win is
still `1 − (0.175 / 0.807) ≈ −78 %`. The declared contract permitted ≤ 5 %
control *regression*; both controls improved, so the contract is met on the
strict reading, and the target clears the ≥ 30 % floor by a wide margin under
either accounting. The headline −82.5 % is reported with this caveat rather than
as a clean isolated delta.

## Disposition — **ACCEPTED** (threshold met)

Target: **2.3944 ms → 419.95 µs**, −82.5 % headline / ≈ −78 % after discounting
the binary-wide layout shift. Declared floor was ≥ 30 %. No control regressed.

The remaining ~420 µs is the `ExpressionFinder` scan plus 300 expression parses,
which this finding does not touch; the quadratic prefix rescan is gone. Cost
moved from O(expressions × offset) to one O(bytes) table build plus an
O(log lines) binary search per expression, so the win grows with document size.

Output is byte-identical. Line numbers are proved equal to the naive
`content[..offset]` newline count at **every char-boundary offset** of a mixed
LF/CRLF/Unicode document (`line_at_offset_matches_naive_at_every_offset`), and
every discovered URL is proved to actually appear on its reported line across
the whole committed corpus (`remote_discovery_line_positions_match_fixture_text`,
≥ 300 expressions via the `remote_heavy` tier).

Both guards were mutation-tested: an off-by-one (`pos <= offset`) and a
char-index table are each caught by the suite.

## Cross-platform classification — **OS-identical**

Classified from the actual diff, per Checkpoint 9's instruction. The change is
confined to `discover_remote_urls_from_expressions` and its two private helpers
in `compose/remote.rs`: a byte scan for `\n` and a `partition_point` binary
search. No filesystem access, no URL runtime, no `cfg`-gated path, and no
line-ending normalization changed — CRLF is handled identically before and
after (a `\r\n` counts as one break because only `\n` is counted, on every OS),
which `expression_lines_with_crlf_newlines` pins. Windows compile evidence +
this macOS behavioral run + ordinary Linux CI are therefore sufficient; F33
requires no real non-macOS behavioral run.
