Declared threshold (before capture)
-----------------------------------
Target operation: resolving a remote `::file` / `::code` / expression URL
through `RemoteFetchRuntime` (register + fetch + point-of-use `get_content`).
Minimum repeatable win: >= 5% on the target operation.
Maximum permitted control regression: 0% (no path may get slower).

Result 1 — copy-cost model (what Arc<str> actually trades)
----------------------------------------------------------
  store  String->Arc<str>    (NEW cost, once per URL) : 1.167 us
  read   String::clone       (baseline, per consumer) : 0.667 us
  read   Arc<str>::to_string (candidate owned facade) : 0.791 us
  read   Arc::clone          (candidate shared path)  : 0.000 us

`FetchSlot::Ready` is populated by MOVING `RemoteFetchOutcome.body` (a String
built by `String::from_utf8`). Storing `Arc<str>` cannot reuse that allocation
(the refcount header is inline), so it adds one full body copy per URL that the
pre-change code never paid.

The public owned `get_content` facade must keep returning `String` (the plan
preserves it; a new public shared accessor is barred by the standing "no new
public Rust API shape change" contract). `Arc<str>::to_string` is marginally
SLOWER than `String::clone`, so every owned consumer regresses.

Only a crate-internal shared accessor helps, and only for consumers that need
just `&str`. Auditing the five call sites, exactly one qualifies:
  - engine.rs `::code`      -> wrap_in_code_block(&body, ..)   : &str only  [helped]
  - engine.rs `::file`      -> Markdown::try_from_content(body): needs owned [regressed]
  - preflight/collect.rs    -> returns Option<String>           : needs owned [regressed]
  - resolve_ctx.rs (x2)     -> returns Option<String>           : needs owned [regressed]

Net per typical document (one URL, one consumer):
  ::file / preflight / expression : +1.167 (store) +0.124 (read) = +1.29 us WORSE
  ::code                          : +1.167 (store) -0.667 (read) = +0.50 us WORSE
`::code` only breaks even at ~2 consumers of the SAME url (1.167/0.667 ~= 1.75),
which requires a document transcluding one remote URL as code twice or more.

Result 2 — proportion against the operation the body belongs to
---------------------------------------------------------------
  register_and_fetch + get_content (loopback wiremock, median) : 534.5 us
  one body copy                                       (median) :   0.667 us
  one body copy as a share of the operation                    :   0.125 %

Loopback is the MOST favorable case for the copy mattering; a real network fetch
is 10-100x slower, driving the share toward zero. Even converting every copy to
a refcount bump could not reach the declared 5% floor: the entire copy budget of
the operation is 0.125%.

Disposition: NO-WIN -> REJECTED, code removed
---------------------------------------------
The change is a net pessimization for every single-consumer case, regresses the
owned-facade consumers unconditionally, and its best case is ~2 orders of
magnitude below the declared threshold. Per the standing Benchmark & Evidence
Contract ("A no-repeatable-win finding closes through a recorded no-win
disposition AND removal of the unnecessary code"), the implemented `Arc<str>`
slot, the crate-internal shared accessor, and the `::code` call-site change were
all reverted. `remote_fetch.rs` and the `::code` path are byte-identical to their
pre-Phase-10 state; the harness above was deleted.

Cross-platform classification: OS-IDENTICAL, and moot — no code shipped.
The inspected path (per the plan's instruction not to preclassify 35.3) contains
no `cfg`, no filesystem branch, and no OS-divergent runtime behavior: it is slot
storage plus an in-memory copy. The Tokio/reqwest runtime below it was not
touched.
