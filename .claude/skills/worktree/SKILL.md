# Worktree Package Area

Like many package areas in Rusty Biscuit, the `worktree` package area has two distinct packages:

1. Library: `worktree` is the library where the business logic for how we handle git worktrees is regulated
2. CLI: `worktree-cli` (binary name of `wt`) is the CLI which leverages the worktree library for most of it's functionality

The `worktree-cli` crate contains both a binary target (`src/main.rs`, binary `wt`) and a library target (`src/lib.rs`). Shared modules such as `commands` and `perf` are declared in both `lib.rs` and `main.rs` so they are available to integration tests (which use the library target) and to the binary.

Because every shared module compiles twice, its `#[cfg(test)]` unit tests also run twice, once per target, under different module paths (`worktree_cli::…` and `wt::…`). An `insta` snapshot in such a unit test therefore gets two different snapshot names, and one of them always fails. Keep snapshot tests in an integration test (`cli/tests/wrapper_protocol.rs` holds the shell-wrapper snapshots).

## Shell wrapper protocol

- `wt --completions <bash|zsh|fish|powershell>` (`cli/src/shell_integration.rs`) is the only source of the `wt` shell function and the completion registration. The registration is generated in-process with clap's `EnvCompleter`, so nothing sources `COMPLETE=… wt` at startup.
- The wrapper sets `WT_SHELL_WRAPPER=1` on exactly the `wt` calls it makes. `cli/src/env.rs::shell_wrapper_active()` treats only that value as proof. Never infer the wrapper from a captured stdout, because scripts, `just`, and agents capture it too.
- Protocol lines on stdout: `cd:<path>` and `remove-handoff:<token>`. The wrapper acts only after `wt` exits 0, stops if `cd` fails, and never evaluates output. The POSIX wrapper collects the values in its read loop and acts after it, so the handoff call keeps the terminal's stdin.
- The PowerShell wrapper calls the absolute executable path captured at generation, because Windows Terminal ships its own `wt.exe` alias. It switches `[Console]::OutputEncoding` to UTF-8 for the call and sets `[Environment]::CurrentDirectory` along with `Set-Location`.
- `cli/tests/shell_wrapper_exec.rs` runs the generated bash wrapper (and zsh on macOS) against a stub `wt` on `PATH`. fish has no L1 execution test; PowerShell's is `cli/tests/powershell_wrapper_exec.rs` (Windows only).

## Exit codes and interactivity

- `cli/src/exit.rs` maps errors to 0 (done or `Cancelled`), 1 (failure), 3 (`WorktreeError::RefusedToLoseWork`), and 4 (`WorktreeError::BlockedByEnvironment`, `WorktreeError::DirectoryInUse`); clap owns 2. Those two variants carry Prose markup that `main.rs` prints as-is. Other errors are escaped with `Prose::escape_text`.
- `env::is_interactive()` means stdin and stderr are terminals and `CI` is unset or empty. Stdout is never consulted.

## Name resolution

`worktree::worktree::resolve_worktree(entries, name)` and `completion_names(entries)` are pure functions over parsed porcelain; `find_worktree` and `worktree_names` only add the git call.

- `base` is always the main checkout.
- Any other name matches branch names on every checkout, and directory basenames (raw or dasherized input) on linked worktrees only. The main checkout's basename is the repository name.
- More than one distinct worktree returns `WorktreeError::AmbiguousWorktree`. Never pick the first.

## Fork-origin records

`worktree::fork_origin` stores `{ base_branch, base_sha, created_at }` per branch in `<repo hash>.fork-origins.json`. The file sits beside the comparison cache (`cache::repo_cache_file`) and is keyed by the main worktree's path. `create_worktree(branch, base, from)` records only newly created branches, as a best-effort write that never fails a create. `--from` must name a local branch (`refs/heads/…`), and a detached HEAD requires `--from`. `ForkOriginStore::prune(exists)` drops the records `exists` rejects; the listing drops records of deleted branches and keeps records whose parent was deleted. It prunes the file as reread at prune time, not the copy it loaded before its remote wait, and a record created at or after its ref read (`WorktreeList::refs_read_at`) is kept unless `rev-parse --verify` finds no branch, so a `wt create` during that wait keeps its record (`listing::repo_tests::a_fork_record_written_while_the_listing_waits_survives_its_prune`).

## Include building blocks

`worktree::include` resolves `.worktreeinclude` membership through Git's byte-oriented `ls-files --others --ignored --exclude-from` and `check-ignore --stdin -z --verbose --non-matching` intersection. `IncludeRules::locate` distinguishes missing, empty, present, and indeterminate rules. `guarded_kind` rejects nested repositories, linked directories, and Windows reparse ancestors; paths remain Git's native bytes until filesystem access. Git for Windows rejects verbatim exclude paths, so the resolver passes a simplified canonical spelling.

`worktree::compare` hashes every same-size included file with `biscuit_hash::blake3_hash_reader`; a size change avoids the read. A missing digest means the copy baseline is untrusted. `worktree::include::copy` holds source-file and destination-directory handles through copying and publication, so a parent link swap cannot move the copy outside the checkout. It clones from the open source handle where supported, byte-copies on unsupported clone errors, and publishes regular files without replacing existing destinations. `CopyOutcome::copied` carries `None` instead of an observation when the source changed mid-copy. `worktree::copy_record` persists per-worktree baselines under a 16-hex-digit canonical-path key, bound to a random marker in Git's admin directory. `record_path` resolves missing destination suffixes so its key is stable before and after `git worktree add`; `load` treats corruption and identity mismatch as untrusted. `create_worktree` chooses the checkout holding the fork branch, or the main checkout when no checkout holds it or when reusing a branch. It clears a stale destination record before adding the worktree, then copies included files and writes trusted observations; failures after the add are warnings in `CreateResult.include`. `fill_worktree_statuses` prunes records for removed worktrees after a successful listing: a record goes only when its worktree is missing from the listing's `worktree list` **and** its admin directory no longer holds the record's marker, since that list predates any worktree created during the remote wait. Removal deletes a record immediately after the directory is removed; cleanup failures are warnings.

## `wt remove`

The library half is `worktree::remove` (`lib/src/remove/`); the CLI half is `cli/src/commands/remove/` (`mod.rs` flow, `policy.rs`, `report.rs`).

- `inventory`: one `git status --porcelain=v1 -z -uall --ignored=matching`. `included::classify_included` evaluates the target’s own rules or, only when missing, the base checkout’s rules. New, changed, and unknown selected ignored files need consent; unchanged copies and ordinary ignored files are disposable and summarized by name. `Inventory::fingerprint` hashes each dirty path's status and working content (a regular file's content includes its git mode, `100755` when owner-executable, on Unix, so a chmod alone refuses a handoff; a dirty directory, which is how git lists an untracked nested repository or a modified submodule even under `-uall`, contributes every path and file under it, `.git` included, symlinks not followed, `/`-separated keys), protected included content and rules/baseline bindings, and the whole index from `git ls-files --stage -z` (mode, object ID, stage, path), so restaging under an unchanged `MM` still changes it (BLAKE3). Every name and symlink target enters as its exact OS bytes (`as_encoded_bytes`, length-prefixed), and git's `-z` output is parsed as bytes (`git::git_from_bytes`), because a lossy decoding maps `\xff` and `\xfe` to one U+FFFD and let a changed symlink pass the handoff; on Windows a status path that is not UTF-8 is `GitParse`. It returns `WorktreeError::Io` when a path under a dirty entry cannot be read (the CLI turns that into exit 4 on both runs) and `GitCommand` when the index cannot be listed. Non-UTF-8 file-name tests skip on macOS (APFS refuses the names) and run on Linux.
- `safety::assess` classifies Safe / Pretty safe / Not safe / Unknown from one `for-each-ref --contains <tip>`, with the PR lookup (sniff, 2 s) on a parallel thread. An `origin/*` ref other than `origin/<default>` counts only after the live check (`live_remote::LsRemote`). With `force_remote`, the destination (`remote_branch`, which an upstream can make `origin/<default>`) is dropped from the ref set before every tier, and `lost_commits` always excludes `origin/HEAD`, an alias that would bring the destination back. Tests inject `PrSource` and `RemoteHeads` stubs. `safety::reconfirm` is the handoff's second-run proof: a local default branch, other local branch, or tag proves the tip with no PR lookup and no network; otherwise an exact-tip PR, then only an `origin/*` ref whose live head verifies, `origin/<default>` included (`assess` trusts that one as of the last fetch).
- `worktree::live_remote::run_noninteractive` (a top-level module, shared with the `wt list` live-head store `worktree::remote_head`) is the only way removal code touches the network. It disables every credential prompt and kills the whole process tree at the deadline (process group on Unix, `taskkill /T /F` on Windows). A plain `Child::kill` leaves the transport holding the pipe. Output is complete or `Err`: stdout that could not be read to its end is an error, never `Ok("")`, and `LsRemote` rejects any line that is not `<40 or 64 lowercase hex>\t<refname>`, so only a complete answer without the exact ref is `Ok(None)` (absent).
- `default_target::select_default_target` picks `main` or `origin/main` (the descendant; origin when diverged). Phase 5's list reuses it.
- `policy::decide` is pure: (situation, flags, scripted answers) to actions. Its L1 matrix covers every tier × contents × flag subset × mode.
- Git runs through `git::git_from(base, dir, ..)` (`git -C`, cwd = base). `run` calls `set_current_dir(base)` right after resolving the target, so neither `wt` nor a git child holds the worktree on Windows.
- Move-first: inside the target with `WT_SHELL_WRAPPER=1`, the first run writes `handoff::HandoffRecord` (`<repo hash>.handoff-<token>.json`, 60 s) and prints `cd:` + `remove-handoff:`. The v3 state binds the effective rules and copy baseline. `--handoff` consumes the record before judging it, then `verify` checks "caller outside the target" first (exit 4) and then every stored field (exit 3); `run_handoff` then refuses (exit 3) when the `--force-remote` destination, its push endpoint, or its live head differs from the approved one, is now absent, or cannot be reached (approved absent accepts only a verified absence). The second run reads every local fact again (`Facts::local`) but asks the network only for what the approved actions need: `Keep`, an explicit `Delete`, or no branch makes no PR or live request; `DeleteIfSafe` runs `safety::reconfirm`; a remote approval runs one preflight. Its refusals print only the reason, never the first-run report, and an explicit delete prints no "(N lost)" suffix. The zero-network tests in `cli/tests/remove.rs` point origin at `http://gitea.test/…` with every proxy variable aimed at a local counting listener, since a file-path origin never reaches the PR lookup. The endpoint is `remote::push_endpoints` (`git remote get-url --push --all origin`, git's own spelling, never canonicalized); the deletion's `ls-remote` and `push` address that URL, not the `origin` nickname (which `ls-remote` would resolve to the fetch URL), and several push URLs make `--force-remote` refuse (exit 3) before anything is removed. Git need not take that argument literally, with no switch to make it: it rewrites a URL again (`ls-remote` by `insteadOf`, `push` by `pushInsteadOf`, else `insteadOf`), and reads a name matching a configured remote as that remote (fetch URL for `ls-remote`, push URL for `push`). So `remote::endpoint_reinterpretation` (`git config --null --list`, every scope and `-c`; section and variable come back lowercased, the remote name keeps its case and git matches it case-sensitively) must find no rewrite rule whose value prefixes the endpoint, no `remote.<endpoint>.*` key of any kind, and no legacy `remotes/<endpoint>` or `branches/<endpoint>` file (`rev-parse --git-path`): otherwise preflight yields `RemoteState::ReinterpretedEndpoint` and both runs refuse (exit 3) before any mutation, and `delete_remote_branch` re-checks before pushing. `git remote get-url <name>` cannot answer "is this a remote": it says "No such remote" for remotes defined in global scope or by `-c`, which `push` still uses. The safety tiers' `origin/*` live checks still use `origin`, matching the fetch that made those refs. A branch approved only because it was safe must still be safe.
- On Windows `remove::remove_worktree` runs `check_not_in_use` (rename to a sibling and back) first. A held directory is `WorktreeError::DirectoryInUse`, which exits 4.
- Tests: lib unit tests use `remove::test_support::TestRepo` (local bare `origin`, plus a `pusher` clone for other people's pushes). `cli/tests/remove.rs` sets `NO_COLOR=1`, because `wt` colors stderr even when it is captured. `cli/tests/level2_remove.rs` drives bash, zsh, and fish wrappers in tmux, with a `wt` shim that runs `WT_TEST_BETWEEN` before the handoff call. `just test-l2 <substring>` matches test names only, and a quoted `-E '<filterset>'` breaks the recipe's bash, so run one binary with `BISCUIT_TEST_REQUIRED_BACKENDS=tmux cargo nextest run -p worktree-cli --features terminal-tests -E 'binary(level2_remove)'` (the variable turns a missing-backend skip into a failure). `cli/tests/powershell_wrapper_exec.rs` is Windows-only L1. `cli/tests/level2_powershell_remove.rs` is the Windows L2: PowerShell 5.1 in a ConPTY pseudoconsole (`xpty`, no window, no focus) launched *inside* the worktree, the prompt answered through the console, and the assertions read the console's own screen buffer (`$Host.UI.RawUI.GetBufferContents`), since ConPTY's output stream is a repaint, not text in order. A third case runs `wt remove --force-worktree` from the base repo while a windowless `ping` stands in the worktree, and asserts exit 4 with files, registration, and branch intact. It needs no terminal backend, so CI never runs it: `windows-latest` hosts none of `l2-backends` and the L2 cell is an accepted gap. Run it with `./scripts/cross-check.sh --os windows worktree-cli --features terminal-tests level2_powershell` and read the durations (about 5 s each; a skip is 0.0x s).

## `wt list`

`worktree::worktree::list_worktrees` uses `worktree::cache` to persist SHA-pair comparison results under the user cache directory. The cache key is `(target_tip_sha, branch_tip_sha, CACHE_FORMAT_VERSION)` (version 2), so one cache serves the `-> {default}` column, the `-> parent` column, and the caption (local default vs `origin/<default>`), and any tip movement self-invalidates. Dirty working-tree status is never cached and remains a live `git status` check.

- `parse_worktree_state` reads `worktree list`, the default branch, one `for-each-ref refs/heads refs/remotes` (`listing::RefTips`), and the fork-origin store. `fill_worktree_statuses` runs dirty status, the caption, the target (`default_target::choose_default_target`, with ancestry taken from the cached caption counts, so a warm run has no `merge-base`), the tree (`listing::build_tree`, pure), every comparison, and the fork-store prune. The CLI starts graph gathering and the PR request between the two.
- Prune only after a successful `for-each-ref`; an empty ref set would make every record look deleted.
- `pull_requests` (store format 4): `<repo hash>.prs.json` binds its answer to `origin_digest` (`biscuit_hash::blake3_hash` of the exact `origin_url(main)` value, `git remote get-url origin` run against the main checkout); the raw URL is never stored. Every successful write stamps a new random `publication` id (`new_attempt_id`) and its `writer` (`refresh` or `listing`) beside `fetched_at`, which is whole seconds and can repeat; `stored_publication(store, origin, now)` reads both (`Publication { id, writer }`) under `select_cached`'s rules. One ordering rule binds both writers: a write happens only under the PR refresh lock and only when no other answer was published after the writer's request began, so an overlapping listing's older answer never replaces a worker's newer one (`pull_requests::tests::a_foreground_answer_never_replaces_*`, `list::tests::…::a_miss_answer_overtaken_by_a_forced_worker_*`). `select_cached(store, origin, now)` gives `Fresh` (< 60 s), `Stale` (>= 60 s, still shown), or `Miss` (none, corrupt, other format, future `fetched_at`, other or no origin); a stored empty list is an answer. So every cache hit costs one git call. `fetch_and_publish` is the foreground miss request (300 ms `LIST_DEADLINE`, made without the lock); it reads the store's publication id before the request and stores its answer only if it then takes the lock nonblocking and finds that id unchanged, otherwise it stores nothing and this run shows its own answer until the post-wait reread; it returns `Err(PrFailure)` for a failed request (sniff's credentials conditions by kind via `PrFailure::from_unavailable`, everything else `Other`) and `Ok(None)` when `origin` changed during it; `refresh(store, main, clock, force, connect)` is the PR half of the background worker (`REFRESH_DEADLINE` 10 s; `force` skips the freshness recheck, never the lock; `RefreshOutcome::Failed` carries the `PrFailure`), the hidden `wt internal-refresh <main checkout> [--attempt <id>] [--force]` (`cli/src/commands/refresh_worker.rs`, which ignores any path that is not a main checkout's top level; without `--attempt` it makes its own id). That worker runs the PR half and the live-head half (`remote_update::run_attempt`) on two scoped threads, each joined separately with panics discarded, so neither blocks nor suppresses the other. A repository in `~/.wt.json` (`Preferences::ignores_origin`) makes no provider request in either half (`PrStatus::Ignored`). With `--force`, after both halves join, it writes the completion receipt; a panicked half is recorded as failed. `wt list` (`list::gather_remote`) settles any PR-miss foreground request first (skipped under `-r`/`--ff`, whose forced worker asks, and for an ignored repository), then, whenever there is an `origin`, launches the worker **once** (`refresh_worker::launch(main, &LaunchArgs { attempt, force })`, through `sniff::process::configure_detached_child`, null stdio, main checkout as cwd; the returned `WorkerHandle` only answers `has_exited`) and waits for its attempt in `list/wait.rs`: 3 s (`ORDINARY_BUDGET`) for ordinary listing, `ATTEMPT_MAX_AGE` (`FORCED_BUDGET`) for `-r`/`--ff`, which also wait for the receipt; a `contended` PR half waits for the holder's lock and counts only if the PR store then holds a refresh-written publication id that differs from the one at launch (`WaitEnv::pr_publication`, which reads a `listing` answer as `None`; `fetched_at` cannot tell a same-second replacement), since a failed or skipped holder stores nothing and a listing can store its answer whenever the lock is momentarily free, such as just after a failed holder releases it (`wait::tests::a_forced_wait_never_takes_a_listings_answer_for_a_contending_holders`): otherwise the run relaunches once, and a second such contention ends as `PrStatus::Failed { Other }` (`list_flags::refresh_*_contending_holder_*`, `refresh_shows_a_holders_answer_that_replaced_a_young_one_within_its_second`). `wait::wait` is pure over `WaitEnv` (store, receipt, lock probes, clock) and follows only its own token's attempt; it adopts another attempt only after its own worker exited without recording one while the head lock is held (never probing before, see `refresh_lock_held`); an early-exiting contender otherwise, a spawn failure, or a worker that dies mid-attempt is `WaitEnd::Unavailable` at once; a forced run whose lock holder is for another origin or branch waits for it and relaunches. The spinner (`wait::Progress`, biscuit-terminal `Spinner`, 150 ms delay, stderr only when it is a terminal) follows the phase and is cleared before anything renders. Only then do `--ff` (`worktree::fast_forward::fast_forward_default`), `WorktreeList::reread_refs`, and the local gather run, so refs, counts, and graph describe the post-fetch state. `list::ListSeams { connect, launch, wait_budget, forced_budget }` injects the PR request, the launch, and the waits in unit tests (stub launchers write the real store); there is still no live-head seam in the foreground. The caption (`list_table::caption_markup`) is one sentence: the comparison with `origin/<default>` (`local origin/<default>` only in the fetch-failed and still-pulling rows), then a dim italic suffix from `RemoteStatus` (none for `CheckedNow`, since a fresh check that found the tracking ref current needs no date; the integration tests prove that row with `remote_fixture::assert_checked_now`; one variant per spec §4 row; `list::remote_status` maps the `WaitEnd`; `LastKnown` dates a row without an answer, by the reflog via `tracking_ref_changed_at` only when no answer is stored). `list::credential_line` (§5) and `list::fallback_notice` (§8) read only this run's followed attempt's `ApiNote` and this run's PR failure (foreground, or the receipt's under `-r`/`--ff`), with names from sniff's `credential_env`; `list_table::render_hint` (§6, when the wait timed out or a PR refresh is still running) and `render_notes` (`--ff` refusal or §9 suggestion, then §8; the suggestion follows the post-wait comparison under every `RemoteStatus` except `StillChecking` and `StillPulling`, so a failed check or fetch still suggests `--ff` to the local tracking ref) are placed by `list_table::assemble` (table, graph, hint, verbose, blank line, notes). `-r`, `--ignore-api` (records `~/.wt.json` before launching; no origin or a local path exits 1), and `--ff` are global `Cli` flags that `main.rs::reject_listing_flags` refuses (exit 2) with every other command. The worker: it holds a nonblocking `fs4` lock on the persistent sidecar `<repo hash>.prs.lock` (`pr_lock_path`, never deleted) from the freshness recheck through publication, so contention makes no request; the foreground writer takes the same lock only to publish. Both writers stamp `fetched_at` at the request's start and store only if `origin` still matches afterwards (a foreground answer for a changed `origin` is not shown either); a failure is never stored. `PrListing::is_stale_at(now)` decides the age line at render time. The stale timing gate is `perf_pr_request::perf_list_meets_sla_with_a_stale_answer_and_a_failing_refresh` (reseeds a stale store per sample, asserts every `pr gather` < 300 ms, since the 1 s full-command bound alone would hide a reintroduced wait); `perf_a_held_live_head_check_costs_the_listing_only_its_wait` and `perf_a_held_fetch_costs_the_listing_only_its_wait` bound a stalled worker at 3 s plus the 1 s bound; `perf_command_sla` holds the 1 s bound with a worker that answers at once (`MixedFixture::with_local_origin`, a bare copy in sync); `-r` against a held check and `--ff` against a held fetch are bounded by the worker's 10 s and 60 s deadlines (the 60 s test has a 90 s nextest override in `.config/nextest.toml`); the deterministic no-join proof is the `list_prs` tests whose captured `.output()` returns while the worker's request is still held. `ProxyStub::closing_after(hold)` counts connections and drops each after `hold`, since sniff's 3 s connect timeout would otherwise race the listing's 3 s wait against a hanging proxy. Measurements and the `git status` findings are in `worktree/docs/performance-testing.md`. Tests inject the source, so they count requests with a stub; test origins use `example.invalid` hosts so a user `insteadOf` rule cannot rewrite them. `FakeGitea` answers the worker's branch-head request (`/branches/`) 404 at once (or, after `hold_branch_heads`, once released, which holds the check with no connect timeout racing the 3 s wait) and counts it apart (`branch_requests`), so `requests()` counts PR requests only; through `ProxyStub` (HTTPS) each worker makes one connection per half. Match PRs by source repository **and** branch (`PrListing::for_branch`); `placement` puts the badge by the PR's target.
- `remote_head` (format 2): `<repo hash>.remote-head.json` holds `{ format_version: 2, answer, attempt }`. `answer` is `{ origin_digest, branch, sha, checked_at, source: api|git|fetch }` for `origin`'s default branch (`sha: null` is a verified absence; object IDs are 40 or 64 lowercase hex); a format-1 file reads as an `answer` with `source: git` and no attempt. `attempt` is `{ id (32 hex, `new_attempt_id`), origin_digest, branch, started_at, phase, outcome, api }`; each half is validated on its own, so a bad attempt never costs the answer, and `select_attempt` also drops one that is in the future, for another origin or branch, or older than `ATTEMPT_MAX_AGE` (75 s). The writers `begin_attempt`, `set_phase`, `finish_attempt`, and `publish_answer` read-modify-write under the caller's lock, refuse another attempt's id, and keep the other half. `<repo hash>.refresh-receipt.<attempt id>.json` (`refresh_receipt_path(main, id)`, or `receipt_path_beside(head_store, id)`; `write_receipt`, `load_receipt`) records how both halves of one forced attempt ended, one file per attempt so overlapping `wt -r` runs never replace each other's (`wait::tests::overlapping_forced_runs_each_read_their_own_receipt`); a receipt for another id, origin, or branch, or older than the attempt, is ignored. A forced `wait::wait` deletes the receipt of every attempt it launched when it returns (`WaitEnv::discard_receipt`), and the forced worker, before writing its own, deletes this repository's receipts last modified more than `ATTEMPT_MAX_AGE` ago (`remove_stale_receipts`; no wait outlives that), which also clears the old single `refresh-receipt.json`. Binary tests find receipts by prefix beside the store (`list_flags::receipts_beside`), since the wait deletes them. `PrFailure` (typed PR failure, used by the receipt and by `pull_requests`) lives here too. `select_cached_head(store, origin, default, now)` reads `answer` and gives `Fresh` (< 60 s), `Stale`, or `Miss` (no origin or default, unreadable, invalid field, future `checked_at`, another origin digest or branch). `refresh_lock_held(store)` probes `<repo hash>.remote-head.lock` by taking it for an instant, so a worker starting at that moment finds it contended and exits: probe only a worker already running. `Caption` carries the tracking tip from the same `RefTips` snapshot. The caption rows, reasons, age units, and the no-origin rule are proven by the `list_table::caption_snapshot_*` snapshots (plus `credential_lines_*`, `closing_notes`, and `output_order`); `caption_markup` renders even when `caption` is `None` (no local default, no tracking ref, or a failed comparison), and `TableFacts::from_list` drops the caption when `remote` is `None` (no `origin`).
- `remote_update::run_attempt(AttemptRequest { store, main, id, ignore_api }, &Seams { api, git, now, monotonic })` is the live-head half. It takes the remote-head lock nonblocking (a contender writes nothing and asks nothing: `AttemptEnd::Contended`), writes the attempt before any request, and validates the default branch (`live_remote::is_valid_branch_name`, which also refuses names git would expand, such as `@{-1}`). The check (`BranchHeadSource`, production `SniffBranchHeads`) asks the provider API, then `ls-remote` (`GitRemote`, production `GitTransport`) within one `REMOTE_HEAD_REFRESH_DEADLINE` (10 s) measured on `monotonic`: `Unsupported` is Git in phase `checking` with no note; any other API error is `checking-fallback(reason)` with an `ApiNote` for the §5 conditions (a 404 is `not-visible` only when `key_in_use` is `None`, which cannot see sniff's host-bound `SNIFF_*_TOKEN`). Only `ls-remote`'s `Ok(None)` is `absent`. It publishes the check, then fetches (`FETCH_DEADLINE` 60 s) when the answer differs from `refs/remotes/origin/<default>`, and publishes the fetched tip (`source: fetch`, stamped at the fetch's start). A failed fetch whose tracking ref moved anyway gets one recheck with its own budget: `fetched` only when the remote still has that tip. Origin and branch are re-read after each network step (`unavailable`). Tests: `lib/src/remote_update/tests.rs` (real bare origin and `pusher`, scripted API, Git real unless scripted, a test clock).
- `fast_forward::fast_forward_default(main, default) -> FfResult` (`--ff`): re-reads `refs/heads/<d>` and `refs/remotes/origin/<d>` and their ancestry right before the move; no checkout holds the branch: `update-ref` compare-and-swap; otherwise it re-verifies the holder is still on the branch and runs `merge --ff-only --no-autostash <verified sha>` there under `LC_ALL=C` ("would be overwritten" is `FfRefusal::DirtyCheckout`). It never creates, forces, or touches another ref; `UpToDate` covers in sync and ahead. A checkout switching branches between the check and the merge is the one gap git gives no atomic guard for.
- `live_remote` runs git with `LC_ALL=C`. `run_transport` types failures (`TransportError { failure: GitFailure::{Timeout, Credentials, Other}, reason }`): the deadline is `Timeout`, a failed exit is `classify_git_failure(stderr)` (S3's credential patterns, else `Other`); `run_noninteractive` keeps the string form for removal. `fetch_argv` adds `--no-recurse-submodules --refmap=` to the spec's command, since a configured submodule recursion or extra `remote.origin.fetch` would otherwise touch other refs. `tracking_ref_changed_at` is `None` without the ref or its reflog (an existing ref without a reflog prints nothing and exits 0).
- `api_preference`: `~/.wt.json` (`dirs::home_dir`, beside but separate from `~/.worktree.json`) is `{ format_version: 1, ignore_api: [{ host, port, path }] }`, written by `--ignore-api`. `RepoIdentity::from_origin` wraps sniff's raw `remote_identity` and owns the port policy: HTTPS 443 unless explicit, SSH to a known provider host on the standard SSH port (none spelled, or 22) 443 (so SSH and HTTPS remotes of one repository match), other SSH, including an explicit nonstandard port on a known provider, its port or 22 (no scheme field: one host and port is one server); a local path has no identity. `load` treats a missing, unreadable, corrupt, or other-format file as empty; `add` refuses such a file (`WorktreeError::PreferenceUnwritable`) instead of replacing it, and serializes writers on `~/.wt.json.lock` for at most 2 s.

From `METRICS_MIN_WIDTH` (100) columns both comparison cells append dim green `+ahead` and dim red `-behind` (zero side omitted) before any PR badge. - `commands/git_graph.rs` only gathers `GraphFacts` (full SHAs, fork points, merge commits, refs, `incomplete`) and builds a biscuit-terminal `GitGraph`; `GitGraph` owns lanes, tags, merges, trimming, and sizing. Gathering (`git_graph/topology.rs`) is two stages on scoped threads: `History::classify` (R4 with R4-A1: `C` is the leading run of `rev-list --first-parent --parents T..X` that is in `rev-list --ancestry-path T..X`) decides per selected branch against its drawn parent's tip, the default lane tip, then a diverged `origin/<default>` tip: unmerged, merged directly (lane `T --not C^1`, `with_merge(T, C)`), no separate history (a label at `T`, never an empty lane), or integrated otherwise (lane, no merge, incomplete). Merged directly and no separate history are strong and win at the first candidate that yields one; integrated otherwise is weak, so the walk continues and returns it only when no later candidate is strong (a parent that has `T` only by way of `main` loses to `main`'s direct merge: `MergedDirectly { after_indirect: true }`). A `GatherGap` before any weak result is the result; one after it returns the weak result. A merged branch's fork is measured against `C^1`, or against its parent's tip only when the merge went elsewhere and was not found after an indirect match (the parent's tip contains `T` otherwise). A deferred direct merge whose fork no lane draws gets its merge edge, an unconnected lane, and the notice from `GitGraphPlan::incomplete` (gathering itself reports no gap). In `a_direct_merge_into_the_default_branch_beats_the_parents_indirect_containment` the fork `W1` is drawn after all, because the parent `fix/wt-ux` continued after its own merge at `W1` and its lane is extended through it (below). Then every branch lane is built in parallel (`first_parent_entries`, `log --first-parent`), and the default lane last from what they did not place. Every lane is first-parent; fork, merge, label, and default-ref commits are anchors, placed by `rev-list --first-parent --count A..tip` and verified in one `log --no-walk=unsorted --ignore-missing` (a plain `rev-parse` batch fails on any `tip~d` past the root), with `+N` squares for the exact runs between. The default lane runs down to its oldest anchor plus that anchor's first parent (from `%P`, no extra call), so a merge is never its first commit; the focused view also caps its window there. Git's exit 1 ("no") is read through `worktree::git::git_command_allow_no_match` and trusted only when `rev-parse --is-shallow-repository` says `false`; any failure, unparseable line, or shallow "no" is a `GatherGap`, which sets `GraphFacts::incomplete` and never drops the graph (only an unreadable default lane does). Verbose (`commit_details_since`) keeps its all-parents semantics and shares the focused view's one `merge-base`. A lane's boundary (the first commit below it) is classified too (`place` → `extend`, sharing one `Classifications` cache per gathering): while a candidate merged it directly at `C`, the stops containing it become `C^1`, the lane is re-read (`History::lane_window`, whose `LaneWindow` also feeds `first_parent_entries`), and `with_merge(B, C)` is added oldest first before the tip edge; the fork becomes `merge-base(C^1, B)` of the oldest edge. The walk stops at an ordinary fork or indirect integration, and at the branch's fork-origin `base_sha` when that is `B` or newer on the tip's first-parent chain (`History::chain_distance`; a malformed, unknown, or off-chain value is ignored, an unknown one in a shallow clone is a gap), so a branch created at an already merged tip stays unconnected with the notice. An ordinary lane pays two extra Git calls for this (`--is-ancestor` and one first-parent chain; the `--ancestry-path` call is skipped when the boundary is on the candidate's first-parent chain). Every gathered line passes its branch tip (`GraphLine::with_tip`): `GitGraph` labels a line without commits at that tip and never at its fork, and a tag, fork, or merge commit it cannot draw sets `GitGraphPlan::incomplete` ("Some history is not shown") instead of being substituted. `GraphLine::with_merge(source, destination)` (a `LaneMerge`, appended oldest first) draws a `merge`; a source in the middle of a lane makes `GitGraph` emit that lane in segments (pause after the source and the lanes forked at it, `merge` at the destination, resume after it), one merge per destination commit, merged lanes ordered before the siblings they merge into, a cycle broken by drawing the later edge as a plain commit (incomplete); the height cap keeps a lane with every merge destination's lane, and trimming never folds a source or destination; `biscuit-visualized` restores the merge's second parent and widens commit spacing only as far as colliding tags (different commits, overlapping rows) need for a one-em gap, so an isolated long label such as `origin/main` keeps the renderer's default step (`biscuit_visualized::mermaid::default_gitgraph_commit_step()`). It filters PRs by source repository first, because `GitGraph` matches by branch name alone. There is no minimum terminal width for the graph. See `worktree/docs/git-graph.md`.
