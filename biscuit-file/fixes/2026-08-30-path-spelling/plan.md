# Plan: path spelling tests, canonicalization guard, and consistent home lookup

## Summary and definition of done

The spec asks for three things, in dependency order:

1. **Windows lexical rules tested on every host** by extending the existing
   `PathIdentity` Windows text entry point (`from_windows_text`, test-only) so
   candidate ordering, first-seen provenance, and containment run through
   production code. No second parser.
2. **Canonicalization routed through `canonicalize_simplified`** wherever a
   result leaves a private comparison, plus a source guard (modeled on
   `claudine/cli/tests/l1/dispatch_inventory.rs`) over the five packages
   (`biscuit-file`, `claudine`, `claudine-cli`, `darkmatter`, `darkmatter-cli`).
3. **One home reader.** `biscuit_file::home_dir()` changes from
   `dirs::home_dir()` to `std::env::home_dir()` filtered to absolute paths;
   Claudine's ~40 `dirs::home_dir` sites and Darkmatter's duplicate in
   `RequestSnapshot::from_process` route through it.

Current-state facts the plan relies on (verified 2026-10-03):

- `PathIdentity::from_windows_text` exists under `#[cfg(test)]` in
  `lib/src/file_reference/portable/path_identity.rs`; tests live in
  `path_identity/tests.rs`.
- `biscuit_file::home_dir()` (`file_reference/context.rs`) uses `dirs::home_dir()`.
- `canonicalize` appears in about 92 production files (biscuit-file 7,
  claudine 43, darkmatter 42) before test exclusion is applied precisely.
- `dirs::home_dir` has about 45 production sites in claudine lib/cli.
  `claudine/lib/src/dispatch/loader.rs` already uses `std::env::home_dir`.
  Several sites are inside `#[cfg(test)]` and are out of the guard.
- Cross-package source reads in a test need `[package.metadata.ci.tests]
  source-inputs` (see `claudine/cli/Cargo.toml`, `docs/cicd/test-inputs.md`).

**Done means:**

- [x] Every row of the spec's lexical table has a test that runs on all hosts
      through production code, plus an ordering/provenance test that fails
      when one comparison rule is deliberately broken.
- [x] No unlisted `canonicalize` or `dunce::canonicalize` call, and no
      direct `dirs::home_dir` / `std::env::home_dir` in Claudine outside the
      approved capture boundary, survives in the five packages; the guard
      enforces this and its fixtures prove it fails on violations and stale
      exceptions.
- [x] A child-process round trip proves Claudine config load and save both
      land under a fixture `HOME`/`USERPROFILE`.
- [x] Docs, READMEs, and skills describe the new lookup and the
      `USERPROFILE` rule; the implementation log records out-of-scope findings.
- [x] `just test` and `just lint` pass in `biscuit-file`, `claudine`, and
      `darkmatter`; platform evidence gaps are stated explicitly.
      (Darkmatter `just test` keeps its 2 pre-existing Phase 1 baseline
      failures, which read unrelated `.claude/skills/claudine/` content, and
      the `md_entry_points_agree_on_every_reference` 30 s timeout; native
      Windows evidence is missing because of build-win-native's storage
      floor. Both are in the Phase 6 log.)

## Phase 1: Rulings and baseline

Goal: settle the author decisions that change the work, and record the
baseline before any edit.

### Necessary Rules

These need the author's ruling before the phase they gate. Each states the
default the plan assumes if the author does not object (`yolo: true`).

- **R1 (gates Phase 4): home lookup policy.** Spec Open question 1.
  Plan assumes **option 1**: change `biscuit_file::home_dir()` to
  `std::env::home_dir()` filtered to absolute. This changes native Windows
  behavior for every default caller with an overridden `USERPROFILE`.
  Choosing option 2 or 3 requires revising the spec's "Consistent home
  lookup" section first; Phase 4 must not start until the spec matches.
- **R2 (gates Phase 3): scope of remediation and guard.** Spec Open question 2.
  Plan assumes **option 1**: five packages only; findings elsewhere go in the
  implementation log. No new dependencies in other areas.
- **R3: approved process-capture boundary.** The guard rejects direct home
  lookups in Claudine "except at an approved process-capture boundary". Plan
  rules that the only boundary is the one call inside
  `biscuit_file::home_dir()` (outside Claudine); Claudine itself gets no
  direct call. Claudine entry points capture once via
  `biscuit_file::home_dir()` and pass the value down. Sites in
  `#[cfg(test)]` code are excluded by the scanner, not excepted.
- **R4: Claudine depends on biscuit-file with `file-reference`.** The helper
  sits behind that feature. Ruling: Claudine already enables it (it calls
  `biscuit_file::home_dir()` in `steer/service.rs`); confirm in Task 1.2 and
  do not move the helper out of the feature (the spec preserves the feature
  boundary).
- **R5: where captured homes live in Claudine.** Ruling: request-scoped code
  (permissions context, protect path, provider behaviors) takes the home from
  its existing injected context; ambient convenience sites (logs, cache,
  backups, init, uninstall) call a single small Claudine function that
  delegates to `biscuit_file::home_dir()`. That function is a wrapper, not a
  second lookup policy, and the guard allows the call to biscuit-file only.
- **R6: wider measurement.** No performance spike (the spec rules one out).
  If the author wants a workspace-wide canonicalization audit with
  remediation, that is the R2 option 2 decision, not a measurement.
- **R7: scanner implementation.** Ruling: a lightweight token scanner using
  `syn` only if `syn` is already a dev-dependency of the host test package;
  otherwise the blanking approach used by `dispatch_inventory.rs`. Decide in
  Task 2.1 from the existing dependency tables; add no new crate.

### Spikes

None. The spec's own figures answer the performance question (existing sites
are replaced one-for-one, and filesystem call counts are preserved), and
Windows `std::env::home_dir` behavior is already exercised by
`claudine/lib/src/dispatch/loader.rs`.
