## Migration Benchmark Harness

### Purpose

Every patch that shifts darkmatter's public render paths (`for_terminal`, `as_html`) from the legacy pulldown-cmark event-stream serializers onto the new fold-then-render-tree pipeline must be measurable with a single, repeatable `cargo bench` invocation. The harness is a **measurement stick**, not an optimization target. Its job is to surface regressions and confirm that the tree path stays within an acceptable cost envelope of the legacy path across the full migration.

The baseline comparison must be honest about the current implementation:
Darkmatter's legacy renderers are event-driven, but not allocation-free. They
preprocess the whole body for escaped inline markers, buffer code blocks,
buffer tables, and build target output strings. The tree path adds an owned
`Document`; the benchmark should measure the real delta rather than assuming a
pure streaming baseline.

### Bench file layout

All benchmark targets live in `darkmatter/lib/benches/`, Criterion-based, one `[[bench]]` entry per file in `Cargo.toml`. The existing files remain untouched; the new harness adds one file:

| File                      | What it measures                                                                    | Status               |
|---------------------------|-------------------------------------------------------------------------------------|----------------------|
| `render_pipeline.rs`      | Legacy `Markdown::from` + `for_terminal` / `as_html` / parse-only / highlight       | Existing — untouched |
| `compose_pipeline.rs`     | Compose stages (interpolation, page blocks, cleanup, normalization)                 | Existing — untouched |
| `render_tree.rs`          | Tree fold + `render_markdown_document` / `render_browser_document` per stress input | Existing — untouched |
| `schema_validation.rs`    | Frontmatter JSON Schema validation                                                  | Existing — untouched |
| **`migration_parity.rs`** | **Side-by-side legacy vs tree for every render target, same fixtures**              | **New**              |

### The new file: `migration_parity.rs`

A single Criterion bench file that exercises **both** paths against the **same** frozen inputs and emits **paired** benchmark functions so `cargo bench` reports them in adjacent rows.

#### Fixture set

Four programmatically generated stress documents, reused from `render_tree.rs`:

| Name                  | Character                            | Why                                                        |
|-----------------------|--------------------------------------|------------------------------------------------------------|
| `large_code_block`    | 600-line fenced Rust block           | Isolates syntax-highlighting cost and code-node allocation |
| `large_table`         | 8-column x 200-row GFM table         | Stresses table alignment and cell iteration                |
| `deeply_nested_lists` | 14 levels, 3 siblings                | Exercises tree depth and list-item nesting                 |
| `many_links_images`   | 120 paragraphs with links and images | Dense inline-node count                                    |

Each fixture is generated by an identical function in the new file (copy the four generators from `render_tree.rs`). The generators are small and deterministic; duplicating them avoids coupling the new harness to the old bench file's internals.

#### Benchmark functions

Five top-level benchmark groups. Each group runs both the legacy and tree paths for one render target against every fixture, so a single `cargo bench` invocation produces a full before/after matrix.

| Group name                | Legacy path                                                 | Tree path                                                                                             | Fixture scope     |
|---------------------------|-------------------------------------------------------------|-------------------------------------------------------------------------------------------------------|-------------------|
| `migration/terminal`      | `Markdown::from` + `for_terminal`                           | `Markdown::from` + `fold_markdown_to_document` + `render_terminal_document`                           | All four fixtures |
| `migration/browser`       | `Markdown::from` + `as_html`                                | `Markdown::from` + `fold_markdown_to_document` + `render_browser_document`                            | All four fixtures |
| `migration/markdown`      | *(no legacy equivalent — Markdown roundtrip is tree-only)*  | `Markdown::from` + `fold_markdown_to_document` + `render_markdown_document`                           | All four fixtures |
| `migration/fold_only`     | `Markdown::from` + legacy parser/processor drain            | `Markdown::from` + `fold_markdown_to_document`                                                        | All four fixtures |
| `migration/full_pipeline` | `Markdown::from` + `compose_with(default)` + `for_terminal` | `Markdown::from` + `compose_with(default)` + `fold_markdown_to_document` + `render_terminal_document` | All four fixtures |

Within each group, bench functions are named `{fixture}/legacy` and `{fixture}/tree` so Criterion's HTML report places them side by side.

The `fold_only` legacy side should not be just `Markdown::from`; that would
compare a near no-op against a full parser walk. It should drain the current
render parser stack without writing target output:

```text
preprocess_escaped_markers
  -> Parser::new_ext(...)
  -> InlineStyleProcessor
  -> RuleProcessor
  -> black_box drain
```

Use the terminal/parser option set for this baseline unless the parser-option
policy later introduces a shared function.

#### Pinned configuration

- `TerminalOptions::max_width = Some(120)` — deterministic, no live terminal detection.
- `TerminalOptions::color_depth = Some(ColorDepth::TrueColor)` for the normal
  terminal benchmark, plus a separate `migration/terminal_no_color` group using
  `ColorDepth::None` to pin the current early-return fast path.
- `TerminalOptions::image_mode = TerminalImageMode::Never` unless a fixture
  explicitly measures image behavior. This keeps ordinary terminal benches from
  depending on host graphics capability.
- `HtmlOptions::default()` — consistent across both paths.
- `BrowserRenderOptions::default()` / `MarkdownRenderOptions::default()` — consistent for tree renders.
- `TerminalRenderOptions::default()` — consistent for tree terminal renders (uses the same 120-width optimistic `Terminal`).
- `source = SourceDescriptor::Virtual { name }` — no filesystem hits.
- `sample_size(20)` — matches existing benches.

#### Command

```text
cargo bench -p darkmatter --bench migration_parity
```

Before/after a migration patch:

```text
# Baseline before the patch
cargo bench -p darkmatter --bench migration_parity -- --save-baseline pre-migration

# After the patch
cargo bench -p darkmatter --bench migration_parity -- --baseline pre-migration
```

This produces Criterion's `change:` column showing the regression or improvement for every fixture/target pair.

### What the harness does NOT do

- No optimization work. The harness measures; it does not tune.
- No pass/fail performance threshold in code. Human review decides whether a
  regression is acceptable for the migration stage.
- No compositional or schema benchmarks — those are covered by the existing `compose_pipeline.rs` and `schema_validation.rs`.
- No biscuit-terminal component benches — those live in `biscuit-terminal/lib/benches/` and are out of scope for the darkmatter migration.
- No `as_ast` path — the MDAST path is a dead end and will be retired per the roadmap.

### `Cargo.toml` addition

```toml
[[bench]]
name = "migration_parity"
harness = false
```

### Memory measurements

Criterion does not provide peak RSS or allocation counts by itself. The
Criterion harness is still the required wall-clock baseline, but memory should
be captured by a second, explicit command once the first tree path exists.

Recommended shape:

```text
cargo run -p darkmatter-cli -- render <fixture> --output terminal
cargo run -p darkmatter-cli -- render <fixture> --output html
```

Run those under the workspace's chosen allocator/RSS profiler and record the
command in this feature directory. Do not block the first harness on choosing a
profiler; do require that every public cutover note says whether memory was
measured and how.

### Expected cost envelope

The tree pipeline builds an owned `Document` (heap-allocated nodes, source
registry, metadata) where the legacy pipeline consumes the event stream and
writes target output directly but still performs substantial buffering. The
tree path is expected to be **more expensive in allocation for simple
single-target prose**, closer on realistic buffered documents, and strongest
when one fold feeds multiple target renders. The harness reports the numbers so
a human can judge whether a regression is acceptable during the migration and
whether the final state is acceptable as a permanent cost.
