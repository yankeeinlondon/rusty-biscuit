# Review: Darkmatter Code-Block Rendering Failures

## Findings

### High: The invariant suite is red; long prose overflows every layout scenario

`cargo test -p darkmatter --test render_invariants --color=never` fails in `layout_invariants_hold_across_matrix`. The committed empty ledger at `darkmatter/lib/tests/render_invariants.rs:275` is not true for the current implementation: the `prose_wrap` fixture at `darkmatter/lib/tests/render_invariants.rs:81` violates I1 containment in all five scenarios.

Observed failures:

- `prose_wrap / margins_2_w80`: line width 179 > terminal width 80
- `prose_wrap / repro_ml4_mr4_mt1_mb1`: line width 183 > terminal width 120
- `prose_wrap / left_only_w100`: line width 181 > terminal width 100
- `prose_wrap / right_only_w100`: line width 181 > terminal width 100
- `prose_wrap / vert_mt2_mb2_w100`: line width 175 > terminal width 100

This violates the spec's I1 requirement: no rendered line may exceed the physical terminal width after decoration. Since the failing fixture is ordinary prose rendered through `DarkmatterPage` (`darkmatter/lib/tests/render_invariants.rs:227`), this is not limited to code blocks. Fix the prose wrapping/layout path or update the invariant only if the spec is intentionally relaxed; do not ship with the ledger empty while the live set has regressions.

### High: The code-theme inversion tests fail as written

Both I7 tests fail in the same targeted run:

- `i7_code_block_inverts_theme_against_dark_terminal` fails at `darkmatter/lib/tests/render_invariants.rs:457`
- `i7_code_block_inverts_theme_against_light_terminal` fails at `darkmatter/lib/tests/render_invariants.rs:480`

The tests assert exact truecolor background SGR strings generated by `theme_bg_ansi`, but the page setup at `darkmatter/lib/tests/render_invariants.rs:445` and `darkmatter/lib/tests/render_invariants.rs:470` does not force `ColorDepth::TrueColor`. That makes the test environment-dependent and currently red here. If the implementation is correct, make the tests deterministic by setting `with_color_depth(ColorDepth::TrueColor)` or by normalizing accepted color encodings before asserting. If the output is genuinely not using the inverted theme, fix the renderer. Either way, the user-facing I7 requirement is not currently verified by a passing test.

### Medium: Mermaid image fallback coverage is conditional and can silently skip the fallback path

`mermaid_image_fallback_honors_layout_under_decoration` only checks the fallback when the rendered output contains the `mermaid` pill, and returns early otherwise (`darkmatter/lib/tests/render_invariants.rs:523`). That means environments where `mmdc` succeeds do not verify the image-fallback branch at all, even though the prior review specifically called out that path. The deterministic `MermaidMode::Text` matrix cell exercises the shared emitter, but it would not catch a future regression that routes only the `Image` failure branch back to the old behavior. Add a way to force image rendering failure in-process, or factor the fallback decision behind an injectable helper so this path is always tested.

## Test Rigor Classification

- Code-block terminal rectangle / right-boundary / blank-line behavior: Level 2 tests now exist in `darkmatter/lib/tests/level2_render_tree_terminal.rs`, including the page-path checks at `level2_page_code_panel_is_contiguous_inverted_rectangle` and `level2_page_no_double_blank_rows_between_code_blocks`. I did not run them because the Level 1 invariant suite already fails.
- Prose containment under page layout: strongest verification is Level 1, and it is failing.
- Code-theme inversion: strongest deterministic verification is Level 1, and it is failing. The Level 2 page test depends on the same intended contrast behavior, but the lower-level contract must be green first.
- Mermaid image fallback under decoration: conditional Level 1 only; fallback can be untested when image rendering succeeds.
- No Level 3 requirements found; the spec does not assert OS keyboard-event behavior.
