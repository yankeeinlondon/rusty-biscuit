# GitHub REST API Definition Plan (Schematic)

## Skills Used
- `schematic`
- `rust`
- `rig`

## Goal
Add a first-class GitHub REST API definition to `schematic-definitions`, wire it into `schematic-gen` so `--api github` and `--api all` generate it into `schematic/schema/src`, and update `schematic/justfile` workflow ergonomics for GitHub generation.

## Source Inputs Reviewed
- `sniff/docs/github-api.md`
- `schematic/definitions/src/*` (module + type patterns)
- `schematic/gen/src/main.rs` (API resolution and `all` generation wiring)
- `schematic/justfile`

## Scope Decision
GitHub has a very large REST surface. For this implementation, define a focused, production-useful slice aligned to the design doc’s four required use cases (README discovery/content, PRs, issues, tags/releases), while preserving a clean expansion path for more endpoint families later.

## Planned Endpoint Set (V1)
All endpoints use base URL `https://api.github.com`.

1. `GetRepository`  
   `GET /repos/{owner}/{repo}` -> `RepositoryInfo`
2. `GetGitTree`  
   `GET /repos/{owner}/{repo}/git/trees/{tree_sha_or_ref}` -> `GitTreeResponse`
3. `GetGitTreeRecursive`  
   `GET /repos/{owner}/{repo}/git/trees/{tree_sha_or_ref}?recursive=1` -> `GitTreeResponse`
4. `GetRepositoryContentRaw`  
   `GET /repos/{owner}/{repo}/contents/{path}` -> `ApiResponse::Text`  
   Endpoint header override: `Accept: application/vnd.github.raw+json`
5. `ListPullRequests`  
   `GET /repos/{owner}/{repo}/pulls?state=all&sort=updated&direction=desc&per_page=100` -> `Vec<PullRequestSummary>`
6. `ListPullRequestFiles`  
   `GET /repos/{owner}/{repo}/pulls/{pull_number}/files?per_page=100` -> `Vec<PullRequestFile>`
7. `ListIssues`  
   `GET /repos/{owner}/{repo}/issues?state=all&per_page=100` -> `Vec<IssueSummary>`
8. `GetIssue`  
   `GET /repos/{owner}/{repo}/issues/{issue_number}` -> `IssueSummary`
9. `ListIssueComments`  
   `GET /repos/{owner}/{repo}/issues/{issue_number}/comments?per_page=100` -> `Vec<IssueComment>`
10. `ListIssueTimeline`  
    `GET /repos/{owner}/{repo}/issues/{issue_number}/timeline?per_page=100` -> `Vec<TimelineEvent>`
11. `ListTags`  
    `GET /repos/{owner}/{repo}/tags?per_page=100` -> `Vec<RepoTag>`
12. `ListReleases`  
    `GET /repos/{owner}/{repo}/releases?per_page=100` -> `Vec<Release>`
13. `GetTagReference`  
    `GET /repos/{owner}/{repo}/git/ref/tags/{tag}` -> `GitRef`
14. `GetAnnotatedTag`  
    `GET /repos/{owner}/{repo}/git/tags/{tag_sha}` -> `AnnotatedTagObject`

## Implementation Plan

### Phase 1: Add `schematic-definitions` GitHub module
Files:
- `schematic/definitions/src/github/mod.rs` (new)
- `schematic/definitions/src/github/types.rs` (new)

Actions:
1. Create `define_github_api() -> RestApi` using `schematic_define` primitives.
2. Configure auth and headers:
   - `auth: AuthStrategy::BearerToken { header: None }`
   - `env_auth: ["GITHUB_TOKEN", "GH_TOKEN"]`
   - default headers:
     - `Accept: application/vnd.github+json`
     - `X-GitHub-Api-Version: 2022-11-28`
     - `User-Agent: schematic-github-client`
   - `env_mapping` bearer token fallback chain (`GITHUB_TOKEN`, `GH_TOKEN`).
3. Define the 14 endpoints above with accurate `ApiResponse` variants.
4. For README/raw content endpoint, set endpoint-specific `Accept` header override.
5. Add tight unit tests in `mod.rs`:
   - metadata/auth/header correctness
   - endpoint count and key path assertions
   - raw endpoint uses `ApiResponse::Text` + accept override

Type modeling in `types.rs`:
- Add compact response types needed by V1:
  - `RepositoryInfo`, `UserSummary`, `BranchRef`
  - `GitTreeResponse`, `GitTreeEntry`
  - `PullRequestSummary`, `PullRequestFile`
  - `IssueSummary`, `IssueComment`, `TimelineEvent`
  - `RepoTag`, `TagCommit`, `Release`
  - `GitRef`, `GitRefObject`
  - `AnnotatedTagObject`, `AnnotatedTagger`, `TagVerification`
- Use `serde` defaults/`Option<_>` for frequently omitted fields and forward-compat behavior.
- Add round-trip serialization tests for key structs.

## Known Risks and Mitigations

1. Query parameter ergonomics in generated clients
- Risk: current generator does not fully leverage `EndpointParams` for optional query building.
- Mitigation: encode stable defaults in endpoint paths (as above) for V1; schedule query-builder enhancement as follow-up.

2. GitHub response shape variability
- Risk: fields may differ by repo visibility, permissions, or API evolution.
- Mitigation: prefer optional fields and minimal required type surface; avoid over-constraining models.

3. Auth strictness
- Risk: bearer auth strategy may enforce token presence even for public repos.
- Mitigation: keep authenticated-first default (best practice from design doc); if needed, add documented follow-up variant for unauthenticated use.
