# Unified Agent Migration Plan (Claudine)

## Design Authority Rule

This migration is design-led.

1. `claudine/docs/unified-agent.md` is the canonical source.
2. Existing symbols that conflict with the design are migration debt.
3. Compatibility shims are temporary and must not replace canonical unified-agent types.

## Scope

Implement the unified-agent architecture in `claudine/lib` and refactor `claudine/cli` to consume it.

In scope:
- Canonical unified-agent type system and `Agent` trait
- Per-agent capability implementations for all 8 agents
- Registry/query APIs for capabilities, paths, status, and confidence
- Refactor of linking capability source-of-truth to unified-agent model
- CLI refactors (`providers`, `link`, provider parsing/display surfaces)
- Claude Code integration checks to ensure Claude CLI hook workflows still function

Out of scope for this pass:
- Rewriting unified event runtime model from `unified-events` (already in place)
- Changing hook payload schemas from providers
- Adding new external dependencies unless required

## Current-State Findings (Post Review)

### Existing capability system conflicts with design
- `claudine/lib/src/linking/capabilities.rs` defines `ProviderCapabilities`, `ResourceSupport`, `SupportLevel`, and `ResourceFormat`.
- This model is link-centric and omits most required unified-agent fields:
  - runtime controls
  - config capabilities
  - confidence profile and gaps
  - docs partitioning (`skills_docs`, `slash_docs`, etc.)

### Capability source is fragmented
- `events::Provider` currently owns docs URL, aliases, skill support, event support, and native mappings.
- `linking::capabilities` separately owns resource support and paths.
- `config::mod` separately hardcodes config file paths and binary detection mappings.

### Linking path model is incomplete for unified-agent goals
- `claudine/lib/src/linking/paths.rs` only models 4 providers (`claude`, `gemini`, `codex`, `opencode`).
- Unified-agent design requires 8 agents and richer path discovery semantics (user/project/admin/extension precedence).

### CLI depends directly on legacy capability symbols
- `claudine/cli/src/commands/providers.rs` reads `linking::capabilities_for` + `LinkableResource`.
- `claudine/cli/src/commands/link.rs` renders support/detail tables from legacy `SupportLevel`/`ResourceFormat`.
- Multiple CLI commands parse provider names from `events::Provider`, not from a unified agent registry.

### Claude-specific documentation gap remains partially open
- `claudine/docs/agent-cli/opencode.md` is a placeholder and blocks high-confidence OpenCode capability data.
- `claudine/docs/cross-referencing/claude-code.md` is present and can be consumed for capability population.

## Symbol Conflict Matrix (Design Wins)

| Existing Symbol | Location | Conflict With Design | Migration Decision |
|---|---|---|---|
| `ProviderCapabilities` | `claudine/lib/src/linking/capabilities.rs` | Design canonical type is `AgentCapabilities` | Replace as canonical; keep adapter shim temporarily |
| `SupportLevel` | `claudine/lib/src/linking/capabilities.rs` | Design canonical status is `CapabilityStatus` | Migrate all status logic to `CapabilityStatus`; map old enum only during transition |
| `ResourceFormat` | `claudine/lib/src/linking/capabilities.rs` | Design uses `CommandFormat`, `AgentDefinitionFormat`, `ConfigFormat` | Split format semantics per capability area |
| `Provider` as capability identity | `claudine/lib/src/events/provider.rs` and consumers | Design introduces `AgentId` identity for capabilities | Keep `Provider` for event runtime, add explicit `AgentId <-> Provider` bridge |
| `ALL_PROVIDERS` (linking) | `claudine/lib/src/linking/capabilities.rs` | Duplicates provider registry concern | Replace with unified-agent registry iteration |
| Hardcoded `ProviderSkillPaths` fields (`claude/gemini/codex/opencode`) | `claudine/lib/src/linking/paths.rs` | Design requires all 8 agents and richer path discovery | Refactor paths builder to derive from `Agent::capabilities()` |
| CLI support table model (`Skill/Cmd/Agent/Hooks` from linking enums) | `claudine/cli/src/commands/providers.rs` | Design requires canonical capability areas and statuses | Rebuild CLI tables on unified-agent model |

## Migration Strategy

Use an additive-then-cutover strategy:

1. Add new `agents` module with full canonical types and registry.
2. Populate all 8 agents with static capability builders.
3. Bridge old call sites to new model with temporary mappers.
4. Cut CLI and linking over to new APIs.
5. Delete legacy capability symbols after all consumers are migrated.

This keeps the code buildable throughout while enforcing design-first canonical ownership.

## Phase Plan

### Phase 0: Baseline + Guardrails

Goal: lock current behavior and establish migration gates.

Primary files:
- `claudine/lib`
- `claudine/cli`

Tasks:
- Capture baseline:
  - `cargo test -p claudine`
  - `cargo test -p claudine-cli`
  - `cargo clippy -p claudine -- -D warnings`
  - `cargo clippy -p claudine-cli --no-deps -- -D warnings`
- Record provider-facing CLI behavior snapshots for:
  - `claudine providers`
  - `claudine link --support`
  - `claudine hooks --support`
- Add migration checklist section in this plan for completion tracking.

Exit criteria:
- Baseline test/lint state captured.
- Known user-facing output surfaces identified before symbol cutover.

### Phase 1: Introduce Canonical Unified-Agent Types

Goal: implement design structs/enums/trait verbatim as the new capability authority.

Primary files:
- new `claudine/lib/src/agents/mod.rs`
- new `claudine/lib/src/agents/model.rs` (or equivalent split)
- `claudine/lib/src/lib.rs`

Tasks:
- Implement design-canonical types:
  - `AgentCapabilities`, `AgentMeta`, `AgentDocs`, `ConfigCapabilities`
  - `RuntimeCapabilities` and all sub-structs
  - `SkillsCapabilities`, `SlashCommandCapabilities`, `SubagentCapabilities`, `ScriptCapabilities`
  - `PathDiscovery`, `FrontmatterContract`, `ConfidenceProfile`, `AreaConfidence`
  - enums: `AgentId`, `ConfigFormat`, `ReasoningStyle`, `BillingModel`, `CapabilityStatus`, `ActivationStyle`, `InvocationStyle`, `AgentDefinitionFormat`, `CommandFormat`, `Confidence`
- Implement canonical `Agent` trait exactly per design intent (including `validate()` defaults).
- Re-export new agent module in `claudine/lib/src/lib.rs`.

Exit criteria:
- New canonical types compile and are publicly available.
- `Agent` trait is available and test-covered independently of legacy linking module.

### Phase 2: Add Per-Agent Implementations + Registry

Goal: define all eight agent structs and a unified registry API.

Primary files:
- new `claudine/lib/src/agents/claude_code.rs`
- new `claudine/lib/src/agents/codex.rs`
- new `claudine/lib/src/agents/gemini_cli.rs`
- new `claudine/lib/src/agents/goose.rs`
- new `claudine/lib/src/agents/kimi_code.rs`
- new `claudine/lib/src/agents/opencode.rs`
- new `claudine/lib/src/agents/qwen_cli.rs`
- new `claudine/lib/src/agents/roo_code.rs`
- new `claudine/lib/src/agents/registry.rs`

Tasks:
- Implement dedicated structs:
  - `ClaudeCodeAgent`, `CodexAgent`, `GeminiCliAgent`, `GooseAgent`, `KimiCodeAgent`, `OpenCodeAgent`, `QwenCliAgent`, `RooCodeAgent`
- Populate static capability builders from design matrix and referenced docs.
- Add registry functions:
  - `agent_for(id: AgentId) -> &'static dyn Agent`
  - `all_agents() -> &'static [&'static dyn Agent]`
  - parse/fuzzy helper(s) for CLI-facing names/aliases
- Add validation tests:
  - all agents return zero `validate()` issues (or explicit expected warnings where confidence gaps remain)
  - confidence gaps are populated, not silently omitted

Exit criteria:
- All 8 agents are discoverable through one registry.
- Capability data is centralized and trait-backed.

### Phase 3: Build Event/Config Interop Layer (AgentId <-> Provider)

Goal: preserve event-runtime behavior while moving capability identity to `AgentId`.

Primary files:
- `claudine/lib/src/events/provider.rs`
- new `claudine/lib/src/agents/interop.rs` (or in registry)
- `claudine/lib/src/config/mod.rs`

Tasks:
- Add explicit conversion APIs between `AgentId` and `events::Provider`.
- Move capability-oriented methods off `Provider` where duplicated:
  - docs URL
  - skill/slash/subagent support predicates
- Keep event-specific methods on `Provider`:
  - event support matrix
  - native event mappings
  - payload detection
- Refactor config discovery metadata (`binary`, config path, display name) to read from unified-agent registry instead of hardcoded tuples where possible.

Exit criteria:
- Event runtime remains stable.
- Capability identity and event identity are clearly separated.

### Phase 4: Refactor Linking to Unified-Agent Capabilities

Goal: replace legacy linking capability tables with unified-agent data.

Primary files:
- `claudine/lib/src/linking/capabilities.rs`
- `claudine/lib/src/linking/mod.rs`
- `claudine/lib/src/linking/paths.rs`
- `claudine/lib/src/linking/discovery.rs`
- `claudine/lib/src/linking/conflict.rs`

Tasks:
- Replace `ProviderCapabilities` internals with adapters over `AgentCapabilities`.
- Rework path discovery to use `PathDiscovery` by resource area and scope.
- Expand linking provider set from 4 providers to all agents where status/format allows safe linking.
- Replace stringly provider IDs in linking pipeline with `AgentId` (or internal strongly typed wrapper).
- Keep short-lived compatibility wrapper functions (`capabilities_for`, etc.) for CLI migration, then remove.

Exit criteria:
- Linking reads capability data exclusively from unified-agent registry.
- Legacy capability duplication is eliminated.

### Phase 5: Refactor Claudine CLI to Unified-Agent Model

Goal: keep CLI UX intact while switching to new canonical library APIs.

Primary files:
- `claudine/cli/src/commands/providers.rs`
- `claudine/cli/src/commands/link.rs`
- `claudine/cli/src/commands/hooks.rs`
- `claudine/cli/src/commands/init/mod.rs`
- `claudine/cli/src/commands/init/prompts.rs`
- `claudine/cli/src/commands/dry_run.rs`
- `claudine/cli/src/commands/handle.rs`

Tasks:
- `providers` command:
  - build table from unified-agent registry
  - derive skill/slash/subagent/script/runtime indicators from canonical statuses
- `link --support` and provider detail:
  - render from `AgentCapabilities` fields (`CommandFormat`, `AgentDefinitionFormat`, confidence, notes)
- Provider parsing/display:
  - resolve CLI input via unified-agent parser first
  - map to `Provider` only when dispatch/config operations require it
- `init` and provider-selection prompts:
  - use registry display names/docs/availability metadata
- Preserve existing command names and default behavior for backward compatibility.

Exit criteria:
- CLI compiles against unified-agent APIs.
- Existing user workflows remain intact with richer capability output.

### Phase 6: Claude CLI Compatibility Refactor (Critical)

Goal: ensure Claude Code CLI integration remains correct after model migration.

Primary files:

- `claudine/lib/src/adapters/claude.rs`

  - `dry-run --provider claude` mock payload + parsing behavior
- Confirm no change to Claude hook response semantics in dispatch pipeline.

Exit criteria:
- Claude Code hooks continue to register, dispatch, and respond exactly as before.
- No regressions in Claude-focused tests.

## Risks and Mitigations

1. Risk: Breakage from identity split (`Provider` vs `AgentId`).
- Mitigation: explicit conversion module + compile-time exhaustiveness tests.

2. Risk: Linking behavior changes when moving from 4-provider hardcoding to 8-provider capability-driven discovery.
- Mitigation: stage rollout with snapshot tests and per-provider enablement checks by `CapabilityStatus` and format compatibility.

3. Risk: CLI output churn breaks user expectations.
- Mitigation: preserve command interfaces, add output regression tests for key commands.

4. Risk: Claude Code hook registration regressions.
- Mitigation: dedicated phase and regression suite for `config/claude.rs` and `handle` flow.
